# Every limit is on by default, and a limit exceeded has its own status

| limit | default | answered with | why this value |
|---|---|---|---|
| request head | 8 KiB | 431 | larger than any head a browser sends with ordinary cookies, small enough that an idle read buffer stays one size class |
| fields: header fields, and the fields of a `Form[T]` body | 100 | 431 for headers, 413 for a form | far above real requests; bounds the work of parsing a head, and of looking up the keys of a form ([ADR 0044](0044-the-body-type-decides-how-a-body-is-read.md)) |
| request body, per route | 1 MiB | 413 | Huma's default; a JSON API body larger than this is usually an upload, which a route opts into |
| time to read the head | 10 s | connection closed | bounds a client that opens a connection and trickles bytes; armed only when the head did not arrive whole with the read that woke the connection, so a head that came in one segment, nearly every one, changes no timer (2026-11-04, [`docs/research/optimisation-pass/`](../research/optimisation-pass/report.md)) |
| time to read the body, per route | 30 s | 408, connection closed | bounds a body sent a byte a second; an upload route raises it |
| TLS handshake | 10 s | connection closed | the same reasoning as the head; `Limits.HandshakeTimeout`, from accept to the end of the handshake, counted against the connection limit meanwhile ([ADR 0017](0017-tls-now-http2-later.md)) |
| idle keep-alive | 60 s | connection closed | above common load balancer idle timeouts, so the balancer closes first |
| write | 30 s | connection closed | a streaming response applies it to every chunk of at most 64 KiB and lifts only its total ([ADR 0030](0030-streaming-is-a-return-type.md)); on a keep-alive connection the deadline stays armed between answers and is moved forward only when less than half of it is left, so a write has between 15 and 30 s, and it is cleared when the connection goes quiet: arming and clearing it on every answer was two runtime-timer changes a request (2026-11-04, [`docs/research/optimisation-pass/`](../research/optimisation-pass/report.md)) |
| connections | 90% of the process's file descriptor limit | not accepted | the engine stops calling accept, and the kernel's backlog holds the rest |
| JSON nesting | 64 levels | 400 | [ADR 0015](0015-json-is-our-own-codec-on-jsontext.md) |
| errors listed in a 400 | 20 | truncated | [ADR 0012](0012-client-errors-are-400-problem-json.md) |
| WebSocket message, per route | 64 KiB | close 1009 | [ADR 0046](0046-websocket-origins-and-inbound-limits.md) |
| time to finish a WebSocket message that did not arrive whole (`MessageTimeout`) | 30 s | close 1008 | [ADR 0046](0046-websocket-origins-and-inbound-limits.md) |
| WebSocket messages being assembled, app-wide | 64 MiB | close 1013 | [ADR 0046](0046-websocket-origins-and-inbound-limits.md) |
| bytes queued to send on one WebSocket (`SendQueue`) | 1 MiB | close 1008 | [ADR 0037](0037-a-slow-reader-is-closed-not-buffered-forever.md) |
| bytes queued to send on all WebSockets together (`SendBudget`) | 64 MiB | close 1013 | [ADR 0037](0037-a-slow-reader-is-closed-not-buffered-forever.md) |
| WebSocket heartbeat (`HeartbeatInterval`, `MissedPongs`) | ping every 30 s, close at the 2nd missed pong | close 1008 | [ADR 0039](0039-heartbeats-run-on-one-timer-wheel.md) |
| text of a `Multipart[T]` form (`MaxFieldBytes`, `MaxFormBytes`) | 64 KiB a field, 1 MiB for all the text of a request | 413 located at the field | the bound a client controls, judgements not measured ([ADR 0044](0044-the-body-type-decides-how-a-body-is-read.md)) |
| file bytes of `Multipart[T]` requests held in memory (`UploadMemory`) | 256 KiB a request (fixed in code), 32 MiB for the app | a file past either goes to an unlinked temporary file in `UploadDir` (`os.TempDir()`), with no answer | judgements, not measurements of a workload: 10,000 connections each sending 1 MiB of files and stopping would hold 10 GiB if each request kept its own, and 32 MiB when the app's share is the bound; a negative value or an `UploadDir` that does not exist or cannot be written is refused by `New` ([ADR 0044](0044-the-body-type-decides-how-a-body-is-read.md)) |
| time to read the body of an `Upload` route | `max(30 s, MaxBody / 128 KiB/s)` | 408, connection closed | the rate floor of 128 KiB/s is a judgement, unmeasured; the derived value is logged as `default` ([ADR 0044](0044-the-body-type-decides-how-a-body-is-read.md)) |

Each can be set on the app, and the per-route ones (request body, time to read the body) on a route or a group as the options `MaxBody` and `BodyTimeout`, and the start-up log lists every limit the app has, each marked `default` or `custom` on its own line ([ADR 0026](0026-no-global-state-and-one-behaviour.md)): head, fields, body, head timeout, body timeout, idle, write, the TLS handshake, the effective connection limit (the 90% of the file descriptor limit, computed, not the word "default"), JSON nesting and the errors listed in a 400. The route option `MaxMessage(n)` and the options `AllowOrigins`, `AllowAnyOrigin` are the WebSocket ones; `MaxMessage` must be positive and below the reassembly budget, and a negative WebSocket field of `Limits` panics in `New` like every other. The handshake row is logged for every app, whether or not it serves TLS, so the log does not depend on which listener is started later. The WebSocket rows (message size, message timeout, reassembly budget, send queue, send budget, heartbeat interval, missed pongs) are logged when the app has a WebSocket route, each marked `default` or `custom`. A zero field of `Limits` is the default; a negative one makes `New` panic, naming the field and saying a limit cannot be switched off, because it would otherwise be read as "no limit" (a `-1` read from a config as "unlimited" is the mistake this catches). The check is in `New`, when the options are applied, and not at start: routes copy the body limit and timeout at Registration, before anything serves, and a test app that never reaches the start would not be told. The route-level `MaxBody(0)` stays refused while the app-level zero means the default: the asymmetry is deliberate, a zero in a struct is "not set" and a zero in an option is a value. An option's value must be positive: `MaxBody(0)` on a route or a group is refused at Registration, because zero would otherwise mean either "no limit" or "refuse every body" and a limit that is on by default is never switched off by accident. A limit is never answered with the 400 of ADR 0012: the request was not wrong in its content, it was too large or too slow, and Gin's separate 413 for `MaxBytesError` is the precedent ([`docs/research/gin-echo/`](../research/gin-echo/report.md)).

**A `Multipart[T]` route** has no default `MaxBody` either, for the `Upload` reason, and its worst case is `MaxBody` of disk and 256 KiB of memory for each request in flight: the start-up line of the route states it, says `unbounded` when the route has no `MaxInFlight` and `UploadDir` is on tmpfs (a spill there is memory), and the app logs a warning for a directory on tmpfs instead of refusing it.

**Not here, except for uploads:** a limit on requests in flight separate from connections. With a goroutine per connection and requests served in order, connections bound requests in flight, so a general per-route concurrency limit waits for a workload that needs one. An `Upload` route is that workload: memory is not what bounds it (a streamed part holds about 4 KiB), bandwidth and the handler's disk are, and a handler that spools each part to a temporary file lets an unauthenticated client fill the disk at line rate for the whole body time. So a route or group option `MaxInFlight(n)` bounds the uploads in flight: `n` must be positive (zero is refused like `MaxBody(0)`), the count is kept for each route (a group's option gives each of its Upload routes its own count, since a route is what has a handler and a disk of its own to protect), an atomic counter is checked after the head and before `100 Continue`, and a request over it is answered 503 with `Retry-After` and the connection closed, so the client never sends the body. It has no default, because a default would 503 legitimate traffic; the start-up log prints "in flight: unlimited" for an `Upload` route so the choice is visible. Cost: one atomic add and one atomic sub (claim, not benchmarked). Evidence: [`docs/research/decisions-bodies/`](../research/decisions-bodies/report.md), section R4.

**What was rejected (the Upload defaults):** giving an `Upload` route a default of 32 MiB and 60 s, which accepts 32 MiB silently from anyone, is wrong in both directions for real routes (an avatar wants 2 MiB, a video 2 GiB), turns its failure into a 413 found by a user in production where a refusal is found at start-up, and gives a 408 after 60 s to a client on 1 Mbit/s with 80% of the file sent, since 60 s for 32 MiB is a floor of 4.3 Mbit/s. `MaxBody` is therefore required for an `Upload` route ([ADR 0044](0044-the-body-type-decides-how-a-body-is-read.md)); only the time has a derived default. An explicit `BodyTimeout`, from the route, a group or `WithLimits`, is used as it is and logged as custom; the derived one is logged as `default`, with the route, in the start-up lines (`upload POST /avatar: body timeout`).

**What was rejected (the negative-limit rule):** refusing only a negative `HandshakeTimeout`, and only when a TLS listener starts, which left the other nine fields silently replaced by their defaults (measured in [`docs/research/decisions-small/`](../research/decisions-small/report.md), probe `neglimits`: all ten fields accepted a negative value in `New`). A panic at start or in `Serve` was rejected for the reason above, and so was clamping a negative to the default with a Warn, because the project's rule is refusal before the first request ([ADR 0007](0007-mistakes-are-refused-at-registration.md)).
