# Services start once the app has bound its listener and stop in reverse around Shutdown

An application owns things that must live exactly as long as the app does: a database pool, a queue consumer, a scheduler, a registration in a service registry. Until now bites had nowhere to put them: `Shutdown` drains and closes ([ADR 0029](0029-shutdown-drains-and-then-closes.md)) and the application wrote the rest around `Listen` by hand, in an order each application got right or wrong for itself. Decided and built on 2026-11-04 (`service.go`, `service_test.go`). This ADR is the roadmap's "hooks around the app's life"; its "scheduled and background work" is built on it as two constructors, `Worker` and `Every`, decided below (2026-11-05); cron expressions are not part of it.

**Decision.**

- **A `Service` is a value with a name and up to three functions, registered with `app.Service(s)`.** One way to do it, and the only one.

  ```go
  type Service struct {
      Name           string
      Start          func(ctx context.Context) error
      BeforeShutdown func(ctx context.Context) error
      Stop           func(ctx context.Context) error
  }

  app.Service(bites.Service{
      Name:  "orders-db",
      Start: func(ctx context.Context) error { return pool.Ping(ctx) },
      Stop:  func(ctx context.Context) error { return pool.Close(ctx) },
  })
  ```

  A nil function means there is nothing to do at that moment. At least one must be set. A Service is data, not a registration call, so a module (configuration, discovery, gRPC, a message consumer) and the workers of the roadmap's scheduled and background work return a `Service` the application passes to `app.Service`, and nothing else is added to `App` for them.
- **`Start` runs after the listener is bound and before the first connection is accepted, in registration order, one at a time.** A handler never runs while a service it depends on is not started, which is the point of a service ([principle 2](0077-four-principles-in-the-order-they-win.md)). The address is bound first, so "address in use" is returned before any service starts. A connection that arrives during `Start` waits in the kernel's backlog, with no 503 and no readiness answer, so a probe sees a slow start, not a failed one (the deploy guide says to use a start-up probe for a service that starts slowly).
- **`Start` returns when the service is running; it does not block.** A worker starts its goroutine in `Start` and returns. The `ctx` passed to `Start` is the service's life, not the start's: it is cancelled just before the service's `Stop` is called (or when the app closes), with the cause `ErrServerClosed`, so `go run(ctx)` is the correct body of a worker. It carries no deadline; the start's deadline is `WithServiceTimeout` below, enforced by the framework by not waiting any longer, and the `ctx` is cancelled when it passes. The trap this avoids, a `Start` context that ends when `Start` returns and silently stops every worker that took it, is the one most easily met with the interface-and-context shape other frameworks have.
- **`BeforeShutdown` runs when `Shutdown` starts, in reverse registration order**, after readiness has failed ([ADR 0052](0052-health-and-readiness-follow-shutdown.md)) and before the shutdown delay and before the listener closes. It is where a service leaves a registry or stops taking work from a queue, while the app still serves. `Close` does not run it (Close is "now"), so `Stop` must work when it never ran.
- **`Stop` runs once the drain is over, in reverse registration order**, with `Shutdown`'s own context: after the listener is closed, requests in flight have finished or been cut, and WebSockets and streams have been told to go ([ADR 0029](0029-shutdown-drains-and-then-closes.md)). A service registered after another therefore stops before it: a worker that uses the pool stops before the pool closes. Services keep running during the drain, so a handler in flight can still use them. `Stop` is called for a service whose `Start` returned nil (or that has none), never for one whose `Start` failed. Every `Stop` runs even when an earlier one failed.
- **A failed `Start` stops what started, and `Listen` returns the error.** The error of `Start` (or its panic, recovered and turned into an error with the panic value) refuses the start: the services already started get `BeforeShutdown` skipped and `Stop` called in reverse, the listener is closed, no connection was ever accepted, and `Listen`, `Serve`, `ListenTLS` and `ListenUnix` return `bites: service "queue": Start: <error>` wrapping the cause (`errors.Is` and `errors.As` see it). The same `Stop` calls get a context that ends after `WithServiceTimeout` in all. Not returning the error and serving anyway was refused: an app that serves without the worker it was written to have is wrong in silence.
- **`Listen` and `Serve` return only after the services have stopped.** Their value is still `ErrServerClosed` after a Shutdown, but it comes once the `Stop` calls are done (or abandoned, below). `net/http` documents the trap this closes: `main` returns when `ListenAndServe` returns, and with `Shutdown` running on another goroutine the process exits in the middle of the drain. Here the idiom `go app.Shutdown(ctx)` followed by `app.Listen(addr)` is safe. With no Service registered nothing changes.
- **A function that does not return before its deadline is abandoned, logged, and the rest go on.** `BeforeShutdown` and `Stop` get `Shutdown`'s context. `BeforeShutdown` hooks share the first half of what is left of it (the shutdown delay then takes at most half of what remains, as [ADR 0052](0052-health-and-readiness-follow-shutdown.md) says, and the drain the rest), so a hung hook cannot spend the drain. When the context is done and a function has not returned, the framework stops waiting for it, logs `bites: service "worker": Stop did not return before the shutdown context ended; it is abandoned`, and calls the next one with the done context. Go cannot kill a goroutine, so the abandoned one is leaked until the process ends; the log says which. A function called when the context is already done (the rest after a deadline, every one under `Close`) is waited for at most `WithServiceTimeout`. `Shutdown` returns the errors of all functions joined with the engine's, and `context.DeadlineExceeded` for an abandoned one.
- **`WithServiceTimeout(d)`, 30 s by default**, is how long the framework waits for one `Start`, and for one function that is called with a context already done. It is an option of the app, given once, and `d` must be positive. It is on by default because a `Start` that waits forever on a database that never answers would otherwise hold the port, the deploy and the log in silence ([principle 2](0077-four-principles-in-the-order-they-win.md)).
- **The lifecycle belongs to the app, and happens once.** The first `Serve` that has bound its listener runs the `Start` phase; any other `Serve` of the same app (TCP and Unix together, [ADR 0068](0068-one-app-serves-several-listeners-and-a-unix-socket-is-a-socket-like-tcp.md)) waits for it and then accepts, or returns its error. `Shutdown` and `Close` stop the services once, whichever listener is asked. An app is not restarted after it stopped. `Shutdown` called while `Start` is running cancels the services' contexts, waits for the phase to end (within its own context), stops what started and makes every `Serve` return `ErrServerClosed`.
- **A refusal raised inside a function is a failure too.** `App.Service` called from a `Start` meets the refusal below as a panic, which is recovered like any other and fails that `Start`, so `Listen` returns `bites: service "outer": Start: panic: app: Service "inner" registered at ...`; the refusal text is in the error and in the log.
- **A function that panics is a failure, not a crash.** The panic is recovered and logged as an error with the stack, as a handler's is, and treated as that function returning an error.
- **Nothing happens in silence.** Each function logs when it ends, one line: `bites: service started` (`service`, `took`), `bites: service stopped`, `bites: service left` for `BeforeShutdown`, at Info, and at Error with `err` when it failed, at Warn when abandoned. The start-up settings gain a line `services` listing the names in order, and `service timeout`, marked `default` or `custom` ([ADR 0026](0026-no-global-state-and-one-behaviour.md)).
- **Under `bitetest.Start` the hooks run, synchronously.** `Start` returns after the `Start` functions have returned, so a test that begins with a request sees a started service; a `Start` that fails fails the test (`tb.Fatalf`, with the error). `app.Shutdown` (the `Server` has no Shutdown of its own) and the end-of-test cleanup run `BeforeShutdown` and `Stop` (cleanup is `Close`, so `Stop` with a done context, and `bitetest` waits for it), so a test leaks no worker. The hook's deadlines are real time, never the app's clock, as the WebSocket client's are ([ADR 0074](0074-the-bitetest-websocket-client-reads-on-its-own-goroutine-and-times-out-in-real-time.md)); the shutdown delay of [ADR 0052](0052-health-and-readiness-follow-shutdown.md) stays on the app's clock.

- **`Worker` and `Every` are constructors of a `Service`, not a second way to register one.** `func Worker(name string, run func(ctx context.Context) error) Service` is `Start: go run(ctx)` with the Service's life as `ctx`, and `Stop` waits for `run` to return, bounded as every function is (Shutdown's context, `WithServiceTimeout` under `Close`). A `run` that returns before `Stop` (an error or nil) or panics is logged at Error with the worker's name and the error, and is not restarted: restarting hides a dependency that is down and needs a back-off policy the framework would have to choose; a worker that must survive loops inside `run`. An error after the context was cancelled is a Warn, except `context.Canceled`.
- **`func Every(name string, interval time.Duration, fn func(ctx context.Context) error, opts ...EveryOptions) Service` calls `fn` once per interval, on the app's clock, serially, and by default the first call is one interval after the start.** Not at start: a `Start` returns when the service is running and must not wait for work (the rule above), a deploy of many instances would run every sweep at the same second, and the three uses (a sweep of sessions and codes, a purge, a check each minute) lose nothing by waiting one interval. A job that does need a run at start (warm a cache, reconcile what a crash left behind) says so with `EveryOptions{AtStart: true}`, one options value like every `...Options` of the core (two are refused at the call). The start call runs on the Service's goroutine after `Start` has returned, so the start still never waits for work and the rule above holds; it is the same call as an interval one (clock, logger, `ctx`, serial, error at Warn, panic recovered), and `Stop` cancels its `ctx` and waits for it. The intervals still count from the start, so a start call that overruns the first interval drops the ticks it missed and the Warn counts them. Only a deployment that sets the option runs its sweep at the same second on every instance, and the option is where that choice is written. The calls are fixed-rate: the due time advances by `interval` from the first, so a one-minute check stays on the minute and does not drift by the run time. A run that overruns is never overlapped; the ticks it missed are dropped, not queued, and one Warn says how many (`skipped`). An error from `fn` is logged at Warn with the name (`job`) and the loop goes on; a panic is recovered, logged at Error with the stack, and the loop goes on. The first timer is armed inside `Start`, so a test that advances the clock after `bitetest.Start` cannot miss it.
- **The Service's life context carries the app's clock and logger.** `Every` reads the clock from it and the logs name the app's logger, so `Now(ctx)` and `Logger(ctx)` work on the `ctx` of a `Start`, `Worker` and `Every` with no new exported name: a private key on the context the framework makes in `runStarts`. A test moves an `Every` by advancing `bitetest.Clock`.
- **`Worker` and `Every` panic at the call, with the line, for what cannot work:** an empty or unshowable name, a nil `run` or `fn`, and an interval of zero or less. They are refused at the constructor rather than at `App.Service` because the mistake is in their own arguments and the line of the constructor is the line to fix.

**Refusals** (rows of `refusal_test.go`; every message ends with `registered at <file:line>`):

- `app: Service has no name: set Service.Name, the word the log and the errors call this service by` (also for a name with a space or a quote, which the log line would not show whole).
- `app: Service "queue" has no Start, BeforeShutdown or Stop: a service with nothing to run is a mistake; set at least one of them`
- `app: Service "queue" is registered twice, first at <where>: a name is one service; give the second its own name`
- `app: Service "queue" registered at <where> after the app started serving: services can be added only before it does` (the same rule and words as `Use`; a `Start` that registers a service meets it).
- `app: WithServiceTimeout(0) is not a time to wait: give a positive duration, or leave it out for 30s` and `app: WithServiceTimeout is given twice`.
- `bites.Worker: the name is empty or has a space, a quote or a control character: give the word the log and the errors call this worker by, such as "mail-sender"` and `bites.Worker("mail"): run is nil: give the function the worker runs until its ctx is cancelled`.
- `bites.Every: the name is empty or has a space, a quote or a control character: give the word the log and the errors call this job by, such as "purge-deleted"`, `bites.Every("purge"): fn is nil: give the function called once every interval`, and `bites.Every("purge"): the interval 0 is not a time between calls: give a positive duration, such as time.Minute` (also for a negative one).
- `bites.Every("purge"): 2 options values were given; give one EveryOptions`. No combination inside `EveryOptions` is refused because it has one field, and `AtStart` with any valid interval is meaningful: nothing about the start call can be told wrong before the first request.

**What it costs** ([ADR 0003](0003-the-trade-budget.md)). `Worker` and `Every` are off the request path: a goroutine and one timer for the life of the app, no allocation per request (`AtStart` adds one call on that goroutine, not on a request). None of the four axes moves, and `TestARouteBesideAServiceKeepsTheRequestAllocationsAtTwo` measures it: 2 allocations for the typed JSON POST beside a Service with all three functions set. Hooks run only when the app starts and stops: a slice of services and one lifecycle value on the `App`, and no field on a connection, a route or a request, so the 2 allocations of a typed JSON request (3 with the done channel) and the memory per idle connection are unchanged, and throughput and p99 have nothing to move. A test carries a `Service` through the existing budget test (`TestARouteBesideAServiceKeepsTheRequestAllocationsAtTwo`), which would fail if the request path read it. Start-up costs the time of the `Start` functions, which is the application's.

**Scenarios it was put against.**

- _A database pool and a worker that uses it._ Registered in that order. Shutdown: the listener closes, requests drain, the worker's context is cancelled and its `Stop` waits for the goroutine, then the pool closes. In the other order the worker would write to a closed pool; the rule makes the order the registration order, one place to read.
- _The third of five services fails to start._ The first two are stopped in reverse, the port is released, `Listen` returns `bites: service "c": Start: ...`, and the log says which. No request was served by an app missing a service.
- _A rolling deploy with a registry and `WithShutdownDelay(5*time.Second)`._ SIGTERM: readiness fails, `BeforeShutdown` deregisters from the registry, the delay keeps serving while the balancer learns, the listener closes, the drain runs, `Stop` closes the registry client.
- _A `Stop` that ignores its context._ Shutdown's context is 30 s: the function is abandoned at 30 s with its name in the log, the rest of the `Stop` calls run, `Shutdown` returns `context.DeadlineExceeded` joined, and the process can exit.
- _`main` as `go app.Shutdown(ctx)` then `return` after `Listen`._ Safe: `Listen` returns after `Stop`.
- _TCP and Unix on one app._ Both `Serve` calls wait for one `Start` phase; one `Shutdown` stops everything once.
- _A `Start` that takes 20 s while a balancer probes._ The probe connects (the kernel accepts into the backlog) and waits; it is answered after the start. A start-up probe with a long enough budget is the platform's answer, and the log shows the `Start` that is slow.
- _A hostile client during `Start`._ It can fill the backlog and no more; nothing of bites is allocated for those connections until they are accepted, so the limits of [ADR 0024](0024-limits-are-on-by-default.md) apply from the first accept.
- _A hook that registers a route or a service._ `Start` runs after the router is frozen; the call panics with the refusal above.
- _A background worker and a purge of rows deleted more than 30 days ago._ `bites.Worker("mailer", run)` and `bites.Every("purge-deleted", time.Hour, fn)` are each a `Service` with a `Start` and a `Stop` and no field the struct lacks, which is the test that the shape was enough. Shutdown: the context of each is cancelled, a call in progress finishes (or is abandoned at Shutdown's deadline), and the pool registered before them closes after.
- _A worker whose `run` fails at 3 a.m._ `run` returns an error: one Error line names the worker and the error and says it is not restarted. The app keeps serving; an operator sees the line and the worker's missing work, not a loop that hides a broken dependency by retrying every millisecond. A worker that must survive loops inside `run`.
- _A scheduler that must reconcile what a crash left, then check each minute._ `bites.Every("meeting-check", time.Minute, fn, bites.EveryOptions{AtStart: true})`: `fn` runs right after the start on the Service's goroutine with the app's clock and logger, `Start` has already returned so connections are accepted meanwhile, and a Shutdown during it cancels its `ctx` and waits. A reconcile that takes three minutes drops the two ticks it overran, with one Warn naming how many were skipped, and the next call is at the next multiple of the interval.
- _An `Every` whose run takes five minutes on a one-minute interval._ The next run waits for it, never overlaps it, the four ticks it missed are dropped and one Warn says `skipped=4`; a burst of four catch-up runs would hit the database exactly when it is slow.

**What it fails at.**

- A connection during `Start` sees no answer at all, not a 503. The alternative, accepting at once and failing readiness until every `Start` ends, would let a handler run before a service it needs; the safer order costs a slower first byte.
- An abandoned function leaks its goroutine and may still be running when the process exits mid-write. The log names it; the framework cannot do more than Go allows.
- A `Start` or `BeforeShutdown` that calls `Shutdown` or `Close` on its own app and waits deadlocks on the phase it is part of (`Shutdown` waits for the phase to end within its context, and with no deadline forever). It must call it from its own goroutine.
- A service that needs the listener's address (to register itself) cannot get it from `Start`, which runs before accepting but after the bind; the address is in the `listening` log line, and giving it to the service is left until an application asks.
- `Stop` after a `Close` cannot be graceful: its context is already done, so a service gets a chance to flush only as far as it ignores the context.
- Services are one flat ordered list. A dependency between two services is the order they are registered in, written by the application; there is no graph and no readiness per service.
- Registration order decides both starts and stops, so a service that must start early but stop late cannot be expressed; it is two services.

**Considered.** Frameworks around this, read in [`docs/research/framework-gap/`](../research/framework-gap/report.md):

- **Several callback registrations** (Fiber's `OnListen`, `OnPreShutdown`, `OnPostShutdown`, Hertz's `OnRun` and `OnShutdown`, Kratos' `BeforeStart`, `AfterStart`, `BeforeStop`, `AfterStop`, Echo v5's `BeforeServeFunc`; [`fiber.md`](../research/framework-gap/fiber.md) section 9, [`hertz-fuego.md`](../research/framework-gap/hertz-fuego.md) section 1.9, [`microservices.md`](../research/framework-gap/microservices.md) 1.5). Rejected as the shape: a start and its stop are two calls in two places, the order of stops is whatever order the application happened to register them, and there are four spellings for one pairing. Kept: the moments they name are the moments of the three fields.
- **A `Service` interface with `Start`, `String`, `State`, `Terminate`**, started in order and terminated in reverse (Fiber v3 services, <https://docs.gofiber.io/api/services>). The order and the reverse are kept. Rejected as the shape: a closure needs a named type with every method, an app that only stops something must write an empty `Start`, and its `Terminate` has no place for a step before the listener closes, which a registry needs. A struct of functions has the same ordering and lets a module return a value.
- **`Hooks.OnStart` and `OnStop` in `humacli`** (<https://huma.rocks/how-to/graceful-shutdown/>; [`huma.md`](../research/framework-gap/huma.md)): a pair, which is the right size, but `OnStart` is what runs the server, not a hook beside it, and there is no order among several.
- **Encore's `Shutdown(force context.Context)` on a service struct**, which Encore waits for indefinitely ([`microservices.md`](../research/framework-gap/microservices.md) 4.10): the wait without a deadline is the trap this ADR bounds. go-zero's `AddShutdownListener` and go-micro's `micro.BeforeStop` ([`microservices.md`](../research/framework-gap/microservices.md) 2.10, 3.10) are single callbacks with no pairing.
- **`http.Server.RegisterOnShutdown`** (<https://pkg.go.dev/net/http#Server.RegisterOnShutdown>; [`chi-stdlib.md`](../research/framework-gap/chi-stdlib.md) 2.3): the functions run on their own goroutines, Shutdown does not wait for them, and the documentation says they must not block, so a worker's drain is not waited for. Rejected for the same reason `main` returning early is a trap.

What was rejected, with the reason:

- **Cron expressions and jitter for `Every`.** Cron stays on the roadmap as a later addition (a module or a second constructor, with the time zone and daylight-saving rules it needs argued then); an interval is what the three uses ask for, and a schedule at a time of day is `Every` with a short interval and a compare against `Now(ctx)`. Jitter is for a fleet hammering one resource; no application has asked, and an option is a second way to say the interval.
- **Restarting a `Worker` that returned, with a back-off.** Rejected: the policy (how long, how many times, when to give up) is the application's, and a silent retry of a failing dependency is the trap the principles refuse. It is logged and left stopped.
- **"A job that wants a run at start calls the function once before registering" as the only way, and a first run at start as the default.** The first was the position of the first version of this ADR. The call before registering runs in the caller's goroutine, before the app has a clock or a logger on a context, so it cannot be a call of the job: `Now(ctx)` and `Logger(ctx)` are the app's only on a Service's context, an error is the caller's to log, and nothing bounds it by `Stop`. An application (Athena's meeting scheduler) gave up `Every` for a `Worker` with its own tickers because of exactly this, which is the second spelling of periodic work this ADR exists to avoid. The second is still rejected: a deploy of many instances would run every sweep at the same second, and the three uses lose nothing by waiting. The option keeps the default and moves the call onto the Service's goroutine, where the start never waits for it.
- **Catching up the missed ticks of `Every`**, or a `time.Ticker` that holds one pending tick: the first is a burst on a slow database, the second runs a late tick straight after an overrun without saying so. Dropped and logged says what happened.
- **A `Worker` that blocks in `Start`** (`errgroup`): rejected above for every Service.

- **`Start` that blocks until the service ends** (the `errgroup` and `Run` shape, which makes a worker one line). Rejected: a resource (a pool, a registry entry) has no loop to block on, and two kinds of service would be two ways to do one thing. A blocking worker is `Start: go run(ctx)`, which the roadmap's scheduled and background work wraps in one constructor.
- **Passing `Start` a context that ends when `Start` returns, with the deadline on it** (the common shape): it silently kills `go run(ctx)`. The context is the service's life and the deadline is the framework's wait.
- **Accepting connections while `Start` runs, with readiness failing until they end.** Rejected for the reason above: a route can be served before the service it uses exists, and not every app has `WithHealth`. A balancer that cannot wait is a start-up probe's job.
- **Starting services before binding the listener.** Rejected: the common failure, the port in use, would start every worker and then tear them down.
- **Running `Stop` before the drain** (stop the workers, then the requests). Rejected as the default: a request in flight uses a pool and a cache; closing them first fails the very requests the drain exists to finish. A service that must leave first has `BeforeShutdown`.
- **Stopping in start order** or an explicit priority integer: the reverse of start is the order of dependency by construction, and a number is a second thing to keep in step with the registration.
- **`Close` running `BeforeShutdown`.** Rejected: `Close` is the app saying it will not wait; a network call to deregister with a done context fails at once anyway. `Stop` is where a service makes sure it left.
- **A signal handler that calls `Shutdown`.** Still refused ([ADR 0029](0029-shutdown-drains-and-then-closes.md)); the application's two lines of `signal.NotifyContext` are the same with services.
- **Hooks that may register services after start**: refused as `Use` is, since the order of stops would depend on timing.
- **A global registry of services** or an `init`-time `bites.RegisterService`: refused by [ADR 0026](0026-no-global-state-and-one-behaviour.md); a service belongs to one app, and two apps in one test must not share it.
- **Wrapping a single error in `errors.Join`.** `Shutdown` returns the one error as it is when only one function or the engine failed, so `err == context.DeadlineExceeded` and `errors.Is` both keep working for code written before Services; the join is only made for two or more.
- **`BeforeShutdown` with no deadline on `Shutdown`'s context** is waited for until it returns, because there is no half to take; `Shutdown(context.Background())` gives a hung hook no bound. `Shutdown` should be given a context with a deadline, as the deploy guide does. `WithServiceTimeout` bounds only a function called with a context already done.
- **A `ServiceError` type** for the failed start: the wrapped `fmt.Errorf` carries the name and the phase in its text and the cause for `errors.Is` and `errors.As`; a type would be a new exported name with nothing an agent needs from it.
