# The documentation is three layers, and tests hold it true

**The documentation answers three questions in three folders.** `docs/guide/` answers "how do I do this?", one page per task, in reading order, with worked examples. `docs/reference/` answers "what exactly is this name, and what does it take?", one page per area of the API, with a heading for every exported name. `docs/design/` answers "why does it work this way, and what was rejected?", one page per topic, which joins the ADRs of that topic and links each one. `docs/README.md` is the map: one row per guide page, with the reference and design pages that go with it. The ADRs stay the rule in force ([ADR 0033](0033-the-rules-are-build-steps.md) for how a rule is held); a design page is where a reader starts and an ADR is where the evidence is.

**Every page of the three layers opens with the same five lines**: the title on line 1, one bold sentence saying what the page is on line 3, and on line 5 the same topic in the other two layers (`**Guide:** ... · **Reference:** ...` on a design page, a link or "none" for each). A reference heading is the name itself in code (`` ### `App.Get` ``), so its anchor is predictable (`#appget`) and a guide page can link a name without opening the reference. A design page has the sections Overview, Rules, Decisions (a table: ADR, what it decides) and Open questions.

**Tests hold it, in `docs_test.go`, on every `go test`:**

1. every page of the three layers opens with the five lines above;
2. prose is one paragraph a line and has no em dash, in the three layers, the ADRs, the roadmap, `README.md`, `GLOSSARY.md` and `CLAUDE.md`;
3. every relative link in those files points at a file that exists, and every `#anchor` at a heading that produces it;
4. `docs/README.md` links every page of the three layers;
5. every ADR is linked from a design page, so no decision is left out of the topic pages;
6. every exported name of `bites` and `bitetest` (types, functions, constants, variables, and the methods of exported types) has its heading in `docs/reference/`, so a new API without its reference fails the build;
7. `docs/reference/README.md` lists every heading of the reference once, written by `go test -run TestTheReferenceListsEveryHeadingOnce -update`;
8. every Go block marked `<!-- compiles -->` (a whole file), `<!-- compiles: decls -->` (declarations, joined with the page's earlier ones) or `<!-- compiles: body -->` (statements, with `app` and `ctx` in scope) is compiled and vetted against the module, with the imports it names added, and a whole-file block whose package is a test package (`package orders_test`) is also run, since 2026-11-04: an example test that compiles and fails is a page that lies, and the testing guide's WebSocket example did, unseen, until an agent ran it ([`docs/research/agent-usability/`](../research/agent-usability/run-2/report.md)). A failure is reported at the page's line. `-short` skips this one, because it runs the `go` command.
9. the doc comment of every type alias of `bites` (`Opt`, `Date`, `StreamWriter`, ...) names each exported method and field of the type it stands for, since `go doc` shows an alias with its own comment only and an agent reading `go doc bites.Date` would otherwise not learn `Date.Sub` exists (`alias_doc_test.go`, added 2026-11-04 after the second agent usability run).

**Why, from this repository.** Before this decision the only prose a user could read was `README.md`, `doc.go` and the ADRs, and two of those were wrong within days: at milestone 2's commit `README.md` still said "There is no code yet" and listed shipped features as planned, and `doc.go` said middleware, Providers, streaming, WebSockets, TLS and the OpenAPI document were not built. Nothing checked either. The ADRs stayed right because every change edits them in place, which [ADR 0033](0033-the-rules-are-build-steps.md) and the change checklist in `CLAUDE.md` enforce by habit and review; the guide and reference have no such habit yet, so they get tests. The exported-name check is the one that matters most: the API grew by about 150 names in milestone 2, and a reference that is complete when written and incomplete a month later is worse than none.

**Considered:** Go's own `go doc` and pkg.go.dev as the reference. They are kept (doc comments stay, and are what an editor shows), but they order names alphabetically, cannot group a name with the guide task it serves, and do not say which ADR decided it. The reference pages link the code; they do not replace doc comments.

**What was rejected:** one large guide page (bites' API covers routing, input, responses, middleware, Providers, streams, WebSockets, OpenAPI and operations; one page is a scroll nobody finishes, and an anchor into it is unstable); keeping complete example programs in a folder and linking them from the guide (the page and the program drift, and the build stays green while the page is wrong; the page's own block is the one compiled); Go testable examples (`Example*` functions) as the only checked code (they are checked, but they live in `_test.go` files a reader of the guide never sees, and they cannot hold a partial snippet that a page builds up across sections); and a published site in this milestone (a site generator is a dependency outside the standard library for the repository's tooling, and GitHub renders the Markdown with its anchors; a site is decided with the first release in milestone 3).

**What it fails at:** the checks see structure, links, names and compilation, not truth: a page can describe a behaviour wrongly and still pass, so a change that alters behaviour still edits its guide and reference pages by hand, as it edits its ADR. The em dash and paragraph checks are lexical and can be fooled by an unusual line. A body block's unused variable fails to compile, so a snippet has to use what it declares.
