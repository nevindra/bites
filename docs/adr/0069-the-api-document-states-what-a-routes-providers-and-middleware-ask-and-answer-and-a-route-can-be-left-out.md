# The API document states the credentials a route's Providers read and the refusals its middleware can answer, and a route can be left out of it

The OpenAPI document of [ADR 0020](0020-descriptions-come-from-registration-and-later-from-doc-comments.md) describes how a route is secured from what the route already runs: the scheme of every `BearerAuth`, `BasicAuth` and `APIKeyAuth` Provider ([ADR 0054](0054-auth-providers-parse-the-credential-and-the-application-verifies-it.md)) the route resolves is a `securitySchemes` entry and the operation's `security`, with the 401 they answer; a `RateLimiter`'s middleware ([ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md)) adds the 429 and `CSRF` ([ADR 0057](0057-csrf-trusts-the-browsers-origin-and-falls-back-to-a-double-submit-token.md)) the 403. A Provider the application wrote states its scheme by being given to `CustomAuth`; `AnyAuth` makes one Provider of several credentials, which the document lists as alternatives; an `Opt` field of an auth Provider's type makes the credential optional, which the document states with the empty requirement. A route option, `Undocumented()`, leaves a route, or every route of a group, out of the document; the mounts of `stdhttp` and the pages of `modules/docsui` use it. Decided and built on 2026-11-01, milestone 3 wave 2 (`openapi.go`, `auth.go`, `ratelimit.go`, `openapi_test.go`, `testdata/openapi/secured.json`); `CustomAuth`, `AnyAuth` and the optional credential built on 2026-11-02 (`auth.go`, `provide.go`, `auth_test.go`, `security_budget_test.go`). The header and cookie a Provider reads, and the error statuses a route names with `ErrorStatuses`, built on 2026-11-04 after the second agent usability run found neither could be stated (`provide.go`, `openapi.go`, `provide_test.go`, `openapi_test.go`).

```go
func Undocumented() RouteOption
func CustomAuth[T any](scheme SecurityScheme, provider func(ctx context.Context, req Request, deps struct{}) (T, error)) func(context.Context, Request, struct{}) (T, error)
func AnyAuth[T any](providers ...func(ctx context.Context, req Request, deps struct{}) (T, error)) func(context.Context, Request, struct{}) (T, error)
```

**The rule, security.**

- _From the Providers the route runs._ The Providers a route runs are the ones its Input's fields resolve to, and those they need in turn ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)); a Provider in force on the app or a group that the route never asks for is not run and adds nothing. Each of them that `BearerAuth`, `BasicAuth`, `APIKeyAuth`, `CustomAuth` or `AnyAuth` made is an auth Provider, and reads one credential or, for `AnyAuth`, one of several. Every Provider a route runs must succeed, so the route's `security` is every combination of one way through each auth Provider: the credentials of two Providers are one Security Requirement holding both (`[{"apiKeyAuth": [], "apiKeyAuth.X-Tenant-Key": []}]`); an `AnyAuth` of Bearer and an API key is two requirements (`[{"bearerAuth": []}, {"apiKeyAuth": []}]`); an optional credential adds the empty requirement (`[{"bearerAuth": []}, {}]`). Requirements that come out the same are listed once, in the order the Providers run and the alternatives were given. A route with no auth Provider has no `security`, and the document has no top-level `security`, so an unsecured route is not described as secured by default.
- _The schemes._ Bearer is `{"type": "http", "scheme": "bearer"}` named `bearerAuth`; Basic is `{"type": "http", "scheme": "basic"}` named `basicAuth`; an API key is `{"type": "apiKey", "in": "header", "name": <its header>}`, named `apiKeyAuth` for `X-API-Key` and `apiKeyAuth.<header>` for another, so two headers are two schemes. A `CustomAuth` scheme is its `SecurityScheme` as OpenAPI writes it: another HTTP scheme is `<scheme>Auth` (`digestAuth`), a key in a cookie is `cookieAuth.<name>`, a client certificate is `mutualTLS` and OpenID Connect is `openIdConnect`; one whose entry is the same as another's shares its name, so a `CustomAuth` of `Scheme: "bearer"` with no `BearerFormat` is `bearerAuth`. Two Providers of one scheme with different realms or types share an entry: the realm is not in OpenAPI. Two different entries that would take one name are told apart by a suffix, `.2`, in the order the routes are registered.
- _The answers they add._ A route with a scheme gets a 401 that refers to `components.responses.Unauthorized`, a problem+json answer with the `WWW-Authenticate` header, and a 400 that refers to `Error` when the route has no 400 already (a malformed credential is a 400, [ADR 0054](0054-auth-providers-parse-the-credential-and-the-application-verifies-it.md)); an optional credential has them too, since one that is sent and not good is still a 401. A route whose middleware includes a `RateLimiter`'s gets a 429 that refers to `TooManyRequests`, with `Retry-After`, `RateLimit-Policy` and `RateLimit`; a route behind `CSRF` gets a 403 that refers to `Error` for every method but GET, HEAD, OPTIONS and TRACE, which CSRF lets through. App middleware runs for every request, and `App.Use` may come after the routes ([ADR 0048](0048-groups-and-the-order-things-run-in.md)), so it is read when the document is built at start rather than at each route's Registration. `Unauthorized` and `TooManyRequests` are in `components.responses` only when an operation refers to them, so a document without security is the one it was.
- _How a Provider is recognised._ A Provider is a plain function, and the framework keeps no package-level record of the ones it made ([ADR 0026](0026-no-global-state-and-one-behaviour.md)), so it is recognised by its code. Each of the five constructors returns its Provider through one method, `asProvider`, that is never inlined (`//go:noinline`) and returns the method value of `provide`, so every Provider one constructor makes for a type `T` has one code address whatever its receiver. At Registration the code of a Provider of shape `func(context.Context, Request, struct{}) (T, error)` is compared with that of `asProvider` on an unused receiver of each of the five for the same `T`, which runs no constructor. Only a match is called, with a probe context that the five recognise as their first statement and answer by reporting the credentials they read, without reading a request. A Provider the application wrote is never called at Registration, which `TestAProviderOfTheSameShapeAsBearerAuthIsNeverCalledAtRegistrationAndAddsNoSecurity` and `TestACustomAuthProviderStatesItsSchemeAndIsNeverCalledAtRegistration` hold. `RateLimiter.Middleware` and `CSRF` return method values made in methods that are not generic, whose code is the method's wrapper whatever the receiver, and are recognised the same way, with no call at all.

**An application's own Provider states its scheme with `CustomAuth`.** `CustomAuth(scheme, provider)` returns `provider` as it is, behind one comparison against the probe, together with a `SecurityScheme`: `Type` `"http"` with `Scheme` (and `BearerFormat` for a bearer token), `"apiKey"` with `In` (`"header"` or `"cookie"`) and `Name`, `"mutualTLS"` (a client certificate, [ADR 0066](0066-client-certificates-are-verified-by-the-tls-config-and-read-as-verified-chains.md)), or `"openIdConnect"` with `OpenIDConnectURL`; `Description` for any. The scheme lives with the Provider, so every route that runs it is described the same way and no route can disagree with another, which is what a route option could not promise (below). The framework cannot read the application's code, so the scheme is the application's word for what its Provider reads, as a `Descriptions` method is its word for what a field means ([ADR 0020](0020-descriptions-come-from-registration-and-later-from-doc-comments.md)). The Provider may have dependencies (revised 2026-11-04, after the third agent usability run had to call `Sessions.Load` inside its session user to give it to `CustomAuth`): a Provider with dependencies is recognised by the code of `CustomAuth`'s Provider for its own `T` and `D`, and called with the probe and a zero `D`, which it answers before reading anything ([ADR 0056](0056-a-session-is-sealed-in-a-cookie-and-changed-by-returning-its-cookie.md) for the session it reads). A key in the query is refused for the reason `APIKeyAuth` reads none ([ADR 0054](0054-auth-providers-parse-the-credential-and-the-application-verifies-it.md)): a query is written in access logs. OAuth 2 is not a `Type`, since its flows and scopes would need a design of their own (open question in the design page); an OAuth 2 access token is described as `"http"` with `Scheme: "bearer"`.

**Several credentials on one route are `AnyAuth`.** `AnyAuth(p1, p2, ...)` takes two or more Providers of one `T` that the five constructors made (a nested `AnyAuth` gives its alternatives, in order), and is a Provider of `T`. The scheme of each says where its credential is sent, so a request is matched without running any: the first, in the order given, whose credential the request carries runs, and its answer is the answer. "Carries" is what the Provider itself would not call missing: an `Authorization` of its scheme, a header of its name that is not empty, a cookie of its name, a verified client certificate; a header sent twice counts as carried, so that the Provider answers its 400. A credential that is carried and not good is that Provider's 401 (or 400, or 500), and the next is not tried: an expired token must reach the client as `invalid_token` so it refreshes, and trying a second credential would let a client spray several at each request against several verifiers. A request that carries none is answered by the first Provider, whose 401 gets the challenge of each other alternative that has one (`WWW-Authenticate` once for each, which RFC 9110 11.6.1 allows), so a client learns every way in. A `CustomAuth` alternative has no challenge the framework knows: its own 401 is its Provider's.

**An optional credential is an `Opt` field.** An Input field, or a Provider's dependency, of type `Opt[T]` that no Provider of `Opt[T]` covers on the route is filled by the optional form of the route's Provider of `T`, when that Provider is an auth Provider ([ADR 0023](0023-provided-sections-are-checked-at-registration.md), edited in place): a request that carries none of its credentials gets an absent `Opt` and the Provider does not run; one that carries one runs it, and a value is present, or its error is the answer. A token that is sent and not good is a 401, never an anonymous request: a client with an expired token that got the anonymous page would not know to refresh, and a client that sends a token means to be someone. The optional form is built with the Provider at its `Provide`, so the route's Providers stay one list resolved at Registration and the value lives on the stack like any other ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)). An explicit Provider of `Opt[T]` is used when there is one. A route that needs both `T` and `Opt[T]` is refused: the credential is required there, and the two would run the verifier twice.

**A Provider's own parameters are the route's.** A Provider whose dependencies hold a `Header` or `Cookie` section ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)) reads those values on every route that runs it, so each is a parameter of those operations, described as the Input's would be. A parameter the Input states too (both read `X-Tenant`) is listed once, and required when either requires it; the operation gets the 400 of `InvalidInput`, since the Provider's section is checked as the Input's is.

**A handler's own error statuses are named with `ErrorStatuses`.** What the framework answers by itself is stated from what the route runs, as above. What the handler decides at run time (a `NotFound` when the row is missing, a `Conflict`, a 412) cannot be seen in its types, so a route option names it: `ErrorStatuses(404, 409)` on a route or a group adds each status as a reference to `components.responses.Error`, and a status the framework already states keeps its own response. It states and does not enforce: an error status the handler returns and the option does not name is still sent as it is, and the `default` response still covers it. A status whose answer carries data is stated with `ErrorStatus[T](status)` instead, which adds the fields of `T` to the problem in the document ([ADR 0088](0088-an-error-that-carries-data-states-its-type-with-error-status-and-sends-it-with-members.md)).

**A ticket in the query.** `CustomAuth` takes `In: "query"` for an API key, for a Provider that reads a `Query` section, which only a WebSocket route and an event stream route allow ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)): a browser's `WebSocket` and `EventSource` cannot send a header, so a short-lived ticket in the URL is how a page that holds a token opens them, and the document states it as `apiKey` in `query`. `AnyAuth` sees it carried when the query has the key with a value. `BearerAuth` and `APIKeyAuth` still read no query.

**What a `File`, a `Bytes` or a `Stream` sends, and the headers a handler sets.** Built 2026-11-04 after the third agent usability run found its NDJSON export and its downloads described as any bytes. A `File` is described by what `File` itself does ([ADR 0064](0064-a-file-answers-its-own-conditional-and-range-requests.md)): a 200 and a 206 with `ETag`, `Last-Modified`, `Accept-Ranges` and `Content-Disposition` (and `Content-Range` on the 206), each optional since a `File` may send none of them, a 304, and the 412 and 416 it refuses with. The media type of a `Bytes`, `File` or `Stream` is set at run time, so it stays `*/*` unless the route option `MediaType` states it, and a header the handler sets in an answer's `Header` is stated by `SendsHeader[T](name, description)` (revised 2026-11-05: it was `SendsHeaders(names...)`, which could state a header only as an optional string with no words, and is replaced, not kept beside it, so a header has one way to be said; [ADR 0020](0020-descriptions-come-from-registration-and-later-from-doc-comments.md) holds the rule and what was rejected). Both state and do not check, as `ErrorStatuses`; `MediaType` is refused on a route whose answers all have a media type already, and `SendsHeader` refuses `Content-Type` and `Location`, which `MediaType` and `SetsLocation` state, so each thing has one way to be said.

**The rule, leaving a route out.** `Undocumented()` on a route, or on a group for all its routes, leaves the route out of `paths`; its types are not described, so a type the document could not describe is not refused there, and the check that the document can hold its path ([ADR 0020](0020-descriptions-come-from-registration-and-later-from-doc-comments.md)) is not made. The route is served as any other. A `Tag` on it, usually a group's, is ignored. `stdhttp.Mount`, `MountMethods` and `MountGroup` add it to every route they register, since a mounted handler's types (`any` returning `Bytes` or `Stream`) say nothing about what it serves ([ADR 0019](0019-plain-http-handlers-are-a-slow-path.md)); `docsui.Mount` adds it to the page and its script ([ADR 0071](0071-the-api-documentation-ui-is-a-module-that-loads-a-pinned-cdn-version.md)). It is not access control: an undocumented route answers anyone who finds it.

**What it costs.** At Registration, for each Provider of the auth shape, five method values made and compared, and for a match one call with the probe; for `AnyAuth`, the same for each of its arguments when it is made; at start, a scan of each route's middleware and the app's. Per request, each auth Provider begins with a type assertion of its context against the probe's type, one comparison and no allocation; `AnyAuth` looks for each credential before the one sent (a scan of the head's copy, [ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)), and an optional field looks for its credentials once. The typed POST stays at **2 allocations** behind each, measured in `TestTheSecurityMiddlewareAndProvidersCostWhatTheirADRsSay` (`security_budget_test.go`) on 2026-11-02: `BearerAuth` and `APIKeyAuth` (unchanged), `AnyAuth` of Bearer and an API key answered by its second, `CustomAuth` around a Bearer Provider, and an `Opt` field of `BearerAuth` with a token and with none. `RateLimiter.Middleware` returning a method value rather than a closure changes nothing a request pays. Not inlining `asProvider` costs nothing a request pays, since it runs at Registration. Memory per idle connection: none. Throughput and p99 are not measured yet; they wait for the serial run of wave 2. **Axes:** none of the four moves.

**Refusals** (rows of `refusal_test.go`): `Summary`, `Description` or `OperationID` on a route that `Undocumented` leaves out, given on the route or inherited from its group, since the document would drop it without a word. `ErrorStatuses` with no status, with a status outside 400 to 599 or one named twice in a call, and on an `Undocumented`, WebSocket or static route, which the document leaves out. `MediaType` on a group, of a value that is not `type/subtype` or has a wildcard, or on a route with no `Bytes`, `File` or `Stream` answer; `SendsHeader` with a name that is not a header name, no description, a name given twice, a type that is not text, `Content-Type` or `Location`; and either on an `Undocumented`, WebSocket or static route. At construction, `CustomAuth`: a nil Provider; a `Type` that is not one of the four (OAuth 2 named in the message); `"http"` with a `Scheme` that is not a token; `BearerFormat` for a scheme that is not bearer; an API key `In` the query or anywhere but a header or a cookie; an API key header that is `Authorization` or `Cookie` or not a token; a cookie name that is not a token; an `OpenIDConnectURL` that is not an absolute `http` or `https` URL; a field its `Type` does not have. `AnyAuth`: fewer than two Providers; a nil one; one the five did not make, since where its credential is sent is not known; two that read the same credential (`BearerAuth` and a `CustomAuth` of `Scheme: "bearer"`), since the second would never run. At Registration: an `Opt[T]` field whose `T` has a Provider the five did not make, naming that Provider's line and the two ways out; a route that needs both `T` and `Opt[T]`. **What cannot be caught before the first request:** the scheme given to `CustomAuth` is the application's word, and a Provider that reads a cookie while its scheme says a header is described wrongly and, in `AnyAuth`, never runs for a request that carries only the cookie; a Provider the application wrote and did not give to `CustomAuth` is not recognised and its route has no `security`; a `RateLimiter.Allow` called inside a Provider, the way a limit per user is written, adds no 429 by itself, so `ErrorStatuses(429)` on its routes states it and is documented as `TooManyRequests` rather than `Error` (the fourth agent usability run wrote the limit and found its 429 missing); a middleware the application wrote around `CSRF` or a limiter adds nothing. Each is the honest limit of reading the document from what the route runs: the framework describes what it made, and what the application said about what it made.

**Scenarios it was put against.**

- _The reference workload_ ([ADR 0002](0002-the-reference-workload.md)): `BearerAuth(jwt.Verify)` on the API ([ADR 0062](0062-jwt-verification-is-a-module-whose-key-fixes-the-algorithm.md)), a `RateLimiter` by address on the app, `APIKeyAuth` on `/v1` for machine clients, sessions and `CSRF` on the admin pages, `/metrics` and `pprof` mounted with `stdhttp`. The document has `bearerAuth` on every API route that reads the user and none on `/health`, 429 everywhere, 403 on the admin pages' POSTs, and no `/debug/pprof/` or `/docs` entry. A generated client sends the token where the document says. `testdata/openapi/secured.json` is that shape, with a product page open to everyone and personal to a signed-in caller (`[{"bearerAuth": []}, {}]`) and a partner API reached by a token, a session cookie or a client certificate (`[{"bearerAuth": []}, {"cookieAuth.sid": []}, {"mutualTLS": []}]`), and it validates against the official OAS 3.1 schema.
- _A route that refines the user_: an `Admin` Provider that needs the `User` from `BearerAuth` makes its routes require `bearerAuth`, though the route's Input names only `Admin` (`TestAProviderThatNeedsTheCallerMakesItsRouteRequireTheCallersScheme`); a `Viewer` Provider that needs `Opt[User]` is filled for a guest and for a signed-in caller (`TestAProviderMayNeedTheCallerAsOptional`).
- _One API for browsers and machines_: `AnyAuth(CustomAuth(cookie "sid", fromSession), BearerAuth(jwt.Verify))` on the API group. A browser's request carries the cookie and runs the session Provider; a CLI's carries a token and runs the verifier, and the session Provider is not called (`TestACustomAuthProviderRunsAsItIsAndInAnyAuthOnlyWhenItsCookieIsSent`). A request with neither is a 401 whose challenge is Bearer's, the only one the framework knows.
- _A client that sends an expired token and a good API key_ to `AnyAuth(Bearer, APIKey)`: a 401 with `error="invalid_token"`, and the key's verifier is not called (`TestAnyAuthAnswersACredentialThatIsNotGoodWithItsOwnErrorAndTriesNoOther`). Sending only the key is a 200.
- _An anonymous reader of an article page whose browser holds a stale token_: the optional route answers 401, the client refreshes or drops the token, and then reads anonymously; the same reader with no token gets the page and the verifier never runs (`TestAnOptFieldOfAnAuthProviderIsAbsentWithNoCredentialAndFilledWithAGoodOne`, `TestAnOptFieldStillAnswersACredentialThatIsNotGoodWith401AndAMalformedOneWith400`).
- _A hostile client reading the document_: it learns which routes need which credential, which every client must learn to use the API, and nothing about the realm or the keys. It also learns which routes accept no credential at all, which it could learn by sending none. The routes an operator does not want listed are left out with `Undocumented`, which hides them from the document and not from the client.
- _An application Provider with BearerAuth's exact signature_ that counts its calls: zero calls at Registration, and no security from it; given to `CustomAuth`, still zero calls and its scheme stated.

**What it fails at.** Recognition is by code, so what the application wraps without `CustomAuth` is not seen (above), and it rests on `asProvider` not being inlined, which `//go:noinline` guarantees and the tests hold. `CustomAuth`'s scheme can be wrong, and nothing checks it against what the Provider reads. A Provider with dependencies cannot be given to `AnyAuth`, nor made optional, though `CustomAuth` takes it: `AnyAuth` and the optional form call their Provider without filling anything first, and an optional form is a Provider of `Opt[T]` whose `T` Go cannot name inside a type it only holds as a type parameter. `AnyAuth`'s alternatives must provide one type, and its choice is by order, not by which credential is good. A request with no credential to an `AnyAuth` whose first alternative is a `CustomAuth` gets that Provider's own answer: the other alternatives' challenges are added only when it is a `*StatusError` 401, and a `CustomAuth` alternative adds no challenge to another's 401. The requirements of a route are a product, so a route of many `AnyAuth` Providers lists many combinations; none of the routes tested has more than four. A verifier that answers 403 for a missing scope is not described unless the route names it with `ErrorStatuses(403)`, since that status comes from the verifier's error at run time ([ADR 0049](0049-errors-are-found-with-errors-as-and-timeouts-wait.md)); the `default` response covers it otherwise. `ErrorStatuses` can fall out of date with the handler, and nothing checks the two against each other. A route with a body and a credential has one 400 in the document, `InvalidInput`, whose `errors` member a malformed credential's 400 does not carry. `bearerFormat: JWT` is not written for `BearerAuth`, since it does not know what its verifier checks; `CustomAuth` can say it. Scopes are always the empty list: no Provider declares them, and OAuth 2 flows are not described. The 403 of CSRF is stated for every state-changing method, also for a token-authenticated client that CSRF always lets through.

**What was rejected.** A `Security(...)` route option the application writes: it states a second time what the Providers already say and can disagree with them, route by route, which is the mistake the types-as-contract design exists to refuse; `CustomAuth` puts the statement on the Provider, once, where every route that runs it reads it. A record of every Provider the constructors made, keyed by the function: package-level state ([ADR 0026](0026-no-global-state-and-one-behaviour.md)). Calling every Provider with a probe at Registration: it runs application code (a database lookup) before the first request. Returning a named function type from the constructors: `Provide`'s parameter is a function type, so the name is gone by the time Registration sees the value. A top-level `security` with an empty requirement on public routes: it is the same document said twice. An `x-` extension for the realm: no client reads it. For leaving a route out, an option per module (`stdhttp.Undocumented`, a flag of `docsui.Config`): one route option serves both and any application route, and a module needs no core hook it lacks ([ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)); and leaving out every route that returns `any`: a route returning an interface with `Returns` is described and should stay. For a handler's error statuses, making `ErrorStatuses` a promise held at run time (an unnamed status turned into a 500): an honest 404 from a dependency would become a server error, which is worse for a client than a status the document did not list; and reading the statuses from the handler's code: a status comes from a value at run time, which Registration cannot see.

_Rejected for `CustomAuth`, `AnyAuth` and the optional credential (2026-11-02)._ An `OptionalAuth(p)` constructor returning a Provider of `Opt[T]`: a second name where the field's type already says "may be absent", and recognising it would need the code of `OptionalAuth` for the `T` inside `Opt[T]`, which a generic function holding `Opt[T]` cannot name; the `Opt` field asks for it in the words the Input already uses. Making the zero `T` stand for "anonymous": a handler would test a sentinel, and the type would not say the route serves anyone. Treating a credential that is sent and not good as anonymous on an optional route: the stale-token scenario above. Trying the next alternative of `AnyAuth` when one is not good: the expired-token scenario, and a verifier per credential sent. A `CustomAuth` that takes a verification function and reads the credential from where its scheme says: a client certificate is not a string, a cookie may be sealed ([ADR 0056](0056-a-session-is-sealed-in-a-cookie-and-changed-by-returning-its-cookie.md)), and the application's Provider already reads it; the framework needs where the credential is only to know whether it was sent. Comparing a Provider's code with that of a function each constructor makes for `T`, the device this ADR used until 2026-11-02: `AnyAuth`'s constructor recognises its arguments, so making a reference `AnyAuth` would recognise its own arguments without end; and a method value made inside a generic function is a closure of that place, not the method's wrapper (measured on 2026-11-02 with `runtime.FuncForPC`: `BearerAuth[...].func1` for the Provider `BearerAuth` returned, `(*bearerAuth[...]).provide-fm` for the same method value made elsewhere), so the reference has to come from the one place the constructors use, `asProvider`.
