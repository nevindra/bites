# Four principles, in the order they win

bites is held to four principles, decided by the maintainer on 2026-11-04. When two pull apart, the one earlier in the list wins.

1. **An AI agent uses it first; a person's experience comes second.** An agent that sees only the signatures, the doc comments and the refusals uses an API correctly on the first try. There is one way to do each thing, a signature is the whole contract, every exported name and field has a doc comment saying what it holds and what its zero value does, and a misuse that can be caught is a refusal whose message says what to change. Where what reads best to a person and what an agent gets right differ, the agent wins.
2. **It is safe: an agent can use it without a hidden trap and debug it from what it is told.** A mistake is refused at Registration with the route, the field and the line ([ADR 0007](0007-mistakes-are-refused-at-registration.md)); a client error is a problem+json that names the field ([ADR 0012](0012-client-errors-are-400-problem-json.md)); limits are on by default ([ADR 0024](0024-limits-are-on-by-default.md)); nothing pooled reaches user code ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)); a failed request says why in the log and the span. Nothing is skipped, defaulted or ignored in silence: when the framework does something the code did not say, it says so where an agent will read it.
3. **It covers a lot, so that many applications can be built on it fast.** Breadth is a goal: what Go frameworks commonly ship is on the roadmap, built in the order of how many applications need it ([ADR 0002](0002-the-reference-workload.md)), and no feature is refused for scope alone. That includes what a service among several needs (configuration, discovery, gRPC, message consumers), so an application can be split into microservices on bites when that is chosen. The core stays standard-library-only, and what needs a dependency or serves fewer applications is a module under `modules/` ([ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)). Breadth never buys a second way to do a thing or a feature that cannot be made safe: principles 1 and 2 win.
4. **It is fast and low on memory, without chasing the last percent.** The numbers it has are held by tests so they never rise by accident, and a change that raises one states the new number and why in the table of [ADR 0003](0003-the-trade-budget.md); work to go below them waits for an application whose load needs it. An application that needs the last few percent is served by nilo, the Zig framework, so bites does not chase it. What is refused is bloat: a cost a feature does not need, or one that grows with something a client controls.

**Standard library types and idioms are not a principle of their own.** One is used when it is what an agent gets right first, which is often, since agents have read far more standard-library Go than any framework's; a new idiom is used when an agent gets it right more often, and is argued as any design is, by principle 1, with no ADR needed for being a departure. The decisions taken under the earlier principles stand until revised: a decision argued only from familiarity to a Go developer is open to revision when an agent would be served better.

**What each asks of a change** is written in [`CLAUDE.md`](../../CLAUDE.md), and for users in the [README](../../README.md#principles).

**Scenarios it was put against.** An agent adds a route with a field misspelled in lower case: principle 2 refuses it at Registration instead of decoding nothing ([ADR 0015](0015-json-is-our-own-codec-on-jsontext.md)). A feature most frameworks have, a template engine: principle 3 reopens it as a module where the earlier rule refused it; principle 1 still decides its shape, one way to render. A JSON codec swapped in for speed: principle 4 would welcome it, principles 1 and 2 refuse it, because the 400 that names a field depends on the codec ([ADR 0015](0015-json-is-our-own-codec-on-jsontext.md)). A feature that adds an allocation per request: principle 3 outranks principle 4, so it ships with its row in ADR 0003 stating the number, where before it needed an ADR of its own.

**What it fails at.** Principle 1 has no test of its own: whether an agent gets an API right is judged by reading the signatures and refusals as an agent would, not measured. Ranking breadth over speed lets the request path grow slower one stated row at a time; the guard is that each row is written and measured, not that the total is capped. Dropping familiarity as a principle can make bites stranger to a person reading it, which principle 1 accepts.

**What was rejected:**

- **Three principles with the two hard axes winning** (the rule until 2026-11-04): AI agent friendly, familiar to a Go developer, and fast and low memory, where allocations per request and memory per idle connection outranked everything and either rose only with an ADR naming the number, and a departure from the standard library's type or idiom needed an ADR with its evidence. It was replaced because the maintainer builds many applications on bites and needs breadth more than the last allocation, nilo covers the workloads that need the last percent, and familiarity to a person ranks below what an agent gets right.
- **Breadth by parity rejected** (ADR 0002's rule from 2026-11-03 to 2026-11-04): a feature fewer applications need waited for a trigger however many frameworks had it, and the Not goals of the roadmap were refused outright. Replaced by principle 3: the roadmap is still ordered by how many applications need a feature, but an item waits for its turn, not for a trigger, and each Not goal refused for scope alone was reopened.
