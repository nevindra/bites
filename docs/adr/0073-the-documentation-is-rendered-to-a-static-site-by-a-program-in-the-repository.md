# The documentation is rendered to a static site by a program in the repository that uses the standard library only

`go run ./cmd/bites-site -out DIR` renders `README.md`, `GLOSSARY.md` and everything under `docs/` (the guide, the reference, the design pages, the ADRs, the roadmap and the research reports) to HTML in `DIR`, mirroring the repository's layout (`docs/guide/routing.md` becomes `docs/guide/routing.html`, a folder's `README.md` its `index.html`). It publishes nothing: where `DIR` goes is the user's decision, and the site is relative-linked so it works from any path and from disk. This answers the open question of [ADR 0050](0050-the-documentation-is-three-layers-held-by-tests.md) about a published site by deciding how it is built, not where it is hosted.

**The renderer is ours, for a Markdown subset.** The documentation is written in a small, regular Markdown (one paragraph a line, [ADR 0050](0050-the-documentation-is-three-layers-held-by-tests.md)): ATX headings, paragraphs, fenced code, flat and nested lists, tables, block quotes, rules, code spans, emphasis, links, images and autolinks. `internal/site` renders exactly that in about four hundred lines, with raw HTML escaped and never passed through, so the repository's tooling keeps the rule of [ADR 0006](0006-no-third-party-dependency-in-the-core.md) as well as the core does. A Markdown dependency (goldmark) would be a separate module ([ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)) and was not needed: the check of the build below is what keeps the subset honest.

**What the build guarantees.** Every relative link is resolved to the page it names (a folder to its index, `.md` to `.html`, an anchor kept), and every anchor is checked against the headings of the target with GitHub's slug rule, which is the rule `docs_test.go` holds the Markdown to. A link that does not resolve fails the build and is listed. A link to a file that is not documentation (a source file, a benchmark result) cannot be a page: with `-repo-url https://host/owner/repo` it points to that file on the branch `-branch`, and without it the text stays and carries its target in a `title`, counted in the build's output. A folder of `docs/` with pages and no README (the ADRs) gets a generated listing. A layer's sidebar is in the order its README links the pages. The stylesheet is one file, light and dark by the browser's setting, and there is no script, no web font and no external request.

**Its refusals.** None at Registration; it is a tool. It exits 1 on a broken link or anchor, a missing `README.md`, or an output directory it cannot write.

**Axes:** none; nothing in the framework changes.

**Scenarios it was put against.** The repository's own documentation, which a test builds on every `go test` and requires to have no broken link (147 pages at the time of writing). A page with a hostile `<script>` in its text: escaped. A table with a code span containing a bar: kept in its cell. A heading used twice: numbered as GitHub numbers it, so the existing links keep working. A reader without JavaScript: the site is complete.

**What it fails at.** There is no search and no syntax highlighting of code blocks; both are left out because each is either a script or a dependency, and the guide's pages are short enough for the browser's find. A Markdown feature outside the subset (a footnote, a setext heading, an inline HTML tag) renders as text, and the build does not warn, since `docs_test.go` already holds the pages to the subset's one-paragraph-a-line rule but not to a list of features. Link checking covers the pages it renders: a link to a file inside `docs/research/` other than Markdown is a repository link. The hosting, the domain, the versioned copies of a site per release and a `sitemap` are not decided.

**What was rejected:** Hugo, mkdocs or another generator (a toolchain outside Go for a repository whose contributors have `go`); goldmark in the root module (a dependency in the module that promises none); publishing from CI now (the user decides where the site goes, and a release is the point at which a version of the site means something).
