# A field can be filled by a Provider, and a route whose Provider is missing is refused

Besides its sections, an Input may have fields of a type that a Provider fills: a function from the request view to that type or an error, registered for the type on the app or on a group of routes ([ADR 0048](0048-groups-and-the-order-things-run-in.md)). The usual case is the authenticated user: `Auth User` in an Input is filled by the Provider registered for `User`, and a Provider that rejects the request returns its error (401, 403). A route whose Input asks for a type that no Provider covers on that route is refused at Registration ([ADR 0007](0007-mistakes-are-refused-at-registration.md)).

**How Providers compose.** A Provider may take other provided types as its own input: `func(ctx, req Request, deps struct{ Session Session }) (User, error)`. The graph is checked at Registration, and a cycle or a missing link is refused naming the chain. A Provider runs only when the route's Input, or a Provider it needs, names its type, so a costly one is paid only by the routes that ask for it, and it runs at most once a request.

**What a Provider is, and is not.** It is a function the application registers; it reaches Postgres or a token key through whatever it closes over, as a handler does through its struct ([ADR 0014](0014-services-are-plain-go-values.md)). The framework injects nothing else: no container, no lifetimes, no scopes.

**Logging what a Provider found.** A Provider may add attributes to the request's log record (the user's ID), and the access log writes them, which is how middleware that runs before Providers still logs who made the request.

**Why:** the common Go pattern, middleware putting the user into `ctx` and the handler taking it out by key, fails at request time with a nil when a route is registered outside the group that has the middleware. Here that mistake is a panic at start-up naming the route and the type. None of the frameworks examined checks it.

**Replacing a Provider.** `Provide[T]` is refused when the same scope or any enclosing one already has a Provider for `T`, naming both lines. `Override[T]` replaces an outer Provider for its scope and everything below it, and is refused when there is nothing to override. Each route resolves one map from type to Provider, nearest scope first, built at Registration, and a Provider's own dependencies resolve from that same map, so one request never holds two different `User` values under one type. The point is tests (a fake `User` in place of the session one) and the occasional subtree that really authenticates differently, written in a word that a reviewer can grep. A Provider for `T` that asks for `T` is a self-cycle and stays refused; the decorator idiom is a distinct type such as `Admin`. Evidence: [`docs/research/decisions-middleware/`](../research/decisions-middleware/report.md), section R11.

**Built in step 6 of milestone 2.** A Provider is `func(ctx context.Context, req Request, deps D) (T, error)`, where `D` is a struct whose exported fields are the provided types it needs, or `struct{}` when it needs none; `T` and `D` are inferred from the function. It is registered by `app.Provide(fn)`, `g.Provide(fn)` and `g.Override(fn)`, and by the options `bites.Provide(fn)` and `bites.Override(fn)`, which a group and a single route take (a route is the innermost scope). An app has no `Override`, since nothing encloses it. Each scope's options are applied from the app inward, so each route resolves one list of Providers, nearest scope first, at Registration. An Input field that is not a section is a provided field, and its route runs the Providers its provided fields need and the Providers those need, each once, in an order where a Provider comes after its dependencies and the Providers the framework made for authentication (`BearerAuth`, `BasicAuth`, `APIKeyAuth`, `CustomAuth`) come before the others, the rest following the order of the Input's fields, after the group and route middleware and before the Input is decoded ([ADR 0048](0048-groups-and-the-order-things-run-in.md)). A route runs at most 16 Providers. A Provider's error is the answer, exactly like a handler's ([ADR 0049](0049-errors-are-found-with-errors-as-and-timeouts-wait.md)), and a panic in one is the engine's 500 ([ADR 0028](0028-panics-are-recovered-by-the-engine.md)). A route with Providers is served through the middleware chain even when it has no middleware, because the chain builds the `Request` view a Provider receives. `Request.AddLogAttrs` records what a Provider found, and `Request.AppendLogAttrs` copies those attributes into a slice the caller owns, which is how the access log, a middleware outside every Provider, reads them once `next` returns; the list is cleared when the request ends.

**An `Opt[T]` of an auth Provider's type is the optional credential.** Built 2026-11-02 ([ADR 0069](0069-the-api-document-states-what-a-routes-providers-and-middleware-ask-and-answer-and-a-route-can-be-left-out.md)). A provided field, or a Provider's dependency, of type `Opt[T]` that no Provider of `Opt[T]` covers on the route resolves to the optional form of the route's Provider of `T`, when that Provider was made by `BearerAuth`, `BasicAuth`, `APIKeyAuth`, `CustomAuth` or `AnyAuth`: the form is made with the Provider at its `Provide`, runs the Provider only when the request carries one of its credentials, and is absent otherwise. It is one more entry of the one list the route resolves, nearest scope first, so an `Override` of `T` by an auth Provider changes its optional form too, and a Provider of `Opt[T]` the application registers is used before it. **The credential first** (decided 2026-11-04). Until then independent Providers ran in the order of the Input's fields, which no page stated, so an Input that named its tenant before its user answered a request with neither a 400 for the tenant, and the client was told to fix a header when it was not signed in; an agent met it in the usability test ([`docs/research/agent-usability/`](../research/agent-usability/run-2/report.md), row 3). Authentication runs first because who is calling is the question every other answer depends on, as a middleware guard would ask it first. A Provider the application writes itself for authentication is not known to be one: it is written with `CustomAuth`, which is how a credential is stated for the API document too.

**What it fails at:** an `Override` of `T` by a fake the test wrote leaves `Opt[T]` with no Provider on the routes that ask for it, which is refused; the test gives the fake to `CustomAuth` with the scheme the real one reads (and sends that credential), or provides `Opt[T]` itself in the same scope. Refused, as rows of the table: an `Opt[T]` whose `T` has a Provider the framework did not make (where its credential is sent is not known), naming that Provider's line; and a route that needs both `T` and `Opt[T]`, which would run the Provider twice for a credential the route requires anyway.

**How the values are held.** Each Provider runs in a step of its own whose frame keeps its value and its dependency struct on the stack while the next step, and at the end the decoding and the handler, run below it; the steps pass the values by pointer through a fixed array of 16 slots, and the Input's provided fields are filled by copying. Nothing is boxed in an interface or put in a pooled buffer, so a route with Providers costs the same 2 allocations as one without, at any depth ([ADR 0003](0003-the-trade-budget.md)). The pointers are to frames that are still running, and the runtime moves them when the stack grows; a test grows the stack and runs a collection between two Providers to hold that.

**A Provider reads a header or a cookie through a section of its dependencies.** Built 2026-11-04, after the second agent usability run wrote a tenant Provider that read `X-Tenant` with `req.Header` and so had no 400 that named it and no parameter in the API document. A field of `D` named `Header` or `Cookie` whose type is a struct is a section, not a provided type: it is compiled at Registration as the Input's section of that name is, decoded into the request's slab before the Provider runs, and checked with the same rules, so a missing or malformed value is the 400 that names `header.X-Tenant` and the Provider does not run. The API document states it as a parameter of each route that runs the Provider ([ADR 0069](0069-the-api-document-states-what-a-routes-providers-and-middleware-ask-and-answer-and-a-route-can-be-left-out.md)). `Path` and `Body` are refused there: a Provider covers routes whose paths and bodies differ, so what it would read is the Input's to declare. A `Query` section is allowed on a WebSocket route and on a route that answers `SSE` or `Events`, and refused on any other route at its Registration (revised 2026-11-04, after the fourth agent usability run found that a browser's `WebSocket` and `EventSource` cannot send a header, while the websockets guide pointed it at a query token no Provider could read): it is decoded as the Input's query, and a strict Input query lets its keys through. Measured: a route whose Provider reads a `Header` section is 2 allocations, as the plain typed request is ([ADR 0003](0003-the-trade-budget.md)). What was rejected: leaving `req.Header` as the only way, which is the silent trap the run fell into; every section in a Provider, which would let one Provider read a body that the handler's Input reads too; and a `Query` section on every route, where a header is the place for a credential and a query is kept by proxies and histories. What it fails at: a header both the Input and a Provider declare is decoded twice, once into each, and the two may state different rules, of which the document keeps the one that requires it.

**Refusals in the table (rows of `refusal_test.go`):** a provided field no Provider covers on the route, naming the type; a Provider's dependency no Provider covers, naming the chain from the field; a cycle, naming it; a Provider that needs its own type; dependencies that are not a struct; a `Path`, `Query` or `Body` section in a Provider's dependencies, and a `Header` or `Cookie` there that is not a struct; an unexported dependency; a nil Provider, as a method and as an option; a second Provider of a type in the same scope, from the app and from a group's options; a Provider of a type an enclosing scope provides, on a group and on a route; an Override with nothing to replace, on a group and as a route option; an Override of the same scope's own Provider; and a route that needs more than 16 Providers. The late `Provide` and `Override` rows are in [ADR 0048](0048-groups-and-the-order-things-run-in.md).

**What was rejected:** two spellings of a Provider, one without dependencies (`func(ctx, req) (T, error)`) and one with, because each needs its own name (`Provide` and `ProvideWith`, `Override` and `OverrideWith`, on the app, the group and as options) and the second name is the one a reader has to learn when a Provider gains a dependency; the price is `struct{}` in a Provider that needs nothing. Holding the values in a per-route frame type built with `reflect.StructOf`, which costs one allocation a request for `reflect.New`, and boxing each value in `any`, which costs one for every value that is not a pointer: both break the guarded axis for no gain. An `Override` in the same scope as the `Provide` it replaces, which the first build let through as a silent replacement: an Override replaces an outer Provider, and two Providers of a type in one scope are one too many whichever word the second uses.

**Also rejected:** silent nearest-scope-wins, the position this ADR's roadmap item held. Under a parent that provides `User` by session, a package that provides `User` by API key on a nested group, meaning to add a second way in, would change the authentication of everything under that group, a parent's `Account(deps User)` included, with no message: the class of mistake [ADR 0007](0007-mistakes-are-refused-at-registration.md) exists to refuse. Banning overrides altogether was rejected because it loses the subtree and test cases for the price of one word.

**What it fails at:** one more name in the API, and an override changes the dependencies of Providers declared above it in the same subtree. Its determinism depends on the sealing rule of [ADR 0048](0048-groups-and-the-order-things-run-in.md): a parent's Providers all come before any child exists. A Provider that needs nothing still writes `struct{}`. Sixteen Providers a route is a constant chosen without a workload that needs more. The stack device depends on the runtime moving pointers between frames of one goroutine, which it does and which the test holds, but which a future runtime could change; the same device already fills the Input (`unsafe.go`). Throughput and p99 of a route with Providers are not measured yet (the row in [ADR 0003](0003-the-trade-budget.md)).
