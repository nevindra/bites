# Routes are grouped by prefix, and app middleware runs before routing

`g := app.Group("/admin")` returns a group with a path prefix, its own middleware, Providers, limits ([ADR 0024](0024-limits-are-on-by-default.md)) and an OpenAPI tag; groups nest. `Group(prefix, opts ...RouteOption)` takes the same options a route does, built so far `MaxBody`, `BodyTimeout` and `AcceptUnknownMembers`. A group's options apply to every route in it and in the groups nested in it, applied in order from the outermost group inward and then the route's own, so the innermost wins: a route's own option beats its group's, and a nested group's beats its parent's. An option whose value cannot work (`MaxBody(0)`, a nil option) is refused when the group is made, naming the group and where it was registered, even if the group has no route yet. Versioned APIs with different naming are separate apps ([ADR 0011](0011-one-naming-policy-for-wire-names.md)); a `/v1` and `/v2` with one convention are two groups.

**The order a request goes through, fixed:**

1. App middleware, before the route is matched. It sees every request, including those that will be 404 or 405 and a CORS preflight `OPTIONS` that has no route of its own, which is why CORS is app middleware.
2. Route matching: 404 and 405 are produced here, as problem+json ([ADR 0012](0012-client-errors-are-400-problem-json.md)).
3. Group and route middleware (`Use`), outermost group first, then the middleware built for the route by `UseEach` (below), app's function first.
4. Providers the Input needs ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)).
5. Input decoding, then `Validate` ([ADR 0021](0021-validation-is-a-method-and-a-few-constraint-types.md)).
6. The handler.

Middleware sees the request view and the response value ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)); a value a Provider produced reaches the access log through log attributes, not through middleware reading it.

Routes, groups, middleware and Providers can be added only before the app starts serving; adding one afterwards panics.

**Order of calls inside a scope: a late `Use` or `Provide` is refused.** Each group remembers where its first route or child group was registered. A `Use` or `Provide` on that group afterwards panics at Registration, naming its own line, the line that sealed the scope, and "move it above". Without the refusal the call is silently skipped: group options are copied when a child group is made and again when a route is registered, so a later call never reaches a route or a child that already exists (chi refuses the same case: "all middlewares must be defined before routes on a mux"). `Use` and `Provide` are also available as group options (`g.Group("/orders", Use(audit))`), so a module that receives a group already holding routes can still add middleware to its own sub-group, and the mistake cannot be written in that spelling. App-level `Use` is exempt: it runs before routing and is read at request time, so a late call cannot skip a route; the order among `Use` calls is call order, outermost first. App-level `Provide` is not exempt, because a route's Providers are checked at the route's own line ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)) and a Provider registered later would give a false "no Provider for User" there. Evidence: [`docs/research/decisions-middleware/`](../research/decisions-middleware/report.md), section R2.

**A middleware built from the route's identity: `UseEach`.** `app.UseEach(build)`, `g.UseEach(build)` and the option `bites.UseEach(build)` give a function `func(RouteInfo) (Middleware, error)` that Registration calls once for each route it reaches, with the route's `RouteInfo`: `Method`, `Pattern` (with the groups' prefixes), `OperationID`, `Tags` (copied) and the flags `WebSocket` and `Static`. `RouteInfo` is a value with nothing of the framework's inside it. Three outcomes: a `Middleware` runs for this route, a nil `Middleware` means none for this route (the exempt list), and an error refuses the route, as a panic naming the route, the line of the `UseEach` and the line of the route, with the error's text: `GET /orphan: the function given to UseEach (at main.go:9) refused the route: operation "getOrphan" has no permission in the table` then `registered at main.go:12`. That panic is what turns default-deny from a convention into a start-up failure: a route registered without a permission cannot be served, where a per-route `Use(perm(...))` left it open without a word. The middleware closes over what `build` knew (the operation ID), so an audit row needs no lookup at request time, and `next.Call` already returns the `Response` and its status. It is what a permission table keyed on the operation needs: app middleware runs before the match and cannot know the route, and the route is known exactly once, at Registration.

**Where it runs: inside every `Use` of the route, next to the handler.** The built middleware is appended after the route's `Use` middleware in the chain, so a sign-in `Use` on the app, a group or the route has run, and answered 401 if it must, before the permission check reads the user it established; several `UseEach` functions apply outermost scope first (the app's, a group's, a nested group's, the route's own), as `Use` does. Outermost was rejected because the permission check would then run before the sign-in it depends on. The price is that an audit row written by the built middleware does not see an answer a `Use` outside it produced (a 401 from sign-in); for the call of every request keyed by status, an Observer is the tool ([ADR 0051](0051-a-request-is-observed-when-it-starts-and-when-it-has-really-ended.md)).

**Order of calls: a late `UseEach` is refused**, as a late `Use` and `Provide` are, for the same reason: the function is applied when a route is registered, so one registered afterwards would silently skip every earlier route, which is the opposite of default-deny. `app.UseEach` after the app's first route or group, and `g.UseEach` after the group's first route or child group, panic naming the line that sealed the scope and "move it above". Applying it at the start of serving to every route was rejected: the route's registration line, which the refusal must name, is not kept, the function would see routes in a different order than they were declared in, and the rule "a scope's options are fixed when its first route is registered" would have an exception. The option spelling cannot be late. A nil function is refused wherever it is given. `build` runs with the Registration lock held, so it must not register routes.

**Which routes are passed to `build`: every route of the application, and the two the app registers for itself that can be guarded.** Typed routes (a `stdhttp.Mount` route is one, with its method, `Undocumented`, and so an empty `OperationID`), `WebSocket` routes (`WebSocket` true, `Method` GET, no `OperationID`: the document has none) and `Static` routes (`Static` true, `Pattern` ending `/{path...}`), so a default-deny table cannot leave a WebSocket or a file route open without deciding it. And `OpenAPI` and `ServeMetrics`, with `RouteInfo.Builtin` set to `"openapi"` or `"metrics"`, `Method` GET, `Pattern` the path given and no `OperationID`. They were left out at first, on the argument that they have no Input, no group and no `Use`, and the first port of a real application found the hole: its guard, built with `UseEach` to refuse a route it did not know, had no sign-in on `/openapi.json`, which answered 200 to a client with no session, and nothing at start said so. A guard that cannot see a route cannot refuse it, and a guard that sees every route but one is the shape default-deny exists to remove. So they are passed, and `Builtin` is how a guard exempts them: a function that returns nil for `r.Builtin == "openapi"` serves the document openly; one that returns an error for what it does not know refuses it at start (`OpenAPI /openapi.json: the function given to UseEach (at main.go:9) refused the route: ...`), which is loud and correct; one that returns a middleware guards it like any route. Only the app's `UseEach` reaches them (a built-in route has no group), and a `UseEach` after `OpenAPI` or `ServeMetrics` is refused as one after a route is (`app: UseEach is called after OpenAPI /openapi.json (at main.go:5) was registered, so it would not reach it: move UseEach above it`), because it would skip them in silence. An app that never calls `UseEach` is unchanged: the two routes are served with no chain, as before, and cost what they cost. The `docsui` module mounts its page with `app.Get`, so it was always a typed route and always seen. `app.Routes()` returns the same `RouteInfo` of each route in the order it was registered (a copy, from the one value `UseEach` is given, so the two cannot disagree), for a startup check or a route table; it costs nothing a request pays. It takes no lock: the list is published with its length fixed each time a route is added, so a call from another goroutine and a call from a `UseEach` function (which runs under the Registration lock) both return the routes so far. What is still not passed is `WithHealth`'s two paths, which are answered before routing and take no middleware at all: a load balancer's probe carries no credential, and giving the guard a way to refuse it would make an unhealthy-looking service of a correct one. Their policy stays with the app (the paths are the app's to choose and say nothing beyond up or down), and a deployment that must hide them does it at the proxy. `OperationID` is the operationId the document gives the route ([ADR 0020](0020-descriptions-come-from-registration-and-later-from-doc-comments.md)), given with `OperationID` or made from method and path, unique among documented routes by the check that already exists; it is empty for a route the document leaves out, because there is no operation to name, and a `build` that needs a key for those uses `Method`, `Pattern` and `Builtin`.

**What was rejected:** leaving `OpenAPI` and `ServeMetrics` outside `UseEach` with a warning in the guide, which was the first position: a documented hole is still one, and the people it catches are those who built default-deny because they did not trust themselves to remember. Passing them with no mark in the identity was rejected too, since a guard would have to recognise the document by its pattern, which the app chooses. An opt-in (`UseEachBuiltin`) was rejected: it is a second call to forget, with the same hole as default. And `Request.Route()` and `Request.OperationID()`, so that app middleware could look the route up: app middleware runs before the match ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)), so they would be empty in exactly the middleware that wants them, and filled in a route middleware that could have closed over the value at Registration; a field that is empty or full depending on where the middleware sits is a trap, and the answer to "which route is this" for an app middleware that must run on a 404 is that there is none. Matching before the app middleware to fill them was rejected too: the preflight and the 404 are seen by app middleware by design. And leaving a late call silently skipped; and options only, with no `Use` or `Provide` methods, because every Go router user types `g.Use` and `RouteOption` already exists, so the option is the second spelling and not the only one.

**What was rejected (`Routes` under the lock):** the first `Routes` read the list under the Registration lock and said a `UseEach` function must not call it, so that call was a deadlock at start rather than a refusal. A refusal was weighed and could not be exact: Go gives no goroutine identity, so `Routes` could not tell the `UseEach` goroutine from another goroutine calling it at the same moment, and a false refusal at start would be worse than the deadlock. Publishing the list without the lock removes the mistake instead of refusing it.

**What `UseEach` fails at:** it does not reach what is not a route (a 404, a 405, a preflight) or the health paths, so default-deny of those is app middleware's; it cannot see a route registered by code that does not go through the app's registration (a plain `http.Handler` served beside the app); the built middleware sits inside the `Use` middleware, so it cannot audit what they refuse; and a function that returns a middleware for most routes leaves one that returns nil open on purpose, so the exempt list is code to review. It costs nothing a request pays: the function is called at Registration, and a route with a built middleware costs what the same route with `Use` costs (2 allocations, measured in `budget_test.go`), one whose function returned nil what a route with no middleware costs.

**What it fails at:** it refuses harmless code, such as a late `Provide` of a type no earlier route asks for, a uniform rule being easier to teach than a conditional one (claim); app-level `Provide` still depends on call order.

**Built in step 5 of milestone 2 (`Use`).** `app.Use(mw...)`, `g.Use(mw...)` and the option `bites.Use(mw...)` exist; the option is what `g.Group("/orders", Use(audit))` and `app.Get(..., Use(auth))` take, and options apply from the outermost group inward, so a group's middleware wraps the route's. A group is sealed by the first route or child group registered through it, and a `Use` after that panics with the message below. Only the group's `Use` method can be late; the option cannot. A middleware that is nil is refused wherever it is given, naming the route or group and its position in the call. `app.Use` after the app started serving panics like a route does. The request ID of [ADR 0012](0012-client-errors-are-400-problem-json.md) is set by a middleware on its `Request` and carried in every problem+json answer ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)).

**Refusals added with `UseEach` (rows of `refusal_test.go`):** a function that refuses a route of the app, of a group, given as a route option, a WebSocket route, the API document and the metrics page (the message above); `app.UseEach` after `OpenAPI` and after `ServeMetrics`; a nil function on the app, on a group and as a route option (`app: UseEach: the function is nil`); `app.UseEach` after a route and after a group (`app: UseEach is called after GET /x (at main.go:12) was registered, so it would not reach it: move UseEach above it`); `g.UseEach` after a route of the group.

**Refusals added in step 5 (rows of `refusal_test.go`):** group `Use` after a route ("group "/g": Use is called after GET /g/x (at main.go:12) was registered in this group, so it would not reach it: move Use above it", then the line of the `Use`), group `Use` after a child group (the same, naming the group), and a nil middleware in `app.Use`, `g.Use`, a group's `Use` option, a nested group's `Use` option and a route's `Use` option. `app.Use` after serving is a test in `middleware_test.go`, as a route after serving is in `routing_test.go`.

**Built in step 6 of milestone 2 (`Provide`).** `app.Provide`, `g.Provide`, `g.Override` and the options `Provide` and `Override` follow the same sealing: a group is sealed by its first route or child group, and the app by its first route or group, because a group copies the app's Providers when it is made. The options cannot be late. Rows of `refusal_test.go` added in step 6: group `Provide` after a route, group `Provide` after a child group, group `Override` after a route, app `Provide` after a route, and app `Provide` after a group. The app-level `Use` has none, and a late `Use` of the app has no row because it cannot skip a route.

**Bundling options: `Options(opts...)`.** `RouteOption` is a function of an unexported type, so an application cannot write a function that returns one option made of several (`Op(id, summary)`); an application that tried returned a `[]RouteOption` and spread it, after which nothing else could follow in the call. `bites.Options(opts ...RouteOption) RouteOption` applies its members in the order given, as if they stood in the call, and so works on a route, on a `Group`, nested in another `Options`, and beside `Use`, `Provide` and the rest (the scope marker of ADR 0023 is applied by the framework between scopes, not by an option, so a bundle never crosses one). It adds no rule: every refusal of a member is that member's own (`Summary` in a bundle given to a group is refused as `Summary` on a group is), and a nil member is refused naming its position (`Options: option 2 is nil`). A named `Operation(id, summary)` option was rejected as the only fix: it would serve one pairing, and the next bundle (a tag, a body limit and a middleware that always go together) would hit the same wall; with `Options` an application writes `Operation` itself in one line.
