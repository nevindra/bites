# A WebSocket upgrade checks its Origin, and everything a client sends on a socket is bounded

**Origin.** A browser attaches cookies to a WebSocket handshake from any site, and CORS does not apply to WebSockets, so a page on another site can open a socket that a cookie-reading Provider ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)) authenticates as the victim. Every WebSocket route therefore checks `Origin`, before the Providers and the Input are run, and a refused one is a 403 problem+json: otherwise a page on another site makes the server run a cookie-reading Provider (a database lookup) for a request it will refuse. By default the Origin's authority (host and port) must equal the request's `Host`, compared without case, dropping a port only when it is the default of the Origin's own scheme (`https://example.com:443` matches `example.com`), and **never inferring the scheme of the connection**: behind a TLS-terminating proxy the engine sees plain HTTP while the browser's Origin says https, so inferring it would refuse every proxied deployment. Behind a proxy that rewrites `Host`, the Origin's authority may instead equal the `X-Forwarded-Host` that proxy wrote, when the peer is a trusted proxy and the app says its proxies write the header (`TrustedProxies.ForwardedHost`, [ADR 0025](0025-no-proxy-is-trusted-by-default.md)): the value `Request.PublicHost` reads, the rightmost element of the last line, checked to be a host. `Host` is still compared too, so a deployment that sets nothing behaves as before. Other origins are listed with `AllowOrigins(...)` on a route or group, or with `WithAllowOrigins(...)` for the app, each a full origin `scheme://host[:port]`, compared exactly after lowercasing; the dangerous choice is a separate name, `AllowAnyOrigin()`, visible in review and greppable. A handshake with no `Origin` is accepted, because browsers always send one, so a missing header means a client that is not a browser and cannot be used this way; `Origin: null` (sandboxed iframes, `file://` pages) is a mismatch; a repeated `Origin` header is refused. Registration refuses, each naming the route and where it was registered: `AllowOrigins("*")` ("use AllowAnyOrigin() and say so"), `"null"`, an entry with no scheme, with a path or trailing slash, or with any `*` (wildcard subdomains are a later feature), and `AllowAnyOrigin()` combined with a list. Subprotocols are ignored, and the 101 names none. Fifteen cases of the comparison were run ([`docs/research/decisions-websocket/`](../research/decisions-websocket/report.md), probe `origin`): same host, different case, default port, `localhost:3000` against `localhost:8080`, `null`, a trailing slash, userinfo, `example.com.evil.com`, a `ws` scheme, a mismatched default port and IPv6 with a port all gave the answer above.

**Inbound limits**, each answered by closing the socket with the status RFC 6455 gives:

| what a client sends | limit | close status |
|---|---|---|
| a message, reassembled | 64 KiB per route | 1009 |
| a message not finished in `MessageTimeout` | 30 s | 1008 |
| messages being assembled, all sockets together | 64 MiB | 1013 |
| a binary frame to a route whose message type is not `[]byte` | refused | 1003 |
| fragments of one message | 128 | 1009 |
| a control frame | 125 bytes, never fragmented | 1002 |
| pings and pongs, one bucket | burst of 32, refilled at 32 a second | 1008 |
| a text message that is not UTF-8 | refused | 1007 |
| a frame that is not masked | refused | 1002 |
| a close handshake not finished | 5 s | connection dropped |

A handshake without `Sec-WebSocket-Version: 13` gets 426 with `Sec-WebSocket-Version: 13`. The handshake answers are 405 with `Allow: GET` for another method (HEAD included), 400 problem+json for a malformed handshake, 426 for another version, and 403 problem+json for a refused Origin, each with a `detail` that names the route as a WebSocket route. Outbound is bounded by [ADR 0037](0037-a-slow-reader-is-closed-not-buffered-forever.md).

**Assembling a message.** The `ws.Reader` aliases the bytes it is fed and holds no message buffer, and it emits one chunk per read: any message whose first event lacks its end needs assembly, fragmented or not (a 3,000 byte single frame fed in two reads of 1,500 gave three events; a 64 KiB frame arrives as 17 events through the 4 KiB scratch). A message that arrives whole in one read is copied once into a slab of its own and decoded from the copy, never from the read buffer: the codec returns views of what it decodes, and after decoding `{"text":"hello world"}` from the read buffer and reusing it, `Text` read `XXXXXXXXXXX` ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)). That copy is the one allocation of an `OnMessage` ([ADR 0003](0003-the-trade-budget.md)). A message that does not arrive whole is assembled into a fresh allocation that becomes its slab, grown in the size classes 4, 16 and 64 KiB as bytes arrive and charged to an app-wide budget by the capacity held, 64 MiB by default and configurable; the first class is free of charge, so ordinary chat messages never touch the budget. Over the budget the socket is closed with 1013. A route whose `MaxMessage` is above the budget is refused at Registration, since its message could never be assembled. The budget is 64 MiB because it equals the idle footprint of 20,000 sockets, the number [ADR 0003](0003-the-trade-budget.md) holds hard (a judgement, and 256 MiB is also defensible where there is headroom). `MessageTimeout`, 30 s, is armed with `SetReadDeadline` when a message first spills and cleared when it completes, not on the heartbeat wheel: a dribbling sender is bounded by the heartbeat only after two missed pongs, about 60 s, and by a setting the user may raise. Since the Reader holds its own header and mask (about 150 B), the engine returns the pooled scratch after every `Feed` that consumes all its input, even mid-message, so a socket that sent a header and stopped pins nothing pooled. The check for a binary frame is on the first data event, before any assembly, so a binary flood costs one close each. Evidence: [`docs/research/decisions-websocket/`](../research/decisions-websocket/report.md), section R6.

**The measured cost of not doing this.** 20,000 sockets that each send 64 KiB less one byte and stop hold 1,250 MiB with exact allocations, 1,982 MiB by `append` doubling from 4 KiB (8 allocations a socket, rejected), and 1,343 MiB with the size classes, against 72 MB for 20,000 idle sockets. With a 64 MiB budget the process holds at most the budget beside the idle baseline (136 MB). Charging the declared length at the frame header was rejected: it lets a 14 byte header reserve 64 KiB; charging held capacity forces the attacker to send at least 4 KiB, at most a 4:1 amplification.

**Closing with the status the client echoes.** A client that echoes the status the server closed with was refused: a Close frame with 1012 or 1013 failed with 1002 "close status not allowed on the wire" (measured, probe `ctl`; 1000, 1001, 1008, 1009 and 1011 were accepted). Since the budget closes with 1013, a well-behaved client would be logged as a protocol violation. The engine accepts the echo of the status it has itself sent once its own Close is out, while Autobahn's rejection of an unprompted 1012 to 1014 stays. The close codes a client may send are 1000 to 1003, 1007 to 1011 and 3000 to 4999 otherwise.

**Pongs.** Unsolicited pongs are legal keep-alives, so one is never an error, and they drain the same bucket as pings (a burst of 32, refilled at 32 a second; the 33rd at one instant closes with 1008, and 3,200 pings at exactly 32 a second for 100 s were all accepted). A pong costs 16 ns and no allocation in the Reader (1,000,000 at one instant, none refused). In the engine a pong only sets a flag that the heartbeat tick reads and never touches the wheel ([ADR 0039](0039-heartbeats-run-on-one-timer-wheel.md)), because re-arming would take the wheel's global lock and one flooding socket would contend with every other socket's heartbeat.

**What was rejected:** reassembly buffers only for fragmented messages (wrong: see above); a per-socket 64 KiB buffer held for life (1,250 MiB at 20,000 sockets, against [ADR 0005](0005-our-own-http1-engine-with-a-goroutine-per-connection.md)); assembling in a pooled buffer and copying into the slab (a second copy of every large message, and a pool attackers pin); decoding straight from the read buffer (breaks ADR 0008); the heartbeat as the message deadline; `Raw[T]` accepting binary, which has no use, since it decodes JSON; comparing the Origin by plain host and port with no default-port rule (refuses `https://example.com:443`) or by inferring the scheme; and refusing the echo of 1012 and 1013. _Comparing the Origin with `Host` alone behind a proxy_, the position until 2026-11-02: a proxy that rewrites `Host` (an ingress forwarding to `chat.internal:8080`) refused every browser, and the app had to list its own public origin with `AllowOrigins`, which it could not know when it is served under several hosts. What moved it: `X-Forwarded-Host` became readable from a trusted proxy the app says writes it ([ADR 0025](0025-no-proxy-is-trusted-by-default.md)), so the public host is known without a list, under the same trust `PublicURL` already relies on (`TestBehindAProxyThatRewritesHostTheOriginIsComparedWithTheForwardedHostItWrote`). _Comparing with `PublicHost` alone_, dropping `Host` when a forwarded host is present: the `Host` a browser connected to is the request's own authority whatever a proxy adds, and dropping it would refuse a deployment whose proxy writes an internal name there.

**What it fails at:** an app that needs one extra origin on one socket route and has an app list must widen the list or drop it; an attacker who reconnects keeps the budget full, so honest large messages get 1013 for as long as the attack lasts while small messages and all HTTP keep working (evicting the oldest assembly instead of refusing the newest would protect the honest one, not built); a budget too small for an app whose legitimate messages are large; the scheme is not compared, so an `http://` page on the same host passes (the proxy case wins over that gap); a proxy that rewrites `Host` and does not write `X-Forwarded-Host`, or an app that does not set `ForwardedHost`, still needs its public origin listed with `AllowOrigins`; `ForwardedHost` is the operator's word, so a proxy that in fact passes the client's `X-Forwarded-Host` through lets a non-browser client name the host it is compared with, which a non-browser client could already do with `Origin` itself; a client library that insists on a subprotocol (some MQTT over WebSocket clients) closes the socket itself; `MessageTimeout` is a plain read deadline, which a parked socket never sees because a mid-message socket is not idle (claim). The close status of `MessageTimeout`, 1008, has no existing row to follow (1002 and 1009 were the other candidates).

**Refusals to add to the table:** an `AllowOrigins` entry outside the app's list, a `WithAllowOrigins` entry that is not an http or https origin, `AllowOrigins("*")`, `AllowOrigins("null")`, an entry with no scheme, an entry with a path or trailing slash, an entry with a `*`, `AllowAnyOrigin()` with a list, and a route whose `MaxMessage` exceeds the reassembly budget.

**The app's list is shared with CSRF and bounds the nearer lists (revised 2026-11-04).** `WithAllowOrigins` is the app's list of the origins of its own pages, and a `CSRF` with no origins of its own reads it when a request arrives ([ADR 0057](0057-csrf-trusts-the-browsers-origin-and-falls-back-to-a-double-submit-token.md)), so an app with forms and sockets writes it once. A route's or group's `AllowOrigins` still replaces the app's for that scope, but when the app has a list it must be **within** it: an origin outside is refused at Registration (`WebSocket /x: AllowOrigins("https://other.example") is not in the app's list (WithAllowOrigins at app.go:12): add it there, or give the app no list and list origins per route`), because two lists that may disagree are what this removes. `AllowAnyOrigin()` stays allowed on a route of such an app: it lists nothing, and has its own name. Every entry is also checked as `CSRF` checks one (`WithAllowOrigins("ftp://files.example")` is refused: not http or https). The position this replaced, a nearer list replacing the app's with no relation to it, is what an app written before could rely on: it now panics naming both places when its route list names an origin the app's lacks. What was rejected: leaving the nearer list free (the drift of two lists), and a separate app option for CSRF (two spellings of one list).

**Built, and what the ADR left open.** The names are `AllowOrigins(origins...)`, `AllowAnyOrigin()` and `MaxMessage(n)` as route and group options, and `WithAllowOrigins(origins...)`, `WithAllowAnyOrigin()` for the whole app; a route's list replaces its group's, which replaces the app's, and a scope that gives both `AllowAnyOrigin` and a list is refused. `AllowOrigins()` with no origin is refused, so an empty list cannot mean "any" or "none" by accident. `Limits` gains `MaxMessage`, `MessageTimeout`, `ReassemblyBudget` ([ADR 0024](0024-limits-are-on-by-default.md)). The Origin check runs before the Providers, as above, and the 403 names the route as `WebSocket route <pattern>`. `MessageTimeout` is armed through the connection's read deadline when a message first spills out of one read, so on a connection whose clock is the app's it runs on the fake clock in tests. A client Close is answered with the same status and the socket ends; the echo of 1012 or 1013 after the server's own Close is accepted. The pong bucket is shared with pings as written.
