# Every input mistake is a 400 with its errors listed, and every error answer is problem+json

**Every error the framework answers, and every error a handler returns, is problem+json; a page for a browser is the one exception, and it is the handler's own answer.** A `Page` the handler returns may carry a 4xx, sent as HTML, because a browser shows the body of an answer and a problem+json is not a page; and a `Submitted[T]` Body hands the mistakes of its form to the handler, which shows the form again as a Page, instead of answering them as this 400. A mistake outside the form, and every other error, is still answered as this ADR says ([ADR 0078](0078-a-page-for-a-browser-is-a-page-and-a-form-it-shows-again-is-a-submitted-body.md)).

When a request does not fit the route's input, the answer is `400 Bad Request`, `Content-Type: application/problem+json`, listing its errors, each with its location in wire names (`path.id`, `query.page_size`, `body.items[2].qty`) and a message that names what was expected. Decoding does not stop at the first error ([ADR 0015](0015-json-is-our-own-codec-on-jsontext.md)); a syntax error in a JSON body is the one that ends it.

**Bounds.** At most 20 errors are listed, with `"truncated": true` when there were more, so a body of a million bad items cannot become a million-line answer. A message never echoes more than 64 bytes of the client's value, so an error answer cannot be used to reflect content.

**A rule code, so a client can translate a message.** An entry may also carry `"rule"`, a short code for the kind of mistake, and `"min"` and `"max"` for the three rules that have bounds, so a client shows its own sentence ("between 3 and 40 characters") without parsing the English `message`; server-side i18n stays a non-goal ([roadmap](../roadmap.md)). The codes are `type` (the value is not of the field's type: `expected an integer`, `expected a string`, `expected an object`, `expected a UUID`), `required`, `length` (`min`, `max`: a `Length` method), `range` (`min`, `max`: a `Range` method), `items` (`min`, `max`: an `Items` method on a list type), `pattern` (a `Pattern` method; no bounds, and the pattern is in the API document, not the entry), `nonempty` (`NonEmpty`), `positive` (`PositiveInt`, `PositiveInt64`), `values` (an enum's `Values`) and `check` (a `Check` method; the message is the error's text). An entry with no code has no `rule` member: the "out of range for the integer's size" sentence, `must not be null`, `unknown field`, `sent more than once`, the percent-encoding and nesting mistakes, an array of the wrong length, and every `Invalid` from a `Validate` method, whose author owns the words. Like the message, a rule and its bounds come from the type and never from the client's value. For example `{"location":"body.room","message":"must be between 3 and 40 characters","rule":"length","min":3,"max":40}`. **An entry carries only the bounds that exist** (decided 2026-11-03): a bound at the type's own limit is no bound ([ADR 0021](0021-validation-is-a-method-and-a-few-constraint-types.md)), so `Range() (0, math.MaxInt64)` answers `{"rule":"range","min":0}` with no `max`, and the sentence is one-sided (`expected an integer of at least 0`). A client must read `min` and `max` as each optional rather than as a pair; until then an entry for `offset` said `"max":2147483647`, a number the API never meant. The codes cost a request that passes nothing: they are written only when an error is.

**One shape for every error the framework writes.** 404, 405 (with `Allow`), 413, 415, 431, 500 and 503 are problem+json too, and carry the request ID when a middleware has set one (`Request.SetRequestID`, [ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)), as the last member, `"request_id"`: the answers of the framework, and the 500 the engine writes after a panic in a middleware. A client parses one shape. A refusal of the head, which the engine answers before any middleware has run (431), has no ID to carry.

A located error (`Invalid`) returned by a handler, a Provider or a middleware is listed in the same 400 as the decoder's, as one from `Validate` is ([ADR 0049](0049-errors-are-found-with-errors-as-and-timeouts-wait.md)). A plain `error` returned by a handler becomes `500` with no message in the body, and is logged with the request. An error that carries its own status is answered with that status and its message; how that error is found and what reaches the client is [ADR 0049](0049-errors-are-found-with-errors-as-and-timeouts-wait.md).

**Two exceptions to 400, both about the request's form rather than its content:** a body whose `Content-Type` the route does not accept is `415` ([ADR 0044](0044-the-body-type-decides-how-a-body-is-read.md)), and a request over a limit is `413` or `431` ([ADR 0024](0024-limits-are-on-by-default.md)).

**Why:** for the same mistake, Huma answers 400 or 422, Axum 400, 415 or 422, and Actix 404; Fiber answers 500 by default and puts the error's text in the body; Fuego and Poem put Go names (`FIn.age`, `param0`) where wire names belong; Echo names no field at all ([`docs/research/`](../research/README.md)). The shape of the body is taken from Huma, which got it right.

**Considered:** 422 for input that parses but fails validation, as Huma and Axum do. Rejected because a client then has two codes for one kind of mistake, and the distinction is the server's, not the client's.

**What was rejected while building it.** An entry of only `location` and `message`, which was the rule until 2026-11-02. A client that wants its own words (a translated form, a field hint with the bounds) had to parse the English, and the sentence is not a contract. The `rule` member, with `min` and `max`, was added beside the message and not in place of it, because a client that ignores the code still has a sentence to show. A code for each of the framework's own sentences, such as `must not be null` and `unknown field`, was left out: nothing a form shows depends on them. A way for `Invalid` to carry a code of the application's own was left out for now; an entry from `Validate` has no `rule`, as before. Measured axis: none, because the code is written only on the error path (`budget_test.go` and the hot path tests are unchanged and pass).

**What was rejected (2026-11-04).** Every error answer is problem+json with no exception, the rule until the fifth agent usability run: an application with HTML forms could show a form again with a 4xx only as a `Stream`, and the 400 of a bad `Form[T]` reached the browser as JSON ([ADR 0078](0078-a-page-for-a-browser-is-a-page-and-a-form-it-shows-again-is-a-submitted-body.md)).
