# Middleware takes a read-only request view and returns the response value

Middleware is `func(ctx context.Context, req Request, next Next) (Response, error)`. `Request` is a read-only view of the method, path, query, headers and remote address, never pooled ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)). `Response` is the value the inner handler produced, which middleware may inspect or decorate (CORS adds headers, a timing middleware reads the status). Middleware passes a value inward by wrapping `ctx`, and short-circuits by returning without calling `next`. `Next` is a small struct with one method, `next.Call(ctx) Response`, and not a function: it returns no error, because an error from the handler, a Provider or an inner middleware has already become a problem+json Response at that boundary.

**Why this shape:** middleware that held a writer could write twice, which [ADR 0009](0009-the-response-comes-only-from-the-return-value.md) removed from handlers. Gin's `c.Abort()` does not stop the function that calls it and `AbortWithStatus(401)` followed by a write sends 401 with that body ([`docs/research/gin-echo/`](../research/gin-echo/report.md)); returning a value has no such state to get wrong.

**What the Response is.** A small value returned by value: a status, a content type, the headers middleware added, kept in the chain's list and not inside the value (the first version held up to 6 pairs inline, a seventh spilling to the heap; see below), the body's size, and whether the answer is a stream ([ADR 0030](0030-streaming-is-a-return-type.md)), whose function is held by the engine and not by the value. The body itself is opaque: a middleware reads and sets the status and headers, reads `Size()`, or returns a fresh `Response`, but never reads or rewrites the body bytes, and no pooled buffer reaches it ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)). The count of six, which the first version held inline, was counted from the first-party middleware: CORS adds up to 4 headers, the request ID 1, a `Created` with `Cache-Control` 2 more, about 7 with `Content-Type` kept outside the pairs ([ADR 0032](0032-four-first-party-middleware.md), [ADR 0013](0013-other-statuses-are-wrapper-types.md)).

**The body is encoded in the innermost step, after all middleware has been entered, not deferred.** The terminal step turns the handler's output into the Response and appends the body to the engine's own pooled response buffer, which never reaches user code. An error becomes a Response at every `Next` boundary, including the 400s of decoding and of Providers, so an outer middleware (CORS above all, or a browser hides the answer) always sees the final status and can decorate it. A middleware that returns a fresh Response makes the engine truncate the buffer. Early encoding makes the size known, which the access log ([ADR 0032](0032-four-first-party-middleware.md)) and the later request hook need. Measured with three middleware layers over the Response: early encode with 4, 6 and 8 pairs 90, 96 and 107 ns and 0 allocations; a deferred body boxed in an `any` 117 ns and 1 allocation, which breaks the hard axis ([`docs/research/decisions-middleware/`](../research/decisions-middleware/report.md), section R1; a model of the chain's shape, so the real row of [ADR 0003](0003-the-trade-budget.md) for a route with middleware is still measured when step 5 is built). Built, the Response is 80 B and is copied at each layer: the headers middleware added to an answer from `next` are not inside it but in a list in the chain's pooled state, and the Response holds the range that is its own (the first version held six pairs inline and was 272 B, which cost 45 ns a request; the text above said 224 B, from a model without the generation and the text fields). A fresh Response, on the short-circuit path, holds its headers on the heap, so the count of six no longer shapes the type. Its methods take a pointer (`res.AddHeader(...)`, `res.SetStatus(...)`), `Status()`, `Size()` and `ContentType()` read it, and `NewResponse(status)`, `Problem(status, detail)` and `SetBody` make a fresh one to return instead of calling `next`. **What a middleware sees of the inner answer is its status, its size and its Content-Type;** `Size()` is always the size of the body as the handler produced it, uncompressed, because gzip runs in the engine's write step after the whole chain has returned ([ADR 0031](0031-gzip-only-and-off-by-default.md)), so the access log's `size` is the bytes before compression and the `Content-Length` on the wire is smaller; a middleware never sees a `Content-Encoding` the engine adds; for a stream ([ADR 0030](0030-streaming-is-a-return-type.md)) the size is 0 and `Streaming()` is true, because the body is written by the stream's function after the chain has returned, so a middleware sees and may decorate the head of a stream and never its body or its end; the headers the handler set (a wrapper's `Header`, `Location`, `Set-Cookie`) are already in the engine's buffer and are not visible or replaceable, only added to. A middleware that must change one returns a fresh Response, and the inner answer is dropped.

**How a kept `Request`, `Next` or `Response` is harmless ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)).** The strings of a `Request` are copies in the request's own slab, which is never reused, so a kept `Request` reads its own request's bytes for as long as it lives (tested: 300 requests on one connection, each kept, read back after a GC). What a `Request` and a `Next` also hold is a pointer to the request's chain state, which is pooled; that state is never readable through them. Each carries the state's generation, every method that would reach the state checks it first, and the state moves the generation on when the request is answered, so a kept `Next.Call` answers a 500 Response and logs instead of running the chain of whatever request owns the state now, `SetRequestID` does nothing, and `RemoteAddr` and `RequestID` answer zero. A `Response` returned from a different request than the one finishing is refused the same way, with a 500. Generations are numbers from a counter that no two pooled states share, because the pool may drop a state and make a new one.

**The Request is one copy of the head.** The head is parsed out of the connection's pooled scratch buffer, not out of the slab, so a `Request` that pointed into it would hand pooled memory to user code ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)); measured, an alias of the reused buffer read "Bearer AAAA" and then "Bearer BBBB". For a request that has middleware the head, request line and header block as received, is copied once into the request's slab by one `memmove`; `Path`, the raw query and `Header(name)` are substrings of that copy (the header lookup scans the lines and compares without regard to case, without allocating), `Cookie(name)` is the same scan over the `Cookie` fields with the pair parsing of the Cookie section (first of that name wins, quotes removed, malformed pairs skipped) and allocates nothing, `Method` is an interned constant for the nine standard methods, and the remote address is a `netip.AddrPort`, read from the connection when asked (a string would allocate). The body stays hidden from the view. **The Input reads out of the same copy**: `wire.Slab.Alias` records that the copy stands for the read buffer's head, and `Slab.Copy` of bytes inside the head, which is what a Header or Cookie section and every path or query value with nothing to decode does, returns a substring of the copy and copies nothing. The strings are as safe as a copy's: the bytes are in the slab and never written again. So the slab of a request with middleware is the head plus the body, and the target again only when it holds a `%` or a `+` (what is decoded is at most as long as the target); a request with no middleware has the slab it always had, because the engine now makes the slab on its first use and the framework adds the room once the route is known. Measured: 321 B a request with and without middleware, 2 allocations, and the worst case (a fully percent-encoded path and query, a 300 B Authorization, a header and a cookie) still 2. The copy and the view cost about 40 ns, the slab's `make` included.

**What was rejected:** `Next` as a `func(context.Context) Response`, the shape of the first version of this text: a function value made for each layer of each request is an allocation, because the middleware is an unknown function and whatever it is given escapes. Modelled with the same pooled state and three layers, the function shape allocated 2 (96 B, 25 ns) and the struct none (13 ns); with one layer the compiler saw through the model and allocated none, which a chain of functions held in a slice cannot count on ([`docs/research/middleware-core/`](../research/middleware-core/report.md)). Deferring the encode so the Output stays in a slot on the route's frame, which needs the unsafe `noescape` device through the whole chain for no gain on the hot path (same allocations, 88 ns against 90 ns), leaves a kept Response pointing at a dead frame and hides the body size; four inline pairs, too few for CORS plus a request ID plus a `Created`; a lazy copy of the head on each `Header` call, which can copy the same bytes twice (a 432 B head with a 380 B Authorization read by the Input and by a middleware gave one fallback allocation, so 3 where the row says 2, and one head copy in a 2x slab gave none). The earlier premise that the head is already in the slab was wrong: it is in the scratch buffer ([`docs/research/decisions-middleware/`](../research/decisions-middleware/report.md), section R10).

Rejected in the second pass of step 5, with the numbers of [`docs/research/middleware-core/`](../research/middleware-core/report.md): a head copy made lazily on the first `Request` call (the view is passed by value, so the state would sit in the pooled chain state and a kept `Request` would read nothing, losing the tested property that it keeps its own request's bytes; it saves about 40 ns for a middleware that never reads the request); a `*Response` owned by the chain (a kept pointer holds the next request's answer, so the generation check stays, and what it saves is the copy of 80 B); one flat slice of app, group and route middleware built at Registration (the app's runs before the match, so it cannot be composed ahead, and the walk is already one indexed loop at 25 ns a pass-through layer); skipping the Response for a middleware that does not use it (not known before it returns); a chain state kept on the connection instead of a pool (36 ns saved against about 1 KB for every idle connection, a hard axis); and a slab of twice the head for every request with middleware, the first version (450 B a request, and a p99 rise of 30% to 41%).

**What it fails at:** a middleware cannot cache, hash (ETag) or compress a body, so gzip and ETag are engine features ([ADR 0031](0031-gzip-only-and-off-by-default.md)); a discarded inner Response wastes its encode, a few hundred ns on a path that is not budgeted; a head near `MaxHead` (8 KiB) doubles its slab for that request (claim); every request of an app with app-level middleware pays the head copy, about 40 ns, and the p99 of a route behind one middleware is 3% to 4% higher than without and behind three 17% higher, most of the second from the stack the collector shrinks between requests, which a deeper chain grows back further (throughput for three middleware is -8% to -9%; see ADR 0003, which also has the 80 B room every request with middleware reserved until 2026-11-05); the headers a handler set are invisible to middleware (above); the lookup is a scan, quickest for one or two lookups, and an index built per request wins from four, so the choice waits for the count real middleware makes (not measured).

**Rejected: the route in the request view.** `Request.Route()` and `Request.OperationID()` do not exist. App middleware runs before the route is matched, so both would be empty in the middleware that asks, and filled only in route middleware, which can close over the route's identity when it is built at Registration with `UseEach` ([ADR 0048](0048-groups-and-the-order-things-run-in.md)). A getter that is empty or full by where the middleware was registered is a trap; the request view keeps only what is true for every middleware.
