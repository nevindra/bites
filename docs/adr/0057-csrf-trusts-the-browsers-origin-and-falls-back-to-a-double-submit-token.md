# CSRF trusts what the browser says about the origin, and falls back to a double-submit token

`CSRF(CSRFOptions{Origins, Cookie, Header, NotSecure})` is a first-party middleware for routes a browser authenticates with a cookie. Built 2026-11-01, milestone 3 wave 1 (`csrf.go`). It lets a state-changing request through only when the browser says it came from a listed origin, or, from a client that says nothing, when the request carries the token. A refused request is **403 problem+json** ([ADR 0012](0012-client-errors-are-400-problem-json.md)) and goes no further.

**The rule, in order:**

1. `GET`, `HEAD`, `OPTIONS` and `TRACE` pass; they must not change state. One that arrives without the token cookie gets it on its answer.
2. **A request with no `Cookie` header and no Basic credentials passes.** It carries no ambient credential, nothing a browser adds on its own, so there is nothing to forge with it, and a token-authenticated API (a Bearer token, an API key) behind the same middleware is untouched. Basic credentials count as ambient because a browser caches them and sends them with a cross-site form like a cookie (found in review; `TestACrossSiteRequestCarryingCachedBasicCredentialsIsRefusedEvenWithNoCookie`). The one exception, added 2026-11-04 after the third agent usability run found a sign-in form open to it: a form's body (`application/x-www-form-urlencoded`, `multipart/form-data` or `text/plain`) with no `Authorization` header, which the browser says came from an origin not listed, is refused even with no cookie, because a page elsewhere could post the attacker's own credentials to a sign-in form and leave the browser signed in to the attacker's account (login CSRF). It needs only what a form can send, so a JSON client and a token client are untouched, and a form with no browser signal (a script with `curl`) still passes; nothing is configured, since every sign-in form is the case (`TestACrossSiteFormWithNoCookieIsRefusedAsLoginCSRFAndAJSONOrSameSiteOneIsNot`). Considered and rejected: an option to refuse every unlisted `Origin` with no cookie, which a reader must know to set and which would refuse a token client sending JSON from another site.
3. **`Sec-Fetch-Site`**, which every current browser sends and no page can set: `same-origin` and `none` (the user typed it, or a bookmark) pass; `same-site` and `cross-site` pass only when `Origin` is listed, so `app.example.com` may call `api.example.com` when the API lists it.
4. Without `Sec-Fetch-Site`, **`Origin`**: listed passes, anything else is refused, `null` included (a sandboxed frame, a `file:` page, a redirect across origins).
5. With neither header, **the double-submit token**: the `X-CSRF-Token` header must equal the `__Host-csrf` cookie, compared with `crypto/subtle.ConstantTimeCompare`. A form cannot set a header, and a script on another origin can only after a CORS preflight that this app would have to allow ([ADR 0032](0032-four-first-party-middleware.md)).

**Origins are a list, compared with `Origin`, never with `Host`.** A proxy may rewrite the host, and `X-Forwarded-Host` is read only when the app says its proxies write it ([ADR 0025](0025-no-proxy-is-trusted-by-default.md), `Request.PublicHost`), so comparing `Origin` with `Host` would refuse every request behind such a proxy or, worse, be made to pass by a header the client controls. The list is checked as CORS checks its own (full origins, lower case, no pattern, no trailing slash) and must name the app's own origin: a page served from `https://app.example.com` posting to itself sends `Origin: https://app.example.com`, and a browser without `Sec-Fetch-Site` is judged by it. `"*"` is refused.

**One list for the app's pages (revised 2026-11-04).** An app with forms and sockets served from the same pages listed the same origins twice, in `CSRFOptions.Origins` and in `WithAllowOrigins` ([ADR 0046](0046-websocket-origins-and-inbound-limits.md)), and the one it forgot to update either refused its own pages or stayed open to an origin it had dropped. `WithAllowOrigins` is therefore the app's list of the origins of its own pages, and `CSRFOptions.Origins` **empty means that list**. Nothing new is spelled: the app's list already existed, and an empty `Origins`, which was a panic, is the place that takes it.
- _How it is read_: `CSRF` with empty `Origins` returns a different method value, `serveAppOrigins`, which reads the app's list through the `Request` when a request arrives; nothing is mutated at Registration and the middleware holds no state of the app. Registration recognises it by code, as it recognises CORS (`sameCode`), wherever it is given: `App.Use`, a group's or a route's `Use`, `UseEach`.
- _Refused at Registration_ (rows of `refusal_test.go`): empty `Origins` on an app with no list (`CSRF: Origins is empty and the app has no list to take them from: list the full origins of the pages that send forms and scripts to this app ("https://app.example.com"), its own included, in CSRFOptions.Origins, or once for the app, WebSocket routes too, with WithAllowOrigins`) and on an app with `WithAllowAnyOrigin()` (`CSRF: Origins is empty and the app's list is WithAllowAnyOrigin(), which would let every site send requests with the user's cookies: list the origins in CSRFOptions.Origins, or give the app WithAllowOrigins instead`). `WithAllowOrigins` also refuses an entry `CSRF` would, so an entry the sockets accept is never one `CSRF` cannot (`WithAllowOrigins("ftp://files.example") is not a full origin: it must start with http:// or https://`).
- _An app written before_: one that gives `WithAllowOrigins` and a `CSRF` with origins of its own behaves exactly as it did: a `CSRF` with origins of its own keeps them, whatever the app's list holds. Only a WebSocket route list outside the app's list is now refused (ADR 0046). An app that gives no `WithAllowOrigins` is unchanged, and so is one that gives `WithAllowAnyOrigin()` with a `CSRF` that lists its origins.
- _Scenarios_: a chat with a sign-in form on `https://app.example.com` and a socket on the same page lists the origin once, and adding `https://admin.example.com` to the list admits its forms and its sockets together (`TestACSRFWithNoOriginsTakesTheAppsListAndTheAppsWebSocketsUseTheSameOne`). A page of an embedded widget that may open a socket but must not post a form lists both origins on the app and gives `CSRF` the narrower `Origins` of its own (`TestACSRFThatListsOriginsOfItsOwnKeepsThemAndTheSocketsKeepTheAppsList`). A hostile page on `https://evil.example` is outside the one list and is refused by both.
- _What it fails at_: the list admits an origin to forms and sockets alike, so an origin that must open sockets but never post forms is given `CSRF` origins of its own (supported) or a socket route list within the app's; a `CSRF` with origins of its own is **not checked against the app's list**, because Registration cannot read a `Middleware`'s options without global state ([ADR 0026](0026-no-global-state-and-one-behaviour.md)), so an app can still list in `CSRF` an origin its sockets lack; one `CSRF` with no origins serves several apps, each with its own list.
- _Considered, CORS_: **`CORSOptions.Origins` does not default to the app's list.** CORS lets another origin **read** answers with the user's credentials; CSRF and sockets let an origin **send**. An origin may deserve the first trust and not the second, and the reverse (a partner page that reads a public API but must never post a form), so a default would turn one list's widening into another's. It stays explicit, and `CORS` with no origins is still refused (`TestCORSOriginsAreNeverTakenFromTheAppsListAndCORSWithNoneIsStillRefused`). Taking it by default was rejected for the same reason `AllowAnyOrigin` is its own name: a default that grants read access across origins is not one a reader can see in the code.
- _Considered, a new `WithOrigins`_: a second app-level option that both take, with `WithAllowOrigins` kept for sockets, was rejected: two spellings of one list for an app that has sockets, and a rule for which wins. The name `WithAllowOrigins` reads as sockets only; its doc comment and this ADR say it is the app's list.
- _Considered, `AllowAnyOrigin` on a route of an app with a list_: allowed. It is not a list, it has its own name that shows in review, and refusing it would force an app with one public socket to drop its list.
- _Considered, middleware that reads the app's list at the first request_: rejected; the refusal would arrive with the first request, not at Registration ([ADR 0007](0007-mistakes-are-refused-at-registration.md)).

**The token.** 32 random bytes from `crypto/rand`, base64url, in a cookie named `__Host-csrf` with `Secure`, `Path=/` and `SameSite=Strict`, and **without `HttpOnly`**, because the page's script reads it and sends it back in the header. The `__Host-` prefix stops a sibling subdomain from planting a token of its choosing; even a planted token cannot be sent in the header from another origin. The middleware gives the cookie on a safe request that has none, so the first page load arms it. The token is not bound to a session: binding would need the session's id in every check, and the header requirement is what stops the forgery, the cookie only being the value the header must match.

**Why the browser's word first.** `Sec-Fetch-Site` and `Origin` are forbidden header names: a page cannot set them, so a browser's request carries the truth about where it came from, with no state on the server and nothing for the page to do. Tokens are the fallback for the clients that send neither, which today means old browsers and non-browser clients that keep cookies (a script with a cookie jar), and those can read and echo a token.

**What it costs.** Allocations: **0** for a request that passes, measured 2 for the typed POST with `Sec-Fetch-Site: same-origin` and with the token and no `Origin` (`TestTheSecurityMiddlewareAndProvidersCostWhatTheirADRsSay`): the headers and the cookie are substrings of the request's copy of the head, and the comparison reads them where they lie. Giving the token cookie on a safe request allocates the token and the `Set-Cookie` line, once a browser. A refused request pays for its problem+json. Throughput and p99 are not measured yet; they wait for the serial run of wave 2.

**Refusals at construction** (rows of `refusal_test.go`): `"*"`; an origin that is not a full origin (as CORS refuses it); a cookie name or header name that is not a token; a `__Host-` or `__Secure-` cookie with `NotSecure`. **What cannot be caught before the first request:** a list that omits the app's own origin (every same-origin POST from a browser without `Sec-Fetch-Site` is then refused, visibly, in the first test); a route that changes state on `GET`, which no middleware can protect; and the order with CORS, which must come first so that a refused request still carries CORS headers and the page can read the 403.

**Scenarios it was put against.**

- _The reference workload's web side_: pages on `https://app.example.com` with a session cookie, the JSON API on the same origin. Every form and `fetch` sends `Sec-Fetch-Site: same-origin`; nothing to configure but the one origin.
- _A hostile page_ on `https://evil.example` that auto-submits a form to `/transfer`: `Sec-Fetch-Site: cross-site` with an unlisted `Origin`, refused; in a browser without `Sec-Fetch-Site`, `Origin: https://evil.example`, refused (`TestAStateChangingRequestFromAnotherSiteIsA403`).
- _A sibling subdomain_ `blog.example.com` taken over: `same-site`, unlisted, refused; it cannot plant a `__Host-` token either.
- _A mobile client with a Bearer token and no cookies_: rule 2, untouched.
- _A command-line client with a cookie jar and no `Origin`_: it must read the token cookie and echo it, as any double-submit scheme asks.
- _A WebSocket handshake_: a `GET`, so this middleware passes it; a WebSocket's origin is checked by its own rule ([ADR 0046](0046-websocket-origins-and-inbound-limits.md)), from the same list when the app gives one.

**What it fails at.** A state change on a safe method. A client TLS certificate is an ambient credential the middleware does not see, so a route authenticated by one (mTLS, built by the transport track) is outside its reach. With `NotSecure` the token cookie has no prefix, so a sibling subdomain can plant one; it still cannot send the matching header from another origin, so the check holds only as long as no listed origin is compromised. A browser that sends neither `Sec-Fetch-Site` nor `Origin` on a cross-site POST and also lets a page set a custom header without a preflight: none is known. An app served on several origins must list them all. The token fallback asks the page's script to echo the cookie, so a page with no script and a browser with no `Origin` cannot post; such a browser is older than 2020. A form handler that relies on the token cannot get it from the body: a middleware does not see the body ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)), so the token travels in a header only.

**What was rejected.** Synchronizer tokens kept in the session and checked in every form: state on the server, a token rendered into every page, and a framework that never sees the body cannot read a form field. Comparing `Origin` with `Host` (above). Checking `Referer` when `Origin` is missing: it is stripped by `Referrer-Policy: no-referrer`, the default of [ADR 0053](0053-security-headers-are-one-middleware-with-safe-defaults.md), and by privacy settings, so it would refuse good requests. `SameSite` cookies alone: they leave same-site attacks open (a taken-over subdomain is same-site), and a session cookie with `SameSite=None` for an embedded app has no protection from them. A token bound to the session by HMAC: stronger against a planted cookie, which the `__Host-` prefix already stops, at the price of coupling CSRF to `Session` ([ADR 0056](0056-a-session-is-sealed-in-a-cookie-and-changed-by-returning-its-cookie.md)) and a key to manage.
