# A File answers its own conditional and range requests, one range at a time, with an ETag made of its time and size

Every `File` ([ADR 0043](0043-cookies-and-bodies-other-than-json.md)), and so every file `Static` serves ([ADR 0065](0065-static-files-are-a-route-with-twins-cache-rules-and-a-fallback-that-never-hides-a-404.md)), carries validators and evaluates the request's preconditions and its `Range` itself, in `sendFile` (`file.go`), before anything is opened. Built 2026-11-01, milestone 3, track C.

**The validators.** A file with a modification time gets `Last-Modified` and a strong `ETag`: `"` + its modification time in nanoseconds since 1970, in hex + `-` + its size in hex + `"`, such as `"18e3f01f9870d1c7-493e0"`. A file with no modification time (an `embed.FS`, an `fstest.MapFS` without one) gets neither from `File`, because the only other honest tag is a hash of the bytes, which `File` would compute on every request; `Static` over an `embed.FS` hashes each file once at Registration and gives that tag instead. An `ETag` or a `Last-Modified` in the `File`'s `Header` replaces the made one, in the answer and in every comparison, so a handler whose file is a function of a database row can give the row's version; an `ETag` there that is not an entity-tag (unquoted, a quote inside) is a 500, logged, per response, like a bad content type. The tag is computed into a buffer on the stack and copied into the head (`Response.HeaderBytes`), so it costs no allocation; the `Last-Modified` string the earlier code made is gone the same way.

**The preconditions**, in the order of RFC 9110 section 13.2.2: `If-Match` (strong comparison; `*` matches the file, which exists), else `If-Unmodified-Since`; then `If-None-Match` (weak comparison), else `If-Modified-Since` for GET and HEAD only. A failed `If-Match` or `If-Unmodified-Since`, and a matching `If-None-Match` on a method other than GET or HEAD, is a 412 problem+json ([ADR 0012](0012-client-errors-are-400-problem-json.md)). A matching `If-None-Match`, or an `If-Modified-Since` at or after the file's time (whole seconds), on GET or HEAD is a 304 with the `ETag`, `Last-Modified`, the `Cache-Control`, `Content-Location`, `Expires` and `Vary` of `Header`, the cookies, and nothing else: no `Content-Type`, no `Content-Length`, no body and nothing opened (RFC 9110 section 15.4.5). A header that does not parse (a date in no HTTP-date form, a list with an unquoted tag) is treated as absent, as section 13.1 allows. An entity-tag list is read by its quotes, not by its commas, because an opaque tag may hold a comma. The IMF-fixdate every client sends is parsed by hand without allocating; the two obsolete date forms go through `time.Parse`.

**One range, never several.** A GET whose `Range` is one byte range (`bytes=a-b`, `bytes=a-`, `bytes=-n`, the unit in any case) is a 206 with `Content-Range: bytes a-b/size` and exactly those bytes, sent as a sized stream of `b-a+1` bytes from offset `a` ([ADR 0030](0030-streaming-is-a-return-type.md)): the file is `Seek`ed when it can be (an `os.File`, an `embed.FS` file) and read up to the offset otherwise. A range whose start is past the end, and a suffix of 0, is a 416 problem+json with `Content-Range: bytes */size`. A `Range` of several ranges, of another unit, or that does not parse, a `Range` on HEAD or on any method but GET, and one on an empty file are ignored and the whole file is sent with a 200, which RFC 9110 section 14.2 allows. `If-Range` is honoured: a tag compared strongly, or a date equal to the file's time, and when it no longer names the file the `Range` is ignored. Every 200 says `Accept-Ranges: bytes`; an `Accept-Ranges: none` in `Header` turns ranges off for that answer.

**Why one range.** `multipart/byteranges` needs a second way to frame a body (a boundary, a part head per range, a length computed over all of them) for a handful of clients: browsers, video players, PDF.js and download managers ask for one range at a time. And several ranges are the shape of the attack that took Apache down in 2011 (CVE-2011-3192): hundreds of overlapping ranges that the server answers one part each. Ignoring the list sends the client what a server without ranges would, which every client handles. Coalescing overlapping ranges into one is a later step if a client is found that needs it.

**gzip.** A 206 and a 416 are never compressed: the engine already skips a status of 206 and any head with `Content-Range` ([ADR 0031](0031-gzip-only-and-off-by-default.md)), and a file is a stream, which is never compressed. `TestA206IsNeverCompressedAndA416KeepsItsContentRangeWithGzipOn` holds it.

**What it costs** (the allocation axis of [ADR 0003](0003-the-trade-budget.md); idle memory: none, no connection field was added; throughput and p99: not measured yet, waits for the serial run of wave 2). Measured on the AMD Ryzen 7 9700X on 2026-11-01, over the in-memory connection, against the index of this worktree (milestone 3 wave 0) built in the same session and interleaved three times: a whole `File` of 10 bytes from an `os.Root` **13 allocations a request** where the same test of the commit before measured 14 (16 earlier in the session, the drift of `os.Root` that ADR 0003 records), so the validators cost nothing and the `Last-Modified` string went; a **304 costs 5** (the stat, the context and the slab: no open, no stream); a **206 costs 13**, the same as the whole file (`TestAConditionalOrRangeFileAnswerCostsNoMoreThanTheWholeFile`, `TestAFileAnswerAllocatesWhatTheStatTheOpenAndTheStreamNeed`). A 412 and a 416 are client errors and not budgeted.

**Refusals.** None at Registration: everything here is a value of a response or a header of a request. A bad `ETag` in `Header` is a 500, logged, per response, for the reason a bad content type is ([ADR 0043](0043-cookies-and-bodies-other-than-json.md)).

**Scenarios it was put against.**

- _The reference workload_ ([ADR 0002](0002-the-reference-workload.md)) serving its front end's assets: a browser revalidates `index.html` with `If-None-Match` and gets a 304 of a few hundred bytes that opened nothing.
- _A video player seeking_: one `Range` per seek, a 206 each, the connection kept.
- _A hostile client with 500 overlapping ranges_: the list is ignored after one scan for a comma and the file is sent once; the test sends exactly that.
- _A resumed download whose file changed_: `If-Range` with the old tag no longer matches and the client gets the whole new file, never a splice of two versions.
- _A file rewritten within the same nanosecond with the same size_: it keeps its tag. On a file system with coarse times (FAT's 2 s, some network file systems' 1 s) that window is real.

**What it fails at.** The tag is a time and a size, not the bytes: a file rewritten in place with the same size within the time stamp's resolution keeps its tag (nginx and Apache make the same trade); a handler that needs better gives its own `ETag`. Two replicas whose copies of a file have different times give different tags, so a client that moves between them revalidates for nothing (a deploy that preserves times, or `Static` over an `embed.FS`, does not). A `File` from an `fs.FS` with no times has no validators at all unless `Static` hashed it. Several ranges are never answered as such. A 304 is decided from the stat, so a file whose time is in the future (a clock skew at deploy) answers `If-Modified-Since` with 200 until its time passes.

**What was rejected.** `multipart/byteranges` (above). A weak `ETag` from time and size: honest about what it is, but `If-Range` and `If-Match` need a strong one, and a weak tag would make every resumed download start over. Hashing the bytes for every `File`: a read of the whole file per request, or a cache keyed by an `fs.FS` that may not be comparable (`fstest.MapFS` is a map). Answering a `Range` on HEAD with 206 headers: RFC 9110 defines ranges for GET only.
