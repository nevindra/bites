# A Topic reaches the other instances through a Broker, and Postgres LISTEN/NOTIFY is the first one, a module

A [`Topic`](0047-a-socket-is-a-handle-and-a-topic-is-a-broadcast.md) reached the sockets of one process. An application split over several instances needs a message published on one to reach the sockets of all, and every such application meets the same bugs when it joins them by hand: a `NOTIFY` payload over 8000 bytes that fails or is cut, a `LISTEN` connection that drops and is never reopened, notifications missed while it was down with nothing to say so, and a message delivered twice or in two orders. Until now `examples/chat` carried that code in `listener.go`. Decided on 2026-11-04 and built.

**Decision.**

- **The core has a seam, `bites.Broker`, and one constructor, `bites.NewTopic`.** A Topic made with `NewTopic(name, broker, opts)` publishes through the broker and delivers to its own sockets only what the broker hands back. The zero `Topic[Out]` is unchanged: one process, no broker, the cost the budget test holds. There is one way to make a Topic that crosses instances.

  ```go
  type Broker interface {
      Accepts(name string) error
      Publish(ctx context.Context, name string, payload []byte) error
      Subscribe(name string, deliver func(payload []byte), gap func()) (stop func())
  }

  func NewTopic[Out any](name string, broker Broker, o TopicOptions) *Topic[Out]
  type TopicOptions struct { OnGap func(); MaxPayload int; Log *slog.Logger }
  func (t *Topic[Out]) PublishLocal(v Out) error
  ```

- **A message reaches the publishing instance's own sockets only through the broker.** `Publish` on a brokered Topic encodes and hands the bytes to `Broker.Publish`; it does not touch the local sockets. The broker's contract is to deliver to every subscriber of the name, this instance's included, and then `Topic` decodes, frames once and queues on its sockets ([ADR 0038](0038-a-broadcast-is-framed-once-and-shared.md)). So a message is never delivered twice to the publisher's sockets (there is no local path to double), and every instance hears the same messages in the same order, the publisher's among them. Delivering locally first and filtering the echo by an origin id was rejected: it needs an id in every payload, and two instances publishing at once would each hear their own message before the other's, two orders for one topic. The price is that a `Publish` that fails delivers nothing, not even locally, and returns the error: the application decides what a message that could not be announced means (the chat example logs it; the message is in its history).
- **The wire encoding is the framework's codec, with options of its own, and a type that cannot take it is refused at `NewTopic`** (revised 2026-11-04). The payload is written and read by the same codec that writes a Socket's frames ([ADR 0011](0011-one-naming-policy-for-wire-names.md)), compiled with options that are the same on every instance whatever each app's naming (snake_case names, unknown members read past, a type with its own JSON methods delegated to with no registration, since no document describes the payload), so an `Out` that reaches a socket of this instance crosses the broker as it is: an `Opt` stays absent or present, a `Null` stays null. A `[]byte` is a base64 string, so the payload is always text, which Postgres needs. A type the codec refuses (a channel or function field) panics at `NewTopic` with the cause. The broker's payload is the delivery's to keep (a rule of `Broker`), so it is decoded in place and the allocations of a brokered `Publish` stay 7. What cannot be caught: a type that encodes one way here and another there (`MarshalJSON` that depends on state), or two instances running different versions of `Out` beyond an added field; a payload that does not decode is dropped and logged at Warn with the topic and the size, never delivered half. **The first build used `encoding/json`**, chosen because the core's codec was thought too tied to one app to be shared between instances; an application then found that an `Opt` field of a Topic's type was written as `{}` by `encoding/json` and read back empty, every value dropped without a word, so its server frames used pointers and its client frames `Opt`, two optional types for one protocol. The codec with fixed options is as stable between instances as `encoding/json`, and it is the one the Socket already trusts.
- **A Topic listens while it has a socket.** The first `Subscribe` of a socket calls `Broker.Subscribe` and the last `Unsubscribe` (or the last socket closing) calls the `stop` it returned, counted under one lock so a join and a leave that race end in the right state. A Topic nobody is in costs the broker nothing and needs no `Close`, which suits a Topic a room, made when its first socket joins and dropped when empty (a family of them is a [`Topics`](0084-a-name-made-from-data-is-a-key-of-a-topics-family.md), which does that and publishes to a key no Socket of this instance is in). `Subscribe` and `stop` must not block on the network.
- **The server's own code hears a Topic with `Topic.Listen(fn func(Out)) (stop func())`** (decided 2026-11-04, from an application that keeps caches of sessions and suspended tenants that must drop an entry on every instance at once). Before it, the delivery reached only Sockets and `Broker` was not for an application to call, so such an application opened a second `LISTEN` connection of its own, with its own reconnect and its own gap handling, or did not cache. `fn` is a subscriber like a Socket: a Topic made with `NewTopic` listens to its broker while it has a Socket **or** a function (so a Topic of functions only needs no Socket), `fn` is called with every message the broker delivers from any instance, this one's included, in the broker's order, and a gap is the same `TopicOptions.OnGap`, where a cache clears itself. On a zero Topic `fn` hears what `Publish` sends in the process. `fn` runs on the delivering goroutine and must not block; a panic in it is recovered and logged at Error with the topic's name; `stop` is idempotent and safe from `fn`; `Len` still counts Sockets only, since it is what a room shows. The cost to a Topic that has no function is one map read under the lock it already takes, and the allocation guard of `Publish` is unchanged.

  ```go
  evictions := bites.NewTopic[Evict]("cache.sessions", broker, bites.TopicOptions{OnGap: cache.Clear})
  stop := evictions.Listen(func(e Evict) { cache.Delete(e.Key) })
  // on revocation, on any instance: evictions.Publish(Evict{Key: id})
  ```

- **A Topic carries a reference with `Topic.Resolve(fn func(Out) (Out, bool))`** (a family's is `Topics.Resolve(fn func(key string, v Out) (Out, bool))`, [ADR 0084](0084-a-name-made-from-data-is-a-key-of-a-topics-family.md)) (decided 2026-11-04, from an application whose messages could pass the 7999 bytes of a notification). Each instance runs `fn` on every message the broker delivers, before its Sockets and its functions get it, and they get what it returns; `false` drops the message there. So a large message is published as its id and read from the database once per instance, on the same path, in the broker's order, where before the application needed a second `Broker.Subscribe` of its own and a `PublishLocal` back into the Topic. A method on the Topic and not a field of `TopicOptions`, because `TopicOptions` is not generic and a field would be `any`, checked only when the program runs; the method is typed by the Topic's `Out`. Set once (a second call panics), refused on a zero Topic (nothing crosses a broker there), not run by `PublishLocal` (a local message is already whole). When `Out` is a tagged union ([ADR 0083](0083-a-json-value-of-several-kinds-is-a-tagged-union-of-opt-variants.md)), the reference is a variant the union's `ServerOnly` method names (revised 2026-11-05): the payload codec carries it as any variant, the API document and the clients never see it, `Listen` functions get whatever the Topic delivers, and a message that still holds a server-only variant after `Resolve`, or on a Topic with none, is not sent to its Sockets and is logged at Warn with the Topic's name and the variant; rejected, a second type parameter for the payload (`Topics[Out, Wire]`), which doubles every Topic signature. It runs on the delivery goroutine, so a slow `fn` holds back the messages after it; a panic in it is recovered and logged, and drops that message only. Rejected: `OnReceive func(payload []byte) (Out, bool)`, which hands the application the bytes and the decoding the Topic already does; and resolving on the publishing side (the receiving instances are the ones with sockets to serve).

- **Limits are on by default, on both sides, and an over-limit `Publish` is a typed error** (revised 2026-11-05, from an application that could not tell "publish a reference instead" from "the broker is down" and computed `7999 - len(prefix) - len(key) - 1` itself). `TopicOptions.MaxPayload` (1 MiB by default) bounds the encoded message: `Publish` over it returns a `*PayloadError{Name, Size, Limit}` and sends nothing, and a payload over it that arrives is dropped and logged. A broker with a lower limit returns the same type from `Broker.Publish` (the interface says so), with `Limit` the most bytes the payload of that name may have, what the broker counts besides it already taken off: `pgnotify`'s 7999 bytes count the name and a newline, so its `Limit` is `7999 - len(name) - 1`. A Topic returns the broker's `*PayloadError` as it is, so `errors.As` finds it from `Topic.Publish`, `Topics.Publish` and the broker alike; any other failure of the broker stays a wrapped plain error. The error's text says the name, the size, the limit and what to do (send less, or publish a reference and give the Topic a `Resolve`). `bitetest.TestBroker` requires it of a broker (the `Name`, the size and a `Limit` of exactly `MaxPayload`) and `bitetest.Broker.Limit` makes the in-memory one return it.
- **`MaxPayload` stays 1 MiB when a broker is given, and the Broker has no method that reports its limit.** A default of "whatever the broker accepts" needs the limit before the first message, which means a second way to learn it beside the error of `Publish` that already carries it exactly; `MaxPayload` also bounds what arrives from other instances (a hostile publisher with database access), which must not depend on a broker's word, and the limit of a broker such as Redis or a database may depend on the name or on the server's settings, which only the failing `Publish` knows. A program that wants to fail early sets `MaxPayload` to the figure it knows. A broker may have a lower limit and says so in the `*PayloadError`. Without the bound, one hostile or buggy publisher could make every instance allocate a large message per delivery.
- **Backpressure is the socket's, as before.** A delivery frames once and queues on each socket without blocking; a socket whose queue is full is closed ([ADR 0037](0037-a-slow-reader-is-closed-not-buffered-forever.md)) and does not hold the broker's delivery goroutine. `Publish` on a brokered Topic can block for the broker's round trip, bounded by the broker's own timeout (5 s in `pgnotify`), so a handler that publishes does so after it has committed and treats a failure as a log line, not as the request's failure. Ordering: the broker delivers a name's messages in the order it received them, one at a time, and `Topic` queues each on every socket before the next, so every socket sees one order. For Postgres that order is commit order, the same on every instance; two publishers racing are ordered by Postgres, and a single publisher that waits for each `Publish` is heard in its own order.
- **A gap is a callback on the Topic, and what the clients are told is the application's.** When the broker may have lost messages (for Postgres, the `LISTEN` connection dropped and came back), it calls the `gap` it was given, once the subscription is live again, and `TopicOptions.OnGap` runs. The framework cannot send a client anything itself: it does not know the shape of `Out`, and a frame of its own would break every client's decoder. `OnGap` is where the application tells its sockets, usually with `PublishLocal(Out{Kind: "resync"})`, which reaches the sockets of this instance only and is `Publish` on a Topic without a broker; the client then reads the history route, which is where anything committed in the gap is. With no `OnGap` the gap is logged at Warn naming the topic and the option, so it is never silent ([principle 2](0077-four-principles-in-the-order-they-win.md)). A panic in `OnGap` is recovered and logged.
- **`modules/pgnotify` is the Postgres broker**, with its own `go.mod` and `github.com/jackc/pgx/v5` ([ADR 0006](0006-no-third-party-dependency-in-the-core.md), [ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)). `pgnotify.New(Options)` returns a `*Broker`; `Run(ctx)` holds the one `LISTEN` connection; `Close()` stops it. One connection and one Postgres channel carry every Topic of the application: the notification is the topic name, a newline and the payload. One channel was chosen over a channel a topic because `LISTEN` on a connection that is blocked reading would have to be interrupted for each new room (the connection is not safe to interrupt mid-read), the identifier limit of 63 bytes would be a limit on topic names, and a subscription made while the connection is busy would have a window in which it hears nothing; with one `LISTEN` at connect there is none. The price is that every instance receives the notifications of topics it has no socket for and discards them by a map lookup, which is the load Postgres already sends a listener on one channel.
  - **The limit.** A notification (name, newline, payload) is at most 7999 bytes, because Postgres refuses 8000 and over. `Publish` over it returns `pgnotify: the notification for "room.1" is 8000 bytes (name, newline and payload), over the Postgres limit of 7999: ...` and sends nothing; it is checked before the pool is used, so it holds with the database down. A payload that is not valid UTF-8 or holds a NUL, which Postgres cannot carry, is refused the same way. The constant is held by a test that sends 7999 and 8000 bytes to a real Postgres.
  - **The connection.** A connection that cannot be made or drops is retried after a pause that starts at 100 ms, doubles to 10 s, has 20% jitter (instances that lost the database together do not return together) and resets once a connection was listening; each failure is logged at Warn with the error and `retry_in`, each success at Info. An idle connection is checked with `SELECT 1` every 30 s, so a connection dropped without a reset is found in at most one period and not never. `Options.OnState` reports each change, which is how an application fails its readiness (`app.SetReady`) while it cannot hear, as `examples/chat` does.
  - **The gap.** After a reconnect has re-issued `LISTEN`, the subscriptions that were live when the connection dropped, and those made while it was down, are told. A subscription made while the connection is up is not (there is nothing missed), and the first connection of the process tells the subscriptions made before it came up.
  - **Where it connects** (decided 2026-11-04): `Options.URL` or `Options.Config`, a `*pgx.ConnConfig`, one of the two and not both. An application's test helper copied a template database and set `ConnConfig.Database` on the pool's config, then built the broker from `pool.Config().ConnString()`, which still named the database it was first parsed from: the broker listened there and delivered nothing, with no error. A config is taken as set, the listening line names the database and the host, and a string rebuilt from a config is no longer the only way in.
  - **Publishing** uses a `pgxpool.Pool`, the one the application passes (the chat example shares its store's) or one the module opens from the same URL; `SELECT pg_notify($1, $2)` autocommits, and a `Publish` has a 5 s timeout.
- **Lifecycle.** Today the application runs `go broker.Run(ctx)` and `defer broker.Close()` before closing its pool, as `examples/chat` does. Once [ADR 0079](0079-services-start-after-the-app-binds-and-stop-in-reverse-around-shutdown.md) is built the broker is a Service, and nothing in the broker changes for it: `app.Service(bites.Service{Name: "pgnotify", Start: func(ctx context.Context) error { go broker.Run(ctx); return nil }, Stop: func(context.Context) error { return broker.Close() }})`. `Run` returns on the service's context ending, `Close` waits for it, and a Service registered after the database pool's stops before it, which is the order the example writes by hand. `Start` does not wait for the connection: the instance reports itself not ready through `OnState` until it listens, so a slow database is a probe that fails and not a start that hangs. A `BeforeShutdown` is not needed: the sockets are told to go by the drain ([ADR 0029](0029-shutdown-drains-and-then-closes.md)) and `Close` ends the delivery.
- **`bitetest.Broker` is the in-memory broker for tests.** `bitetest.NewBroker()` is one instance on a new bus, `Peer()` another instance on the same bus, `Async()` (each subscription delivers on a goroutine of its own, as `modules/pgnotify` does, instead of on the publisher's), `Fail(err)` makes publishes fail, `Gap()` signals a gap and `Subscriptions(name)` counts the Topics listening. Delivery is synchronous on the publisher's goroutine, so a test needs no sleep. It is in the test package because an application's tests need the same thing and writing a broker fake is the work this ADR is meant to save.

- **`NewSocketOwners` is the second user of the Broker** (decided 2026-11-05): a `SocketOwners` made with it publishes an order `{owner, status, reason}` under its name and each instance closes its own Sockets of the owner, listening while it holds a Socket as a Topic does ([ADR 0047](0047-a-socket-is-a-handle-and-a-topic-is-a-broadcast.md) has the rules). Its gap is handled where a Topic's is left to the application: because a missed sign-out cannot be told from none, the default closes every Socket it holds with 1012, spread as Shutdown's go-away is, and `SocketOwnersOptions.OnGap` replaces it. The refusals are an empty name, a nil broker and a name the broker does not carry, in the forms of `NewTopic`'s.

**Refusals** (rows of `refusal_test.go`, each ending `registered at <file:line>`; the module's rows are in its own tests):

- `NewTopic: the name is empty: give the name every instance uses for this topic, such as "room.7"`
- `NewTopic "room.1": the broker is nil: give the Broker this topic publishes through, or use a zero bites.Topic[Out] for a topic of this process only`
- `NewTopic "room.1": MaxPayload is -1, which is not a limit: give a positive number of bytes, or zero for 1 MiB`
- `NewTopic "room.1": the broker does not carry this name: <the broker's reason>` (for Postgres, a newline, a NUL, invalid UTF-8, or over 255 bytes).
- `NewTopic "room.1": the message type <T> cannot be sent through a broker: <the codec's reason>: use a type a Socket can send, without channel or function fields`
- `pgnotify.New: URL is empty ...`, a URL that does not parse, a `Channel` over 63 bytes, a negative duration, `MaxBackoff` below `MinBackoff`, each ending `registered at <file:line>`.

**What it costs** ([ADR 0003](0003-the-trade-budget.md)). The zero `Topic` gains one pointer field, nil, and `Publish` one nil comparison: the guard on allocations per `Publish` is unchanged (exactly 1 for up to 64 subscribers, `TestAPublishToManySubscribersBuildsTheFrameOnceAndCostsTheSameForOneAsForAHundred`), and nothing is added to a connection, a route or a request, so the two guarded axes (allocations per request, memory per idle connection) do not move. A brokered `Publish` plus its delivery to one local socket costs 7 allocations, measured with the in-memory broker (`TestABrokeredPublishCostsTheEncodingTheDeliveryAndTheFrameAndNothingPerSubscriber`): the message's encoding, its decoding, the frame and the broker's own copies; the same 7 for 1 and for 10 subscribers, so nothing is added per subscriber. It is a new row of the table, not a raised one. Throughput of the HTTP path has nothing to move. **Memory per Topic** (measured 2026-11-04, [`docs/research/topic-cost`](../research/topic-cost/README.md)): a zero Topic 120 B, a `NewTopic` with no socket 320 B, the first socket of a brokered Topic 312 B with its broker subscription, each further socket 37 B (re-measured at commit f7ac6c3 with the working tree of 2026-11-04, after two leaks were fixed: `bitetest.Broker`'s stop kept the subscription, and a Socket kept the last Topic it left); the payload's encoder and decoder are compiled once per `Out` type and shared, so a Topic per User or per room compiles nothing. A name made from data, such as a Topic per User or per room, is a key of a [`Topics`](0084-a-name-made-from-data-is-a-key-of-a-topics-family.md), which makes each Topic when its first Socket joins, drops it when the last leaves and publishes to a key this instance has no Socket for; a key with its Socket costs 783 B and nothing once it has left. The typed over-limit error (2026-11-05) and the key given to a family's `Resolve` move neither guarded axis: a Topic's publish path is not the request path, the error is built only for a message over a limit, and a keyed resolver is one closure made with a key's Topic.

**Scenarios it was put against.**

- _The `LISTEN` connection dies (a failover, `pg_terminate_backend`)._ `OnState(false)`, readiness fails, a Warn names the error and the pause, the connection is reopened, `LISTEN` re-issued, `OnState(true)`, then each Topic's `OnGap` runs and tells its sockets to read the history. `Publish` meanwhile still works if the pool does, and its messages reach the instances that are listening. A message committed during the gap was never delivered live to this instance, and the gap is the signal that says so. Tested against a real Postgres.
- _A payload of 7999 and one of 8000 bytes._ The first is sent and heard; the second is a `*PayloadError` naming the limit and the size, nothing sent. A message of 8001 bytes encoded is the same error with 8001. No truncation anywhere.
- _A slow consumer._ Its queue fills, it is closed with 1008 or 1013 and leaves the Topic; the delivery goroutine and every other socket are unaffected, because a delivery queues and returns.
- _Two instances publish at once._ Postgres commits one before the other and both instances hear that order, tested with 80 interleaved publishes from two brokers compared message by message.
- _A hostile or huge message._ A publisher with database access can write any notification to the channel: one that is not ours (no name) is dropped and logged; one over `MaxPayload` is dropped; one that does not decode is dropped. None reaches a socket half-made. A hostile client of the WebSocket cannot make an instance publish anything: only the application's code calls `Publish`.
- _A Topic dropped while a delivery is in flight._ The delivery decodes and queues on an empty set, which is a no-op; the stop is idempotent.
- _The application restarts all instances at once._ Each has `missed` set for subscriptions made before its first connection, so the first connection tells them; no socket exists yet in practice.
- _Shutdown._ `Close` ends `Run` and the pool it opened; sockets are closed by the app's drain, not by the broker.

**What it fails at.**

- **Postgres keeps no notification for a listener that is down.** The gap signal says it happened; it cannot return the messages. The application must have a place to read them from (a history route), and a design that has none cannot recover with this broker. A durable stream is a different broker (Kafka, NATS JetStream) and would sit behind the same interface with a `gap` that rarely fires.
- **The publish is not in the transaction that stored the message.** `examples/chat` used to issue `pg_notify` in the statement that inserted the row, so a notification existed exactly when the row did. With the broker the handler publishes after the commit, and a crash between the two loses the live notification (the history has the message). An outbox or `pg_notify` inside the application's own transaction is a real need and is not built; it is a different feature, since it ties publishing to the application's transaction, and nothing in the seam prevents `pgnotify` offering it later.
- **A subscription made while the connection is up hears nothing before its `LISTEN` took effect, and there is none to wait for:** the connection already listens on the shared channel, so the window is zero for a topic joined after start. A client that reads its history after joining may see a message in both, and must treat the message id as the key.
- **Every instance receives every topic's notifications.** At a rate the database or the network cannot carry for all instances, a channel per topic or per shard is the next step; it needs the dynamic `LISTEN` this design avoided.
- **A type with its own JSON methods is trusted to round-trip**: the refusal catches a type that cannot encode, not one whose `MarshalJSON` and `UnmarshalJSON` disagree. The test that proves such a type round-trips is the application's.
- **`Publish` blocks for the database's round trip** and a stuck database costs the timeout on every call; a publish on a request path should not be the only thing standing between the client and the answer.

**Considered and what was rejected.**

- **A `Topic.Broker` field or a method `topic.Attach(broker)` on the zero Topic:** two spellings of one thing, and a field that could be set after sockets joined; rejected for `NewTopic`, which fixes name and broker before the first socket and is where the refusals live.
- **Delivering locally and publishing remotely, filtering the echo by an instance id:** above; two orders.
- **A channel per topic:** above.
- **The broker also decoding (`Subscribe` yielding `Out`):** it would make `Broker` generic and push the type into every module; bytes keep the seam one interface for every `Out`.
- **Telling the sockets of a gap with a framework frame:** it cannot match the application's `Out`; `OnGap` plus `PublishLocal` lets the application send a frame its clients already decode.
- **Leaving sign-out to a recipe of a brokered `Topic` and `Listen`:** every application wrote it again and none handled the gap the way a sign-out needs (fail closed); `NewSocketOwners` is that recipe once, with the gap decided. `Topic.Listen` stays for what is not a Socket's order, such as a cache.
- **The application calling `Broker.Subscribe` itself for its own messages:** it works on bytes, with no `MaxPayload`, no decoding, no recovered panic and no log line, and the gap callback would be a second place beside `OnGap`; a Topic already does all of that for Sockets, and `Listen` gives it to a function.
- **`Broker.Limit(name string) int` to learn the limit before publishing** (suggested): a second way to learn what `Publish` already says exactly, and a number a Broker can only guess when its limit depends on the server; see the `MaxPayload` item above.
- **A `*PayloadError` that names the whole notification (name, newline, payload) as Postgres counts it:** the application would subtract the name itself, the computation this error exists to remove.
- **A separate type for server subscribers (a `Channel[T]` beside `Topic[T]`):** a second spelling of "a named stream of typed messages between instances", with its own constructor and options; the one difference is who receives, and `Listen` beside `Subscribe` says that.
- **Function subscribers that run on a goroutine each, or behind a queue:** the order between instances would be lost, and a queue needs a bound and a policy for a slow function; a function that must do slow work starts its own goroutine, and the guide says so.
- **Redis pub/sub and NATS as modules (`modules/redisbroker`, `modules/natsbroker`):** wanted, not built here. They fit the interface (Redis pub/sub loses messages while disconnected and signals a gap the same way; NATS core is the same; JetStream could replay and fire `gap` rarely). The seam is shaped so that neither needs a core change: `Accepts` (Redis channel names have no length limit, NATS subjects have a syntax), a payload limit of their own, and a connection loop with the same `OnState`. They go on the roadmap as modules when an application asks.
- **`LISTEN` through a Postgres connection pool:** `LISTEN` belongs to a session; a pooled connection would lose it on release. One dedicated connection is the only correct shape.
- **Reconnecting forever without a limit and without logging:** the shape of most hand-written listeners; the log line with `retry_in` is the minimum an operator needs.
