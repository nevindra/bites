# A WebSocket route is typed like an HTTP route, and so are its messages

`r.WebSocket("/rooms/{id}", rooms.Join)` registers a route whose handler is `Join(ctx, in JoinRoom, s *Socket[Out]) (Inbox[In], error)` ([ADR 0047](0047-a-socket-is-a-handle-and-a-topic-is-a-broadcast.md)). The Input is decoded and checked exactly as an HTTP route's is: its Sections, its Providers (so `Auth User` works), the refusals at Registration and the 400 policy, all before the upgrade, so a request that would be refused is never upgraded; its `Origin` is checked as well ([ADR 0046](0046-websocket-origins-and-inbound-limits.md)). The returned Inbox carries the message handlers, and its message type is a Go type: `OnMessage(ctx, msg T)` receives `T` decoded from JSON. A message that does not decode closes the socket with status 1007, unless the Inbox has a handler for malformed messages.

**Why:** the upgrade request is an HTTP request, and every way it can be wrong (a bad path parameter, no authenticated user) is one an HTTP route already refuses; giving it a second, weaker pipeline is how authentication gets skipped on the socket that needed it most.

**What was rejected (the name):** the value was first called Session[In], and `Handlers[In]` was considered as its replacement. Both lost to Inbox, because `Handlers` collides with [ADR 0014](0014-services-are-plain-go-values.md)'s `Handlers` struct of route methods (`type Handlers struct{ db }` is a common Go habit, and a route function returning `Handlers[Msg]` reads as handlers returning handlers) and with `http.Handler`, and `Session` is what every web developer expects for a login session, which milestone 3 builds. Evidence: [`docs/research/decisions-middleware/`](../research/decisions-middleware/report.md), section "Session rename".

**Binary frames follow the message type.** A route whose `Msg` is `[]byte` accepts both text and binary frames, and `Send` with an `Out` of `[]byte` writes a binary frame; every other `Out` is written as a text frame. Any other `Msg`, `Raw[T]` included, answers a binary frame with a close of 1003 (unsupported data): `Raw[T]` is `T` decoded from JSON with its bytes kept, so a binary frame to it is JSON in an unexpected frame type. The route records `acceptsBinary` once at Registration. Origin is checked before the Input and its Providers ([ADR 0046](0046-websocket-origins-and-inbound-limits.md)). Evidence: [`docs/research/decisions-websocket/`](../research/decisions-websocket/report.md), section R8. **What was rejected:** letting `Raw[T]` accept binary, as first proposed.

**Built: what a message type may be.** `Msg` is a struct, a slice or a map (decoded from JSON), `[]byte` (a text or binary frame's bytes, copied), or `Raw[T]` (decoded and with the exact bytes kept). A `Msg` that holds a `Form[T]` or an `Upload` is refused at Registration (those are kinds of request body), and so is a `Msg` that JSON cannot decode into (a channel or function field); the row names the route, the field and the type. `Out` is any type JSON can write, or `[]byte`; an `Out` that is one of the framework's response types (`OK[T]`, `Created[T]`, `Stream` and the rest) is refused, because a message has no status or headers. A message that does not decode is a `*MalformedError` whose field errors are located at `message.<field>` (not `body.<field>`), so a client reading its own socket's error is not told about a body it did not send. `OnMalformed(ctx, raw, err)`: returning nil drops that message and keeps the socket, returning an error closes it with 1011; without the function the socket closes with 1007. The 400 for the upgrade request itself is the HTTP route's, unchanged.
