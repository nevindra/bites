# The first middleware are the four the reference workload needs, and the rest follow on the roadmap

First-party middleware is CORS, a request ID, an access log through the app's slog logger, and a per-route timeout answered with 503. Recovery is not middleware ([ADR 0028](0028-panics-are-recovered-by-the-engine.md)). Milestone 2 ships these four. Rate limiting, CSRF, security headers, sessions, auth Providers, conditional requests and compression are milestone 3 ([`docs/roadmap.md`](../roadmap.md)): every production framework needs them, so they are scheduled rather than left waiting for someone to ask. Each is built whole, because a security middleware done halfway is worse than none.

**Built in milestone 3, wave 1 (security).** `SecurityHeaders` ([ADR 0053](0053-security-headers-are-one-middleware-with-safe-defaults.md)), the auth Providers `BearerAuth`, `BasicAuth` and `APIKeyAuth` ([ADR 0054](0054-auth-providers-parse-the-credential-and-the-application-verifies-it.md)), `NewRateLimiter` ([ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md)), `NewSessions` and `Session` ([ADR 0056](0056-a-session-is-sealed-in-a-cookie-and-changed-by-returning-its-cookie.md)) and `CSRF` ([ADR 0057](0057-csrf-trusts-the-browsers-origin-and-falls-back-to-a-double-submit-token.md)) follow the shape of the four: constructors in the root package that refuse a configuration that cannot work with a `RegistrationError` naming the constructor, the field and the line. The order they go in, outermost first: `RequestID`, `CORS`, `SecurityHeaders`, the address limit, `CSRF` on the app or the cookie-authenticated group, then the auth Providers, which run after every middleware ([ADR 0048](0048-groups-and-the-order-things-run-in.md)) and where a limit per user is called.

**What was rejected:** the first version of this ADR left everything beyond these four "until a named workload needs one". Users of a framework without rate limiting or CSRF protection do not wait; they assemble their own, often wrongly.

**Built in step 7 of milestone 2.** The four are in the root package (`CORS`, `RequestID`, `AccessLog`, `Timeout`), not a subpackage; three are plain `Middleware` values and `AccessLog` has been an `Observer` since milestone 3 (below): each reaches the app's logger and clock and the request's slab through the `Request` it is given, which only the root package can do without adding methods to the public `Request` ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)). Each is made by a constructor that takes an options struct (`CORS(CORSOptions)`, `RequestID(...RequestIDOptions)`, `AccessLog(...AccessLogOptions)`) or a duration (`Timeout(d)`), and the constructor refuses a configuration that cannot work with a `RegistrationError` naming the constructor, the field and the line it was called from ([ADR 0007](0007-mistakes-are-refused-at-registration.md)). Order is the application's: `app.Use(RequestID(), CORS(...))` puts the id on every answer, `WithObserver(AccessLog())` logs every request whatever the order of the middleware, and `Timeout` goes on a route or a group with `Use`.

**CORS** is app middleware, because a preflight is an `OPTIONS` that no route has ([ADR 0048](0048-groups-and-the-order-things-run-in.md)). Origins are full origins (`https://app.example.com`, with a port when it is not the default), matched exactly against the lower-case form browsers send, or wildcard subdomains, and an origin nothing lists may be decided at run time (the next paragraph). The single entry `"*"` allows any origin and is refused with credentials, with another origin, and as the method or header list when credentials are on, because a browser reads `*` literally then. `"null"` cannot be listed. A preflight is answered by the middleware with a 204: with the `Access-Control-Allow-*` headers when the origin is listed, the requested method is in `Methods` (GET, HEAD and POST by default) and every requested header is in `Headers` (none by default, so a JSON API names `Content-Type`), and with none of them otherwise, which is how the browser is made to refuse the real request. Every other answer to a listed origin gets `Access-Control-Allow-Origin` (the origin echoed, never a list), `Access-Control-Allow-Credentials` and `Access-Control-Expose-Headers` when configured, and it is added to what `next` returned, so a 404, a 405 and every problem+json carry it and the page can read the error. `Vary: Origin` is on every answer of a configuration that decides by origin (a list, a wildcard subdomain, `AllowOrigin`), also for a request with no `Origin` and for an unlisted one, so a cache cannot hand one origin's answer to another; a preflight varies on the two request headers as well. With `"*"` there is no `Vary`. An `OPTIONS` without `Access-Control-Request-Method` is not a preflight and goes on to the router. Allocations: none on a simple request, none without an `Origin`; a preflight builds a fresh `Response` and is not budgeted.

**RequestID** uses the header `X-Request-ID` (configurable), the name gateways, load balancers and most client libraries already send, and keeps what the client sent when it is 1 to 64 bytes of letters, digits and `-_.:`. That admits UUIDs, ULIDs, hex trace ids and the ids proxies add, and keeps out whatever could split a header or break a log line, since the id is client-controlled text that is echoed in a header, in every error body and in the log. An id that does not fit is replaced, not rejected: a formatting mistake is no reason to fail a request. Otherwise it generates 16 hex digits from `math/rand/v2` (64 random bits, unique enough to find one request in a log, not a secret), written into the request's slab, which `serveChain` makes 16 bytes larger for a request whose chain holds `RequestID`, so that the id costs no allocation of its own. Registration recognises it in the chain (it is a method value, as a `RateLimiter`'s middleware is for [ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md)), so a chain without it reserves nothing; `RequestID` called from inside another middleware is not seen, and its generated id then costs one allocation. Until 2026-11-05 every request with middleware reserved the room (80 B with the `RateLimit` header's), which made the collector run more often on routes that wrote nothing there ([ADR 0003](0003-the-trade-budget.md)). It calls `Request.SetRequestID` before `next` and adds the response header after, to whatever `next` returned.

**A handler reads the request id and gets a logger from its context** (added with milestone 4, item 9). `RequestIDFrom(ctx)` returns the id a middleware gave the request with `SetRequestID`, and `Logger(ctx)` returns the app's logger with `request_id`, `method` and `route`, of which `request_id` and `method` are the attribute names of the access log, so a handler's line and the access line are joined on `request_id`. The Request is read by a middleware or an Observer, which hold a `Request`, with `Request.RequestID`; a handler holds only its `ctx`, so the context functions exist beside it and are the one way for a handler (no guide recipe had a handler take the id through a Provider, and a Provider is the wrong tool for it: it runs per Input, not per log line). The name `RequestIDFrom` follows `TraceFrom`; `RequestID` is the middleware. Both reach the request through `reqctx.Of(ctx)` (the unexported key the request's context answers), so they work on a context the handler derived, allocate nothing on the lookup, and `SetRequestID` and the route match write the id, the app's logger, the method and the route pattern on the request's `reqctx.Ctx`, which is made per request and never pooled. They are strings of the request's slab (never reused, ADR 0008) or constants and the app's own logger, so a context kept after the request answers with its own request's values and no copy is made. The context does not point at the pooled `chainRun`. A non-standard method is copied once on the path without middleware. `Logger` allocates when called (12 allocations on a text handler with the three attributes, the `With` of slog), nothing for a request that does not call it. **What was rejected:** reading the id in a handler through a Provider that takes `Request` (one allocation-free call, but per Input, and a second spelling), and the function named `RequestID`, which the middleware already holds. `route` on the access record was built and dropped because the sixth attribute takes a slog.Record past its five inline attributes and costs AccessLog one allocation (2 to 3), a guarded axis, while `request_id` already joins the lines.

**AccessLog is an Observer** ([ADR 0051](0051-a-request-is-observed-when-it-starts-and-when-it-has-really-ended.md); decided and built on 2026-11-01 for milestone 3). `AccessLog(...)` returns an `Observer`, given with `WithObserver(AccessLog())`, and writes one record, message `request`, through the logger it was given or the app's, at the level it was given (Info), when the request has really ended: `method`, `path` (without the query, where secrets go), `status` (what was sent), `size` (the body bytes written, after gzip), `duration` (the Outcome's, from the parsed head to the last byte, on the app's clock), `request_id` when a middleware set one, `trace_id` and `span_id` when the request has a trace ([ADR 0059](0059-the-core-carries-w3c-trace-context-and-records-no-span.md)), `streaming=true` for a Stream or SSE ([ADR 0030](0030-streaming-is-a-return-type.md)), `abandoned=true` when the client left ([ADR 0049](0049-errors-are-found-with-errors-as-and-timeouts-wait.md)), `panicked=true` after a panic, then the attributes Providers and middleware added with `AddLogAttrs`, read with `AppendLogAttrs` ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)). So a stream's record has its real status, the bytes it sent and its whole life as the duration; a panic leaves a record with the 500 and `panicked=true`; a gzipped answer logs its compressed size; and a `Problem` a middleware returned (a 401 from an auth middleware, the 503 of `Timeout`) logs the size of the body sent. A level the logger does not log costs one `Enabled` call. The health and readiness probes of [ADR 0052](0052-health-and-readiness-follow-shutdown.md) are not observed and not logged. Tests (`accesslog_test.go`): `TestTheAccessLogOfAStreamIsWrittenWhenItEndsWithTheBytesItSent`, `TestTheAccessLogWritesARecordAfterAPanicWithPanickedAndThe500`, `TestTheAccessLogSizeIsTheCompressedSizeWhenGzipCompressedTheAnswer`, `TestTheAccessLogSizeOfAProblemAMiddlewareReturnedIsTheBodySent`, `TestTheAccessLogMarksARequestWhoseClientLeftAsAbandoned`, `TestTheAccessLogWritesTheTraceIdAndSpanIdOfARequestThatHasATrace`. Because the record is written after the client has its answer, a test reads it by waiting for it. Its record carries `error`, the text of `Outcome.Err`, when the application returned an error the framework answered (added 2026-11-03), so the access line of a failure says why without a second line; a 400 the framework wrote has none, and only a failed request pays for the text.

**AccessLog as it was in milestone 2, replaced:** a middleware given with `app.Use`, writing its record after the chain had returned. For a Stream the chain returns before the body is written, so the record said the status the stream would send, `size` 0 and `streaming=true`, and its duration was the time to produce the stream; a stream that later failed still logged 200. A panic left no record, since the chain does not return. `size` was the uncompressed body, and a `Problem` a middleware returned was logged as `size=0`, because that body is rendered only when it is written. Keeping it a middleware beside the Observer was rejected: those faults would stay, and the core would carry two ways to log a request.

**Timeout** is [ADR 0049](0049-errors-are-found-with-errors-as-and-timeouts-wait.md) built: `AfterFunc` on the app's clock, so a test moves `bitetest.Clock` and nothing sleeps. When it fires it cancels the request's own context with `context.DeadlineExceeded` as the cause (not a derived context, which would cost the allocations of `WithCancel` and arm the disconnect watcher on every request) and waits for the chain; the answer is a 503 problem+json with the request id, whatever the handler returned, and the handler's own answer, value, error or Stream, is dropped by returning a fresh `Response`, so a stream function that arrives late never runs. The handler is therefore never abandoned and never answered over; one that ran more than twice its deadline is logged at Warn with the method, path, deadline and how long it ran. Whether the timer or the chain won is one compare-and-swap on a small state, so there is no wait for a callback and no lock. A request that ends in time stops the timer and returns the timer, its callback and its state to a pool kept by the middleware, which is why it allocates nothing after the first; a timer whose callback might still be running is left to the collector, so a late callback cannot touch a later request. A Stream returned before the deadline is not under it: its function runs after every middleware has returned, so the deadline bounds the time to produce the stream and not its life, which the stream ends itself on its context.

**Origins decided per request (milestone 4, item 7).** `Origins` also takes a wildcard subdomain, `https://*.example.com` (`https://*.example.com:8443` with a port): `*.` is only ever the whole leftmost label and stands for one or more labels (`a.example.com`, `a.b.example.com`), never the apex, which is listed separately. The scheme and the port are matched as written. What follows `*.` must be a valid full origin by the check exact entries get and have at least two labels, so `*.com` and `*.localhost` are refused. A wildcard is matched label by label on the lower-case origin a browser sends: the origin has the entry's scheme, ends in its `.example.com[:port]`, and what remains in front is non-empty labels of lower-case letters, digits, `-` and `_`. That is why `https://evilexample.com` (no dot), `https://example.com.evil.com`, `https://a.example.com.`, `https://a..example.com`, an origin with a path, a fragment or userinfo, `null`, upper case, another port and another scheme do not match; each is a test. `CORSOptions.AllowOrigin func(origin string) bool` decides an origin that `Origins` does not match, for a tenant's own domain looked up at run time: it is called last, only for an origin that is lower-case `scheme://host[:port]` (never `null`, never a malformed one), true allows it exactly as a listed origin is (echoed, never `*`, with `Credentials` when set), it must be safe to call concurrently, and a panic in it is a request panic like any middleware's. `Credentials` is allowed with both, because the exact origin is echoed. Refused at construction: `"*"` together with a wildcard entry or `AllowOrigin`; a `*` that is not the whole leftmost label; a wildcard over fewer than two labels; `Origins` empty and `AllowOrigin` nil (the message names `AllowOrigin` as the other way). Axis: none. A simple request matched by a wildcard entry or allowed by an `AllowOrigin` that allocates nothing costs the same 2 allocations as a listed origin (rows of `TestATypedJSONPOSTBehindTheFirstPartyMiddlewareCostsWhatTheTableOfADR0032Says`); the match walks a slice of entries with no allocation, and `AllowOrigin`'s own allocations are the application's. A middleware with a wildcard list pays one scan of the entries for an unlisted origin, linear in their number, which is why a long list of tenants belongs in `AllowOrigin` behind a map. **What it fails at:** a wildcard also allows a subdomain that a tenant, an attacker with a dangling DNS record or a takeover controls, so a wildcard with `Credentials` trusts every host under that domain; the answer for it is to list the tenants, or decide in `AllowOrigin`, and a hand-written suffix check in `AllowOrigin` (`strings.HasSuffix(origin, "example.com")`) is the bug the wildcard entry exists to avoid, which the guide says in as many words. The two-label floor does not know public suffixes: `https://*.co.uk` is accepted and would allow every site under `.co.uk`, so the reference tells the application to name a domain it controls; a public suffix list was not taken in, since it is data that changes and the core takes no dependency.

**CORS on part of the app is `Paths`, and CORS on a group is refused (2026-11-04).** The third agent usability run gave CORS to an `/api` group, and every preflight was a 405 with nothing to say why: a group's middleware runs after routing, which answers an `OPTIONS` no route has. `CORSOptions.Paths` lists the path prefixes CORS covers (`/api` covers `/api` and `/api/...`, not `/apis`); a request outside them is passed on untouched, with no `Vary: Origin`, so the pages of a site and its API share one app. `CORS` given to a group or a route through `Use`, `Group.Use` or a `UseEach` function is refused at Registration, recognised by its code as the API document recognises `CSRF` and a `RateLimiter` ([ADR 0069](0069-the-api-document-states-what-a-routes-providers-and-middleware-ask-and-answer-and-a-route-can-be-left-out.md)), and the message points at `App.Use` and `Paths`. Allocations: none added; the check is a prefix comparison per entry. What was rejected: answering a group's preflight by routing every `OPTIONS` to the group's middleware, which would change what the router answers for every app to serve a case `Paths` covers; and leaving it to the guide, which the run read and still missed. What it fails at: a CORS wrapped in the application's own middleware is not recognised, and is not refused.

**Refusals added in step 7 (rows of `refusal_test.go`):** CORS with no origin; `"*"` with another origin; `"*"` with credentials; an origin without a scheme, with a path or trailing slash, with a wildcard, `"null"`, or with a port that is not a number; a method or header that is not a token; `"*"` as a method or header with credentials, or beside other headers; a negative or sub-second `MaxAge`; a `RequestID` header that is not a token; two options values given to `RequestID` or `AccessLog`; a `Timeout` of zero or less. **What cannot be caught before the first request:** a `Timeout` on a route that returns a Stream (a middleware is an opaque function; the behaviour above is the answer), an order that puts `CORS` before `RequestID` (a preflight then has no id), and a CORS origin list that does not match what the browser sends.

**Allocations** (ADR 0003 has the table; measured on the typed JSON POST of `budget_test.go`): `RequestID` generated or taken 0, `CORS` on a simple request 0, `Timeout` 0 on the fake and on the real clock, `AccessLog` 0 up to five attributes (method, path, status, size, duration) and 1 more when there are six or more, because a `slog.Record` holds five inline, so with `RequestID` in front it is 1 (3 allocations a request, a number this ADR names), and a text or a JSON handler cost the same; measured again with `AccessLog` as an Observer, unchanged (the rows of `TestATypedJSONPOSTBehindTheFirstPartyMiddlewareCostsWhatTheTableOfADR0032Says`), and 3 with a trace's two ids (`TestAnAccessLogWithATraceCostsWhatTheTableOfADR0059Says`). Throughput and p99 are not measured yet and wait for the serial run.

**Throughput and p99** (measured 2026-11-01, [`docs/research/m2-request-path/`](../research/m2-request-path/report.md), each alone against the same route with no middleware): `CORS` GET -6.2% and POST -6.5% req/s, `RequestID` -8.6% and -5.9%, `Timeout` -9.0% and -7.9%, `AccessLog` -20.5% and -17.7% with 1.3 us of CPU a request (measured when it was a middleware; as an Observer it is not measured yet); p99 +20% to +32% for each. About 5 points of each, and most of the p99 rise, were the chain's fixed cost that any middleware paid then, which was the 80 B of slab room every request with middleware reserved (ADR 0003); the rest is the middleware's own work, 300 to 400 ns for the first three. `RequestID` alone measured again on 2026-11-05, with its room counted per chain ([`docs/research/middleware-p99/`](../research/middleware-p99/report.md)): GET -6.0% and POST -5.3% req/s, p99 +6% and +6%, about 270 ns of CPU, 321 B a request (its 16 B of room), inside the 10% on both. `AccessLog` is outside the 10% of ADR 0003 because formatting a log line through slog's text handler is that much work; a faster record would bypass the app's logger and its handler, which is a decision left open, not taken.

**What it fails at:** an access log that pairs with a request id costs an allocation, which puts that pair at 3 allocations a request ([ADR 0003](0003-the-trade-budget.md) names it); a handler that never looks at its context makes `Timeout` late, visibly, and not early; a stream's life is not bounded by `Timeout`; a panic skips the CORS headers because the chain does not return; a generated id has 64 bits, so it identifies a request in one service's logs but is not a trace id across services ([ADR 0059](0059-the-core-carries-w3c-trace-context-and-records-no-span.md) is the trace id); the access record is written after the answer, so it is not there yet when a client, or a test, has just read its response. The throughput of `AccessLog` as an Observer is not measured yet; it waits for the serial run of wave 2.

**What was rejected:** answering the 503 at the deadline while the handler still runs, for the reasons in [ADR 0049](0049-errors-are-found-with-errors-as-and-timeouts-wait.md); deriving the timeout's context with `context.WithTimeout` or `WithCancelCause`, which is two or more allocations and arms the disconnect watcher on every request, against cancelling the request's own context, which already reports `DeadlineExceeded` as its error when that is the cause; CORS origin patterns (`https://*.example.com`) in the first version, because a pattern is a security decision that deserves its own rules and a list is enough to start (milestone 4 gives it those rules: one wildcard form, whole leftmost label, two labels at least, matched label by label); regular expressions for origins, because one wrong anchor or unescaped dot is `evilexample.com` and the engine would have to compile and run them on every request; a glob such as `https://app-*.example.com` or `https://*.*.example.com`, which has no use a tenant list or `AllowOrigin` does not cover and more ways to match a lookalike; an `AllowOrigin` that sees the whole request (the method, the path, a cookie), because the origin is the only input the browser's rule depends on, a decision on anything else would not hold for the preflight (which has no cookie and a different method) and a cache keyed on `Vary: Origin` would serve one request's answer to another; a wildcard that also matches the apex, because `*.example.com` meaning "example.com and below" is how a parent domain gets allowed by accident; echoing the requested headers in a preflight, because it allows whatever a page asks for; generating the id with a `[16]byte` in the chain's pooled state, which would hand a pooled string to user code ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)); a 16-byte id string allocated for every request, which is one allocation for something most requests do not need to keep.
