# The reference workload is a JSON API over Postgres, with WebSockets

Every design is judged against one application shape first: a JSON API whose handlers call Postgres, beside WebSocket connections held open for a long time. That shape decides what is measured (a handler blocked on a database call, and many idle WebSockets, not only a "hello" route) and what goes into the first two milestones.

**It decides order and measurement, not who bites is for: bites is a framework offered to the public** (decided by the maintainer on 2026-11-03). A feature is judged by how many of the applications put in front of users would need it, never by what one application needs, so a design is argued from the reference workload, from the frameworks compared in [`docs/research/framework-gap/`](../research/framework-gap/report.md) and from scenarios stated in general terms, not from a port of one codebase. **Breadth is a goal** (decided 2026-11-04, [ADR 0077](0077-four-principles-in-the-order-they-win.md)): what Go frameworks commonly ship belongs on the roadmap, so that many applications can be built on bites fast, and that includes what Go microservice frameworks ship (configuration, discovery, gRPC, message consumers, read from their documentation in [`docs/research/framework-gap/microservices.md`](../research/framework-gap/microservices.md)), so an application can be split into services on bites when that is chosen. What most of those applications need is on the roadmap under Important and is built first; what fewer need is under Fairly important, then Nice to have when only a few do, and is built in that order once the tier before it is done, not when an application asks. The roadmap has no milestones since 2026-11-04: the tiers are the order. Each item keeps a trigger, written as a need an application shows, which moves it forward when it appears ([`docs/roadmap.md`](../roadmap.md)). A feature with a dependency, or that fewer applications need, is a module ([ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)), so breadth does not make the core larger for an application that does not use it. What is already built for production (rate limiting, CSRF, sessions, security headers, observability, static files) stays and is maintained.

**What was rejected:**

- **A feature waits for its trigger, and parity is refused** (the rule from 2026-11-03 to 2026-11-04): an item under Later or Nice to have was built only when its trigger appeared, however many frameworks had it, and what the roadmap listed as Not goals was refused outright. It was replaced when the maintainer ranked breadth above speed ([ADR 0077](0077-four-principles-in-the-order-they-win.md)): bites is used to build many applications fast, and a framework that waits for each feature to be asked for sends an application to a second framework in the meantime. The cost it named, each feature being code to keep correct and secure, still holds and is paid by putting such features in modules and holding them to the same refusals and tests.
- **Scope set by the maintainer's internal tools** (the rule on 2026-11-03): the internal tools, one of them first, decided scope; what they needed was built under Now, what they might need waited with a trigger, and what only a public framework needs was built only if this ADR was revised. It was replaced the same day because the work began to fit one application: triggers were written as that application's needs, ADRs were argued from its port, and a guide's example was named after it, while a framework is used by applications its maintainer never sees. The features built under that rule (`UseEach`, `App.Routes`, `Request.Cookie`, `stdhttp.Handler`, checked formats, a float `Range`, `Outcome.Err`, `RequestIDFrom`, `Logger(ctx)`, `Deprecated`, `Attachment`) are general and stay; the ADRs that cited the port as evidence now argue from the general case.
- **Order, not scope** (the rule from 2026-10-31 to 2026-11-03): what every production framework needs was on the definition of finished with a milestone, whether or not the reference workload used it, and only optional optimisations waited for a workload. It was replaced when the map of what Fiber, Gin, Echo, chi, Huma, Hertz and Fuego have ([`docs/research/framework-gap/`](../research/framework-gap/report.md)) put 46 features on the roadmap for parity, most of which few applications use (HTTP/2 to clients, Socket.IO, PASETO, prefork, JSONP), while each feature of a framework that owns its own engine, codec and parsers is code to keep correct and secure. Under the old rule they would all have been built before bites was called finished.
- **The first version of this ADR** said a feature serving none of the three parts of the workload "waits until a workload that needs it is named". That left features no production framework ships without, rate limiting and CSRF among them, waiting for someone to ask, while their absence sends users to assemble them badly or to another framework. The rule now in force differs from it by building first what most applications need, whether or not the reference workload uses it, and by writing each waiting feature on the roadmap with its trigger, so it is planned rather than forgotten.

The Postgres driver is the application's choice (pgx is the obvious one) and not part of the framework; how a handler reaches a pool is a framework concern, and is decided in its own ADR.
