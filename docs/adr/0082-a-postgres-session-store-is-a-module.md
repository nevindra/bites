# A Postgres session store is a module, and it is an OwnerSessionStore

[ADR 0056](0056-a-session-is-sealed-in-a-cookie-and-changed-by-returning-its-cookie.md) gave `Sessions` a `SessionStore` seam and, for revocation, `OwnerSessionStore`, and left the store to the application. An application that runs only Postgres (most of those the reference workload describes) then writes the same store: a table, an upsert, a way to find the rows of one User, and a job that deletes expired rows, and each gets one of them wrong (the id stored in the clear, an owner scan on every revoke, rows never deleted). Decided on 2026-11-04 and built.

**Decision.**

- **`modules/pgsession` is the Postgres store**, with its own `go.mod` and `github.com/jackc/pgx/v5` ([ADR 0006](0006-no-third-party-dependency-in-the-core.md), [ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)); the core changes nothing. `pgsession.New(Options) *Store` returns a `bites.OwnerSessionStore`. `Options` are `Pool` (the application's `*pgxpool.Pool`, required, never closed by the store), `Table` (`bites_sessions`), `SweepEvery` (10 minutes) and `Log` (`slog.Default()`).
- **The id is stored only as its SHA-256.** The cookie holds a sealed random id ([ADR 0056](0056-a-session-is-sealed-in-a-cookie-and-changed-by-returning-its-cookie.md)); a copy of the table (a backup, a replica, a SQL injection elsewhere, a developer's dump) then holds no value that, sealed with the application's key, makes a cookie. The id is 128 random bits, so a fast hash without a salt is not guessable by brute force and the hash is one `sha256.Sum256` with no allocation worth a name. The row is `id_hash bytea PRIMARY KEY, owner text NULL, data bytea NOT NULL, expires timestamptz NOT NULL`, with a partial index on `owner` (`WHERE owner IS NOT NULL`) and one on `expires`. The data is `bytea`, the framework's own JSON bytes: the store never reads inside it, and a `jsonb` column would re-encode it (key order, number text) and make the store a second reader of a format that is the framework's.
- **The owner is a column of the row.** `SaveOwned` is one upsert (`INSERT ... ON CONFLICT (id_hash) DO UPDATE`) that sets owner, data and expiry together, so an id changing hands is found under its new owner at once and a save and an owner change are never two statements. `DeleteOwner` is `DELETE ... WHERE owner = $1` through the partial index, and its count is `RowsAffected`; an owner with nothing is `(0, nil)`. An empty owner is stored as NULL (`NULLIF($2, '')`): kept, and no `DeleteOwner` finds it; `DeleteOwner("")` is `(0, nil)` without a query. `Save` is `SaveOwned` with no owner, so a plain save also clears an owner, as "replacing what id had" says.
- **Expiry is judged on the application's clock, passed as a parameter.** `Load` reads only a row with `expires > $2` and the sweep deletes `expires <= $1`, where the parameter is `bites.Now(ctx)`: the request's ctx carries the app's clock, and so does the ctx of a Service's `Start`, which is what `bites.Every` hands the sweep. An expired row never loads whether or not the sweep ran. It is the clock that computed `expires` (`Sessions`, on `WithClock` or `bitetest.Clock`) and that checks the expiry sealed in the cookie, so the store, the cookie and the test clock agree; a ctx with no app reads `time.Now()`.
- **`WithTx(ctx, q)` lets a session change join the application's transaction.** It returns a ctx that makes `Load`, `Save`, `SaveOwned`, `Delete` and `DeleteOwner` run on `q` instead of on the pool, so a password change sets the hash and ends the other sessions atomically: `sess.RevokeOthers(pgsession.WithTx(ctx, tx))`, then `tx.Commit`. `q` is a `pgsession.Querier`, the two methods the Store runs statements with (`Exec` and `QueryRow`), which a `pgx.Tx`, a `*pgxpool.Conn` and a `*pgxpool.Pool` satisfy, so a connection held for a `SELECT ... FOR UPDATE` works as well as a transaction. Only this Store reads the value; `Sweep` and `CreateTable` stay on the pool, being maintenance and DDL. The Store never begins, commits or rolls back `q`. A `q` whose transaction has ended returns the pgx error (`pgx.ErrTxClosed`) wrapped with the operation, and never falls back to the pool, so a change meant to be atomic is not made outside its transaction in silence. A nil `q` panics at the call, naming what to give.
- **Expired rows are swept by a `bites.Service`.** `(*Store).Service() bites.Service` returns a Service named `pgsession`: `app.Service(store.Service())` ([ADR 0079](0079-services-start-after-the-app-binds-and-stop-in-reverse-around-shutdown.md)). The Service is a `bites.Every("pgsession", SweepEvery, ...)` ([ADR 0079](0079-services-start-after-the-app-binds-and-stop-in-reverse-around-shutdown.md)): `Start` returns at once and the sweeps run on the app's clock (the first after one period, so a start never waits for the database); `Stop` cancels it and waits for a sweep in progress. The Service interface fit, so the store needs no `Run`/`Close` pair as `pgnotify` has: `pgnotify` blocks on a connection it owns and reports its state, and this has nothing to report, so the one lifecycle the app already has is used. `Sweep(ctx) (int, error)` is exported because a test, a cron job or an application that sweeps on its own schedule calls the same code. A sweep deletes in batches of 1000 with `FOR UPDATE SKIP LOCKED`.
- **`Schema()` and `CreateTable(ctx)` are both there, and that is one way to do a thing.** They are one DDL text and not two spellings of a feature: `Schema` is the text for an application that applies its schema with a migration tool (goose, Atlas) and must own the statement; `CreateTable` runs exactly that text for one that has none. They cannot differ because one calls the other's string, and both use `IF NOT EXISTS`. Dropping `CreateTable` would make every small application paste SQL to start; dropping `Schema` would make every application with migrations copy it out of the source. The store never creates a table by itself on `New` or on `Start`: the creation of schema in a production database is the application's decision, and a missing table is a wrapped Postgres error at the first `Load`, naming the table.
- **Errors are wrapped, never swallowed**: `pgsession: load: <pgx error>`, and `save`, `delete`, `delete owner`, `sweep`, `create table <name>`, with `errors.Is`/`errors.As` working through them. A failed sweep is logged at Warn with the table and tried again at the next tick; a failure of a request-path operation is the error the framework answers with a 500.

**Refusals** (rows of `modules/pgsession/pgsession_test.go`, each ending `registered at <file:line>`; the module's rows are in the [reference](../reference/pgsession.md#pgsessionnew)):

- `pgsession.New: Pool is nil: give the application's *pgxpool.Pool, such as pgxpool.New(ctx, url)`
- `pgsession.New: Table "<name>" is not a plain identifier: ...` for a name with a character other than letters, digits and underscore, a leading digit, or over 50 bytes. The name is quoted into the SQL, so the check is what keeps a configured table name from becoming SQL; 50 bytes leave room for the index suffix inside the 63 of an identifier.
- `pgsession.New: SweepEvery is -1s, which is not a time: ...`.
- Not caught before the first request: a table that does not exist or has another shape (the first `Load` says so with Postgres's own message), and two `Sessions` types over one table, which share owners ([ADR 0056](0056-a-session-is-sealed-in-a-cookie-and-changed-by-returning-its-cookie.md)): give each its own `Table`.

**What it costs** ([ADR 0003](0003-the-trade-budget.md)). The core: none; no file of it changes and the two guarded axes (allocations per request, memory per idle connection) do not move. The module: a session store costs one round trip to Postgres per request that loads a session (a primary-key lookup on a 32-byte key) and one per save; a request that does not read the Session does not touch the database. Per store, one goroutine sleeping on a ticker. Per row, a 32-byte key, the owner text, the data and 8 bytes of expiry, plus two small indexes. The sweep adds a batch delete every 10 minutes whose cost is the number of rows that expired. No number is raised.

**Scenarios it was put against.**

- _A hostile client_ sends a forged or stolen cookie: a forged one does not open (the seal), an id of another User is unguessable (128 random bits, then sealed), and the owner never comes from the client. A client cannot make the store run SQL: every value is a bound parameter and the only interpolated text, the table name, is checked at `New`.
- _A database dump or a read-only SQL injection elsewhere in the application_: the table holds hashes, owners and data. The hashes are not ids, and without the sealing key an id could not become a cookie either. The data and the owner are readable, as for any row; a session that holds a secret should not hold it in the data.
- _A revoke racing a save_ (a refresh of a sliding session included): `DeleteOwner` and an in-flight `SaveOwned` are two statements and the later one wins. A request that loaded the session before the revoke and saves after puts it back with its owner. This is the case [ADR 0056](0056-a-session-is-sealed-in-a-cookie-and-changed-by-returning-its-cookie.md) names and the store does not close it (closing it needs a revocation list the save consults, a second table and a second read on every save): the application's Provider of the User refuses a disabled User on every request, and the order is disable, revoke, close the sockets.
- _Many instances share one table_: every operation is one statement on the primary key or the owner index, so there is nothing to coordinate; an instance that revokes is seen by the others on their next `Load`, with no cache between. There is no cache on purpose, because a cached session would outlive a revocation.
- _The sweep on several instances at once_: each runs the same batch delete; `FOR UPDATE SKIP LOCKED` makes a row one instance is deleting invisible to the others, so none blocks on another and no row is deleted twice (tested: four concurrent sweeps of 3000 expired rows delete 3000 between them). Instances sweeping at the same moment waste a little work; they cannot harm each other, so no leader is elected.
- _A long outage of the sweep_: the next one deletes in batches of 1000 and holds no lock on the table or a long transaction; expired rows were never loadable meanwhile.
- _The same id saved twice at once_ (two tabs): the upsert is atomic and the later commit wins, which is the semantics of `Save` ("replacing what id had").
- _An application that loses the database_: `Load` returns the wrapped error and the request is a 500, not an anonymous session; treating a store failure as "no session" would sign every User out on a blip and, for a login page, hide the fault.

**What it fails at.**

- **A session revoked is gone for the next `Load`, not for a request in flight**, and an in-flight save can put it back (above).
- **A request on an application clock that jumps** (an operator setting it back) sees expired sessions live again until their `expires`; the cookie's expiry moves with it too, so nothing disagrees. Instances of one application must keep time with NTP, as for any signed expiry.
- **An application that holds a transaction open across a request** holds the row locks of its `DeleteOwner` until it ends; `WithTx` leaves its length to the application.
- **A row per session and a round trip per request.** An application whose sessions are read on every request at a rate the database cannot serve wants a cache in front (which defeats immediate revocation unless it listens for it) or the sealed-cookie mode for what need not be revoked. The module does not cache.
- **`DeleteOwner(ctx, owner, keep)` keeps the row of `keep`**: one statement, `DELETE ... WHERE owner = $1 AND id_hash <> $2`, with `keep` hashed like every id. An empty `keep` hashes to the SHA-256 of the empty string, which no id has, so it keeps none (`TestDeleteOwnerKeepsTheSessionItIsToldToKeep`).
- **`DeleteOwner` deletes expired but unswept rows too** and counts them, so the count can include a session that had already ended. It is a count of rows forgotten, which is what [ADR 0056](0056-a-session-is-sealed-in-a-cookie-and-changed-by-returning-its-cookie.md) says.
- **The schema is not migrated.** A later version of the module that changes the table needs a migration the application runs; `Schema` shows what the version expects and nothing compares it with what exists.
- **It serves Postgres only.** MySQL and SQLite stores, and Redis, fit the same interface and are modules when an application asks.

**Considered and what was rejected.**

- **Storing the raw id as the key:** simplest, and a dump then hands out every live id. The hash costs one function call.
- **A salted or slow hash (HMAC with a server key, bcrypt):** the id is 128 random bits, not a password; the work of a slow hash buys nothing against an input that cannot be guessed, and a key would tie the table to a secret that rotation would have to carry.
- **A `jsonb` data column:** it would let SQL query inside sessions, a feature nothing asked for, at the price of re-encoding the framework's bytes and a second reader of their format.
- **`LISTEN`-based invalidation** (each instance caches sessions and drops one when a revoke notifies): a cache the module does not need, with a gap on every reconnect during which a revoked session still reads; one primary-key lookup is the cost it saves and the revocation delay is the price. The `Broker` seam of [ADR 0081](0081-a-topic-reaches-other-instances-through-a-broker-and-postgres-is-a-module.md) could carry it if an application's load asks.
- **An owner index in a separate table** (`owner`, `id_hash`): two writes for one save that must be in one transaction, an orphan when they are not, and a join on revoke. A column and a partial index are the same lookup in one row.
- **An owner column with an empty string, not NULL:** the partial index would hold every anonymous session, which is most rows of an application with a cart for visitors, to serve a lookup that never asks for them.
- **Creating the table on `New` or `Start`:** the store would run DDL against a production database on the application's behalf, and `New` would need a context and the database. `CreateTable` is a call the application makes on purpose.
- **Making `Sweep` the only API (no Service) or the Service the only API (no `Sweep`):** the first makes every application write the goroutine; the second leaves a test or a cron job reaching into private code.
- **A `Run(ctx)` and `Close()` as `pgnotify` has:** two more names for what the Service already is.
- **Deleting expired rows on `Load`:** a write on a read path, which a replica could not serve and which turns a read-heavy request into a transaction.
- **Judging expiry with Postgres's `now()`** (what it did): one clock for every instance, but not the clock that computed `expires`. An application on a test clock (`bitetest.Clock` reads 2026-01-01) had every session expired at once, and a database clock that drifted from the application's disagreed with the sealed cookie. Passing `bites.Now(ctx)` as a parameter costs nothing and makes the three agree.
- **`Session.ID()`, so the application can write its own `DELETE` in its transaction:** the id is the bearer secret, which this module keeps only as a hash so a dump hands none out; an accessor would put it in handler code, logs and tracing. `WithTx` runs the framework's own `DeleteOwner` in the application's transaction and the id never leaves the Store.
- **A `DeleteOwner` that takes an executor** (`DeleteOwner(ctx, tx, owner, keep)`): it changes the `OwnerSessionStore` interface of the core for one store, and every other store (memory, Redis) would carry a parameter it cannot use. A ctx value read only by this Store leaves the interface as it is.
- **`WithTx` taking `pgx.Tx` only:** a connection acquired from the pool (`*pgxpool.Conn`) is the other thing an application runs a unit of work on; a two-method interface that both satisfy is no more to learn and refuses nothing a caller could mean.
