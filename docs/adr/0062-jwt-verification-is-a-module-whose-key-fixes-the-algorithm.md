# JWT verification is a module whose key fixes the algorithm

`modules/jwt` ([ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)) verifies a JSON Web Token (RFC 7519) signed with HS256, RS256 or ES256, with the standard library's crypto only, and its `Verify` method is the verification function `BearerAuth` takes ([ADR 0054](0054-auth-providers-parse-the-credential-and-the-application-verifies-it.md)), so the whole integration is one line:

```go
v := jwt.New[Claims](jwt.Config{Keys: jwt.Keys(jwt.RS256("2026-11", pub)), Issuer: "https://id.example.com", Audience: "api", Clock: app.Clock()})
app.Provide(bites.BearerAuth(v.Verify))
```

Decided and built on 2026-11-01, milestone 3 wave 2 (`modules/jwt/jwt.go`, `jwks.go` and their tests). The core parses no token and holds no key; the module imports the core's exported API only (its test fails otherwise).

**The rule.**

- _The key fixes the algorithm._ A `Key` is made for one algorithm by `HS256(id, secret)`, `RS256(id, *rsa.PublicKey)` or `ES256(id, *ecdsa.PublicKey)`, and the token's `alg` is never used to choose how to verify: it must equal the selected key's algorithm exactly, or the token is refused with `ErrAlgorithm` before its signature is looked at. So `"alg": "none"` cannot pass against any key, and an RS256 public key can never be used as an HMAC secret (the confusion attack), because a key made by `RS256` only verifies RSA signatures. The constructors refuse what would be weak whatever the token says: an HMAC secret under 32 bytes (RFC 7518 3.2), an RSA modulus under 2048 bits, a curve other than P-256.
- _The key is chosen by `kid`._ A `KeySource` answers `Key(ctx, kid)`. `Keys(...)` is a fixed set: with one key a token without `kid` uses it; with several, rotation, a token must name its key. `JWKS(url, JWKSOptions)` fetches a JSON Web Key Set (below).
- _The order of the checks_, each before the next costs anything: the length against `MaxSize` (8 KiB by default) before any decoding, so a huge header is refused without base64 or JSON; exactly three parts of strict unpadded base64url; a header that is a JSON object with a string `alg`, a string `kid` if any, and no `crit` (no extension is understood, so one that must be understood is refused); the key; the algorithm; the signature over the ASCII `header.payload` (HMAC compared with `hmac.Equal`, RSASSA-PKCS1-v1_5 with SHA-256, ECDSA P-256 whose signature must be the 64-byte JOSE `r||s` form, RFC 7518 3.4, so a DER signature or a truncated one fails); and only then the claims.
- _The claims._ `exp` is required (`ErrNoExpiry`: a token that never expires is refused, RFC 8725's advice taken as the rule); `exp`, `nbf` and `iat` are NumericDates checked against `Config.Clock`, the app's clock (`app.Clock()`, so `bitetest`'s fake clock moves token time too), widened by `Leeway`, 30 seconds by default and refused below 0 or above 5 minutes: expired when now is at or after `exp + leeway`, not yet valid when `nbf` or `iat` is later than `now + leeway`. `iss` must equal `Config.Issuer` and `aud` (a string or an array) must contain `Config.Audience` when they are set. The payload is then decoded with `encoding/json` into the application's type `C`, unknown members ignored.
- _The errors._ Every failure is one of `ErrMalformed`, `ErrAlgorithm`, `ErrUnknownKey`, `ErrSignature`, `ErrExpired`, `ErrNotYetValid`, `ErrIssuer`, `ErrAudience`, `ErrNoExpiry`, each wrapping `bites.ErrInvalidCredentials`, so `BearerAuth` answers 401 with `error="invalid_token"` and an OAuth client refreshes. A key source that could not look (a JWKS endpoint down) returns an error that does **not** wrap it, and the answer is a 500: an outage does not tell every client its token is bad, which is [ADR 0054](0054-auth-providers-parse-the-credential-and-the-application-verifies-it.md)'s rule. No error text holds the token or any part of it (`TestNoErrorTextHoldsTheTokenOrItsSignature`).

**JWKS is built, in the module, with net/http.** An identity provider (Keycloak, Auth0, Cognito, Entra ID, Google) publishes its signing keys as a JWKS and rotates them on its schedule, and the `kid` is how a token names the new one; without fetching, every rotation is a deploy of the application. That is most of the reason to have a JWT module, so it is built, and the module may import `net/http` ([ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)); an application with fixed keys never calls it. Its rules: the URL must be `https` (`http` only on the loopback, for tests), and the default client follows a redirect only to `https`, at most five; the set is fetched on the first lookup, under one mutex, so a hundred concurrent lookups on a cold set make one fetch; a `kid` the set lacks causes a fetch only when the last attempt is older than `MinRefresh` (1 minute), so a client sending random `kid`s causes at most one fetch a minute; the set is fetched again after `MaxAge` (1 hour); a failed fetch keeps the old set, so a known `kid` still verifies during an outage; a document over `MaxSize` (1 MiB) fails; the fetch does not take the request's cancellation (`context.WithoutCancel`, bounded by the client's 10-second timeout), because it serves every waiting lookup and one client leaving must not fail it for all. A JWK is read when its `kty` is `RSA` (2048 bits or more) or `EC` on P-256 (the point checked on the curve), its `use` is `sig` or absent and its `alg` fits its type or is absent; `oct` keys are skipped, since a symmetric secret is never published.

**What it costs.** The module's, not the core's: the core's axes are unchanged. Allocations of `Verify` with a one-field claims type, measured with `go test -run '^$' -bench . -benchmem -benchtime=2000x -count=3` in `modules/jwt` on the Ryzen 7 9700X, on the working tree of milestone 3 wave 2 over commit 4291b54, the same in all three runs: **HS256 23, RS256 25, ES256 36** allocations a token (about 1.3, 2.4 and 2.0 KB), mostly the three base64 decodes, the JSON of the header and the claims decoded twice (once for the registered claims, once into `C`), and `big.Int` for ES256. A request behind `BearerAuth(v.Verify)` pays these on top of the core's 2. Time per token is not quoted, since the machine was shared; throughput is not measured yet and waits for the serial run of wave 2. A cache of verified tokens was not built (see below).

**Refusals.** At construction, each a panic naming the file and line of the call, held by the module's tests: `HS256` with a secret under 32 bytes; `RS256` with a nil key or one under 2048 bits; `ES256` with a nil key or another curve; `Keys` with no key, a zero `Key`, two keys of one id, or several keys one of which has no id; `New` with no `Keys`, a `Leeway` below 0 or above 5 minutes, a negative `MaxSize`; `JWKS` with a URL that is not https or a negative option. **What cannot be caught before the first request:** a wrong `Issuer` or `Audience` (every token is then a 401, which the first test against the identity provider shows), a JWKS URL that answers 404 (every token a 500, logged), a clock far off.

**Scenarios it was put against.**

- _The reference workload_ ([ADR 0002](0002-the-reference-workload.md)) behind an identity provider: `JWKS` with its URL, `Issuer` and `Audience` set; tokens verify, the `sub` lands in the claims type, a rotation publishes a new `kid` and its first token causes one fetch; an expired token is a 401 that the client library reads as "refresh".
- _A hostile client_: `alg: none` with an empty signature (refused against HS256, RS256 and ES256 keys); an HMAC token keyed with the RSA public key's bytes and `alg: HS256` against an RS256 key (`ErrAlgorithm`); a truncated signature, a DER ECDSA signature, a 100 KiB header (refused on length before decoding), padding, four parts, a `crit` header, a random `kid` in every request (no fetch within `MinRefresh`); none reaches the payload's JSON.
- _The identity provider down_ at start: every lookup within a minute of the failed fetch returns that error, a 500, and the endpoint is asked once a minute, not once a request. Down after a good fetch: cached keys keep verifying.
- _Known vectors_: RFC 7515 A.1 (HS256, with RFC 7519 3.1's claims, verified with a clock set before its 2011 `exp`) and A.3 (ES256) verify as published. RS256 is tested with a generated 2048-bit key, since A.2's vector was not reproduced with certainty.

**A token for a test comes from `jwttest.Token`** (built 2026-11-04), a package of the module that signs HS256 with a secret the test also gives the verifier and fails the test on a short secret or claims that are not an object. Every application that tests a route behind `BearerAuth` needs a token, and an agent in the usability test found no way to make one and wrote its own signer ([`docs/research/agent-usability/`](../research/agent-usability/report.md), row 2). It is a package apart, named as `httptest` is, so that issuing tokens in production stays out of the module until an application needs it ([roadmap](../roadmap.md#fairly-important-what-many-applications-need)); a `Sign` beside `Verify` was rejected for that reason.

**What it fails at.** HS256, RS256 and ES256 only: no PS256, EdDSA, ES384 or RS512, and no encrypted token (JWE). One `Audience` and one `Issuer` per verifier. `encoding/json` matches member names without regard to case, so a signed token's `EXP` is read as `exp`, which only its issuer can produce. A token without `exp` is refused, which some internal issuers do not set. Every request verifies its token again: no cache of verified tokens, so a hot API pays the signature each time (RS256 and ES256 cost tens of microseconds). The JWKS mutex is taken by each lookup that misses, so a flood of unknown `kid`s serialises on it without fetching. Revocation before `exp` is not checked: the claims type and the application's own lookup are where a `jti` deny list goes. The API document does not say `bearerFormat: JWT` ([ADR 0069](0069-the-api-document-states-what-a-routes-providers-and-middleware-ask-and-answer-and-a-route-can-be-left-out.md)).

**What was rejected.** Taking the algorithm from the token's header, as early libraries did: it is the cause of both the `none` and the key-confusion attacks. A list of allowed algorithms beside the key: two places to keep in step where one, the key, says it. A third-party JWT library: it would bring its own algorithm and key handling to audit, and the three algorithms are a few calls each into the standard library. JWKS left to the application: rotation is the common case, and every application would write the same fetch with the same mistakes (fetching per unknown `kid` without a floor, cancelling the shared fetch with one request's context). A cache of verified tokens: it trades a signature check for memory holding bearer credentials and an eviction policy, and is not needed until a measurement asks for it. Decoding the claims once into a type that must embed the registered ones: it would force the application's type to carry fields it may not want.
