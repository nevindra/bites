# A request is observed once when it starts and once when it has really ended

An app may be given one or more **Observers** with `WithObserver(...Observer)`. An Observer is told when a request starts and when it has really ended, and it is what metrics, tracing and the access log are built on, in the core or in a module. Decided on 2026-11-01 for milestone 3 and built the same day (`observer.go`, `observer_test.go`).

```go
type Observer interface {
	// Start runs once the head is parsed, before app middleware.
	// The context it returns is the one the middleware, the Providers and the handler get.
	Start(ctx context.Context, req Request) context.Context
	// End runs once, after the last byte of the answer was written or the connection was given up,
	// with the context this Observer's own Start returned.
	End(ctx context.Context, req Request, out Outcome)
}

type Outcome struct {
	Route    string        // the pattern that matched, "/users/{id}"; "" for a 404 and a 405
	Status   int           // what was sent: 500 after a panic, 503 after Timeout, 101 for an upgrade
	Read     int64         // body bytes read from the client
	Written  int64         // body bytes written, after gzip; 0 when abandoned
	Duration time.Duration // from Start to End, on the app's clock
	Streamed, Upgraded, Panicked, Abandoned bool
	Err      error         // the error the application returned that the framework answered; nil for none
	Panic    any           // the value recovered when Panicked; nil otherwise
	Stack    []byte        // the panicking goroutine's stack, from runtime/debug.Stack in the recover; nil otherwise
}
```

**What a tracker needs: the error and the panic (revised 2026-11-03).** `Outcome` tells `Panicked` and also the three values an application reports to Sentry or a tracker like it. `Err` is the error the application returned that the framework answered: from a handler, a middleware, a Provider or a stream's function before its first byte, whatever status it was answered with (a `HasStatus` 404 and an unmapped error answered 500 alike, since the tracker's filter is the Observer's own `Status >= 500`), and the error a stream's function returned after its first byte, which cut the stream. It is the value returned, unwrapped by nothing, so `errors.As` finds the application's types. It is recorded where `answerError` answers (the one place every returned error passes), so the framework's own answers are not in it: a 400 for a body that does not decode, a 404, a 405 carry nothing a tracker needs. The last error answered stands. A middleware that replaces the answer to an error with a status below 400 has handled it, and `Err` is nil (the check is on the final status and not on a stream); a client that left is not an error, since nothing is answered. `Panic` is the value `recover` returned (a `panic(nil)` arrives as a `*runtime.PanicNilError`) and `Stack` is `runtime/debug.Stack()` taken inside the recover, the same call that already fed the log line, so naming the panicking function. Both are the application's own values, not pooled, so [ADR 0008](0008-no-pooled-object-reaches-the-user.md) holds; the Observers of one request share the one `Stack` slice and copy it before changing it. A panic in a WebSocket's `OnMessage` or `OnClose` happens after the request ended and is not in any Outcome. A consequence: `Outcome` holds a slice, so it is no longer comparable with `==`. The guide has an Observer that reports to a tracker through a two-method interface, with no import.

**Why a middleware is not enough.** A middleware sees the chain return, and the chain returns before four things an observer must see: a stream's function, which runs after every middleware has returned ([ADR 0030](0030-streaming-is-a-return-type.md)), so its end, its size and its failure are invisible; a panic, after which the chain does not return at all ([ADR 0028](0028-panics-are-recovered-by-the-engine.md)); the bytes written, which gzip changes after the chain ([ADR 0031](0031-gzip-only-and-off-by-default.md)); and the body of a `Problem` a middleware returned, rendered only when it is written. These are the faults [ADR 0032](0032-four-first-party-middleware.md) listed for `AccessLog`.

**Why Start returns a context.** Tracing needs its span in the context the handler passes to its database calls, so that their spans become children. Returning the context is how Start puts it there; returning `ctx` unchanged costs nothing.

**One interface with both methods.** An Observer that only counts writes a Start that returns `ctx`, one line, rather than the framework finding optional methods by type assertion on every request.

**Order.** Observers run in the order given for Start and in reverse for End, so the first one given wraps the others, as the first middleware does. `WithObserver` given twice is refused in `New`. Health and readiness answers ([ADR 0052](0052-health-and-readiness-follow-shutdown.md)) are not observed.

**AccessLog is an Observer.** `AccessLog(...)` returns an `Observer` and is given with `WithObserver(AccessLog())`, not `app.Use`. Its record is written at End, so it has the real status and size of a stream, a record after a panic with `panicked=true`, the compressed size, and the size of a `Problem` a middleware answered ([ADR 0032](0032-four-first-party-middleware.md) has the record). `RequestID` stays a middleware, and End reads the id it set. This changes the type of an exported name, which is done before v0.1.0 or not at all.

**A head the engine refuses before it parses** (a request line that is not HTTP, a head over its limit) has no `Request` and is not observed; it is logged at Debug, as now. A metric of malformed traffic is a later decision, taken when a deployment asks for it.

**A panic in an Observer.** In Start it is the request's panic: recovered, answered 500 and logged ([ADR 0028](0028-panics-are-recovered-by-the-engine.md)), and End runs for every Observer whose Start had returned, with `Panicked`. In End it is recovered and logged with the Observer's type, the other Observers' End still run, and the connection is closed, because the answer is already out and the engine cannot tell what state the Observer left.

**As built.** Decisions the ADR left to the code, each tested in `observer_test.go`:

- _Where Start runs._ After the head is parsed and before app middleware, as decided; the route is matched where it always was, inside the chain when the app has middleware, so Start does not see the route and End reads it from `Outcome.Route`. Matching earlier for an observed app would have given Start a route that `Request` has no method to show, at the cost of a second path through the router. `TestObserversStartInTheOrderGivenAndEndInReverseEachWithTheContextItsStartReturned`.
- _The context End gets_ is the one that Observer's own Start returned, so a tracer finds its span where it put it. Each is kept in the chain's pooled state until End and cleared after.
- _An observed request takes the chain's path_, as a route with Providers does: the head is copied once into the slab (no allocation) and the run is kept until End, which releases it; so `Request` keeps working in End (`RequestID` reads a copy the run keeps, since the engine drops its own once the answer is built) and answers zero values afterwards (`TestTheRequestAnObserverKeptAnswersZeroValuesOnceEndHasReturned`, `TestAnObserverReadsTheRequestIDAMiddlewareSetAtEnd`).
- _The engine's side_ is one hook: the framework calls `Exchange.Observe` with its run (an `engine.Ender`) before anything of its own can panic; the engine counts the body bytes read (`ReadBody`, an upload's parts) and written (`write`, a stream's chunks without their framing, after gzip), notes a failed write, and calls `End` from `conn.handle` at each of its ends: after the write, after a stream, at the 101 (`TestAWebSocketUpgradeIsObservedAtThe101`), and where it gives the connection up. With no Observer the engine checks one nil field.
- _Abandoned_ is the client's cause on the context ([ADR 0016](0016-the-handler-context-is-cancelled-on-disconnect.md)) or a write of the answer that failed (the client left without the context noticing, or stopped reading until the write deadline); `Written` is then 0 and `Status` what the chain left (`TestAClientThatLeavesMidHandlerIsObservedAsAbandonedWithNothingWritten`).
- _Not observed_: a head the engine refuses (`TestAHeadTheEngineRefusesBeforeParsingIsNotObserved`), an `OPTIONS *`, which is answered before any route exists to match, and the probes of [ADR 0052](0052-health-and-readiness-follow-shutdown.md).
- _Timeout, panics, streams_: `TestTimeoutIsObservedWithThe503ItAnswered`, `TestAPanicInTheHandlerIsObservedAsPanickedWithThe500`, `TestAStreamIsObservedWhenItEndsWithTheBytesItSent`, `TestAPanicInAnObserversStartIsTheRequestsPanicAndTheObserversBeforeItStillEnd`, `TestAPanicInAnObserversEndIsLoggedTheOthersStillEndAndTheConnectionCloses`.
- _Refusals_ (rows of `refusal_test.go`): `WithObserver` given twice, naming both places; a nil Observer, naming its place in the list.

**AccessLog, built.** `AccessLog(...)` returns an `Observer` (the type change of an exported name, made before v0.1.0) and its record is written at End, as decided; [ADR 0032](0032-four-first-party-middleware.md) has the record as it is now.

**What it costs.** With no Observer, one length check in the framework and one nil check in the engine. With Observers: the copy of the head into the slab that every route with middleware already pays (no allocation, [ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)), two interface calls per Observer, and two reads of the clock. `Outcome` is passed by value and holds no pointer to pooled memory. **Measured: 0 allocations for the hook**, the typed JSON POST staying at 2 with one and with three no-op Observers, behind `RequestID`, and on the real clock over loopback TCP (`TestATypedJSONPOSTWithANoOpObserverStillAllocatesTwice`, `TestANoOpObserverOnTheRealClockCostsNothingOverLoopbackTCP`; [ADR 0003](0003-the-trade-budget.md) has the row). The error and the panic cost nothing on a request that neither fails nor panics (the typed POST stays at 2); `Outcome` grew by an interface, a slice and an interface and is still passed by value with no allocation. On the error path `Err` is stored in a field of the pooled run, and the panic and the stream error in the frame of `conn.handle`, so an idle connection holds nothing and it adds **0 allocations**: a handler error answered 500 costs 7 allocations a request (the log line's) with and without an Observer (`TestAnObserverToldTheErrorOfAFailedRequestAddsNoAllocationToTheFailure`); `Stack` reuses the slice the panic's log line already took. Memory per idle connection: none, since nothing is held between requests (the run goes back to its pool at End). Throughput and p99 against the same route with no Observer are not measured yet; they wait for the serial run of wave 2. What an Observer does (a slog line, a histogram) is its own cost, not the hook's.

**Scenarios it was put against.**

- _The reference workload_ ([ADR 0002](0002-the-reference-workload.md)): a metrics Observer counts by `Route`, method and status, so 404 probes and scanners land under `""` and cannot grow the label set. An SSE feed is observed when it ends, with the bytes it sent.
- _A hostile client_ that opens connections and sends half a head: no Start, nothing observed. It is a connection, not a request, and the limits of [ADR 0024](0024-limits-are-on-by-default.md) close it.
- _A client that leaves mid-handler_: End with `Abandoned`, the status the chain left, and `Written` 0 ([ADR 0049](0049-errors-are-found-with-errors-as-and-timeouts-wait.md)).
- _Timeout_: End sees the 503 the timeout answered, not what the late handler returned.
- _A WebSocket_: End at the 101 with `Upgraded`. A socket's life is not a request; its own events are below (revised 2026-11-04).
- _Pooled memory_ ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)): `Request` is the view middleware already gets, so an Observer that keeps one keeps that request's own bytes; its live methods answer zero values once End has returned.

**An Observer of sockets (decided 2026-11-04, the roadmap's "rest of the production modules").** The first numbers a chat watches in production are the sockets open, the sockets closed because a send overflowed the queue, and the pongs missed; none was observable, since End at the 101 ends the request. An Observer that also implements `SocketObserver` is told, with no second registration (`WithObserver` finds it):

```go
type SocketObserver interface {
	SocketOpened(route string)                  // the 101 is written
	SocketClosed(route string, info CloseInfo)  // once per opened socket, after OnClose
	SocketPongMissed(route string)              // a heartbeat tick found the last ping unanswered
}
```

- _Why an optional interface_: adding methods to `Observer` would break every Observer written; an agent that implements `SocketObserver` finds in its doc comment what each call means, and the compiler holds the three methods together. The three calls are separate methods and not one `Socket(event)` with a kind, because an agent writes each body knowing its own arguments.
- _The reason_: `CloseInfo` gains `Cause`, a `CloseCause` of a fixed set: `client`, `server` (`Socket.Close` or a `CloseError`), `handler_error` (`OnMessage` or `OnMalformed` returned an error or panicked), `queue_full` (a send overflowed `Limits.SendQueue` or `Limits.SendBudget`, the case `Send` reports as `ErrSendQueueFull`), `pong_timeout`, `shutdown`, `client_fault` (the client broke the protocol or a limit on what it may send: a message too large or unfinished, a binary frame to a text route, a malformed message with no `OnMalformed`) and `lost` (no close handshake, 1006). The first thing to start the close stands, as the status already did. The set is fixed so it is a safe metric label; `OnClose` receives it too, so an application can log it without an Observer. Eight values and not the status: a status is the wire's word (1008 is both a slow reader and a pong timeout and a message that never finished), and the cause is the framework's.
- _Where it is called_: the engine tells the framework (`engine.WSWatcher`, optional on the socket's handler): `Opened` after the 101 is written, `PongMissed` from the heartbeat tick, and `Closed` already existed. The calls are recovered and logged like an Observer's End, since the heartbeat's goroutine is shared by every socket.
- _Metrics_ ([ADR 0060](0060-metrics-are-an-observer-in-the-prometheus-text-format-labelled-by-what-the-app-bounds.md)) implements it: `bites_websocket_connections_open` (gauge), `..._opened_total`, `..._closed_total{reason}` and `bites_websocket_pongs_missed_total`, each labelled `route`, a registered pattern.
- _What it costs_: **nothing on the HTTP request path** (the typed POST stays at 2, `TestATypedJSONPOSTCountedByMetricsStillAllocatesTwice` and the other rows of `budget_test.go` pass unchanged). **Idle WebSocket memory is unchanged**: `Cause` sits in the padding of `WSCloseInfo` (48 B before and after) and so does the `WS` (512 B), the route's list of Observers is one pointer in the route's plan and not in the socket, and no per-socket time is kept; `TestTheMarginalHeapAndStackOfAnIdleWebSocketStaysUnderItsCeiling` passes at its ceilings (parked 1,800 B, without parking 4,700 B; the three runs here gave 970 to 2,240 B parked and 3,400 to 3,850 B without, spread of the run and not of the change). An app with no `SocketObserver` pays a nil check at the 101, at a missed pong and at the close.
- _Scenarios_: a chat room of 20,000 sockets on a bad evening: the gauge falls and `queue_full` rises together, which says the readers are slow and not that clients left. A deploy: `shutdown` closes equal the sockets open at the time, and a gauge that does not fall to zero afterwards names a socket that never closed. A phone that goes through a tunnel: `pong_timeout` after two missed pongs, `lost` when the connection is cut with no handshake.
- _Refusals_: none at Registration; there is nothing to misuse that the compiler does not catch, and an Observer that implements only part of the three methods does not satisfy the interface and is simply an Observer.
- _What it fails at_: no duration of a socket's life (it would cost 8 B a socket, and a chat reads it from the open gauge and the rate); no per-socket identity, so an Observer cannot match an open with its close except by counting; the callbacks of one socket are ordered, those of different sockets are not, and a pong missed may race the close it causes; a `SocketClosed` is not delivered for a socket whose 101 could not be written, which never opened.
- _What was rejected_: a field on `Outcome` (the request has ended at the 101); putting events on `Observer` itself (breaks implementers); an identity or the `Socket` in the callbacks (a pooled-object trap and a way to hold a socket from an Observer, [ADR 0008](0008-no-pooled-object-reaches-the-user.md)); counting inside the engine with no Observer (a second metrics path with its own names).

**What it fails at.** A head refused before parsing is not observed. An Observer that blocks in End holds the connection, since End runs on the connection's goroutine. Duration starts when the head is parsed, so the time a slow head took to arrive is not in it. There are now two ways to wrap a request, and the guide has to say which to use: an Observer only watches and cannot answer. End runs after the client has its answer, so a test that reads what an Observer recorded (an access record, a counter) calls `bitetest.Server.WaitEnded` rather than reading it as soon as its request returns ([ADR 0027](0027-an-in-memory-entry-point-runs-the-engine-path.md)). Start cannot see the route.

**What was rejected.** `Outcome` carrying only `Panicked`, as first built: an application has to report a failure to a tracker before a user does, and the Observer is the only place that sees a stream's cut, a panic and the answered error together; a middleware sees neither the panic nor the stream. Fiber, Gin, Hertz and Echo each ship Sentry middleware for the same need. An `Err` that also holds the framework's own 400 and 404: the Input's refusal is not a fault of the application, and a tracker would drown in client typos. An `Err` that is the `*StatusError` the framework built: it would hide the application's own type from `errors.As`. A `Stack` as a string: the log line needs one, a tracker wants bytes, and the conversion is the Observer's to make. A middleware with an end callback, which must allocate a closure per request or pool one that reaches user code, and still cannot see a panic. Separate hooks for metrics and for tracing: two places to keep in step for every new kind of answer. Two optional interfaces, one per method, found by type assertion: the saving is one line in a counting Observer. An Observer told about each body chunk or frame: nothing on the roadmap needs it, and each call would sit on the write path. Keeping `AccessLog` a middleware beside the Observer: its faults would stay, and the core would carry two ways to log a request.
