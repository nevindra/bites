# The Descriptions methods are generated from the doc comments of the fields by `bites-doc`

`go run github.com/nevindra/bites/cmd/bites-doc`, put in a `//go:generate` line of the package that holds the Input and output types, reads that package's Go source and writes `bites_descriptions_gen.go`: for each named struct type with at least one commented field, a `Descriptions() map[string]string` method keyed by Go field name, which is the second place prose comes from in [ADR 0020](0020-descriptions-come-from-registration-and-later-from-doc-comments.md). Nothing about the document changes: the generator fills the structure that was designed for it, and the existing Registration check holds the result against the wire fields, so a comment on a field the codec does not read is refused like a hand-written description is.

**What a description is.** The comment above a field, or the comment after it on the same line; the lines of a paragraph are joined with one space and paragraphs are kept apart by a blank line, so a description is one string of prose and not a wrapped block. The text is kept as written, including the leading field name Go's style asks for ("ID is assigned by the server"): stripping it would need a grammar, and a rule that is wrong for half the sentences is worse than a name that reads as a sentence. A field with no comment gets none. The output is sorted by type and field, formatted with `go/format` and starts with the generated-code line, so it is the same bytes every run and `go vet` and editors treat it as generated.

**Which types.** Every named, non-generic struct type of the package, exported or not, with a documented, exported field (a section type is often unexported because nothing outside the package names it, and a method on an unexported type is in the method set Registration reads; the generator first skipped them without a word, and a Path section with a documented `ID` got no description until it was exported), unless `-types A,B` names them. Fields of a struct embedded by value from the same package are included in the outer type, because the codec reads them as the outer type's own fields and the outer type's method would otherwise shadow the promoted one. A type that already has a `Descriptions` method written by hand is left alone and said so, so adoption can be one type at a time. `-check` writes nothing and exits 1 when the file on disk is not what would be written, which is the line for CI; a test in the repository holds the committed example to the same ([`examples/described`](../../examples/described/described.go)).

**What it says and does not write.** On standard error, one line each: a documented field with `json:"-"` (it is not on the wire, and the Registration check would refuse its description); a documented field of an anonymous struct, such as `Path struct{ ID int64 }`, because a method needs a named type, so the section has to be named for its fields to be described; a generic type; a requested type with no comments. The run still succeeds. When nothing is left to write, a stale generated file is deleted.

**Its refusals.** The generator reads syntax and not types, so it cannot know the wire name of a field or whether a type is used as an Input; that stays with Registration, which panics naming the route and the line for a description of a field the codec does not read ([ADR 0007](0007-mistakes-are-refused-at-registration.md)). What the generator itself refuses: a directory with no Go files, with two packages, or that does not parse.

**Axes:** none. It runs at development time; at run time the method is called once per type at Registration, and the document is built once ([ADR 0020](0020-descriptions-come-from-registration-and-later-from-doc-comments.md)).

**Scenarios it was put against.** A renamed field: the next `go generate` follows the comment, and a forgotten run leaves a description whose key names a missing field, which Registration refuses at the next start. An embedded `Audit` struct: its fields appear on every type that embeds it. A comment with a code block or a list: the text is flattened to prose, so it is the author's job to write the comment as a sentence; nothing in Markdown is interpreted, and OpenAPI renders what it is given. A generated file committed beside the types: the diff of a pull request shows the prose change twice, once in the comment and once in the file.

**What it fails at.** Prose for an operation (`Summary`, `Description`) still comes from route options, because a handler's doc comment is not tied to a route by syntax alone (the same function can be registered twice); the generator does not read function comments. Types from other packages (a type in a library the Input embeds) cannot be described from here. A comment on a field of a nested type is found only if that type is in the same package. Because the key is the Go field name and the text is not edited, a comment that says "Deprecated:" lands in the document as prose and not as `deprecated: true`.

**What was rejected:** a `doc:"..."` tag, for the reason in ADR 0011 that a tag string is checked by nobody; `go/types` to resolve the wire names in the generator (it duplicates the codec's rules in a second place and the two would drift); reading comments at run time (they are not in the binary); generating a method for every struct (an empty map is a method that the check then reads on every type).
