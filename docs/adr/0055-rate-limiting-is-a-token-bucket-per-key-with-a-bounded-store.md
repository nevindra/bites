# Rate limiting is a token bucket per key, in a bounded store, and a limit per user is called by the user's Provider

`NewRateLimiter(RateLimitOptions{Limit, Period, Burst, Key, Store, MaxKeys, Name})` returns a `RateLimiter`. Its `Middleware()` limits every request it sees by a key, the client's address by default; its `Allow(ctx, key)` spends one request of any key and is what a Provider calls once it knows the user, and what a handler calls with a key it read from the body. Built 2026-11-01, milestone 3 wave 1 (`ratelimit.go`).

**The bucket.** A key may make `Burst` requests at once (`Limit` when zero) and earns one back every `Period/Limit`. The in-memory store keeps it as one number a key, the time the bucket will next be full (GCRA, the generic cell rate algorithm, which is this token bucket written so that it needs no second field and no timer). A request is allowed when, after adding one interval to the later of now and that time, the time is at most `Burst` intervals ahead of now. Time is the app's clock ([ADR 0027](0027-an-in-memory-entry-point-runs-the-engine-path.md)), so a test moves `bitetest.Clock` and nothing sleeps.

**The default key is `Request.ClientAddr`** ([ADR 0025](0025-no-proxy-is-trusted-by-default.md)), so a client behind a correctly listed balancer cannot rotate its bucket with `X-Forwarded-For`, and one that talks to the app directly cannot either. **An IPv6 client is keyed by its /64**: a host is usually given a whole /64, and keying by the address would give one host 2^64 buckets. A client with a /48 still has 65,536 keys; the bound on memory below holds against it, the limit per key does not. An address key is tagged with a byte no UTF-8 text starts with, so it never shares a bucket with a key that `Allow` or a `Key` function gives the same limiter. A `Key func(Request) string` replaces it (a tenant header, an API key's prefix); a key of `""` is a bucket like any other, shared by every request that has it, so a key function that fails closes rather than opens.

**What the client sees.** An allowed answer carries `RateLimit-Policy: "default";q=100;w=60` and `RateLimit: "default";r=57;t=3`, the structured fields of the IETF draft `draft-ietf-httpapi-ratelimit-headers` (remaining requests, seconds until the bucket is full). A refused request is **429 problem+json** ([ADR 0012](0012-client-errors-are-400-problem-json.md)) with `Retry-After` in whole seconds, rounded up, and the same two headers with `r=0`; it goes no further, so the handler and its Providers never run. The `Name` (`default`) tells two limiters apart in the headers.

**How it composes with groups and Providers.** Middleware runs before any Provider ([ADR 0048](0048-groups-and-the-order-things-run-in.md)), so a middleware cannot key by the user. A limit by address goes on the app (`app.Use`, which also counts 404s, so a client scanning paths is limited) or on a group. **A limit per user is written in the Provider of the user**: it authenticates, then calls `perUser.Allow(ctx, user.ID)` and returns its error, which is the 429 with its headers thanks to `StatusError.WithHeader` ([ADR 0054](0054-auth-providers-parse-the-credential-and-the-application-verifies-it.md)). Every route that asks for the user is then limited per user, and a route that does not ask for the user is not, which is the same coverage the Provider's Registration check already proves. Several limiters stack: an address limit on the app against floods, a per-user limit in the Provider against one account's overuse, each with its own `Name`. **A limit by a key in the body is written in the handler** (decided 2026-11-04, from an application that limits sign-in per email): only the handler reads the body, so it calls `perEmail.Allow(ctx, in.Body.Email)` and returns its error. `Allow` takes the request's context and no `Request`: the bucket is measured on the app's clock, which the request's context carries (`bites.Now(ctx)`, the clock a test moves with `WithClock`), and on any other context it is the real clock, so a call from a background job works too. The context holds the clock through the pointer it already had to the app's logger, so the `Ctx` keeps its size and the request its allocations.

**The in-memory store is bounded.** `MaxKeys` keys (100,000 by default) in 64 shards, each with its own lock and an equal share. When a new key arrives at a full shard, the shard is swept once: **every key whose bucket is full again is dropped**, which loses nothing, since a full bucket is what a new key gets; when that frees less than an eighth of the shard (a client rotating keys faster than they refill), keys are dropped in the map's own random order until an eighth is free. A sweep is one pass over a shard and frees at least an eighth of it, so it runs at most once every `cap/8` new keys: **a constant cost a new key, amortized, and none for a key already held**. Memory is 50 B a key measured (49 B for IPv4, 50 B for the /64 of IPv6, the heap before and after 100,000 keys, `TestTheMemoryStoreHoldsAKeyInAboutFiftyBytes`, with a ceiling of 64 B), so the default bound is about 5 MB. `TestAClientRotatingKeysNeverGrowsTheMemoryStorePastMaxKeys` sends 100,000 keys through a store of 512 and finds 512 held; `TestEvictionDropsTheKeysWhoseBucketIsFullBeforeAKeyThatIsStillLimited` holds the order.

**A shared store** is the interface `RateLimitStore` with one method, `Take(ctx, key, now, burst, interval) (RateLimitDecision, error)`, atomic for a key, so instances behind one balancer share their buckets. **The stores that exist:** the in-memory one of the limiter (per process, the default), and the module `pgratelimit` (a Postgres row of GCRA a key, one statement a Take, [ADR 0085](0085-a-postgres-rate-limit-store-is-a-module.md)); a Redis script is a module when an application asks, and any store is held to this paragraph by `bitetest.TestRateLimitStore` ([ADR 0086](0086-a-store-is-held-to-its-interface-by-a-conformance-suite-in-bitetest.md)). The store is not told which limiter calls it, so two limiters that share a store share a key's bucket: each gets a store of its own (for `pgratelimit`, its own `Scope`). The key it is given is a string: the address, or the `/64` prefix for IPv6. **A store's error is the answer**, a 500: the limiter fails closed, and an application that prefers to fail open writes a store that swallows its error and allows, a decision about its own risk that the core does not take for it.

**What it costs.** Allocations: **0** with the in-memory store for a key it holds, the typed POST measured 2 (`TestTheSecurityMiddlewareAndProvidersCostWhatTheirADRsSay`): the address key is built on the stack and looked up without a conversion, and the `RateLimit` value is written in the request's slab, which `serveChain` makes 64 bytes larger for each `RateLimiter` in the request's chain, counted at Registration (`slabRoom`; `RequestID` adds 16 the same way), memory a request and no allocation; a route whose chain has no `RateLimiter` reserves nothing for it. A new key costs its map entry (two small allocations); a refused request pays for its problem+json and its headers, not budgeted, like any client error ([ADR 0003](0003-the-trade-budget.md)). With a shared store, the key string and whatever the store does. Throughput and p99 are not measured yet; they wait for the serial run of wave 2 (one lock a request on a shard, a claim of tens of nanoseconds). Memory per idle connection: none.

**Refusals at construction** (rows of `refusal_test.go`): `Limit` of zero or less; a `Period` under a second or not whole seconds (the headers count seconds); more than one request a nanosecond; a negative `Burst`; a bucket that takes more than ten years to refill (its length in nanoseconds is added to a Unix time, and ten years keeps the sum far from overflowing); a negative `MaxKeys`; `MaxKeys` given with a `Store`; a `Name` that is not up to 16 letters, digits, `-` or `_` (it is written inside a quoted string). **What cannot be caught before the first request:** a key function that returns the same key for every client, and a limiter put on a route that its Provider's `Allow` also limits, which counts a request twice.

**Scenarios it was put against.**

- _The reference workload_: `app.Use(ip.Middleware())` at 600 a minute against floods, and a per-user 60 a minute on writes in the user's Provider. A user behind a corporate NAT shares the address bucket with colleagues but has a bucket of their own for writes.
- _A hostile client rotating keys_: from IPv6, each new address in its /64 is the same key; with a key function it controls (a header), the store holds at most `MaxKeys` and every legitimate key whose bucket is full is dropped first; what is lost is the state of keys still limited, which then start afresh. Rotating keys never grows memory.
- _A hostile client behind the app's balancer_ sending `X-Forwarded-For`: the rightmost untrusted element is the key ([ADR 0025](0025-no-proxy-is-trusted-by-default.md), `TestAClientCannotRotateItsBucketWithAForwardedForHeader`).
- _A stale CDN list_: every client behind one edge shares the edge's bucket; coarse, and no client chooses its bucket.
- _Three instances behind a balancer, in-memory stores_: each instance limits on its own, so a client gets up to three times the limit when its requests are spread; a shared store is the answer (`pgratelimit` for the reference deployment of one binary and Postgres), and the guide says so.
- _Redis or Postgres down with a shared store_: every limited request is a 500 until the application's store fails open.

**What it fails at.** Under a flood of new keys the eviction of an eighth by random order drops keys that were still limited, so a heavy client whose key is evicted gets a full bucket again; the bound on memory is bought with that. The headers follow a draft whose field names have changed between versions; a client written against the older `RateLimit-Limit` and `RateLimit-Remaining` does not read them. A limit per user costs the Provider a call even on a route whose handler is cheap. The in-memory store is per process. `Period` must be whole seconds, so a limit like 5 a half-second is written as 10 a second with a burst of 5.

**What was rejected.** A fixed window counter: half the cost in memory, but a client gets twice the limit across a window boundary, and the reset time is the same for everyone, which synchronises retries. A sliding log: exact, and its memory grows with the limit. An LRU list for eviction: exact recency, at the price of a list node and a move on every request, a cost paid by every allowed request to serve the rare full shard; dropping full buckets first loses nothing and needs no bookkeeping. Refusing new keys when the store is full: a client rotating keys would lock out every new legitimate client, a denial of service by design. A per-user limit as middleware reading the context: it runs before the user is known ([ADR 0048](0048-groups-and-the-order-things-run-in.md)). Failing open on a store error as the default: an outage of the store would remove every limit without a word. Keying an IPv6 client by its full address (one host, endless buckets) or by its /48 (a whole site in one bucket). `Allow(ctx, req, key)`, the first shape: the `Request` was there only for the clock, and a handler has no `Request`, so a limit by a body field needed a Provider that handed the `Request` to the handler (an application wrote one, a `Caller`). A `Request` as an Input field the framework fills, so a handler could pass it on: it would let every handler read any header past its Input, the contract the API document is built from ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)). A `Clock` in `RateLimitOptions`: a second place to state the clock, which a test would have to keep in step with the app's. The room for the `RateLimit` header reserved in the slab of every request that had middleware, the rule until 2026-11-05: 64 B, and 16 more for `RequestID`, on routes that had neither, which raised a typed POST from 304 to 385 B a request; the live heap is about 1 MB, so the collector ran in proportion to those bytes (98 cycles a second to 140) and one pass-through middleware cost GET p99 +13% instead of +3% ([`docs/research/middleware-p99/`](../research/middleware-p99/report.md)).
