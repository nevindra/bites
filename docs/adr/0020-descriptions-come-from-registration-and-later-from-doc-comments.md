# API descriptions come from registration options now and from doc comments later

The OpenAPI 3.1 document is described at Registration, from the types, and written once when the app starts serving (below): paths, parameters, schemas and statuses need nothing else. Prose cannot come from types, Go doc comments are not available at run time, and tags are refused ([ADR 0011](0011-one-naming-policy-for-wire-names.md)). So prose comes from two places, built in this order:

1. **Now:** options at Registration (`app.Get(path, h, Summary("…"), Description("…"), Tag("…"))`) for an operation, and an optional method on a type, `Descriptions() map[string]string`, that returns its field descriptions by Go field name, checked at Registration against the type's fields so a description cannot outlive its field.
2. **Built (2026-11-01, milestone 3), [ADR 0072](0072-descriptions-are-generated-from-doc-comments-by-bites-doc.md):** `bites-doc`, a `go generate` tool that reads the doc comments of the fields and writes the same `Descriptions` methods, so a project that adopts it writes prose once, in the comment where Go programmers already write it. It describes fields only; the prose of an operation stays in the `Summary`, `Description` and `Tag` options. Whether an operation is deprecated is a flag of the same kind: `Deprecated()` sets `"deprecated": true` on a route's operation, or on every operation of a group as `Tag` does, and `RouteInfo.Deprecated` tells a `UseEach` function, which adds the `Deprecation` and `Sunset` headers if the application wants them; a route the document leaves out accepts it, as it accepts `Tag`.

**The document is a route record kept at Registration and built once at start.** Every typed route leaves a record when it is registered: its operation (parameters, request body, responses, tags), built from the Input plan, the output plan and the types the route was compiled from, with references to schemas not yet named. So a type the document cannot describe, and a description that names a missing field, are Registration panics naming the route and the line, like any other mistake ([ADR 0007](0007-mistakes-are-refused-at-registration.md)). The names of the component schemas can only be decided once every type is known ([`internal/openapi`](../../internal/openapi/names.go)), so the references are resolved, and the document written as JSON, once, when the app starts serving; a request for it copies those bytes into the response. Nothing about the document runs per request, so it spends none of the four axes of [ADR 0003](0003-the-trade-budget.md) (the plain typed JSON request still costs 2 allocations). A mistake that only the whole set of types shows (two different types with one name and one package path, which no stable component name can tell apart) panics at start, naming the line that asked for the document.

**It is exposed by `app.OpenAPI(path, Info{Title, Version, Description})`.** It registers `GET path` (and so HEAD) serving the bytes as `application/json`, once per app, with a path that starts with a slash and has no wildcard, and a Title and a Version, which OpenAPI requires. It is a method that registers a route, and not an option of `New`, so that a conflict with a route of the application is raised in order, at the line that registered the second, and not before any route exists. It is opt-in: an API description is a decision about what to publish, so nothing is served at a default path. `Info.Servers` says where the API is served, written as the document's `servers`; it is configuration and never read from a request, because the document is the same bytes for every request ([ADR 0025](0025-no-proxy-is-trusted-by-default.md), decided 2026-11-02). **Considered:** a `WithOpenAPI` option (a conflict would surface in `New`, away from the routes); serving `/openapi.json` by default (publishes the API unasked; [ADR 0024](0024-limits-are-on-by-default.md) is about limits, which protect the server, and this exposes it); building on the first request (the first request pays, and a mistake appears at run time).

**What is described.** Each section of the Input: `Path`, `Query`, `Header` and `Cookie` fields are parameters (a list is an array, an `Opt` is not required, a path parameter always is, a constraint type states its bounds, [ADR 0021](0021-validation-is-a-method-and-a-few-constraint-types.md)); a field a Provider fills is not a parameter and not a body ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)). The Body by the way its type is read ([ADR 0044](0044-the-body-type-decides-how-a-body-is-read.md)): a struct, slice or map as `application/json`; `Raw[T]` as the JSON of `T`; `Form[T]` as `application/x-www-form-urlencoded` with the same properties and rules as the JSON of `T`; `[]byte` as `*/*` with no schema; `Multipart[T]` as `multipart/form-data` with the object schema of `T`, a file `{"type": "string", "format": "binary"}` (a list of files an array of those and not required, since it may be empty), an `encoding` entry `{"contentType": "image/png, image/jpeg"}` for each file field whose type has `Accept`, and the `MaxSize` of a file in its field's `description`, because OpenAPI 3.1 has no keyword for the bytes of a binary string (the schema marks a file by the type's own mark, `Options.Files`, since a file has no JSON form); a `Submitted[T]` with a file field is the same; `Upload` as `multipart/form-data` with `{"type": "object"}`, because the parts are the handler's to read. A route that accepts unknown members is described with its own request mode. The success responses by the output type ([ADR 0013](0013-other-statuses-are-wrapper-types.md), [ADR 0043](0043-cookies-and-bodies-other-than-json.md), [ADR 0030](0030-streaming-is-a-return-type.md)): a plain value is a 200 JSON; `OK`, `Created` (with a `Location` header), `Accepted`, `NoContent`, `NotModified` and `SeeOther` (with `Location`) by their status; a `Redirect` as its four statuses; `Text` as `text/plain`; `Bytes`, `File` and `Stream` as `*/*` with no schema, because their content type is a value of the handler's; `SSE` as `text/event-stream`. A route that returns an interface gets the responses of every type it declared with `Returns` ([ADR 0013](0013-other-statuses-are-wrapper-types.md)). A header or cookie that a handler sets at run time is not in the document, as [ADR 0013](0013-other-statuses-are-wrapper-types.md) already says.

**The error answers are `components.responses`, shared.** [ADR 0012](0012-client-errors-are-400-problem-json.md)'s two shapes are `InvalidInput` (the 400, with its `errors` list and `truncated`) and `Error` (every other problem+json answer, with the members `title`, `status`, `detail` and `request_id`; the extra members a `StatusError` can carry are allowed). Each operation refers to `InvalidInput` for 400 when its Input has a section or a `Validate`, to `Error` for 413 and 415 when it has a body that is not `[]byte`, and to `Error` as its `default`, because the statuses a handler's error may carry come from the error and not from the types ([ADR 0049](0049-errors-are-found-with-errors-as-and-timeouts-wait.md)). They are not entries of `components.schemas`, so a type of the application called `Error` cannot collide with them.

**Security, and the answers of the security middleware.** A route that runs a `BearerAuth`, `BasicAuth` or `APIKeyAuth` Provider has its scheme in `components.securitySchemes` and its operation's `security`, with a 401 that refers to `Unauthorized`; a `RateLimiter`'s middleware adds a 429 (`TooManyRequests`) and `CSRF` a 403 to state-changing methods ([ADR 0069](0069-the-api-document-states-what-a-routes-providers-and-middleware-ask-and-answer-and-a-route-can-be-left-out.md)). `Unauthorized` and `TooManyRequests` join `components.responses` only when an operation refers to one.

**What is left out, and why.** A route given `Undocumented()`, on itself or its group, is left out with its types; `stdhttp`'s mounts and `docsui`'s page carry it ([ADR 0069](0069-the-api-document-states-what-a-routes-providers-and-middleware-ask-and-answer-and-a-route-can-be-left-out.md)). A WebSocket route is in `paths` as the `get` its handshake is (decided 2026-11-04): its parameters from the Input and its Providers, its `security`, a `101` (the upgrade), `400` (a malformed handshake, or the Input's located 400), `403` (an Origin the route does not allow) and `426` (a WebSocket version it does not speak) as the handshake's refusals ([ADR 0046](0046-websocket-origins-and-inbound-limits.md)), and its messages under the extension `x-websocket`, `clientMessage` (the Inbox's type) and `serverMessage` (the Socket's) as schemas, a `[]byte` one as a binary string, since OpenAPI 3.1 has no keyword for them. `Summary`, `Description`, `OperationID`, `Tag`, `Deprecated`, `ErrorStatuses` and `Undocumented` apply to it as to any route; `Returns`, `MediaType` and `SendsHeader` are refused, since a WebSocket handler returns an Inbox and answers 101 with no body. A route on a method OpenAPI 3.1 has no name for (`Handle("PURGE", ...)`) is left out. A `Summary` or `Description` on a group is refused: one line on every operation of a group would describe none of them; `Tag` on a group is the way to say what the routes of a group are, and a route's own tags follow the groups'. Two routes the document would hold as the same path (`/u/{id}` and `/u/{uid}`, which OpenAPI counts as one) or as the same operation (`/x/` and `/x/{$}`) are refused at Registration, because the document could not state both.

**The names of the component schemas are decided when the document is built, from the set of types, and the application may choose them with `Info.SchemaName`.** By default a component is named by its Go type (a generic instance has its type arguments appended, `Page[users.User]` is `Page_User`, and anything outside `A-Z a-z 0-9 . - _` is written `_`); two different types with one name are told apart by the last element of their package path (`users.User`, `billing.User`), then by the whole path with dots, and two types still alike (one type declared inside two functions) are refused; a type used in more than one mode whose schemas differ gets `.Request`, `.RequestOpen` or `.Response` after its name. A frontend whose generated types already have names (`CommitmentListItem` for `commitment.ListItem`, `DealListItem` for `deal.ListItem`) cannot use the dotted spelling, so `Info.SchemaName func(pkgPath, name string) string` is called once for each type that becomes a component, in a fixed order, with its package path and the default short name (the second step above, before any package qualifier), and returns the component name, or `""` to keep the default rules for that type. What it returns is used for that type whether or not the default would collide, the mode suffixes are added after it, and the types it left alone are named by the default rules among themselves (so a name that was `users.User` because of a collision is `User` once the other `User` is named). It is a field of `Info`, and not a route option, because a component is shared by every route that uses its type, so a name chosen on one route would be a claim about the others; and not an option of `New`, because the document is given where `OpenAPI` is called and the namer belongs to it. It is refused when the document is built, which is when the whole set of types is known, as the collision above is, naming the line that asked for the document: a name outside `A-Z a-z 0-9 . - _`, one name given to two types (both are named), and a name that another type has by default (both are named), because a name is either chosen for every type that needs one or decided by the rules, and a silent merge would give one component two schemas. A namer that gives a name per call, from its arguments alone, is the contract: it is not told the mode, so a type's `.Request` and `.Response` stay together. Nothing here runs per request.

**Every operation has an `operationId`, made from its method and path unless `OperationID(id)` gives one.** Built 2026-11-02 (`openapi.go`, `openapi_test.go`, `refusal_test.go`, the goldens). A client generator (openapi-generator, oapi-codegen) names the method that calls an operation by its id, so the id must be unique, a usable name, and stable while the operation stays what it is. The made id is the method in lower case, then each literal segment of the path as words with a capital each (a character other than a letter or a digit separates words), then each wildcard as `By` and its name: `GET /users/{id}` is `getUsersById`, `GET /users/{id}/orders` is `getUsersByIdOrders`, `GET /` is `getRoot`. A given id must start with a letter and hold only letters, digits, `_`, `.` and `-`, which every generator turns into a method name; a space or a slash it would turn into something else. Two operations whose ids differ only in case or in `_`, `.` and `-` (`listUsers` and `list_users`) are refused at the second route's line, naming the first and whether its id was given or made, since a generator makes one method name of both; the fix is `OperationID` on one of them. `OperationID` is refused on a group (one id cannot name every operation of it), and on an `Undocumented` route, a WebSocket route and `Static`, where it would be dropped. Nothing runs per request: none of the four axes moves.

_Scenarios it was put against._ The reference workload: `getUsers`, `postUsers`, `getUsersById`, `deleteUsersById`, and a generated TypeScript client whose methods read as the paths do. A refactor that renames handlers, or moves them onto a `Users` struct as methods: no id changes, so no client breaks. Handlers that are one generic function instantiated for many routes (`docEcho[In, Out]` in the tests) or closures: each route still has its own id. `GET /x` and `GET /x/` (a subtree), or `GET /users/{id}` and `GET /users/by-id`: both make one id, and the second is refused with the fix. A team that wants `getUser` rather than `getUsersById`: `OperationID("getUser")`.

_What it fails at._ A made id is long for a deep path (`getOrgsByOrgReposByRepoIssuesByNumber`) and reads as the path, not as what the operation does; `OperationID` is the remedy, one route at a time. The made id changes when the path does, which is a change of the API anyway, but a client's method name changes with it. The uniqueness refusal applies to every typed route registered, also in an app that never calls `OpenAPI`, as the check of two paths of one shape already does, so two routes whose paths differ only in a trailing slash need an `OperationID` though no document is served.

_What was rejected._ The handler's function name through `runtime.FuncForPC`: a generic handler instantiated for many routes, and every closure, have names a generator cannot use (`docEcho[...]`, `main.main.func3`); methods of several resource types collide (`(*Users).Get`, `(*Orders).Get`); and renaming a function in a refactor would rename a client's method, which is the API changing without the API changing. Making a colliding id unique with a suffix (`getX2`): it depends on the order the routes are registered in, so moving one line renames a client's method without a word, the class of mistake [ADR 0007](0007-mistakes-are-refused-at-registration.md) refuses. Requiring `OperationID` on every route: a hundred lines of names that the method and path already give. The position this ADR held until 2026-11-02, no `operationId` at all: a generator then has to name each method itself, each generator its own way (a claim from their documentation, not a run), so one document gave different clients different names; an id in the document gives them all the same one.

**A section made of embedded structs describes each one by its own method** (decided 2026-11-03). `Query struct{ FilterQuery; Paging }` is the usual way to share a filter or a page between routes, and when both embedded types have a `Descriptions` method Go promotes neither (the name is ambiguous), so the section had none. Each embedded struct's own `Descriptions` now describes its own fields, found recursively through nested embedding. The section struct's own method, when it declares one, is the route's view of the whole: it may describe an embedded field and wins over the embedded type's entry for the same field. A method that is only promoted (one embedded type has it, the section has none of its own) is not taken for the section's own, so it is not checked against fields it was never written for. The two are told apart by what the method returns: a map equal to the one an embedded struct's method returns is read as that struct's. A section that declares a method returning exactly that map gets the same entries either way, and every key it could name is a field of the section too, so the reading cannot change an answer; asking the runtime whether the method is a compiler-made wrapper (its file being `<autogenerated>` through `runtime.FuncForPC`) was rejected as resting on a detail of the toolchain no specification promises. Each type's keys are checked against that type's own fields: an embedded type naming a field it lacks is a Registration panic naming the embedded type. Two embedded types cannot describe one field, because a field of one name in both is two parameters with one wire name, which the compiler already refuses. A JSON body, a response and any struct inside one follow the same rule (decided the same day): each struct the codec inlines (embedded by value, with no JSON name of its own and no JSON methods, asked through `jsoncodec.Inlined` so the document and the codec cannot disagree about which ones) describes its own fields, and the outer struct's own method wins. Without it a body made of two described structs was described by neither, the same silent loss.

**An anonymous `Body` struct is a component named after its Input** (decided 2026-11-03). `Body struct{ Name string }` was inlined into the operation, so a client generated from the document had no type to import and a route that later named the type changed the client's code. The struct now becomes a component called after the Input type with `Body` appended (`CreateUser`'s is `CreateUserBody`), passed through `Info.SchemaName` like any other component, and the `Form[...]` and `Raw[...]` forms are named the same way. Two Inputs that write the same anonymous struct hold one Go type, and that body is written in place in each of their operations, where a client generator names it after the operation (revised 2026-11-04); an Input that is itself anonymous has nothing to be named after and stays inlined. A collision with a type of the same name is the existing duplicate-name panic at start. Responses with an anonymous struct and anonymous structs nested in a type stay inline. What was rejected for the shared body: the alphabetically first Input's name, which held until the second agent usability run read an update route's body as `CreateRoomBody` and took it for a mistake; and a component for each Input with the same schema, which would need the naming of component aliases through `Info.SchemaName` and its collision rules for a case an application avoids by naming the type.

**The document's bytes can be taken without serving it** (decided 2026-11-03). `app.OpenAPIDocument()` returns the JSON the document route serves, built from the routes registered so far, or an error when `OpenAPI` was never called or the document cannot be built. A project that checks its API document into git, or generates a client in a build step, calls it from a test or a `go generate` program. It does not start the app or freeze the routes, it returns a copy, and the bytes equal what the route serves. No YAML encoder is added ([ADR 0006](0006-no-third-party-dependency-in-the-core.md)): a project that wants YAML converts the JSON.

**Field descriptions are checked against the wire.** A struct type with a `Descriptions` method has each name checked against the fields the codec reads and writes for it (so a field left out with `json:"-"`, or a name with a typo, is a Registration panic listing the fields that exist), in a body, a response and the nested types they hold, and against the fields of a `Path`, `Query`, `Header` or `Cookie` section. The description lands on the property (or the parameter); a property that is a `$ref` carries it beside the reference, which OpenAPI 3.1 allows. A text type that the JSON generator cannot describe is documented as a string, which is what it is on the wire. **What it fails at:** a description is in a method away from the field it describes, which is what the generator of ADR 0072 removes; and a nested type's `Descriptions` is checked only where the document reaches it.

**An example, a header's own description and schema, and a deprecated field** (decided 2026-11-05). Three things a generated client and a reader of the document ask for, each said one way, in the place where the thing already lives.

- **An example is a method of the type: `func (T) Example() T`.** A named type (a body, a field's type, a parameter's type, a header's type) may declare it, on `T` or on `*T`. It is read once at Registration on a zero receiver, written with the framework's own encoder, and read back through the decoder the type is read with (the codec's, in which every rule of the type is checked: `Length`, `Range`, `Items`, `Pattern`, `Format`, `Check`, a required member that is missing), so the document cannot carry an example the type itself would answer 400 for. A value its type refuses, a panic, a value the codec cannot write, and a method named `Example` that returns another type are Registration panics naming the type and the rule (the rows `Example that its own type refuses in a Body`, `... in a Query`, `Example that panics` and `Example that returns another type` of the refusal table). The JSON is written beside the type's schema as `examples: [value]`, the 2020-12 keyword of OpenAPI 3.1 (`example` is deprecated in a 3.1 schema, and the media type's `examples` is a map of named, separately described values, a shape this feature does not need), so a type that is a component carries it once, in the component, and every property, parameter and body that refers to it shows it. A response is read back by a plan in which nothing is required (an `omitempty` member may be left out) but every rule of a type still applies; a type the decoder cannot read is checked by writing it only. A struct's `Example` states the value of every field in it, `Opt` and plain `string` fields included, since a field of a common type has no type of its own to carry one. **What it fails at:** one example for a type, so a route that wants another example of a shared type cannot have it (use a type of its own); an example of a type is asked of every mode of it, so it must be valid for the request and the response; and a type of a multipart form has no JSON example.
- **A response header is stated by `SendsHeader[T](name, description)`, which replaces `SendsHeaders(names ...string)`.** `T` is the Go type of the value and gives the schema as it does for a `Query` field (a number is `integer`, a named type states its `Length`, `Range`, `Pattern`, `Format` and its `Example`), and the description is required, since a header that says nothing is what the old option already stated. It is still stated and not checked, and still optional on every success status; a handler still sends a header only through the `Header` of the value it returns ([ADR 0009](0009-the-response-comes-only-from-the-return-value.md)), so no second way to send one exists. Where the framework already states the header (a `File`'s `ETag`), the route's description replaces it. A `T` that is not text (a struct, a slice, a map) is refused when the document is built, and a name given twice, also by a group and its route, is refused, because two descriptions of one header would leave the reader to guess which holds. **What was rejected:** keeping `SendsHeaders` beside the typed one, which is two spellings of one fact (ADR 0077); a `Header` struct with `Name`, `Description` and `Schema` fields, which is a free JSON blob no type checks and which an agent fills in wrongly; and a `required` flag, which a handler that always sets the header says in the description (`SetsLocation` states the one header whose presence the framework knows).
- **A deprecated field is named by a method of its struct: `DeprecatedFields() []string`.** The strings are Go field names, exactly as `Descriptions` keys are, and it is read in the same places: a section's struct (`Path`, `Query`, `Header`, `Cookie`, where the field is a parameter and gets `deprecated: true`), a body type and a response type, and the types nested in them, with each embedded struct's own method describing its own fields and the outer struct's winning. A name that is not a field of the struct is a Registration panic with the fields it has, as a stale description is, so a deprecation cannot outlive its field (rows `DeprecatedFields naming a field a Body does not have` and `... a Query does not have`). The route's `Deprecated()` already marks an operation. **Considered:** a route option naming a wire location (`DeprecatedParam("query.sort")`), which is a string checked only by a lookup at Registration and says on the route what is a fact of the type; a marker type (`Deprecated[string]`), which changes the field's Go type and so every use of it in a handler; and a tag, refused by [ADR 0011](0011-one-naming-policy-for-wire-names.md). **What it fails at:** the deprecation is on the struct, not on a route, so two routes sharing a section struct deprecate the same field; a route that needs its own view embeds the shared struct in a section of its own, whose method wins. A deprecated field is still accepted and still sent: the document states it and nothing is checked or refused.

These are read at Registration, in the document's own build; nothing runs per request, so none of the four axes of [ADR 0003](0003-the-trade-budget.md) moves (the typed JSON request is still 2 allocations, held by its test).

**Evidence.** The documents the generator produces for a representative app are kept as goldens in `testdata/openapi/` and validated whole, with every schema in them, against the official OAS 3.1 schemas in [`docs/research/openapi-valid/`](../research/openapi-valid/) (`go test` there; its own module, because the validator is a third-party dependency and the core imports the standard library only).

**Considered:** a naming hook per route or per type (a method such as `SchemaName() string`): a method on a type would be the type naming itself in a document it does not know the others of, and could not rename a type from a package the application does not own. A `doc:"…"` tag on every field, as Huma does. Rejected because it is the tag ADR 0011 refuses, and a tag string is checked by nobody. The generator was deferred, not rejected: (1) was designed as the structure it fills, and it is built.

**Bodies that are not a JSON schema.** The generator's `Body` hook returns a body description (a schema and a media type, or "raw") instead of mapping a type to a type, because no type has a binary schema. A `[]byte` body root is documented as binary: `content: {"*/*": {}}` for a request, since OpenAPI 3.1 says a binary body needs no schema (`format: binary` is the 3.0 form, which 3.1 replaced with `contentMediaType`), and if a schema is wanted, `{"type": "string", "contentMediaType": "application/octet-stream"}`. A `[]byte` field inside a JSON object stays base64, as the codec writes it. `Raw[T]` stays JSON: it requires `application/json`, decodes into `T` and keeps the bytes beside it ([ADR 0044](0044-the-body-type-decides-how-a-body-is-read.md)), so describing it as `application/octet-stream` would be wrong and would make generated clients send it unvalidated. There is no octet-stream response to describe yet: a handler returning a `[]byte` gets a JSON base64 string today, until a raw-bytes response type is decided with `File`. Measured: `Schema([]byte, Request)` gave `{"contentEncoding":"base64","type":"string"}` for the body root, which is right for a field and wrong for a body. Evidence: [`docs/research/decisions-bodies/`](../research/decisions-bodies/report.md), section "OpenAPI". **What it fails at:** the contract change touches `internal/openapi` and its 12 goldens.

_What was rejected (WebSocket routes, 2026-11-04)._ Leaving them out of `paths`, the rule until the fifth agent usability run, because OpenAPI 3.1 cannot describe a protocol upgrade or its messages and AsyncAPI is the format for them. The run's browser-facing WebSocket authenticated with a ticket in the query, which the document stated on its event-stream route and nowhere for the WebSocket, so the agent wrote it in `Info.Description` where no generator reads it. The handshake is an HTTP `GET` with parameters, credentials and refusals that OpenAPI describes, and only the messages need an extension; an AsyncAPI document beside the OpenAPI one stays possible for an application that wants one, and is not built.
