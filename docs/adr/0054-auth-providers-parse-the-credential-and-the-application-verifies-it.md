# Auth Providers parse the credential, and the application verifies it

`BearerAuth`, `BasicAuth` and `APIKeyAuth` each take the application's verification function and return a Provider ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)) of the application's own type, given to `Provide` on the app, a group or a route:

```go
app.Provide(bites.BearerAuth(func(ctx context.Context, token string) (User, error) { ... }))
```

Built 2026-11-01, milestone 3 wave 1 (`auth.go`). The framework reads the credential out of the request, answers a missing or malformed one, and writes the challenge; the application decides whether a credential is good and what it stands for. A route whose Input has a `User` field and no Provider for it is refused at Registration, as for any Provider, which is the mistake of the context-key pattern this design exists to refuse.

**What the framework parses**, by the RFCs: the scheme of `Authorization` is matched without regard to case (RFC 9110 11.1) and followed by one or more spaces; a Bearer token must be a `b64token` (RFC 6750 2.1); Basic credentials are base64 of `user-id:password`, split at the first colon, and must be UTF-8 (`charset="UTF-8"`, RFC 7617 2.1); an API key is the value of its own header (`X-API-Key` by default), with no space or control character. A credential is read from a header only: RFC 6750's query parameter and a key in the query are not read, because a query is written in access logs, browser history and `Referer`.

**What each answer is.** No credential of the scheme, or another scheme, is **401** with the challenge: `Bearer realm="api"` (no error code, RFC 6750 3.1), `Basic realm="api", charset="UTF-8"`, `APIKey realm="api", header="X-API-Key"`. A malformed one (no token, a character a token cannot have, two `Authorization` headers, Basic that is not base64 or has no colon) is **400**, with `error="invalid_request"` for Bearer. The verification function's error decides the rest:

- an error that wraps `ErrInvalidCredentials` (unknown, expired, revoked, wrong signature) is **401** with `error="invalid_token"` for Bearer;
- a `*StatusError` is the answer as it is, so a token without the scope is a 403; a 401 among them gets the challenge, which RFC 9110 requires of every 401;
- **any other error is a 500**: the verifier could not decide (the database is down). Making every error a 401 would tell every client its credential is wrong during an outage, and a client that discards a token on 401 would log every user out.

The detail of a 401 is a fixed sentence, never the verifier's text, which may name the token.

**A Provider's error can carry headers.** A Provider answers only with an error, so the challenge needed a way onto a problem+json answer: `StatusError.WithHeader(name, value)` returns a copy whose answer carries the header ([ADR 0049](0049-errors-are-found-with-errors-as-and-timeouts-wait.md), edited in place). Rate limiting uses it for `Retry-After` ([ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md)).

**Secrets.** The framework compares no secret in these Providers: a Bearer token and an API key are looked up by the verifier, best by a hash of a long random key, so the stored values are not secrets and no byte-by-byte comparison runs; a Basic password is compared by the verifier, and the documentation says to compare hashes with `crypto/subtle.ConstantTimeCompare`. Where the framework does compare a secret, the CSRF token ([ADR 0057](0057-csrf-trusts-the-browsers-origin-and-falls-back-to-a-double-submit-token.md)), it does so in constant time. **No credential is logged**: the Providers log nothing, the access log writes no header, and no answer carries the credential, held by `TestNoCredentialIsWrittenInTheLogOrInAnyAnswer`, which sends tokens that fail, that make the verifier fail, and that are malformed, behind `RequestID` and `AccessLog`, and searches the log and every answer for them.

**A JWT plugs in as a verification function.** The JWT module, `modules/jwt` ([ADR 0062](0062-jwt-verification-is-a-module-whose-key-fixes-the-algorithm.md), built in milestone 3 wave 2), is a verifier whose method `Verify(ctx, token string) (C, error)` wraps `ErrInvalidCredentials` for a bad signature, an expired token or a wrong audience, and returns a key source's failure (a JWKS endpoint down) unwrapped, so it is a 500; `BearerAuth(v.Verify)` is the whole integration. The core parses no token and holds no key.

**The API document states the scheme.** A route that runs a Provider these three constructors made has the scheme in the document's `securitySchemes` and its operation's `security`, with the 401 ([ADR 0069](0069-the-api-document-states-what-a-routes-providers-and-middleware-ask-and-answer-and-a-route-can-be-left-out.md)). Each constructor returns its Provider through a method that is never inlined, and the Provider's first statement answers a probe context, which is how Registration recognises them without calling a Provider the application wrote; the probe costs each request one type assertion and no allocation.

**Several credentials, an optional one, and a Provider of the application's own.** Built 2026-11-02 ([ADR 0069](0069-the-api-document-states-what-a-routes-providers-and-middleware-ask-and-answer-and-a-route-can-be-left-out.md)): `AnyAuth(BearerAuth(v), APIKeyAuth(k))` is one Provider that runs the first whose credential the request carries; an Input field `Opt[User]` is filled by the optional form of the `User` Provider, absent when no credential is sent and still a 401 for one that is not good; `CustomAuth(scheme, provider)` gives a Provider the application wrote the scheme it reads, so the document states it and `AnyAuth` and an `Opt` field can use it. The verifier stays the application's, and each answer above stays as it is.

**What it costs.** Allocations: **0** for a request whose credential verifies, Bearer and API key measured 2 for the typed POST (`TestTheSecurityMiddlewareAndProvidersCostWhatTheirADRsSay`): the token is a substring of the request's copy of the head ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)) and the value lives on the Provider's stack ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)). Basic decodes into the request's slab, from room left over when there is some (the room a `RequestID` or a `RateLimiter` in the chain did not use, [ADR 0003](0003-the-trade-budget.md)), and allocates its buffer otherwise, which on a route without those two is every request; it is not budgeted. A refused request pays for its problem+json, as any client error does ([ADR 0003](0003-the-trade-budget.md)). Throughput and p99 are not measured yet; they wait for the serial run of wave 2.

**Refusals at construction** (rows of `refusal_test.go`): a nil verification function; two options values; a `Realm` with a double quote, a backslash or a byte outside printable ASCII, which a quoted string cannot carry; `Header` given to `BearerAuth` or `BasicAuth`, which read `Authorization` as their RFCs say; an `APIKeyAuth` `Header` that is not a token, or is `Authorization` or `Cookie`, whose values are not a bare key. **What cannot be caught before the first request:** a verifier that returns a plain error for a bad credential (a 500 where a 401 was meant; the 500 is logged, so it is found at once), and Basic served over plain HTTP.

**Scenarios it was put against.**

- _The reference workload_ with JWTs: `BearerAuth(jwt.Verify)` on the API group, the user's id added with `AddLogAttrs` by the verifier's caller, a 401 with `error="invalid_token"` for an expired token, which an OAuth client library reads as "refresh".
- _A hostile client_ that sends a 300-byte garbage token, `Bearer` twice, a token with a quote, or no scheme: each is a 400 or a 401 with a fixed body, before the verifier runs for a malformed one, so a garbage token never reaches the database.
- _Postgres down_ while the verifier looks up an API key: a 500, logged, and the client keeps its key.
- _A token guessed byte by byte by timing_: nothing the framework does compares the token; a verifier that looks up a hash leaks nothing about the stored key.
- _A machine client with an API key_ behind the same app as browsers with sessions: `APIKeyAuth` on the `/v1` group and a session-based Provider on the pages group, each refused at Registration on a route that asks for its type outside its group.

**What it fails at.** The realm is the same for every route under one Provider. `WWW-Authenticate: APIKey` is not a registered scheme; it says where the key goes, which is all a client can use. A token in a cookie is not read (a session is [ADR 0056](0056-a-session-is-sealed-in-a-cookie-and-changed-by-returning-its-cookie.md)); a Provider that reads one is the application's, given to `CustomAuth`. A Provider the application writes around a verifier and does not give to `CustomAuth` is not recognised by the API document, so its routes have no `security` there ([ADR 0069](0069-the-api-document-states-what-a-routes-providers-and-middleware-ask-and-answer-and-a-route-can-be-left-out.md)). The positions this paragraph held until 2026-11-02, that an optional credential had no spelling and that several schemes on one route needed the application's own Provider trying both, were replaced by `Opt` fields and `AnyAuth` (above).

**What was rejected.** Auth as middleware that puts the user in the context, the common Go shape: a route registered outside the group then gets a nil user at request time, which a Provider refuses at Registration. A verification function returning `(T, bool, error)` with the boolean for "not valid": it is one more shape to learn, and a verifier that wraps a sentinel says why in its own error for its own log. Treating every verifier error as 401 (the outage above). Comparing a static list of API keys in the core with `subtle.ConstantTimeCompare`: it invites keys kept in source and compared in plain form, where a lookup by hash keeps no secret at all; an application with a fixed list writes the comparison in its verifier. Reading a Bearer token from the query, as RFC 6750 2.3 allows (logged everywhere).
