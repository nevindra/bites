# A WebSocket is served by message handlers, and user code never reads from the socket

The user-facing WebSocket API is a set of handlers the engine calls (`OnMessage`, `OnClose`) and a `Send` that never blocks. There is no `conn.Read()` for user code to loop on: the engine owns the read loop, which runs on a goroutine of the socket's while it has bytes to read and on none while it is idle ([ADR 0005](0005-our-own-http1-engine-with-a-goroutine-per-connection.md)).

**Why:** the one way to close the 2.5 to 2.8 times gap to an event loop on idle sockets is to stop holding a goroutine while a socket is idle ([`docs/research/ws-idle/`](../research/ws-idle/report.md)). An API with a user read loop would make that a breaking change for every WebSocket handler ever written, as it is for gorilla/websocket users; with handlers, it is a change inside the engine. The design is whole now and built in stages.

**A socket with no `OnMessage` only sends** (decided 2026-11-04): a message from its client closes it with 1003 and the reason `this socket takes no messages`, and such a route takes `struct{}` as its `Msg`. Until 2026-11-04 the engine dropped the message in silence, malformed or not, while `Inbox`'s doc said a malformed message closes with 1007; an agent building a send-only route met both the silence and the wrong doc in the usability test ([`docs/research/agent-usability/`](../research/agent-usability/report.md), row 6). Dropping it was rejected because the client believes it was heard; a named type for the unused `Msg` was rejected as a second way to say what `struct{}` says.

**Considered:** a `Read`/`Write` connection like gorilla's and coder's, which is more familiar and lets a handler keep its state in local variables. Rejected because it fixes the goroutine per socket into the API forever. State lives in the Inbox value the route returns ([ADR 0036](0036-websocket-routes-are-typed-like-http-routes.md)).

**What was rejected (the name):** calling the value a Session, or `Handlers[Msg]`. Session was renamed Inbox because `Handlers` collides with [ADR 0014](0014-services-are-plain-go-values.md)'s `Handlers` struct of route methods (`type Handlers struct{ db }` is a common Go habit, and a route function returning `Handlers[Msg]` reads as handlers returning handlers) and with `http.Handler`, and `Session` is what every web developer expects for a login session, which milestone 3 builds. Evidence: [`docs/research/decisions-middleware/`](../research/decisions-middleware/report.md), section "Session rename".

**Built.** The engine's read loop is the one that serves HTTP: the connection's goroutine waits on a one-byte read while idle, holding no pooled scratch, and after 100 ms of waiting the socket parks on the engine's poller and the goroutine ends, so an idle WebSocket holds no goroutine and no buffer; bytes give it a goroutine again ([ADR 0005](0005-our-own-http1-engine-with-a-goroutine-per-connection.md), [ADR 0039](0039-heartbeats-run-on-one-timer-wheel.md) for the measured number). This is the change the first paragraph kept possible: no handler changed for it. A WebSocket waits for bytes in one place, `conn.await` in `internal/engine/conn.go`, shared with HTTP; the frame reader is fed from the scratch and the handler runs on the same goroutine, which is why one socket's messages are in order and why a blocking `OnMessage` pauses only that socket. Nothing else reads from the connection.
