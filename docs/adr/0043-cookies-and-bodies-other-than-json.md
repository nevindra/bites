# Cookies are a section and a type with safe defaults, and bodies other than JSON are types

**Reading.** Cookies arrive in the `Cookie` section of an Input, decoded like any text ([ADR 0042](0042-text-values-are-decoded-by-type.md)).

**Writing.** A response sets cookies through the `Cookies` field every wrapper has ([ADR 0013](0013-other-statuses-are-wrapper-types.md)). The `Cookie` type defaults to `HttpOnly`, `Secure`, `SameSite=Lax` and `Path=/`; loosening any of them is written out. Browsers treat `localhost` as a secure context, so `Secure` does not get in the way of development over plain HTTP.

**`Text` and `Bytes`** are built. Both are the shape of the status wrappers of [ADR 0013](0013-other-statuses-are-wrapper-types.md): a 200 with `Body`, `Header` and `Cookies`; `Text` has a `string` body and `Bytes` a `[]byte` body and a `ContentType`. The body is copied into the response as it is, never encoded. A `Content-Type` in `Header` replaces the default, as it replaces the JSON one. The content type of a `Bytes` is a value of the handler's, so Registration cannot see it: an empty one, one that is not `type/subtype`, or one with a control character (a response split) is a 500, logged, per response. A status other than 200 for these bodies waits for a need.

**Bodies other than JSON** are output types of their own: `Text` (`text/plain; charset=utf-8`), `Bytes` (a content type and the bytes), and `File`. CSV and other bodies written over time are a `Stream` ([ADR 0030](0030-streaming-is-a-return-type.md)). There is no content negotiation: a typed value is always JSON.

**`File`** is a 200 whose body is a file, from an `os.Root` or an `fs.FS` (by `Name` inside it), or from `Open` or `Content` for a store or bytes in memory ([ADR 0064](0064-a-file-answers-its-own-conditional-and-range-requests.md)); exactly one of the four, none or several is a 500, logged. It is sent with `Content-Length`, `Last-Modified` (omitted for a zero time) and a content type: the `ContentType` field, else the extension's type, else `application/octet-stream`; a `Content-Type` in `Header` replaces them. `Header` and `Cookies` work as on `Text`. A `Name` that fails `fs.ValidPath` (a `..`, a leading slash, an empty element), a file that does not exist, one that is not a regular file (a directory, a device), and one an `os.Root` refuses (a symbolic link out of the directory) are the same 404 problem+json, so the answer does not say which files exist; any other failure to stat is a 500, logged. An `os.Root` refuses to leave its directory in the call itself (Go 1.24), and an `fs.FS` is only ever given a valid path, so a name from a client cannot name a file outside. HEAD, including the implicit one of a GET route, gets the head with the same `Content-Length` and no body, and opens nothing. Validators (`ETag`, `Last-Modified`), conditional requests (304, 412) and one `Range` (206, 416) are answered by every `File` ([ADR 0064](0064-a-file-answers-its-own-conditional-and-range-requests.md)), and a directory of files is served by `Static` ([ADR 0065](0065-static-files-are-a-route-with-twins-cache-rules-and-a-fallback-that-never-hides-a-404.md)).

**Downloads: an `Attachment` field on `File`, `Bytes` and `Stream`.** When it is not empty the answer carries `Content-Disposition: attachment` with the name written by `mime.FormatMediaType`, which quotes it and writes a name outside ASCII, a line break or invalid UTF-8 as `filename*` (RFC 2231), so no name can split the response. Only the part after the last `/` or `\` is used, so a path from a client or a database is given as it is; a name with nothing left (`dir/`, `.`, `..`) sends `attachment` alone. A `Content-Disposition` in `Header` replaces it, as a `Content-Type` there replaces `ContentType`. It is sent on a 200 and a 206 of a `File`, not on a 304. The header is built only for an answer that has the field set, so it costs a request that is not a download nothing.

**How a `File` is written** is the stream writer with a declared length, not the engine's write path for a buffered answer and not a stream of unknown size. The buffered path holds the body whole in the pooled response buffer, which a 2 GiB file cannot; the chunked stream has no `Content-Length`, which a download wants and a cache or a range later needs. So `Exchange.StreamSized(n)` marks the stream as sized: the head carries `Content-Length: n`, nothing is chunked, the writer's `ReadFrom` reads the file straight into the 64 KiB buffer (one copy, like `io.Copy` to a socket without `sendfile`), each 64 KiB write has its own write deadline as for any stream ([ADR 0030](0030-streaming-is-a-return-type.md)), and a function that writes more than `n` is refused while one that writes fewer closes the connection, as a cut stream does. The connection is kept (HTTP/1.1) when exactly `n` bytes were sent. The file is stat-ed when the answer is built, so a missing file is an ordinary 404 before anything is sent, and opened when the body is written, on the connection's goroutine after the middleware returned, so a response that is never written leaves nothing open. The size and time are those of the stat; a file whose size differs when it is opened is a 500, and one that shrinks while it is sent closes the connection after the bytes that existed. Middleware sees a `File` as a response with `Streaming()` true and `Size()` 0. The cost is in [ADR 0003](0003-the-trade-budget.md).

**What was rejected (File):** reading the file into the response buffer and writing it as a `Bytes` (memory proportional to the file, for each concurrent download); a chunked `Stream` with a `Content-Length` header put in by the handler (the engine owns `Content-Length` and `Transfer-Encoding`, and the two together are a request-smuggling shape); and `sendfile(2)` through `io.Copy` to the socket, which does not exist on the in-memory and TLS connections the engine also runs on and would be a second write path for one output type, so it waits for a measurement that asks for it. **What it fails at:** the type of an extension is the system's MIME table with a built-in fallback, which differs between machines for uncommon extensions (set `ContentType` for those).

**What was rejected (download names):** no helper, with the header written by the application as `mime.FormatMediaType("attachment", map[string]string{"filename": name})` in `Header`, the position of 2026-11-03 morning, on the ground that a helper would be a second spelling of that standard idiom. A review of the developer experience the same day moved it: Gin (`FileAttachment`), Echo (`Attachment`), Fiber (`Attachment`, `Download`) and Hertz (`FileAttachment`) all have one ([`docs/research/framework-gap/`](../research/framework-gap/report.md)), so a Go developer looks for it; the habit it leaves is `fmt.Sprintf` with quotes, which breaks on a quote or a name outside ASCII; and nothing in the signatures of `File`, `Bytes` or `Stream` led an agent to `mime.FormatMediaType`, so the right way was found only through the guide. A field is the one way now, and `Header` keeps the other dispositions (`inline`). A function returning a `Header` (`bites.Attachment(name)`) was weighed against the field and rejected: it would have to be merged with any other header the answer sets, and it is not seen in the struct an agent reads.

**What was rejected, in milestone 3:** answering no `Range` and no conditional request, the position of milestone 2, where a request with `Range`, `If-Modified-Since` or `If-None-Match` got the whole file with a 200 and no `ETag`: a browser re-downloaded every asset it revalidated and a video could not seek. [ADR 0064](0064-a-file-answers-its-own-conditional-and-range-requests.md) replaced it.

**Request bodies other than JSON** are types too, read by the type of the `Body` section: `[]byte`, `Raw[T]`, `Form[T]` for `application/x-www-form-urlencoded`, `Upload` for multipart ([ADR 0044](0044-the-body-type-decides-how-a-body-is-read.md)).
