# A plain http.Handler can be served, and the app served as one, from a separate package, as slow paths outside the budget

A route may be served by an `http.Handler` (pprof, expvar, `http.FileServer`, a third-party handler), so the standard library's ecosystem remains usable. Because the engine is not net/http, each such request builds an `*http.Request` and a `ResponseWriter`; Fiber's bridge, the closest thing measured, costs 16 allocations and a goroutine a request ([`docs/research/fiber/`](../research/fiber/report.md)). Those routes are excluded from the allocation budget of [ADR 0003](0003-the-trade-budget.md), and the documentation says so where the function is described, so nobody puts a hot route there by accident.

**Built (2026-11-01):** `stdhttp.Mount(app, "/debug/pprof/", handler, opts...)`, `stdhttp.MountGroup(group, pattern, handler, opts...)` and `stdhttp.MountMethods(app, methods, pattern, handler, opts...)`. A mount is registered as typed routes, one for each method of `stdhttp.Methods` (GET, POST, PUT, PATCH, DELETE and OPTIONS; a HEAD request is served by the GET route), each with an Input with one provided field (a Provider builds the `*http.Request` from the request view, so middleware, limits, `MaxBody`, `Use` and `Tag` apply as to any route) and, for POST, PUT, PATCH and OPTIONS, a `[]byte` Body, read whole up to the route's `MaxBody` and handed to the handler as `Request.Body`. A pattern with a trailing slash covers a subtree, as in ServeMux; the handler sees the full path, and `http.StripPrefix` hands it the rest. The mount therefore needed one hook in the core and no new kind of route: `Request.Headers()`, an iteration over the head's fields as received, because the Input sections name their fields and a handler of unknown headers cannot.

**How a request is served.** The `http.Handler` runs on a goroutine of its own, because the engine's response is the return value ([ADR 0009](0009-the-response-comes-only-from-the-return-value.md)) and a handler that streams must be able to flush while the engine's goroutine waits to return. The `ResponseWriter` holds the status, the headers (copied when `WriteHeader` is called, as net/http does) and up to 32 KiB of body until the first of three events: the handler returns, it flushes, or it has written 32 KiB. If it returned first the answer is buffered and sent with a `Content-Length` as `Bytes` (status 200, the content type sniffed with `http.DetectContentType` when the handler set none, as net/http does), `NoContent` (204), `NotModified` (304) or a `Stream` for any other status (chunked, since a `Stream` has no length). If it flushed or filled the buffer first the answer is a `Stream`: the buffered bytes go out, then every later write is handed to the stream's function and written to the connection, so a write waits until the connection took it and a slow client slows the handler, as in net/http. A panic before the first flush is a 500 and after it closes the connection with no terminating chunk ([ADR 0030](0030-streaming-is-a-return-type.md)); the request's context is the engine's, cancelled when the client leaves ([ADR 0016](0016-the-handler-context-is-cancelled-on-disconnect.md)), and the stream waits for the handler to return before it ends, so the handler never outlives its request.

**What is supported:** method, path (decoded, with `RawPath` when it differs), `RawQuery`, `RequestURI`, every header of the head, `Host`, `RemoteAddr`, `ContentLength`, the context, `Flush` and `http.NewResponseController(w).Flush()`, `WriteHeader` and `Header`, `http.ErrBodyNotAllowed` on a 204 or 304, `http.FileServer` with `Range` and `If-Modified-Since`. **What is not:** `Hijack` and the deadline setters (the engine owns the connection and its limits, [ADR 0024](0024-limits-are-on-by-default.md)); they return an error through the `ResponseController`. Trailers (`Trailer` and `TrailerPrefix`) and 1xx responses (Early Hints) are dropped; `Request.TLS` is nil; a body on GET, HEAD and DELETE is not read ([ADR 0044](0044-the-body-type-decides-how-a-body-is-read.md)); a `Content-Length` the handler sets is replaced by the engine's. HTTP/2 push does not exist.

**Measured (2026-11-04, in-memory connection, Go 1.27.3, `stdhttp/budget_test.go`):** a mounted GET with a small buffered answer allocates 32 times; a POST with a 1 KiB body 35; a GET whose handler flushes three times 31 to 39. (One fewer each than on 2026-11-01, when the request context's first AfterFunc, the one the mount registers, still made a node and a slice of its own.) The typed JSON request it replaces costs 2 ([ADR 0003](0003-the-trade-budget.md)); the whole difference is the `*http.Request` (its URL, header map and context), the writer, the goroutine and the channels. The numbers are held by a test so a rise fails. No throughput was measured: the route is outside the budget by decision.

**Its refusals.** A mount is a set of typed routes, so every Registration refusal applies: a pattern with a method in it, a conflict with another route. `stdhttp` itself panics, at the line that called it, for a nil handler. A mount is left out of the OpenAPI document: every route `stdhttp` registers carries `bites.Undocumented()` ([ADR 0069](0069-the-api-document-states-what-a-routes-providers-and-middleware-ask-and-answer-and-a-route-can-be-left-out.md), milestone 3 wave 2), since a handler's types say nothing about what it serves, so a `Summary` or `Description` given to a mount is refused as it is on any undocumented route. Until then a mount showed in the document as operations answering `Bytes`, `Stream`, `NoContent` and `NotModified`, which described nothing (`TestMountedRoutesAreServedButLeftOutOfTheAPIDocument`).

**What it fails at.** The goroutine and four channel operations a request are the price of streaming; a handler that never streams pays them too. A response over 32 KiB or flushed has no `Content-Length`, so a download through a mount is chunked. The request body is whole in memory (up to `MaxBody`), so a mount is the wrong place for an upload that should stream; use an `Upload` route. A handler that ignores its context and blocks keeps its stream open until it returns, as it would in net/http. A method outside `Methods` (PROPFIND for a WebDAV handler) is a 405 unless it is named with `MountMethods`, because the mount is one typed route a method and not one method-less route.

**What was rejected:** the first version of this ADR, a method-less mount ("a mount is method-less and therefore conflicts with a catch-all such as `GET /`; the root route of an app that mounts anything is `GET /{$}`"). The router has the method-less pattern ([ADR 0018](0018-the-router-follows-servemux-rules.md)), but nothing could register one except a new kind of route, and per-method typed routes reuse every limit, middleware and Provider rule for free. Method-specific routes also win over a mount whatever their paths, so the root route needs no special spelling. Running the handler synchronously on the engine's goroutine, with a writer that buffers everything: it cannot flush, so pprof's profile endpoint and any event stream would hang until the handler returned.

**The other way, built 2026-11-03: `stdhttp.Handler(app) http.Handler`.** An application that serves an `http.Handler` with `http.Server` and drives it with `httptest` keeps both, and a service moved to bites one route at a time needs the app under its existing mux. `Handler` serves the app on an in-memory listener, the one `bitetest` uses ([ADR 0027](0027-an-in-memory-entry-point-runs-the-engine-path.md)), and for each request dials it, writes the request as HTTP/1.1 (the path and query of `URL`, so `http.StripPrefix` in front works; `Host`; every header but the hop-by-hop ones and `Expect`; the body, chunked when its length is unknown, on a goroutine so an early answer does not wait for it; `Connection: close`, so the answer ends with the connection), and reads the answer back with `http.ReadResponse` into the `ResponseWriter`, flushing each piece of a body of unknown length. `RemoteAddr` is the in-memory peer's address, so `TrustedProxies` decide on the real client ([ADR 0025](0025-no-proxy-is-trusted-by-default.md)); the request's context closes the connection, which cancels the app's with `ErrClientGone` ([ADR 0016](0016-the-handler-context-is-cancelled-on-disconnect.md)). A WebSocket upgrade hijacks the `net/http` connection and copies bytes both ways between it and an in-memory one, so the app answers the handshake itself. `Handler` starts the app before it returns, through an internal hook (`internal/servehook`) that does what `Serve` does first, so a route registered after it panics as after `Listen`; after `Shutdown` a request is a 503 problem+json in the app's shape. Its refusals: a nil app panics; a header that would split the head is a 400 problem+json, since a request a test builds is not checked by `net/http`; a `ResponseWriter` that cannot hijack (HTTP/2, a recorder) answers an upgrade with a 501.

**Measured (2026-11-03, Ryzen 7 9700X pinned to cores 2, 3, 10, 11, Go 1.27.3, at `0230cdf` with this change, three runs):** a typed JSON GET through `Handler` from an `httptest.ResponseRecorder` allocates 64 times (the recorder's own included), 5.8 KB, in 5,047 to 5,071 ns; held by `TestARequestThroughHandlerAllocationsAreMeasuredAndStated`. The same request on the app's listener allocates 2 ([ADR 0003](0003-the-trade-budget.md)). The read buffer and the 32 KiB copy buffer are pooled, which took the first version from 43 KB to 5.8 KB a request; neither reaches a handler ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)). Like a mount, it is outside the budget by decision.

**What it fails at:** the app sees no TLS, since the engine knows TLS from the type of its connection, so `Request.Scheme` is `"http"` behind a `net/http` server that terminated TLS itself, unless a trusted proxy's `X-Forwarded-Proto` says otherwise; trailers are dropped; every request pays a connection in memory and an engine goroutine, so a service whose traffic goes through `Handler` pays about 30 times the allocations of `Listen`.

**What was rejected for it:** the `App` implementing `ServeHTTP` itself, as Gin, Echo and chi do, which needs `net/http` in the core ([ADR 0006](0006-no-third-party-dependency-in-the-core.md)); building an engine exchange from the `*http.Request` without bytes, which would be faster but is a second entry into the engine beside the parser, skipping its limits and its head checks, and is what ADR 0027 rejected for testing; and hijacking every connection to give it whole to the engine, which would take later requests on that connection away from the outer mux and its middleware. The second waits for a service that carries real traffic through `Handler`.

**It lives in its own package**, `bites/stdhttp`, the only one that imports `net/http`. Importing net/http adds 3.4 MB to a stripped binary (3.19 MB without it, 6.64 MB with it, Go 1.27.2), and the core does not make every application pay that; a test fails if the core package's dependencies include `net/http`. An application that already uses `http.Client` links net/http anyway, so the saving is real only for services that make no HTTP calls of their own; the rule is kept because it is free and keeps the engine honest.

**Considered:** not supporting `http.Handler` at all. Rejected because pprof alone is reason enough, and an application that cannot mount existing handlers has to give up the framework to use them.
