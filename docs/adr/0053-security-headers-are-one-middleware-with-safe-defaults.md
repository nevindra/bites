# Security headers are one middleware with safe defaults, and the frame policy has one source

`SecurityHeaders(...SecurityHeadersOptions)` is a first-party middleware ([ADR 0032](0032-four-first-party-middleware.md)) that adds to every answer, errors included: `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, `Cross-Origin-Resource-Policy` and, only when [`Request.Scheme`](0025-no-proxy-is-trusted-by-default.md) is `https`, `Strict-Transport-Security`; `Cross-Origin-Opener-Policy` and `Cross-Origin-Embedder-Policy` only when asked for. Built 2026-11-01, milestone 3 wave 1 (`secheaders.go`); the last three policies settled 2026-11-02.

**The defaults are those of a JSON API**, the reference workload ([ADR 0002](0002-the-reference-workload.md)): `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` (exported as `DefaultCSP`), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, HSTS `max-age=31536000`. An answer of an API is never meant to run as a page, so a policy that lets nothing load costs it nothing and turns a JSON body opened as HTML, or a stored payload reflected in one, into an inert page. An app that serves HTML gives `CSP` its pages' own policy, on the group of those pages.

**The frame policy has one source, the CSP's `frame-ancestors`.** `X-Frame-Options` is derived from it for browsers that predate `frame-ancestors`: `'none'` sends `DENY`, `'self'` sends `SAMEORIGIN`, and a list of origins sends none, since the header cannot name origins and a browser that knows `frame-ancestors` ignores it. A `CSP` without `frame-ancestors` is refused: a policy that forgets the directive leaves the answers frameable, which is the clickjacking the middleware exists to stop, and an app that wants to be framed by anyone writes `frame-ancestors *`, which a reviewer can see.

**`Permissions-Policy` and the cross-origin headers: two on by default, two off until asked.** The evidence is the specifications and MDN, read 2026-11-02, with the OWASP HTTP Headers Cheat Sheet for the recommended values (Permissions-Policy: <https://w3c.github.io/webappsec-permissions-policy/>, <https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Permissions-Policy>; COOP: <https://html.spec.whatwg.org/multipage/browsers.html>, MDN `Cross-Origin-Opener-Policy`; COEP and CORP: <https://fetch.spec.whatwg.org/#cross-origin-resource-policy-header>, MDN `Cross-Origin-Embedder-Policy` and `Cross-Origin-Resource-Policy`; OWASP: <https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html>). What each says and what it breaks is in the list below; no browser was run, so it is reading, not a measurement.

- **`Permissions-Policy: geolocation=(), camera=(), microphone=()` is on by default** (`DefaultPermissionsPolicy`, OWASP's value). It applies to a document, so it costs a JSON API nothing, and on a page it removes three prompts an injected script could raise. It breaks a page group that is a call or a map and has not set its own; that group gives `PermissionsPolicy` or `NoPermissionsPolicy`. The header is a Structured Fields dictionary and a browser skips a member it cannot parse or a feature it does not know, so a typo silently costs the policy; `PermissionsPolicy` is therefore checked for its shape (name=value members, parentheses and quotes closed) and refused when it is not, while feature names are not checked, because the list grows with the browsers.
- **`Cross-Origin-Resource-Policy: same-site` is on by default** (OWASP's value; `CrossOriginResourcePolicy` takes `same-origin` and `cross-origin`). The Fetch check runs on the response of a `no-cors` request, so it stops another site from loading an answer as an `<img>` or `<script>` (the Spectre-style read it exists for) and does not touch a `fetch` under CORS, which `Access-Control-Allow-Origin` decides, nor a top-level navigation. A SPA on another origin reads the API under CORS and is unaffected. It breaks an image, script or frame of this app that a different site embeds (a public avatar endpoint, a widget script, `Static` serving a CDN role); that route gives `cross-origin`, on its group. There is no off switch: `cross-origin` is the same as absent for every browser except one under COEP `require-corp`, where it is what is wanted.
- **`Cross-Origin-Opener-Policy` is an option, not a default.** OWASP recommends `same-origin`, and notes it may not suit REST APIs. On a JSON answer it has no effect, and on a page it cuts the opener's reference to a cross-origin popup, which breaks an OAuth or payment flow; `same-origin-allow-popups` keeps it. A default cannot know which pages open popups, so it is sent only as `CrossOriginOpenerPolicy` (`same-origin`, `same-origin-allow-popups`, `unsafe-none`; `noopener-allow-popups` is too new to offer).
- **`Cross-Origin-Embedder-Policy` is an option, not a default.** `require-corp` blocks every cross-origin `no-cors` image, script, stylesheet or frame that sends no CORP (MDN); a page embedding third-party images, or the documentation page of [ADR 0071](0071-the-api-documentation-ui-is-a-module-that-loads-a-pinned-cdn-version.md) whose CSP allows `img-src https:`, would break. It is wanted only with COOP `same-origin` for cross-origin isolation (`SharedArrayBuffer`), by a page group that knows what it embeds. `CrossOriginEmbedderPolicy` takes `require-corp`, `credentialless` or `unsafe-none`.

**HSTS only over HTTPS.** A browser ignores `Strict-Transport-Security` over plain HTTP (RFC 6797 8.1), so sending it there does nothing except tell a reader the app means HTTPS. Whether a request is HTTPS is `Request.Scheme`: TLS the engine terminated, or `X-Forwarded-Proto` from a trusted proxy ([ADR 0025](0025-no-proxy-is-trusted-by-default.md)). `includeSubDomains` is off by default because it pins hosts this app does not serve; `preload` is refused without `includeSubDomains` and a year, the conditions of the browsers' preload list. `NoHSTS` leaves it out for an app whose balancer sends it.

**What it costs.** Allocations: **0**, every value is a string built when the middleware is made; measured 2 for the typed POST behind it, the same as without (`TestTheSecurityMiddlewareAndProvidersCostWhatTheirADRsSay`, with a row for every cross-origin option set, and with the whole security stack, HSTS included, `TestTheWholeSecurityStackOnATypedPOSTStillAllocatesTwice`). About 300 bytes of headers on every answer with the defaults (the two added by default are about 100 of them, counted from the strings), up to about 400 with every option set. Throughput and p99 are not measured yet; they wait for the serial run of wave 2. Memory per idle connection: none.

**Refusals at construction** (rows of `refusal_test.go`): two options values; a `CSP` with no `frame-ancestors`; a `CSP` with a byte a header cannot carry (a control character, a CR or LF, a byte past ASCII); a `ReferrerPolicy` that is not one of the eight of the W3C specification; a `CrossOriginOpenerPolicy`, `CrossOriginEmbedderPolicy` or `CrossOriginResourcePolicy` that is not one of its values; a `PermissionsPolicy` that is not name=value members or leaves a quote or parenthesis open; `NoPermissionsPolicy` together with `PermissionsPolicy`; an `HSTSMaxAge` that is negative or not whole seconds; `HSTSPreload` without `HSTSIncludeSubdomains` or with less than a year; `NoHSTS` together with an HSTS field. **What cannot be caught before the first request:** a route that sets its own `Content-Security-Policy` in a wrapper's `Header` while this middleware covers it gets two policies, and a browser enforces both, so the default's `default-src 'none'` breaks that page; a middleware cannot see a header the handler set ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)). The guide says to put a page group's own `SecurityHeaders` on that group rather than on the app.

**Scenarios it was put against.**

- _The reference workload_, a JSON API behind a TLS-terminating balancer with trusted proxies: every answer, 404 and 429 included, carries the five headers; HSTS is on because the balancer says `https`.
- _A hostile client_ that sends `X-Forwarded-Proto: https` directly over plain HTTP: its peer is not trusted, `Scheme` is `http`, and no HSTS is sent (`TestHSTSIsSentOnlyWhenTheSchemeIsHttpsFromATrustedProxy`). Nothing it sends changes any other header.
- _A stored XSS payload_ in a JSON field, opened by a victim as a top-level page: `nosniff` with `application/json` keeps a browser from running it as a script or a page, and `default-src 'none'` stops what it would load if it rendered.
- _An admin page group_ serving HTML with its own policy: `SecurityHeaders(SecurityHeadersOptions{CSP: "default-src 'self'; frame-ancestors 'self'"})` on the group gives `SAMEORIGIN` with it.
- _Development on `http://localhost`_: no HSTS, so a developer's browser is not pinned to HTTPS for localhost.
- _A JSON API behind a SPA on another origin (CORS)_: the SPA reads with `fetch` under CORS, which CORP does not govern; COOP and COEP are not sent (`TestACORSFetchFromAnotherOriginIsNotTheBusinessOfTheResourcePolicy`).
- _An app with an OAuth popup_: no COOP by default, so the popup keeps its opener; a page group that wants some isolation writes `same-origin-allow-popups`.
- _A page embedding third-party images_: no COEP by default, so they load; they are other servers' answers and this app's CORP is not on them (`TestTheDefaultsLeaveOutTheOpenerAndEmbedderPoliciesSoPopupsAndThirdPartyImagesKeepWorking`).
- _The documentation page of `modules/docsui`_ under an app-wide `SecurityHeaders`: it gets the Permissions-Policy and `same-site`, no COOP or COEP, and its pinned CDN and `img-src https:` images load (`TestThePageUnderTheDefaultSecurityHeadersStillLoadsItsPinnedCDNAssets`). The CDN sends `Cross-Origin-Resource-Policy: cross-origin` (probe of `cdn.jsdelivr.net`, 2026-11-02), so only its images, not its scripts, would stop a `require-corp` page.

**What it fails at.** Two policies when a handler sets its own (above). The default `Cross-Origin-Resource-Policy: same-site` stops a different site embedding this app's images or scripts until that route says `cross-origin`; the default Permissions-Policy denies the camera, microphone and location to a page group that has not set its own. Cross-origin isolation is possible only by giving both COOP and COEP, and nothing checks that the pair is complete (COEP alone isolates nothing and harms nothing). The CSP is a string the middleware does not parse beyond `frame-ancestors`, so a policy with a typo in another directive is sent as written. HSTS behind a proxy depends on the proxy list being right ([ADR 0025](0025-no-proxy-is-trusted-by-default.md)): a stale list makes `Scheme` `http` and HSTS silent, which fails safe for the server and leaves the browser unpinned.

**What was rejected.** Leaving `Permissions-Policy`, `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy` out and asking a page group to add them by a middleware of its own, the first position: the sources show two of the three are free for an API and the third (`Permissions-Policy`) removes prompts, so the safe default costs nothing and a hand-written middleware is how the header is forgotten. The full OWASP set as defaults (`COOP: same-origin`, `COEP: require-corp`): they break OAuth and payment popups and every cross-origin image, script or frame without CORP, for pages the middleware cannot see, which the rule "safe defaults" does not justify; they stay options for the group that wants isolation. `CORP: same-origin` as the default: it stops a sibling subdomain (`www` embedding `api`'s images) that `same-site` allows. An off switch for CORP: see above. Checking feature names in `Permissions-Policy` against a list: it would refuse a new feature a browser already knows. An `X-Frame-Options` field beside the CSP, the first sketch: two sources for one policy, which can contradict (`SAMEORIGIN` with `frame-ancestors 'none'` is a page that cannot be framed while the header says it can), and the contradiction would have been a refusal of its own. Sending HSTS on every answer, plain HTTP included. `X-XSS-Protection`: the filter it switched on is removed from every current browser and was itself a source of leaks, so the header is not sent. A default CSP for HTML pages (`default-src 'self'`): it is wrong for an API's error pages and right for no page in particular. Off switches for `nosniff` and `Referrer-Policy`: there is no answer of a JSON API that wants a browser to sniff its type, and `ReferrerPolicy` takes any of the eight values.
