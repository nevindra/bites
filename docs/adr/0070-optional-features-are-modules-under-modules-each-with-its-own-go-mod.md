# A feature with a dependency, or that most applications do not need, is a module under modules/, each with its own go.mod

Everything that needs a third-party package (JWT with a key-set client, OpenTelemetry, zstd, brotli) or that only some applications want (the API documentation UI of [ADR 0071](0071-the-api-documentation-ui-is-a-module-that-loads-a-pinned-cdn-version.md)) is a Go module in its own folder under `modules/`, named for what it does: `modules/docsui`, `modules/jwt` ([ADR 0062](0062-jwt-verification-is-a-module-whose-key-fixes-the-algorithm.md)), `modules/otel` ([ADR 0063](0063-opentelemetry-is-a-module-whose-observer-records-the-server-span-and-names-it-to-the-core.md)), `modules/pgnotify`, the Postgres `LISTEN`/`NOTIFY` Broker of a Topic ([ADR 0081](0081-a-topic-reaches-other-instances-through-a-broker-and-postgres-is-a-module.md)), and `modules/config` ([ADR 0080](0080-configuration-is-a-module-that-fills-a-typed-struct-from-flags-environment-and-files.md)), later `modules/zstd`, `modules/brotli`. The core imports the standard library only ([ADR 0006](0006-no-third-party-dependency-in-the-core.md)); a module is how bites ships what the rule keeps out, and how an application that never imports one never links, downloads or audits it.



**The path is `github.com/nevindra/bites/modules/<name>`.** It is a sub-directory module of the repository, which Go supports: the core's `go.mod` ends at the nested `go.mod`, so `go build ./...`, `go test ./...` and `go vet ./...` at the root never enter a module, and a module is tested with `cd modules/<name> && go test ./...`. Its tag is `modules/<name>/vX.Y.Z`, so a module is versioned apart from the core ([ADR 0034](0034-versioning-before-1-0.md)): a fix to the JWT module is a patch bump of that module only.

**Inside the repository a module builds against the core beside it.** Its `go.mod` requires `github.com/nevindra/bites v0.0.0` and carries `replace github.com/nevindra/bites => ../..`, so a change to the core and to a module is one change, tested together, with no tag in between. A release is two steps in this order: tag the core, then in each module replace `v0.0.0` with that tag, delete the `replace` line and tag the module. Until the first release the `replace` is the only link.

**A module uses the core's exported API and nothing else.** Go would let it import the core's `internal/` packages by path, since the path rule looks at the import path and not at the module, so a test in each module fails if any of its own imports is under `bites/internal`; a module is thereby also the test of whether the exported API is enough: a hook a module needs and lacks is a change to the core, argued as one. The core never imports a module.

**A module follows the rules the core does that do not need the standard library only:** a Registration mistake is a panic naming the line that registered it ([ADR 0007](0007-mistakes-are-refused-at-registration.md)), its tests are named as sentences about behaviour and run with and without `-race` ([ADR 0033](0033-the-rules-are-build-steps.md)), and a module that adds work per request states the allocations it adds ([ADR 0003](0003-the-trade-budget.md)). A module that depends on a third-party package says which in its package doc and in its reference page.

**What it costs.** One `go.mod` and one test command a module; a contributor runs the core's `go test ./...` and each module's, and the root's `go vet ./...` does not see the modules. The repository's checks (`docs_test.go`) run from the root and read the modules' reference pages as Markdown only; they do not compile a module's code, so each module's own tests do that. **Axes:** none for the core, since nothing in it changes.

**Refusals.** None can be caught at Registration: this is a layout rule. It is held by what Go does with a nested `go.mod` and by `deps_test.go`, which fails if the core's dependencies include anything outside the standard library or `net/http`.

**Scenarios it was put against.** A hostile dependency update: a module's `go.sum` is its own, so a compromised brotli binding cannot reach an application that did not import `modules/brotli`. An application that wants only JWT: `go get github.com/nevindra/bites/modules/jwt` adds the core and that module and nothing else. A module needing a core hook (the `Request.Headers` iteration that `bites/stdhttp` needed, and `Undocumented`, which `modules/docsui` needed to leave its page out of the API document, [ADR 0069](0069-the-api-document-states-what-a-routes-providers-and-middleware-ask-and-answer-and-a-route-can-be-left-out.md)): the hook is added to the core with its own reference heading, not reached around.

**What it fails at.** A `replace` line is in the module's `go.mod` until the first release, so `go get` of a module from outside the repository fails before the tagging step; that is stated in the module's README and is the reason no module has been tagged. Two `go.mod` files in one repository can drift in the Go version they ask for; the module's `go` line is kept equal to the core's by hand. A `go.work` file would make the replace unnecessary and let `go test ./...` span modules, and was not used because it changes what `./...` means at the root, and an editor opened on a worktree picks up a `go.work` from a parent directory.

**What was rejected:** one module with build tags (the dependency stays in the core's `go.sum`, and `go mod tidy` and a vulnerability scan see it for everyone); a separate repository for each module (a change to the core and its module is two pull requests, and the documentation tests cannot see the module's pages beside the core's); a `contrib/` folder of unversioned packages in the core module (the core's `go.mod` would then carry the dependency); `go.work` at the root, for the reason above.
