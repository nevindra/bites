# A panic in a handler is recovered by the engine, always

Recovery is part of the engine, not a middleware that can be left out. A panic in a handler, a provider or middleware is recovered for that request: if nothing has been written yet, the client gets a 500 with no detail; if a streamed response has begun, the connection is closed, because a half-written response cannot be repaired. Either way the panic and its stack are logged with the request. It cannot be turned off, because a process that dies on one bad request takes every other connection with it.

Panics raised at Registration ([ADR 0007](0007-mistakes-are-refused-at-registration.md)) are not recovered: they are refusals, and the program is meant to stop on them.

**The 500 carries the request id in its header too** (built 2026-11-01, milestone 3 wave 0). The engine's 500 after a panic always carried `request_id` in its body (ADR 0012), but the `X-Request-ID` header of the `RequestID` middleware ([ADR 0032](0032-four-first-party-middleware.md)) was missing, because the middleware adds it on the way out and a panic means the chain never returns. The middleware records the header and its id for the engine before it calls the next layer, and the engine adds the record to its own 500. A route with no request-ID middleware gets no such header. The name is the middleware's configuration and the id is one it validated or generated, so no request bytes reach a response header unchecked (`TestThe500AfterAPanicCarriesTheIDInTheConfiguredHeaderAndAPlainOneCarriesNone`).

**The 500 carries the headers the first-party middleware it left would have added for the client to read it** (2026-11-25, [ADR 0032](0032-four-first-party-middleware.md)). The record is general: `Exchange.AddFaultHeader(name, value)` appends a header line to a buffer in the connection's pooled scratch, emptied when a request begins, and the engine appends it to its 500 after a panic (or when nothing was answered) and to nothing else. `RequestID` records its header, and CORS its `Vary` and `Access-Control-*` headers for the origin it decided, so a browser shows the 500 instead of a CORS error. Recovery stays here: the chain does not catch the panic, and the Observer's `Panicked`, `Panic` and `Stack` are unchanged. The record replaced the request id's own header field, so the connection struct went from 416 to 400 bytes (`unsafe.Sizeof(conn{})` at `13a6e7a` and after, on linux/amd64; both round to the 416-byte size class, so an idle connection holds the same memory), and the scratch, which an idle connection does not hold, from 696 to 720 bytes; it costs no allocation once its buffer has grown. Security headers, rate-limit headers and cookies are not recorded, for the reasons in ADR 0032.
