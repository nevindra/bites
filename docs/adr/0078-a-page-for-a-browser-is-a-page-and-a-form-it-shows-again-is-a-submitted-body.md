# A page for a browser is a Page, and a form it shows again is a Submitted body

An application that serves HTML to a browser shows a form again when it is wrong: the fields, what the person typed in them, and the mistake next to each, with a 4xx status (422 for a form that does not pass; Turbo, for one, renders a form answer again only when its status is a 4xx or 5xx). Until 2026-11-04 bites could not say either half. Every error answer was problem+json ([ADR 0012](0012-client-errors-are-400-problem-json.md)), so the 400 of a bad `Form[T]` reached the browser as JSON, and an error status came only from a returned error ([ADR 0013](0013-other-statuses-are-wrapper-types.md)), so an HTML body with 422 could be sent only as a `Stream`, which is chunked, never compressed, and costs a stream's allocations. The fifth agent usability run ([run-5](../research/agent-usability/run-5/report.md), an event ticketing service with organiser forms) found both: it re-showed its sign-in form as a `Stream` of status 401, and left its event form answering problem+json to a browser. Decided and built on 2026-11-04 (`page.go`, `outplan.go`, `form.go`, `decode.go`, `register.go`, `openapi.go`, `page_test.go`, `budget_test.go`, `refusal_test.go`).

**Decision.**

- **A `Page` is an HTML page for a browser, with its own status.** `Page{Status, Body, Header, Cookies}` is sent as `text/html; charset=utf-8` with `Status`: 0 or 200, or a client error from 400 to 499. It is the one answer type that carries an error status in place of a returned error, and the reason is what reads it: a browser shows the body of an answer, and a problem+json is not a page. An API's error is still a returned error, answered as problem+json, so ADR 0012 holds for every answer the framework makes and for every error a handler returns.
- **A status a Page cannot have is a logged 500 that names the fix.** 401 and 407 must carry a challenge (`WWW-Authenticate`, RFC 9110 15.5.2), which a page does not have, so they are refused with "show the form again with 422, or return Unauthorized for an API"; a 3xx is a `SeeOther`, a 5xx a returned error, and a 2xx other than 200 has no page to show. A `Content-Type` in `Header` is refused too, since a Page is HTML. These are values of the handler's, so they are checked per response, as a `Redirect`'s status is; Registration cannot see them.
- **A `Submitted[T]` Body hands the form's mistakes to the handler.** `T` is decoded exactly as in `Form[T]` (the same fields, wire names, limits and rules); what differs is who answers a bad form. The handler runs whatever the form held, and reads it with `Valid() (T, bool)`, `Problem(name)` (the first message for a field, for a template), `Problems()` (every mistake, as the `FieldError`s a 400 lists), `Sent(name)` and `SentAll(name)` (the text as typed, even when it could not be decoded, to fill the field again), and `Add(name, message)` (a mistake the handler finds against its data, such as a venue booked on that date).
- **Validate's mistakes at the body join the form's.** The Input's `Validate` runs, as on any route, only when decoding found no mistake; what it returns at `body` or `body.*` is added to the Submitted and the handler runs, so a cross-field check is shown on the page like a decoding one. A mistake it returns elsewhere is the 400.
- **What stays the framework's.** A mistake in the path, the query, a header or a cookie is the 400 problem+json, listing the form's mistakes too, since the page cannot show what the URL got wrong; and a body over the limit (413), over `Limits.MaxFields` (413) or of another media type (415) is answered before any form exists. A browser that posts a form sends neither of the last two.
- **A Submitted needs a Page.** A route whose Body is a `Submitted[T]` and whose handler returns no `Page` (alone, in a OneOf, or among its `Returns`) is refused at Registration, naming the two ways out: return a Page, or read the body as `Form[T]` and let the framework answer the 400. A handler that keeps the mistakes and has nowhere to show them would answer a bad form with whatever it returns for a good one.
- **The API document.** A Page is a `200` and a `4XX` `text/html` answer (the range, since which 4xx is the handler's); a Submitted is the same `application/x-www-form-urlencoded` request body as a Form, and the route states no 400 unless another section, or a Provider's, can answer one. The representative golden carries such a route, and it validates against the official OAS 3.1 schema (`docs/research/openapi-valid`).

**Why two form bodies is not two ways to do one thing.** `Form[T]` and `Submitted[T]` decode the same, and answer a bad form differently: one for an API client, which reads a located 400, and one for a browser, which reads a page. Making `Form[T]` always reach the handler was considered and rejected: every API form handler would then have to check the form, and one that forgot would act on a half-decoded value with no error anywhere, the trap principle 2 refuses ([ADR 0077](0077-four-principles-in-the-order-they-win.md)). A route option that turns a Form's 400 into a page (`OnInvalid(func(...) Page)`) was considered and rejected: a second function per route, with a signature of its own that an agent must learn, and the handler that knows the template and the data would not be the one rendering the page. `Page` beside `Bytes{ContentType: "text/html"}` is a second spelling of a 200 HTML answer; it is kept because only a Page carries a 4xx, is documented as HTML, and refuses a stray Content-Type, and the guide gives HTML to browsers as a Page and keeps `Bytes` for any other media type.

**What it costs** ([ADR 0003](0003-the-trade-budget.md)). A Page costs what a `Bytes` costs: its body is copied into the response buffer, no allocation of its own. A Submitted form keeps a copy of the form as sent, so a page can show what was typed even when the handler found a mistake in a form that decoded whole: the copy, the submission and the index of its fields are three allocations a Form does not make, measured at 5 for a valid three-field Submitted POST against 2 for the same Form (`TestASubmittedFormCostsAFormsAllocationsAndThreeForTheCopyItKeeps`, `budget_test.go`). A form with one mistake measured 11 in the same run, the mistakes cloned out of the request's pooled state ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)); that is the path a person who typed something wrong takes, not the hot path. The index is sized by the form's separators, which `Limits.MaxFields` bounds before anything is decoded, so a hostile form cannot grow it past the limit, and a field is looked up in it, not by scanning the body again.

**Scenarios it was put against.**

- _The run-5 organiser forms._ The sign-in form shown again after a wrong password is a `Page{Status: 422}` from the handler; the event form with capacity 0 is a `Submitted[EventForm]` whose handler renders `{{.Form.Problem "capacity"}}` beside the field and `{{.Form.Sent "capacity"}}` in it, with 422; a valid form redirects with a `SeeOther` from the same handler (`OneOf2[SeeOther, Page]`).
- _A hostile client._ A form of a million `&` is refused by its count before decoding (413); a form over `MaxBody` is 413; a bad percent escape is a problem of the form, and `Sent` gives the raw text; a field name of 10 KiB is clipped in the location as for a Form. None reaches the handler as more than `MaxFields` entries.
- _A handler that keeps the form._ A Submitted kept past its request (sent to a goroutine, stored) holds copies: its text, its problems and their locations are the handler's, tested by keeping one across later requests under `-race` (`page_test.go`).
- _A form behind a Provider and CSRF._ `CSRF` is middleware and runs before the route, and the Providers run before the Input, as on any route; a Provider's 401 is still problem+json, and the form is decoded after them and kept the same (tested with a Provider in `page_test.go`).
- _An unknown field._ A submit button's name or a hidden field the type does not declare is a problem `unknown field` at `body.<name>`, as for a Form, so a page that shows only the per-field problems would answer 422 with nothing visible: the guide's template lists `Problems()` at the top of the form, and `AcceptUnknownMembers()` on the route lets the extra fields through.

**What it fails at.** Whether a page shows every problem is the template's; the framework cannot see a page that forgets one. A Page's status is a run-time value, so a 401 is a logged 500 found by a test, not a Registration panic. A multipart form (a file input beside text fields) is a `Submitted[T]` whose `T` has a `FormFile` field, read as `multipart/form-data` and decoded like a `Multipart[T]` ([ADR 0044](0044-the-body-type-decides-how-a-body-is-read.md)), with `Sent` of a file field the empty string and a body over a limit the 413 problem+json; an `Upload` is read part by part by the handler, which decides itself how to answer. An HTML page for a framework error (a 404 for an unknown path, the 400 of a bad path parameter, a 500) is still problem+json; an application that wants HTML there maps it in front of the app, and this ADR does not decide it.

**What was rejected.**

- **Every error answer is problem+json, with no exception** (ADR 0012 until 2026-11-04). Moved by run 5: an application with forms could not show one again in HTML with a 4xx except through a `Stream`, and its validation reached a browser as JSON.
- **A `Status` field on `Bytes` and `Text`**: ADR 0013 keeps error statuses out of the output types an API returns, and a `Bytes` with 404 would be an API error that skips problem+json; a type for pages says what the status is for.
- **The form's mistakes as an error the handler returns** (`return page, bites.Invalid(...)`): a handler returns a value or an error, not both, and the page is the answer.
