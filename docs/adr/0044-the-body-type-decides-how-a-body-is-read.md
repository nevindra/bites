# The type of the Body section decides how a request body is read

| `Body` is | accepts | read as |
|---|---|---|
| a struct, slice or map | `application/json` or `*+json` | JSON, through the codec ([ADR 0015](0015-json-is-our-own-codec-on-jsontext.md)) |
| `Opt[T]` of a struct, slice or map | the same | JSON, or nothing: a request with no body leaves the `Opt` unset |
| `Raw[T]` | the same | JSON, and the exact bytes kept beside the value: `in.Body.Bytes()` |
| `[]byte` | any | the bytes as sent |
| `Form[T]` | `application/x-www-form-urlencoded` | form fields, decoded like text ([ADR 0042](0042-text-values-are-decoded-by-type.md)) |
| `Upload` | `multipart/form-data` | a stream of parts, read by the handler while it runs and never buffered whole |
| `BodyReader` | any | an `io.Reader` over the bytes as sent, read by the handler while it runs and never buffered whole |
| `Multipart[T]` | `multipart/form-data` | fields and files decoded into `T` before the handler runs: a file in memory up to a small bound and in an unlinked temporary file beyond it |

**`Form[T]`** is `type Form[T any] struct{ Value T }`, the shape of `Raw[T]`: a Go type cannot be a bare `T`, so the handler reads `in.Body.Value.Name`. `T` must be a struct, and not an `Opt` or `Null`, which are structs with a presence meaning of their own. Its fields compile exactly as a Query section does ([ADR 0042](0042-text-values-are-decoded-by-type.md)): the same scalar types, a slice filled from repeated keys, `Opt` for a field that may be missing and a required field otherwise, the constraint types and `Validate` of [ADR 0021](0021-validation-is-a-method-and-a-few-constraint-types.md), wire names from the naming policy or `WireNames`, at most 64 fields and 8 lists, and a `Null` or a nested struct refused at Registration with the text a Query field gets. A mistake is a 400 located as `body.name`, a list element as `body.tags[1]`. `+` is a space and `%XX` is decoded, as in a query; a bad escape in a value is `expected a valid percent-encoded value` at the field, and in a name at `body`. A field the type does not have is a 400 `unknown field` at `body.<name>` (clipped to 64 bytes), exactly like an unknown JSON member ([ADR 0015](0015-json-is-our-own-codec-on-jsontext.md)), unless the route has `AcceptUnknownMembers`; this differs from the Query section, which ignores keys it does not know, because a body is the contract of a write and a misspelt field silently dropped is a lost write. A form is sent with `application/x-www-form-urlencoded` (any case, any parameters, so `charset=UTF-8` is fine); any other type, or none, is the 415 of the paragraph below with the detail `the body must be sent as application/x-www-form-urlencoded`. An empty body is a form with no fields, so only the required fields are reported, unlike an empty JSON body, which is `required` at `body`, because "nothing" is a legitimate form (a search with no filters) and not a legitimate JSON document. A form with more fields than `MaxFields` (the count of `&` is checked before anything is decoded, so a body of a million `&` costs one scan) is a 413 `request body has too many fields`: the limit of [ADR 0024](0024-limits-are-on-by-default.md) that bounds header fields bounds the fields of a form, because both are the number of things the parser is asked to look up, and a list a form fills counts each repeated key. A body over `MaxBody` is the usual 413. Decoding is done in the request's own body, in place: the body is read into the slab (or the region of its own) and a value that carries escapes is decoded where it lies, so a string is a view of the body, an escape costs no copy and no allocation, and the typed form POST of [ADR 0003](0003-the-trade-budget.md) stays at 2. This is why a `Form[T]` body is read once and its bytes are not kept: there is no `Bytes()` as on `Raw[T]`, and the bytes the engine hands back are rewritten. In the document, a form body is the object schema of `T` under the media type `application/x-www-form-urlencoded` (`Registry.BodySchema`), a list as repeated keys.

**A `Submitted[T]` is a Form whose mistakes the handler shows** ([ADR 0078](0078-a-page-for-a-browser-is-a-page-and-a-form-it-shows-again-is-a-submitted-body.md)): decoded the same, it keeps a copy of the form as sent and its mistakes, and the handler answers with a `Page`.

**What was rejected (Form):** ignoring unknown fields as Query does (a lost write, above); decoding each escaped value into a fresh slab copy, which costs an allocation per escaped value as the slab holds the body already (a form with `%40` or `+` is the common case, not the rare one); one limit of its own for form fields (`MaxFormFields`), a number nobody has a basis for: `MaxFields` can be raised on the app. **What it fails at:** the 100-field default of `MaxFields` is low for a form with a long list, which must raise it app-wide, since the limit is not per route; a bad escape in a required field also reports the field as `required`, as the Query section does; `multipart/form-data` is not a `Form[T]`: it is `Multipart[T]` when the handler wants the fields and files decoded, and `Upload` when it wants to stream.

`Raw[T]` exists for webhooks: Stripe and GitHub sign the exact bytes, and re-encoding the decoded value does not reproduce them. The handler checks `in.Body.Bytes()` against the signature with the secret its struct holds.

**`Multipart[T]` is a multipart form decoded into a struct** (decided and built 2026-11-04, the roadmap's "multipart form decoded into a struct"). It is the third way to read `multipart/form-data` only in name: the choice an agent makes is one question, **does the handler need the bytes while they arrive?** If it streams a file to a store, checks a signature on the way, or takes a file larger than it can keep, the body is an `Upload`. If it wants the fields and the files together as values (a title and a photo, a CSV and its options), the body is a `Multipart[T]`. It is the shape of `Form[T]` and `Raw[T]`: `type Multipart[T any] struct{ Value T }`, read as `in.Body.Value.Title`. The rules that follow are the ones above for `Form[T]` unless said otherwise: `T` is a struct and not an `Opt` or `Null`; text fields compile as a Query section does ([ADR 0042](0042-text-values-are-decoded-by-type.md)), with wire names, `Opt`, lists from repeated names, the constraint types and `Validate`; at most 64 fields and 8 lists; a field the type does not have is a 400 `unknown field` at `body.<name>` (clipped to 64 bytes) unless the route has `AcceptUnknownMembers`; a mistake is located as `body.title`, a list element as `body.tags[1]`. The prefix is `body`, as for `Form[T]`, so an agent learns one location for every body.

```go
type Photo struct{ bites.FormFile }

func (Photo) Accept() []string { return []string{"image/png", "image/jpeg"} }
func (Photo) MaxSize() int64   { return 5 << 20 }

type NewListing struct {
	Body bites.Multipart[struct {
		Title    bites.NonEmpty
		Price    int64
		Cover    Photo               // exactly one file, required
		Gallery  []Photo             // zero or more files under one name
		Floor    bites.Opt[Photo]    // at most one file
	}]
}

func create(ctx context.Context, in NewListing) (bites.Created[Listing], error) {
	f := in.Body.Value
	r, err := f.Cover.Open() // an io.ReadSeekCloser over this request's copy
	if err != nil {
		return bites.Created[Listing]{}, err
	}
	defer r.Close()
	return save(ctx, f.Title, r, f.Cover.Size) // copy it out here: see Where a file lives
}
// app.Post("/listings", create, bites.MaxBody(20<<20))
```

**A file field is a `FormFile`, or a struct that embeds one.** `FormFile` holds `Name` (the form field, as sent), `FileName` and `ContentType` (as the client sent them, data, never a path: the same rule as `Part`), `Size` (bytes actually received, not declared), and `Open() (io.ReadSeekCloser, error)`, which returns an independent reader over the file each time it is called. There is one spelling for a file: the field type is `FormFile` or a named struct embedding it, `Opt[F]` for at most one, `[]F` for any number under one name (an empty list is legal and a required list is `Validate`'s), and a bare `F` is exactly one and required. What a file must satisfy is a method on the named type, read at Registration as `Length` and `Range` are ([ADR 0021](0021-validation-is-a-method-and-a-few-constraint-types.md)), because a struct tag is the thing [ADR 0011](0011-one-naming-policy-for-wire-names.md) rejected and a method reaches the API document: `Accept() []string` lists the media types allowed (`image/png`, or `image/*`), `MaxSize() int64` the most bytes of that file. A bare `FormFile` accepts any type and is bounded by the route's `MaxBody` alone. Huma's `MultipartFormFiles[T]` ([Request inputs](https://huma.rocks/features/request-inputs/)) takes `form`, `contentType` and `required` tags, `huma.FormFile` and `[]huma.FormFile`, and an `IsSet` flag for an optional file; this takes the same fields from the type, with `Opt` where Huma has `IsSet`.

**Where a file lives, and who removes it.** A file part is received into memory while the request's file bytes in memory stay at or under 256 KiB (fixed in code) and the app's share (`Limits.UploadMemory`, 32 MiB by default, shared by every `Multipart[T]` request) has room (both figures are judgements, not measurements of a workload, and are stated so in `Limits`, the guide and the start-up log); a file whose bytes are still to come reserves what the body says is left of it, up to the 256 KiB, before they arrive, so the share is held for what a client declared and a client that declares and stops holds a reservation, never more than the share; the part that would pass either moves, with what it already holds, to a temporary file in `os.TempDir()` (`Limits.UploadDir` replaces it), and every later file part goes straight to a file. The file is unlinked the moment it is created and read through the descriptor (`io.SectionReader` over `ReadAt`), so nothing is left in the directory by a handler that panics, a crash or a `kill -9`, and the only thing to release is a descriptor, which the framework closes when the request ends. This is why the rule can be stated once: **a `FormFile` is valid while the handler runs.** After the handler returns, `Open` and every reader from it return `ErrUploadClosed`, in memory or not, so a goroutine that kept one fails the same way for a 4 KiB file and a 4 GiB one and never reads another request's bytes ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)); a handler that wants the file after it returns (a queue, a worker) copies it in the handler. What reaches user code is never pooled: the 32 KiB window is the one `Upload` uses and stays pooled; the bytes of a file kept in memory are a block made for that file, and the text of every field is copied into the request's slab, as the text of every other Section is (a field costs one string of its own only when the body did not arrive whole with the head). A handler that returns without opening a file costs the descriptor's close and nothing else. A file field is read, and the file made, only for a field the type has; a part with a name the type lacks is `unknown field` and its bytes are discarded as they are read, never kept.

**Limits.** All four are bounds on what a client controls, on by default, none is a way to get out of `MaxBody`:

| limit | default | answer | set by |
|---|---|---|---|
| the body | `MaxBody`, stated on the route or its group: a `Multipart[T]` route without one is refused, as an `Upload` is | 413 | `MaxBody` |
| one file | the `MaxSize()` of its type, else `MaxBody` | 413 located at `body.cover` (`the file is over 5242880 bytes`) | `MaxSize` method |
| parts | `MaxParts`, 128 | 413 | `MaxParts(n)` |
| one text field | 64 KiB, and 1 MiB for all the text of a request | 413 located at `body.title` | `Limits.MaxFieldBytes`, `Limits.MaxFormBytes` |
| file bytes held in memory | 256 KiB a request, 32 MiB for the app | past either the file goes to disk (no answer) | `Limits.UploadMemory` |
| file bytes on disk | `MaxBody` a request; `MaxInFlight(n)` a route | 413, 503 | `MaxBody`, `MaxInFlight` |

`BodyTimeout` defaults as for an `Upload` (`max(30 s, MaxBody / 128 KiB/s)`), armed when the body is first read. A file over `MaxSize` is refused when its `MaxSize`+1th byte arrives, and the temporary file it filled is closed at once; a part count over `MaxParts`, a part header block or a boundary is refused by the parser exactly as for an `Upload`. The start-up line of a `Multipart[T]` route states the worst case a hostile client can cost, `MaxBody` of disk and 256 KiB of memory for each request in flight, and says `unbounded` when the route has no `MaxInFlight` and the temporary directory is on `tmpfs` (the probe's `/tmp` is, so a spill there is memory). The worst case is the reason the memory rule is two-level: 10,000 connections each sending 1 MiB of files and then stopping would hold 10 GiB if each request kept its own, and 32 MiB when the app's share is the bound ([ADR 0044](0044-the-body-type-decides-how-a-body-is-read.md), memory held for the bytes sent, above).

**Order.** The body is read after the other sections are decoded and before `Validate`, which sees the files: `Validate` may call `Size` and `ContentType` and not read them. A mistake in `Path`, `Query`, `Header` or `Cookie` is a 400 answered before the first byte of body is read (so a `Expect: 100-continue` client is refused with no body sent), and that 400 lists those mistakes only; once they are right, a body mistake is every mistake found in the fields and files of the form, in one 400, up to the cap of 20. This is the one place a body is not read to list its mistakes beside the other sections': a `Form[T]`, a `Raw[T]` and a JSON body are read first and one 400 lists every section, because reading them is cheap, while a `Multipart[T]` may be 2 GiB. A part that ends the body early (truncated, malformed framing) is the `Upload`'s 400 and closes the connection.

**The located 400s.** `body.title` `required` for a missing field, as for a `Form[T]`; `body.cover` `required` for a missing file; `body.cover` `the file is over 5242880 bytes` (413); `body.cover` `the file must be sent as image/png or image/jpeg` (400: the media type of the whole body is the 415, the media type of a part is a mistake in a field, and the exception to ADR 0012 stays one; with three entries the message reads `image/png, image/jpeg or image/gif`); `body.cover` `expected one file, got 2` for a repeated name given to a bare `F` or an `Opt[F]`; `body.price` `expected an integer` for a text field; `body.gallery` `a file part needs a filename` for a plain text part sent under a file field's name, and `body.title` `a text field was sent as a file` for the reverse. A field refused for its type, its name or its kind is not also reported `required`. A text field over its bound is `body.title` `the field is over 65536 bytes` (413), and the text of the whole request `all the text of the request is over 1048576 bytes` (413), located at the field that passed it. The media type check is of the type **the client declared** for the part, which is data and can lie; it is a guard against a mistake, not against an attacker, and the framework says so in the doc comment of `Accept` and in the document, where the type is an `encoding` hint. A handler that must know a file is an image reads its first bytes in the handler (a signature check belongs with the code that decodes the image); a sniffing option waits for a need.

**A `Submitted[T]` whose `T` has a file field is read as multipart.** An HTML form with a file input must be sent as `multipart/form-data`, and the body type has to follow the form, so the media type a `Submitted[T]` accepts is decided by its `T`: `application/x-www-form-urlencoded` when it has no `FormFile` field, `multipart/form-data` when it has one (the same sentence as the table above, applied to `T`). The rest of [ADR 0078](0078-a-page-for-a-browser-is-a-page-and-a-form-it-shows-again-is-a-submitted-body.md) holds: the handler runs whatever the form held, `Problem("cover")` is the first message for a file, `Valid()` reports whether none, `Sent("title")` is the text as typed. `Sent` of a file field is the empty string, because a browser never fills a file input again, and the page says so ("choose the file again"); the `Page` the handler returns closes the request and the file with it. A mistake in another Section is the 400 listing that Section's mistakes only, as the Order paragraph says (the body is not read), where a urlencoded `Submitted[T]` lists the form's too. The limits above apply and a body over them is the 413 problem+json, since no form exists yet to show.

**In the API document**, the body is `multipart/form-data` with the object schema of `T` (`Registry.BodySchema`): a text field as in a `Form[T]`; a file `{"type": "string", "format": "binary"}`, a list of files an array of those, a required file in `required`; and an `encoding` entry for each file field whose type has `Accept`, `{"contentType": "image/png, image/jpeg"}` ([OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.0#encoding-object)); `MaxSize` is stated in the field's `description` because 3.1 has no keyword for the bytes of a binary string. An `Upload` is described as `multipart/form-data` with the type `object` and nothing more, since its parts are the handler's. A list of files is not in `required`, because it may be empty, where a list of text is. A file has no JSON form, so the schema generator is told which types are files (`openapi.Options.Files`, `jsoncodec.Options.Binary`) and describes each as a binary string; `WithJSONSchema` was not used because it is for a type that writes its own JSON and the codec still walks the fields of any other.

**Refusals in the table** (exact text, `POST /x` standing for the route):

- `POST /x: NewListing.Body is a Multipart of Listing, but a Multipart wraps a struct whose fields are the form fields and files` (T not a struct, or an `Opt` or `Null`).
- `POST /x: NewListing.Body has no MaxBody: how much a route may receive is the application's decision (an avatar wants 2 MiB, a video 2 GiB), so there is no default; give the route or its group MaxBody` for a `Multipart[T]` or a `Submitted[T]` with a file and no `MaxBody` (the sentence of the `Upload` row, with the Body's own word).
- `POST /x: NewListing.Body.Value.Cover is a FormFile in a Form; a Form is read as application/x-www-form-urlencoded and cannot carry a file, so make the Body a Multipart`; for a `FormFile` in a `Query`, `Header`, `Path` or `Cookie` section or in a JSON body the text is `POST /x: NewListing.Query.Cover is a FormFile in a Query; a file is a part of a multipart body, so make the Body a Multipart` (`in a JSON body` for the body).
- `POST /x: NewListing.Body.Value.Cover is a *bites.FormFile; a file field is a FormFile, an Opt of one, or a slice of one` for a pointer, a map, an array, a `[]Opt[F]` or an `Opt[[]F]`; and the same text for `[]byte`, `*multipart.FileHeader` and `io.Reader`, which an agent from another framework will try, with the sentence `(bites has no multipart.FileHeader; FormFile.Open returns the reader)` added.
- `POST /x: NewListing.Body.Value.Cover: Photo.Accept returns "image"; an entry is a media type such as image/png or image/*` for an entry that is not `type/subtype` or `type/*` or is `*/*` (which is the bare `FormFile`), and `Photo.Accept returns an empty list; ...` for an empty list (the first draft of this text had a space before the semicolon, a typo).
- `POST /x: NewListing.Body.Value.Cover: Photo.MaxSize returns 0; it is the most bytes of the file, and at most MaxBody` for a size under 1, or over the route's `MaxBody` (a bound that cannot bind is a mistake the agent made).
- `POST /x: NewListing.Body.Value.Gallery has more than 8 lists` (a list of files counts as a list) and the Query section's text for the 64-field and nested-struct limits.
- `POST /x: NewListing.Body.Value.Cover: Photo.MaxSize is func() int; it must be func() int64, the most bytes of the file` (and the same for `Accept`), and `POST /x: NewListing.Body.Value.Cover is a Photo with fields besides the embedded FormFile; a file type is a FormFile or a struct whose only field is an embedded FormFile`: a method of the name with another signature, and a file type that holds more than the file, are refused and not ignored (added in building).
- `POST /x: NewListing.Body is a Multipart on a GET route; a body is sent with POST, PUT or PATCH` as for an `Upload`.
- `POST /x: NewListing holds a Multipart and an Upload; a request body is read one way` for both in one Input (the Body one and a field beside it the other), and `POST /x: NewListing.Body holds a Multipart; a Multipart is the whole Body, read as a form, not a field of a JSON body` for a `Multipart` held by a JSON body or a slice (in a text section it is the text section's own refusal, as for `Upload`). A `Body` of another type now ends the list of body types with `Multipart[T]`: `a Body is a struct, slice or map (read as JSON), []byte, Raw[T], Form[T], Multipart[T], Submitted[T] or Upload`.
- `WithLimits: Limits.UploadMemory is -1, which is not a limit: a limit cannot be switched off, so give a positive number of bytes, or zero for the default of 32 MiB` (the sentence of every other limit, in `MaxFieldBytes` and `MaxFormBytes` too, a row each; the first draft wrote a sentence of its own), and `WithLimits: Limits.UploadDir is "/nope", which cannot hold an upload: it does not exist; it is where a file too large for memory waits while a handler runs, so give a directory that exists and the process can write, or leave it empty for os.TempDir()` for a directory that does not exist, is not a directory or is not writable (a temporary file is made and removed to check), found when `New` runs so that a typo is a start-up failure and not a 500 on the first large file.

**What it costs on the axes.** The typed JSON request: nothing, 2 allocations as before; the body kind is chosen when the route is registered (`bodyPlan.kind`), so a `Multipart[T]` adds a case to a switch the JSON path does not take, and `budget_test.go` fails if that is not so. A `Multipart[T]` request costs the `Upload`'s 3, **measured** over the in-memory connection (exact in `budget_test.go`): 3 with text fields only (they are copied into the slab, so no extra block as the first draft estimated), 5 with one file kept in memory (its record and its bytes: 2 for each file), 8 with a file and a list of one file (the list's backing array is a third), 5 for a 100 KiB file (the buffer is sized once from what the body says is left, not grown by doubling), and 12 to 13 with a file of 300 KiB spilled to disk (the record, and `os.CreateTemp`, the unlink and the descriptor, about 10, not the first draft's 1). The typed JSON request stays at **2** with a Multipart route in the same app, held by a test. Memory per idle connection: unchanged, because nothing is held before the first byte of a file arrives, and the spill bound above is the answer to a client that sends and stops. The probe ([`docs/research/multipart-struct/`](../research/multipart-struct/main.go), 2026-11-04, AMD Ryzen 7 9700X, 3 runs a size, `/tmp` on `tmpfs`, so a spill there measures RAM) put 64 KiB at 2.6 to 3.2 µs in memory against 10.6 to 12.8 µs to a file, 1 MiB at 0.25 to 0.39 ms against 0.19 to 0.22 ms, and 64 MiB at 16.4 to 21.3 ms against 14.1 to 15.4 ms: the file is slower below about 256 KiB and not slower above it, which is where the cut is. The numbers are of the copy alone, no network, no disk-backed directory, and have a spread of 20 to 30% at the small sizes; a disk that is not `tmpfs` was not measured.

**What was rejected (Multipart[T]):** reading the body even when another Section has a mistake, so that one 400 lists both as a `Form[T]` does (the first draft's test name said so): it reads up to `MaxBody` and invites a `100-continue` client to send it for a request already known to be wrong, and the mistakes of the other Sections are one fix away; the claim that the other Sections are decoded and refuse before the body is read was true of an `Upload` (the handler reads it) and of nothing else, and is now true of a `Multipart[T]` by an explicit check; `WithJSONSchema` for the file types (the codec walks any struct without JSON methods, so it fails on the unexported field of `FormFile`); an error text of its own for a negative `UploadMemory` (one sentence for every limit);  `mime/multipart`'s `ReadForm` with `maxMemory`, as Gin and Fiber do, for the reasons the parser paragraph gives (no part count, 10 MiB of headers) and because it keeps its temporary files by name on disk until `RemoveAll`, which a handler that panics skips; a file kept after the handler returns, which makes every path that stores a `FormFile` a lifetime question and asks the framework to count references; one `File` type with tags for its rules, as Huma (`contentType`, `required`); a `MultipartFormFiles[T]` spelling beside `Multipart[T]` (one way); `IsSet` as Huma has it, because `Opt` is the framework's word for "may be missing"; a per-request memory bound alone, which a thousand clients defeat; `Submitted` for files only as a second type, because an HTML form with a file input is the same form with another enctype; a `Part`-like streaming `FormFile`, which is `Upload`. **What it fails at:** the declared media type of a file is the client's word (no sniffing); a file that is still to come reserves what the body says is left, so 128 clients that each declare 1 MiB and send a byte hold the whole 32 MiB share until they stop, and the files of everyone else go to disk, which is slower and safe; a spilled file costs about 10 allocations and a syscall pair, where a file of 256 KiB or less costs 2; a text field costs one string when the body did not arrive whole with the head; a handler that wants a file after it returns must copy it; a body is read in full before the handler runs, so a route that wants to refuse after the first field (a quota on the owner named in field one) pays for the whole body, where `Upload` could stop at once; a spill to a directory on `tmpfs` is memory, found only by the start-up line; the 256 KiB and 32 MiB are judgements, not measurements of any workload; a `Validate` cannot read the file, only its size and type; descriptors held by in-flight requests count against the process limit, so `MaxInFlight` is advised for a route that takes files and is only logged, not required.

An `Upload` is read by the handler, part by part, while it arrives: `in.Body.Next()` returns the next `Part` (its `Name`, `FileName` and `ContentType` as strings, and a `Read` for its body) or `io.EOF` after the last. `in.Body.Each(fn)` is that loop written once: it calls `fn` with each part, skips what `fn` left unread, returns nil after the last part and the first error as it is (from `fn` or from the upload), and adds no allocation to the loop over `Next` (`TestReadingAnUploadWithEachAllocatesWhatTheLoopOverNextDoes`). It passes the `Part` by value, as `Next` returns it: a pointer handed to a function the framework cannot see escapes (`go build -gcflags=-m` reports the part "moved to heap") and would cost an allocation a part. `Upload` is the whole `Body`: it cannot be a field of a JSON body, a slice, or in a text section, and a route with one is refused at Registration. The other sections are decoded and `Validate` runs before the handler, and the body has not been read by then, so a request the Input refuses never gets a `100 Continue` and never sends its body. (Confirmed 2026-11-04 for an `Upload` by `TestTheOtherSectionsAndValidateRunBeforeTheHandlerAndTheBodyIsNotReadWhenTheyFail`, and made true for a `Multipart[T]`, whose body is read by the framework, by a check in `decode`; it is false of `Form[T]`, `Raw[T]` and JSON, whose bodies are read even when a Section had a mistake so that one 400 lists every mistake.)

**Validity.** An `Upload` and every `Part` from it are valid only while the handler runs; read afterwards they return `ErrUploadClosed`, never another request's data ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)). The window the bytes pass through is pooled, which [ADR 0008](0008-no-pooled-object-reaches-the-user.md) allows because the user only ever receives copies of it; every call takes the upload's lock and checks that the request is still the one the handle was made for, so a goroutine that kept a part and reads while the engine closes the request is cut short (the deadline is moved to now) and the connection never waits for it. A `Part` read after `Next` has moved on returns `ErrPartClosed`. Names are data: `FileName` is what the client sent (`../../etc/passwd` included), the framework never opens it, and a handler that joins it to a directory has chosen to trust the client (an `os.Root` refuses it anyway).

**Limits.** A route that takes uploads must state `MaxBody` on the route or on a group above it: an `Upload` route without one is refused at Registration, naming the route and the missing option, because the one number about the application's storage is a decision of the application's author and a default is wrong in both directions (an avatar wants 2 MiB, a video 2 GiB). `MaxBody` set only through `WithLimits` does not count: it is the default for every other route, which is the very thing refused. `BodyTimeout` may be left out: it defaults to `max(30 s, MaxBody / 128 KiB/s)` (256 s for 32 MiB), logged as `default` in the start-up line of the route (the same derivation holds for every route whose body is read whole, below); a `BodyTimeout` from the route, a group or `WithLimits` is used as it is. It covers the whole body, as for every route, and is armed when the handler first asks for a part, not when the head arrives. `MaxInFlight(n)` optionally bounds the uploads in flight ([ADR 0024](0024-limits-are-on-by-default.md)); it is counted per route, also when it was given to a group. `MaxParts(n)` bounds the parts of one upload, 128 by default. A `Content-Length` over `MaxBody` is a 413 before `100 Continue`; a chunked body over it is a 413 when the `MaxBody + 1`th byte arrives.

**The parser** is our own, in `internal/mpart`, streaming over a 32 KiB window, and `mime/multipart` is not used: streaming a 32 MiB part through it holds (18,464 B in 30 allocations in all), but its `NextPart` allows 10 MiB of headers and 10,000 fields per part and has no part-count limit, and one 9 MiB header line allocated 61.7 MB (6.9 times its size), so the limits on parts, part headers and boundary cannot be set around it. The own parser caps a part header block at 8 KiB (431) and 16 fields (431), the number of parts (413), and a boundary at 70 bytes (400, before the body is read, and a missing boundary the same); a content type other than `multipart/form-data` is a 415. A part needs a `Content-Disposition: form-data` with a `name`; one without is a 400. Folded header lines and a repeated `Content-Disposition` or `Content-Type` are a 400. A quoted parameter understands `\"` and `\\` as `mime.ParseMediaType` does. A line that starts with the boundary but continues (`--boundaryX`) is data. A body that ends inside a part, or before its closing delimiter, is a 400 and the connection is closed. After the closing delimiter the epilogue is read and discarded so the connection can carry on; a handler that returns before the closing delimiter leaves a body unread, and the connection is closed after its answer. Transport padding after a delimiter (spaces before the CRLF, which RFC 2046 allows and no client sends) is not accepted. The numbers are fixed in code, not options, but for the parts. It imports no `net/http`, as the standard one does not. Evidence: [`docs/research/decisions-bodies/`](../research/decisions-bodies/report.md), section R4; the parser's tests and a fuzz target are in `internal/mpart`, and the hostile clients (a boundary of 71 bytes, a header that never ends, 129 parts, a body that stops inside a part, a client that trickles, a file name with `..`) in `upload_test.go`.

**Where an upload waits.** On the connection's goroutine, inside the handler's call, in one function (`uploadSource.Fill` in `internal/engine/upload.go`) whose one read is the connection's `Read`. Parking ([ADR 0005](0005-our-own-http1-engine-with-a-goroutine-per-connection.md), step 16) does not reach it: an upload waits inside a request, and only a connection idle between requests parks; the rest of the engine knows no other place an upload waits.

**Errors.** `Each`, `Next` and `Read` return a `*StatusError` for what the client got wrong or the engine refused (400, 408, 413, 431), so a handler that returns the error answers with the right status and problem+json; a handler that swallows it answers what it chooses, and the connection is closed after the answer either way.

**What was rejected (Upload):** a default of 32 MiB and 60 s, for the reasons in [ADR 0024](0024-limits-are-on-by-default.md). **What it fails at:** a chunked upload has no `Content-Length`, so the 413 comes only after `MaxBody` bytes were read (acceptable, since they were streamed, not buffered); the rate floor of 128 KiB/s is a judgement; the body is read by a path of its own, never `ReadBody`; the one deadline covers the whole body, so a client that is slow but steady is cut at `BodyTimeout` however much it has sent (the floor is what sets that time); an upload costs one allocation more than a plain request and one for each part ([ADR 0003](0003-the-trade-budget.md)); and a handler that stops reading early costs the connection.

**A body read whole gets the derived body timeout too** (decided and built 2026-11-09, from a user's report). The reason `Upload` derives its timeout is that a large body needs time, and it holds for any body: a `[]byte`, `Raw[T]`, JSON or `Form[T]` route with `MaxBody(8 MiB)` and the 30 s default needs 2.2 Mbit/s to arrive in time, and a slower link got a 408 on every request, which looks like a network fault and not a setting. So `planBody` (`upload.go`) gives every route with a request body, when neither the route, a group nor `WithLimits` gave a `BodyTimeout`, `max(30 s, MaxBody / 128 KiB/s)`. At or below 3.75 MiB of `MaxBody` that is the 30 s it was, so no existing route changes; above it the route gets the longer time, and the start-up log says so (principle 2): `route PUT /parts: max body bytes` and `route PUT /parts: body timeout, derived from max body bytes`, the second marked `default` as an Upload's is, and nothing is logged for a route whose timeout stayed at 30 s. An explicit `BodyTimeout` is used as it is and not compared with the floor: it is the application's decision, and whoever wrote it saw the number. The cost is none at run time (a number settled at Registration). **What was rejected:** logging only the routes whose `MaxBody` and timeout imply a floor above 128 KiB/s and changing nothing (the default stays wrong for the route and an agent must read a log line to learn it; the derivation is the safe default and the log is how it is seen); a floor applied to an explicit `BodyTimeout` (refusing a number the application chose). **What it fails at:** the floor of 128 KiB/s is the same judgement as for an `Upload`; a slow but steady client now holds a connection, and for a body read whole its buffer, up to the longer time, which `Limits.MaxConns` is the bound of (the buffer is still bounded by `MaxBody` per connection, as it was).

**`BodyReader` is the raw `Upload`** (decided and built 2026-11-09, from a user's report). Resumable upload protocols send each chunk as the raw body of a `PUT` or `PATCH` (S3's `UploadPart`, tus, Google's resumable uploads), and an API may take a file as is (`PUT /files/{name}` with `Content-Type: application/pdf`); a `[]byte` held ten parallel 8 MiB chunks as 80 MiB, and a client that wrapped them in multipart did so only to be streamed. `Body bites.BodyReader` is an `io.Reader`: `Read(b)` fills `b` with the next bytes of the body and returns `io.EOF` at its end, so `io.Copy(store, in.Body)` is the whole handler. It has the rules of an `Upload` and shares its implementation (`Exchange.OpenBody` and `Multipart.ReadRaw` in `internal/engine/upload.go`: the same counter, the same `uploadSource.Fill` as the one place that waits, the same 100 Continue sent when the handler first reads, the same finish): `MaxBody` required on the route or a group above it, refused at Registration if missing (`WithLimits` does not count); `BodyTimeout` derived as for an `Upload`, armed at the first `Read` and covering the whole body; `MaxInFlight(n)` counted per route, a 503 with `Retry-After` before the body is invited; a `Content-Length` over `MaxBody` a 413 before 100 Continue and a chunked body over it a 413 at the `MaxBody + 1`th byte. `Read` returns a `*StatusError` (413, 408, or 400 for a body cut short or a malformed chunked body), so `return ..., err` answers with the right status and problem+json, and the connection is closed after the answer.

**Validity** is ADR 0008's: a `BodyReader` is valid only while the handler runs; after, `Read` fails with `ErrUploadClosed` (the value an `Upload` gives, one name for one fact) and touches nothing, and so does the zero value. The bytes go from the connection into the slice the handler passes, so no pooled buffer is involved, and a read from another goroutine while the request ends is cut short as an `Upload`'s is (`lockKick`). A handler that returns before the end of the body leaves bytes unread, and the connection is closed after the answer; a body read to `io.EOF` (or to its declared length) leaves the connection to carry on. **The media type is neither constrained nor declared:** like `[]byte` it accepts any (no 415), so a handler that wants `application/pdf` checks its `Header` section, and in the API document the request body is `*/*` with the schema `{"type": "string", "format": "binary"}` (OpenAPI 3.1's way to say bytes), with a 413 and no 415. A request with no body reads as an empty one: the first `Read` returns `io.EOF`. Like `Upload` it is the whole `Body`: held by a JSON body or a list it is refused; on a GET, HEAD or DELETE route it is refused by the rule every Body has; `Opt[BodyReader]` by the rule of `Opt`; and it cannot be a message of an `Inbox`. **The name:** `BodyReader` says what it is, the Body as a reader (a bare `Reader` would read as any reader), and the Glossary's _Stream_ is a response.

**What it costs on the axes.** A `BodyReader` request allocates 3, as an `Upload` with no part does (a plain request's 2 plus the handle), for a length body and a chunked one, measured over the in-memory connection and exact in `TestABodyReaderRequestAllocatesOnlyItsHandle`; it has no window (an `Upload` borrows 32 KiB from a pool). Read passes the handler's slice down to the connection's `Read`, so a buffer the handler declares itself is a heap allocation of the handler's own (as `io.Copy`'s 32 KiB is); that is the price of no copy through a window. No existing route changes: the 2 allocations of a typed JSON request hold (`budget_test.go`). Memory per idle connection: none, nothing is held between requests. **What was rejected:** extending `Upload` with a mode for a non-multipart body (one type with two meanings, and `Next` has no sense for a body without parts); `Body io.Reader` (a Provider can give a reader as well, and the type would carry no rule about validity or limits); a `Content-Type` option on the route (a second place to say what a Header section says); reading through the 32 KiB window as an `Upload` does (a copy and a pooled buffer for nothing, since no parser needs the window). **What it fails at:** the 400 for a body cut short and the 408 reach the client only if the handler returns the error (a handler that swallows it answers what it chooses); the 413 for a chunked body comes after `MaxBody` bytes were streamed; a handler that does not read to the end costs the connection; 100 Continue is sent at the first `Read`, so a handler that refuses from the Input alone answers before the client sends anything.

**Refusals in the table:** an `Upload` or a `BodyReader` route with no `MaxBody` (route or group); a `BodyReader` held by a JSON body or a list; an `Upload` on a GET, HEAD or DELETE route; an `Upload` held by a JSON body, a list, or a text section; `MaxInFlight(0)` or a negative one; `MaxParts(0)` or a negative one. A `MaxInFlight` on a route that has no `Upload` is not refused, since a group's option reaches routes of every kind. The OpenAPI description of an `Upload` is `multipart/form-data` with the type `object`.

**An `Opt[T]` Body** is a JSON body that may be absent. `T` must be a struct, slice or map. A request with no body (no `Content-Length` above 0 and not chunked) leaves the `Opt` unset, and the handler reads `b, ok := in.Body.Get()`. A request with a body has it read exactly as a plain JSON body: the same 415 for a non-JSON `Content-Type`, and a required field inside still required (`{}` is a 400 naming `body.note` when `Note` is required). A body of `{}` is a sent body, not an absent one. In the API document its `requestBody.required` is false, and it stays true for every other body. It answers a route such as `POST /spaces/{id}/restore` that takes an optional new name, where a request with no body was a 400 `body: required` and clients sent `{}`. Cost: none on the guarded axes ([ADR 0003](0003-the-trade-budget.md)), one flag check on a request with no body and one store of a bool when a body is read. Refused at Registration: an `Opt` of a scalar (`POST /x: BodyOpt.Body is Opt[string]; an Opt Body is a JSON body that may be absent, so it holds a struct, slice or map`) and an `Opt` of a `Raw`, `Form`, `Multipart`, `Submitted`, `Upload` or `[]byte` (`POST /x: BodyOptRaw.Body is Opt[Raw[struct { N int }]]; an Opt Body is a JSON body that may be absent, and a Raw[struct { N int }] is a Body of its own: give it without Opt`). Tests: `TestAnOptBodyThatIsNotSentIsUnsetAndOneThatIsSentIsReadAsAnyBody`, `TestTheAPIDocumentSaysAnOptBodyIsNotRequired`.

**What was rejected (Opt Body):** any `Opt` Body was refused, as an `Opt` is a field type and has no absent value elsewhere. Also rejected: a body struct whose fields are all `Opt` accepting an empty request in silence, because nothing in the type says absence is accepted and adding one required field would change that behaviour without a word; a `bites.OptBody[T]` marker, a second spelling of `Opt`, which principle 1 refuses; and an empty JSON body read as `{}` for every route, which would turn a client mistake into a write with defaults.

**An empty body:** a `[]byte` body may be empty; a JSON or `Raw[T]` body that is empty is a 400 `required` at `body`. A JSON body is recognised by `application/json` or any `*/*+json` type, in any case and with any parameters.

**A body whose `Content-Type` the route does not accept is a 415**, including a JSON body sent with none at all. That is the one deliberate exception to answering input mistakes with 400 ([ADR 0012](0012-client-errors-are-400-problem-json.md)): the media type is wrong, not the content. A route can accept a missing content type if a client it must serve sends none.

**Memory is held for the bytes a client has sent, never for the length it declared.** The request's slab ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)) is sized to the head's copies, plus the body when the whole declared body (up to the 1 MiB default limit) is already in the read buffer when the head is parsed: the common case, one allocation, and the typed JSON POST of [ADR 0003](0003-the-trade-budget.md) stays at 2. A body that has not all arrived is read into a region of its own, made when the route asks for the body: it starts at `min(Content-Length, 64 KiB)` and doubles, capped at the declared length and at the route's limit, as bytes arrive. A route that never reads its body reserves nothing for it. A chunked body is decoded straight into such a region (4 KiB to start, capped at the limit plus one byte, which is enough to refuse it), with no staging buffer and no second copy. Growing moves bytes, and that is safe because nothing points into the region until the read has finished: the head's copies live in the slab, which never grows, and strings over the body (JSON views, `Raw[T]` bytes, a `[]byte` body) are made only after `ReadBody` returns ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)). The cost is that a body which does not arrive with its head is one allocation more (3 for a typed POST), and a body that grows is copied once for each doubling, about 2 times its size in all; both are paid by a request that is large or slow, not by the common one. Measured in [`docs/research/body-reserve/`](../research/body-reserve/report.md): 200 connections that declare 1 MiB and send nothing held 1,063,177 to 1,063,257 B of heap each, now 71,977 to 72,115 B (64 KiB for the region and about 6 KiB for the connection); a 400 KB chunked body allocated 5.9 times its size, now 2.7.

**What was rejected:** sizing the slab at the head plus the declared `Content-Length` before the handler asked for the body, and reading a chunked body into a pooled staging buffer and then copying it into the slab. Both let a client that opens many connections, declares 1 MiB and goes quiet make the server hold 1 MiB each for the whole body timeout (30 s), a multiplication that `MaxConns` (90% of the file limit) does not bound: 10,000 such connections accounted 10 GiB of heap. The evidence is the side finding of [`docs/research/decisions-bodies/`](../research/decisions-bodies/report.md) and the before numbers in `body-reserve`.
