# A Session is sealed in a cookie, read through a Provider, and changed by returning the cookie Save gives

A `Session[T]` is a value of the application's type `T` kept for a browser across requests. `NewSessions[T](SessionOptions{Keys, ...})` returns the `Sessions[T]` that makes them, and its method `Load` is the Provider ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)) of `Session[T]`. Built 2026-11-01, milestone 3 wave 1 (`session.go`). The word is `Session`; the WebSocket's value is `Inbox` ([ADR 0047](0047-a-socket-is-a-handle-and-a-topic-is-a-broadcast.md)), so the two never share a word.

```go
carts := bites.NewSessions[Cart](bites.SessionOptions{Keys: keys})
app.Provide(carts.Load)

func addItem(ctx context.Context, in struct {
	Cart bites.Session[Cart]
	Body Item
}) (bites.OK[Cart], error) {
	cart := append(in.Cart.Value.Items, in.Body)
	c, err := in.Cart.Save(ctx, Cart{Items: cart})
	if err != nil {
		return bites.OK[Cart]{}, err
	}
	return bites.OK[Cart]{Body: Cart{Items: cart}, Cookies: []bites.Cookie{c}}, nil
}
```

**How a handler reads and changes it, and why this way.** The session arrives as an Input field, filled by `Load`; changing it is `Save(ctx, v)`, `Renew(ctx, v)` or `Clear(ctx)`, each of which **returns the `Cookie` that carries the change**, which the handler puts in its answer's `Cookies` as it would any cookie ([ADR 0043](0043-cookies-and-bodies-other-than-json.md)). Nothing is written behind the handler's back: the answer is still exactly the return value ([ADR 0009](0009-the-response-comes-only-from-the-return-value.md)), a test reads the `Set-Cookie` off the returned value without a server, and a handler that returns early with an error sets no cookie, so a half-done change is never saved. The alternatives each break one of the rules:

- _A mutable session the framework writes after the handler_ (the gorilla/sessions and Express shape, where the handler changes a map and the framework saves it when the response goes out): it is a second channel to the response, the write the handler does not see is the one [ADR 0009](0009-the-response-comes-only-from-the-return-value.md) removed, and when is "after the handler" for a Stream, whose head goes out before its body ([ADR 0030](0030-streaming-is-a-return-type.md))? It also needs a per-request object the framework owns and mutates, pooled or allocated, where `Session[T]` is a plain value on the Provider's stack ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)).
- _A session middleware_ that loads before `next` and saves after: a middleware cannot see what the handler decided ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)), so it would need the same hidden channel.
- _A `SetSession` field on every wrapper_: a second way to set a cookie beside `Cookies`, and one more field on every wrapper type for something most routes do not use.

The price is a line: the handler must put the cookie in its answer, and one that calls `Save` and forgets the cookie changes nothing the browser sees (with a store and a session that already has an id, the store changes and the old cookie still points at it, so the change holds; otherwise it is lost). That cannot be caught at Registration; a test of the handler catches it, and the guide's example is the one above.

**Sealed with AES-256-GCM, standard library only.** The cookie's value is base64url of a 12-byte random nonce and the sealed bytes; what is sealed is a mode byte, the time of the `Save` in Unix seconds, and the JSON of `T` (or, with a store, a 16-byte random id). The cookie's name is the additional data, so a value sealed for one cookie never opens as another. Encryption, not a signature alone: a signed cookie can be read by anyone who has it (a user's id, roles, a cart), and AEAD gives integrity and secrecy for 28 bytes of overhead, less than an HMAC-SHA256's 32. One mode, not two: a choice between signed and encrypted is a choice an application can get wrong for no gain.

**Keys rotate.** `Keys` is a list of 32-byte keys; the first seals, every one opens, in order. Rotation is: put the new key first, deploy, and drop the old one after `MaxAge`. A cookie that opens with no key (forged, cut, or sealed with a dropped key) is a new session, not an error.

**Expiry is sealed.** `MaxAge` (24 hours by default) is the cookie's `Max-Age`, and the time of the `Save` is sealed inside the cookie and checked on every request against the `MaxAge` in force, so a browser, or a thief, that keeps the cookie longer does not keep the session, and a `MaxAge` shortened in a deploy applies at once to the cookies already out (the first build sealed the expiry itself, which kept an old, longer one; found in review, `TestAMaxAgeShortenedInADeployAppliesToTheCookiesAlreadyOut`). It counts from the last `Save`: a handler that saves on every request makes it an idle timeout, one that saves at login makes it absolute, and `RefreshAfter` (below) makes it an idle timeout with no handler's help.

**Cookie flags, safe by default.** `HttpOnly` always (no option drops it: no script needs the session), `Secure`, `SameSite=Lax`, `Path=/`, and the name `__Host-session`: a browser accepts a `__Host-` cookie only from this host over HTTPS with `Path=/` and no `Domain`, so a sibling subdomain cannot plant a session (cookie tossing). When `Domain`, another `Path` or `NotSecure` rule the prefix out, the default name is `session`.

**Size.** A browser keeps 4096 bytes of a cookie, name, value and attributes together. `Save` returns an error when the `Set-Cookie` would be longer, rather than a cookie the browser drops in silence; the error is a 500 and its message says to keep less or give a `Store`. An incoming value longer than 4096 bytes is not decoded.

**Server-side stores.** `SessionOptions.Store` is a `SessionStore` (`Load`, `Save` with the expiry, `Delete`). The cookie then carries a sealed random id, so an id cannot be forged or guessed and a forged one never reaches the store, and the value is the store's. A store is what makes a session revocable: `Clear` deletes it, and a stolen cookie stops working at once. `Renew(ctx, v)` saves under a new id and deletes the old one, for a login: an id an attacker planted or saw before cannot follow the session up (session fixation). Without a store every `Save` seals afresh, so `Renew` is `Save`.

**A store that can find every session of one owner** (decided 2026-11-04). `SessionStore` sees an id and opaque bytes, so "sign out everywhere" and "a disabled User is signed out at once" had no way to be done: only the store, by decoding the data itself, could find the sessions of one User, and then every application wrote that decoder. The rule now: a session type `T` may state its **owner**, the string that names whose session it is (a User's id), with a method on the value receiver, `func (T) SessionOwner() string`, and a store may keep owners by implementing `OwnerSessionStore`:

```go
type OwnerSessionStore interface {
	SessionStore
	SaveOwned(ctx context.Context, id, owner string, data []byte, expires time.Time) error
	DeleteOwner(ctx context.Context, owner, keep string) (int, error)
}
```

`NewSessions` reads `SessionOwner` once (through reflection, at construction, so a `Save` calls a plain function). When `T` has it, every `Save` and `Renew` goes to the store through `SaveOwned` with `v.SessionOwner()` (an empty owner is an anonymous session, kept but not found by any owner), and the application revokes with `Sessions.RevokeOwner(ctx, owner) (int, error)`, which calls `DeleteOwner` with an empty `keep` and returns how many sessions it deleted. `DeleteOwner` forgets every session of the owner but the one whose id is `keep`; an empty `keep` keeps none, and a `keep` that is not a session of the owner keeps nothing of the owner's either. (The first form took no `keep`; the parameter was added for `Session.RevokeOthers`, below, and it breaks a store an application wrote itself: add the parameter.) A browser that still holds the cookie of a deleted session gets a new session on its next request, as for `Clear`. `SaveOwned` replaces the owner an id had (a session that changes hands is found under its new owner), `DeleteOwner` of an owner with nothing is `(0, nil)`, and the store's own namespace is the store's: two `Sessions` types over one store share their owners, so give each its own store or prefix the owner. `T` without `SessionOwner` is unchanged: `Save` is `Save`, and a store that also implements `OwnerSessionStore` is simply never told an owner (an adapter used for every type must not be refused for it), and `RevokeOwner` then returns an error saying so. `RevokeOwner("")` is an error too: an empty owner is no one, and deleting it would read as deleting every anonymous session.

**Refusals of the owner** (rows of `refusal_test.go`, at `NewSessions`): `T` states an owner and there is no `Store` (a sealed cookie cannot be revoked, so the owner would promise what cannot be kept); `T` states an owner and the `Store` is not an `OwnerSessionStore`; `SessionOwner` is declared on `*T` and not on `T` (a `Session` holds a `T`, so the method would never be found, and the revocation would silently find nothing); `SessionOwner` has a signature other than `func() string`. **What cannot be caught before the first request:** an owner that is empty at login for a User who should have one (the session is then anonymous and out of reach of `RevokeOwner`: the owner method is the application's, and a test of the login catches it).

**Scenarios it was put against (owners).**

- _"Sign out everywhere"_: a User with a laptop, a phone and a tablet has three ids under one owner; one `RevokeOwner` deletes the three and returns 3; the three cookies are new sessions on their next request (`TestRevokingAnOwnerDeletesEverySessionOfThatOwnerAndNoOtherOwnersAndReturnsHowMany`).
- _A disabled User_: the application disables the User in its own database first, then revokes. A request that loaded the session just before the revocation and saves it just after would put it back in the store (`SaveOwned` replaces whatever the id has). That is the hostile and racing case, and it is not closed by the store: the gate is the application's Provider of the User, which reads the User on each request and answers 401 for a disabled one, so a resurrected session reads as a disabled User and is refused, and the next `Clear` or `RevokeOwner` removes it. The order to follow is: disable, revoke, then close the sockets ([ADR 0047](0047-a-socket-is-a-handle-and-a-topic-is-a-broadcast.md)). A session that never goes through that Provider (a cart) has no User to disable.
- _A login racing the revocation_: a login that began before the disable finishes after the revoke and creates a new session. Same answer: the Provider rereads the User, and the guide says to check the User's state at login, in the same transaction that reads the password.
- _A hostile client_ sends a cookie for an id of another User's: the id is random, sealed and unguessable (see Server-side stores, above), and the owner is never in the cookie or from the client: it comes from the `T` the server decoded from its own store, or from the value the handler saved.
- _An adapter written for one Redis_ used for several session types: not refused for a `T` without an owner (above), because refusing would force a wrapper per type.
- _A store whose `DeleteOwner` fails halfway_: the error is the answer (a 500 from the handler that revoked) and the count is what the store reports; the sessions not deleted are still valid, and revoking again is safe because deleting what is gone is not an error.

**What this fails at.** It finds sessions only through the store's own index: the store must keep one, and a store that keeps the owner but never indexes it makes `DeleteOwner` a scan (the store's cost, in its documentation). The revocation takes effect for a request at the next `Load`, not for one in flight, and an in-flight `Save` can put its session back (above). A cookie-sealed session cannot be revoked, so an owner is refused there rather than quietly ignored. Revocation is by owner: ending "all sessions older than X" is not here (a store call the application can make itself, and the roadmap holds the question). "All but this one" is `Session.RevokeOthers`, below.

**What was rejected (owners).**

- _The store decodes the data itself_ (the application's store parses `T`'s JSON for the owner): every store repeats a decoder of a type it does not know, and a rename of a JSON field breaks revocation in silence. A method on `T` is typed and checked at construction.
- _An owner as a field of `SessionOptions` taking a function_ (`Owner func(T) string`): a second place to state it beside the type, and a nil function is a valid-looking option that revokes nothing. The method lives with the type, and the type is where an agent looks first.
- _A struct tag on a field of `T`_ (`session:"owner"`): a tag is read at run time by the framework and a typo in it is a silent miss; a method is checked by the compiler.
- _`Save` growing an `owner` argument on `SessionStore`_: a breaking change to every existing store, and an argument most stores would ignore. A second, optional interface leaves the three-method store valid.
- _Making `DeleteOwner` part of `SessionStore`_: same break.
- _`Session.RevokeAll` on the request's own session_ (the owner taken from `Value`): it can only revoke the User of the request, and the case that matters is an administrator revoking another User. `Sessions.RevokeOwner(ctx, owner)` takes the owner as a value and serves both.
- _Refusing an `OwnerSessionStore` given with a `T` that has no owner_: it would force a wrapper per type on an adapter shared by several (above).
- _Sessions closing the owner's sockets itself_: `Sessions` would need to know about sockets and their routes, a second way to close a socket; the two calls are in one handler, in the example of [ADR 0047](0047-a-socket-is-a-handle-and-a-topic-is-a-broadcast.md).

**Sign out everywhere else** (decided 2026-11-04). A password change, or a User who asks to leave every other device, wants the other sessions ended and the one in hand kept. An application that did it with `RevokeOwner` and then saved the current session again left a gap: between the two the browser's id was gone, so a request got a 401 and the save wrote a new row under a new id. `Session[T].RevokeOthers(ctx) (int, error)` takes the owner from `s.Value.SessionOwner()`, calls `DeleteOwner(ctx, owner, id)` with this session's id as `keep`, and returns how many it ended. The browser keeps its cookie, so the handler returns none. It needs what `RevokeOwner` needs (a `T` with `SessionOwner` and an `OwnerSessionStore`, checked by `NewSessions`) and it refuses, with an error that says what to change: a new session, which is not in the store (Save it first, or use `RevokeOwner`); an empty owner; and a session whose id this request already replaced with `Renew` or deleted with `Clear`. The last is checked before anything is deleted: `RevokeOthers` loads its own id from the store, and when it is missing it returns an error saying to call `RevokeOthers` before `Renew`, so a stale id never ends the session the browser now holds (with `keep` naming a row that is gone, `DeleteOwner` would end every session of the owner, the browser's included). To renew the id as well, call `RevokeOthers` first and `Renew` after (`TestRevokeOthersEndsEveryOtherSessionOfTheOwnerAndKeepsThisOne`, `TestRevokeOthersRefusesASessionItCannotKeepAndEndsNothing`, `TestDeleteOwnerKeepsTheSessionItIsToldToKeep`). The check and the delete are two statements, so a session that ends elsewhere between them is not kept: the race of a revoke against a save, already named above.

**A sliding session** (decided 2026-11-04). `MaxAge` counts from the last `Save`, so a session that is only read ends `MaxAge` after login however busy the User is, unless every handler saves again; one application re-saved in its `me` route alone, and Users were signed out in the middle of work. `SessionOptions.RefreshAfter` makes the framework do it: when `Load` opens a session that was sealed more than `RefreshAfter` ago, it saves it again as `Save` would (a new seal time; with a store, the row under the same id with the new expiry, through `SaveOwned` for an owned type), and asks the engine to add the new `Set-Cookie` when the answer's head is completed. It adds it only when the status is under 400 and the answer sets no cookie of the session's name itself, so a handler's `Save`, `Renew` or `Clear` wins and a logout is never undone. A refresh that fails is logged at Warn (`bites: a session was not refreshed; it keeps the expiry of its last Save`) and the request goes on with the session it loaded. Zero is never, which is the behaviour before. `NewSessions` refuses a value that is negative or not under `MaxAge` (a session would expire before it is refreshed); `MaxAge/2` is the usual value and saves a session at most twice a `MaxAge`. A WebSocket's 101 is not refreshed. It is not the default, because that would change in silence how long existing sessions live (`TestASessionUsedAfterRefreshAfterIsSavedAgainSoItLivesMaxAgeFromItsLastUse`, `TestARefreshGivesWayToTheHandlersOwnCookieAndToAnAnswerThatFailed`, `TestARefreshOfAStoredSessionMovesItsExpiryInTheStoreAndKeepsItsId`).

_Against ADR 0009._ This is a header the framework adds that the handler did not return. The rule stays because the exception is narrow: an option the code wrote states it, in the place an agent reads for the session's lifetime; it never replaces a cookie the handler returned; and it is not added to an answer that failed. A handler that wants none leaves the option at zero.

_What it fails at._ A refresh that runs while `RevokeOwner` or `RevokeOthers` runs can save a row that was just deleted. This is the race named above for a handler's `Save`, now taken without the handler asking. The gate is the same: the Provider of the User refuses a disabled User on every request, so a resurrected session of a disabled User is refused. It also adds a store write to a request that only reads, once per session per `RefreshAfter`.

_What was rejected (sliding)._
- _`Session.SavedAt()` with each handler re-saving_: every route must remember to do it, and the application did it in one `me` route only.
- _A middleware_: it cannot see a `Set-Cookie` the handler set (see the `Response` doc in `middleware.go`), so it would undo a `Clear` at logout.
- _A Provider that returns cookies_: it breaks the Provider contract, which returns a value and no part of the answer.
- _Sliding by default_: it would change, in silence, how long existing sessions live.

**Axis it spends:** none, and the budget tests show it: a session type without `SessionOwner` runs the same `Load`, `Save` and `Renew` as before with one nil comparison, so `TestASessionCostsTheAllocationsADR0056Names` is unchanged (6 and 18); one with an owner adds nothing to `Load` and, to `Save`, the owner string's own work.

**What it costs.** With `RefreshAfter` zero, `Load` does one comparison more; a refresh is one JSON encode, one store write and one seal per session per `RefreshAfter`, off the guarded rows. Allocations, with the in-memory test connection and a `T` of two strings in a slice (`TestASessionCostsTheAllocationsADR0056Names`, exact): **6 a request that reads its session** (the plain 2, the decoded cookie, opened in place, and the three that decoding that `T` allocates; a larger `T` costs what its JSON costs), and **18 a request that reads and saves it** (encoding, the plaintext, the seal, the base64 text, the answer's `Cookies` slice and the `Set-Cookie` line). These are a route that uses a session; the typed request without one stays at 2, and a route that does not ask for `Session[T]` does not run `Load`. CPU: one AES-GCM open of a few hundred bytes, under a microsecond (a claim). Throughput and p99 are not measured yet; they wait for the serial run of wave 2. A key that is not the last in the list opens into a buffer of its own, one more allocation during a rotation, because a failed `Open` may write its destination.

**Refusals at construction** (rows of `refusal_test.go`): no key; a key that is not 32 bytes; a key of zeros (a placeholder left in); the same key twice; a cookie name that is not a token; a `__Host-` name with a `Domain`, another `Path` or `NotSecure`; a `__Secure-` name with `NotSecure`; `SameSite=None` without `Secure`; a negative or fractional `MaxAge`; a `RefreshAfter` that is negative or not under `MaxAge`; a `T` that JSON cannot encode. **What cannot be caught before the first request:** a cookie the handler forgot to return (above); a `T` too large for a cookie (a 500 at the first `Save`); keys that are not random.

**Scenarios it was put against.**

- _The reference workload's web side_: a signed-in user's id and roles in `Session[Auth]`, a `User` Provider that needs `Session[Auth]` and answers 401 when it is new, `Renew` at login and `Clear` at logout, with a Postgres store so that an admin can end a session.
- _A hostile client_ that flips a byte, cuts the value, sends garbage base64, a 1 MB value, or a cookie sealed by another app's key: each is a new session, at the cost of a base64 decode and one GCM open per key (`TestACookieThatWasTamperedWithOrForgedIsANewSession`).
- _A stolen cookie without a store_: it works until its sealed expiry and `Clear` cannot stop it. That is the price of not storing anything, written in `Clear`'s documentation; an application that must revoke uses a store.
- _A sibling subdomain_ that sets `session=...` for `.example.com`: the `__Host-session` cookie is not that cookie, and a `__Host-` cookie cannot be set from there.
- _A deploy that changes `T`_: an old cookie that no longer decodes into `T` is a new session.
- _Two requests that save at once_: the last cookie the browser receives wins, as for any cookie; a store sees the last `Save`. There is no merge, and the guide says to keep a session small and to save it where it changes.
- _Login CSRF_ (an attacker logs the victim into the attacker's account): `SameSite=Lax` keeps a cross-site POST from carrying the cookie, and CSRF protection ([ADR 0057](0057-csrf-trusts-the-browsers-origin-and-falls-back-to-a-double-submit-token.md)) covers the login form.

**What it fails at.** Revocation without a store (above). The cookie is visible to the browser as an opaque value, so its size tells an observer roughly how large `T` is. A handler that forgets to return the cookie. JSON is the encoding: compact enough, and a `T` with a field JSON cannot hold is refused, but it is not the smallest. Concurrent saves are last-writer-wins. A session the application wants to read in middleware (an access log of the user) is read through the Provider that needs it, with `AddLogAttrs` ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)), not by middleware.

**What was rejected.** The mutable session written after the handler, a session middleware, and a session field on every wrapper (above). A signed-only mode, and a choice of modes. HMAC-SHA256 with a separate encryption key: two keys to rotate in step for what one AEAD does. A key id in the cookie to pick the key: it saves the trial of the other keys only for a forged cookie or during a rotation, and it is one more field to get wrong; a short list of keys is tried in order. A store keyed by the raw random id in the cookie (no seal): any guessed or enumerated id reaches the store, and the expiry would be the store's alone. `gob` or a binary encoding: JSON is what the rest of the framework speaks, and a `T` readable in a debugger is worth some bytes.
