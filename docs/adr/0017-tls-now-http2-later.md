# TLS ships in milestone 2, HTTP/2 in milestone 4, and what a handler sees never depends on the protocol

TLS is `crypto/tls` inside our engine: `App.ListenTLS` and `App.ServeTLS` take a `*tls.Config`, and the engine wraps each accepted connection with `tls.Server`, so it fits a goroutine per connection unchanged. The connection's own goroutine runs the handshake first, under `Limits.HandshakeTimeout` (10 seconds, [ADR 0024](0024-limits-are-on-by-default.md)) measured on the engine's clock and set once for the connection, never per request; a handshake that stalls is closed at the timeout, and counts against `MaxConns` from accept, so a client that opens connections and says nothing cannot take more than the limit allows. `Shutdown` closes a handshake in progress as it closes an idle wait.

**Only HTTP/1.1 is negotiated for traffic, and `acme-tls/1` for a certificate challenge.** The engine speaks nothing else, so it must never leave a client believing it agreed to h2. A config whose `NextProtos` holds `h2`, or anything but `http/1.1` and `acme-tls/1`, is refused with a panic before anything is served ([ADR 0007](0007-mistakes-are-refused-at-registration.md)); the engine also sets `NextProtos` on its copy of the config to `http/1.1`, followed by `acme-tls/1` only when the config listed it, and does the same on a config `GetConfigForClient` returns, which no check before the first connection can see. `http/1.1` is first and the server's order decides in `crypto/tls`, so a client that offers both gets HTTP/1.1. A client that offers only h2 gets a failed handshake (the `no_application_protocol` alert), not HTTP/1.1; one that offers h2 and http/1.1 gets http/1.1. A plain HTTP request to a TLS port is closed without an answer.

**`acme-tls/1`, built in milestone 3 (2026-11-01, track C).** A CA's tls-alpn-01 validation (RFC 8737) connects offering only `acme-tls/1`, and the challenge is answered by the certificate the handshake presents, which an ACME client's `GetCertificate` (autocert's `Manager.GetCertificate`) returns when it sees that protocol in the hello. So a config that lists `acme-tls/1` is served with it, a handshake that negotiated it is closed by `handshake` at once, quietly, with no request read and no log line (it is not a failed handshake), and real traffic is still HTTP/1.1. A config that lists `acme-tls/1` but has only static `Certificates` (no `GetCertificate`, no `GetConfigForClient`) is refused, since nothing in it can answer a challenge: `the TLS config offers "acme-tls/1" in NextProtos but has only static Certificates, which cannot answer a tls-alpn-01 challenge: set GetCertificate to the ACME client's (autocert's Manager.GetCertificate), or remove "acme-tls/1" (ADR 0017)`. The row of `refusal_test.go` that refuses another protocol now names `spdy/3`. Tested without a real CA: a client offering only `acme-tls/1` negotiates it, `GetCertificate` sees it in `SupportedProtos`, the connection is closed with nothing logged at Debug, and clients offering `h2, http/1.1`, `acme-tls/1, http/1.1` or nothing are served HTTP/1.1 (`internal/engine/tls_test.go`, and `TestAnAppWithAcmeTLSAndGetCertificateAnswersTheChallengeAndServesHTTP11` over loopback). **What it fails at:** it was not run against a real CA (Let's Encrypt's staging), so the claim that autocert issues through it rests on RFC 8737 and the probe of [`docs/research/decisions-small/`](../research/decisions-small/report.md), section 3; and autocert's `GetCertificate` runs under its own 5 minute context, not the 10 s handshake deadline, so a hook that blocks (a slow ACME directory) holds that connection's goroutine past `HandshakeTimeout`, counted against `MaxConns`, until the CA answers.

**A failed handshake is logged by what it says about the operator's certificate** ([`docs/research/decisions-small/`](../research/decisions-small/report.md), section 4). A handshake that ends in a received client alert that rejects the certificate (`bad_certificate`, `unsupported_certificate`, `certificate_revoked`, `certificate_expired`, `certificate_unknown`, `unknown_ca`) is a Warn, "a client rejected the TLS certificate (expired, wrong name or untrusted?)", with the error, the remote address and `suppressed=N`, at most one a minute on the engine's clock; the failures skipped since the last Warn are counted into `suppressed`. Every other failure (a port scan, plain HTTP, a client with only old versions, a handshake that stalled, an error from `GetCertificate`) is a Debug line, and the line is built only when Debug is enabled, so a scanner costs a failed handshake no allocation with Debug off. `GetCertificate` errors are not promoted: with autocert and a host policy a scanner connecting by IP produces them all day. The alert is read from the error as a `*net.OpError` with `Op` "remote error" whose `Err` is `crypto/tls`'s unexported `alert`, a `uint8`, so its number is read with `reflect` (the exported `tls.AlertError` is only wrapped on the QUIC path; the report's claim that it is wrapped here was wrong, found by running it). A client that rejects the certificate and just closes, without an alert, appears as EOF and stays at Debug: that is a limit of what TLS tells the server. No counter is exposed: there is no surface to read it from yet.

**Disconnects and the linger.** The disconnect watcher ([ADR 0016](0016-the-handler-context-is-cancelled-on-disconnect.md)) and `lingerClose` reach the socket through `(*tls.Conn).NetConn()`. The epoll watcher registers for hangup only and never reads, so TLS records are not disturbed, and a peer that leaves, with or without a close_notify, cancels the context with `ErrClientGone`. The reader-goroutine fallback reads through the `*tls.Conn`, where one byte is one decrypted byte, and keeps a pipelined byte as it does for a plain connection. A refused head is answered, then the engine sends close_notify, half-closes the socket and drains it for a moment, as for a plain connection.

**What a TLS connection costs idle**, measured on 2026-10-31 with the harness of [ADR 0033](0033-the-rules-are-build-steps.md) (10,000 to 20,000 connections, each handshaken and served one request, settled 5 s, three interleaved runs, [`docs/research/tls-idle/`](../research/tls-idle/report.md)): **11.9 KB of heap plus stack** a connection kept on a goroutine (parking, below, takes it to 7.6 KB) (11,900 to 11,903 B) and **21.6 KB of RSS** (20,738 to 22,449 B), against 3.2 KB (3,160 to 3,165 B) and 4.1 KB (3,973 to 4,183 B) for a plain connection. The stack is 4,096 B against 2,048 B because the idle read goes through `tls.Conn.Read`; the heap is 7.8 KB against 1.1 KB, the two directions' cipher state and record buffers. RSS is about 10 KB over heap plus stack because a TLS handshake allocates about 57 KB of garbage and the runtime keeps those spans after the collection. A plain connection did not move (3,162 B against 3,161 B for the commit before, same session). `TestTheMarginalHeapAndStackOfAnIdleTLSConnectionStaysUnderItsCeiling` holds a TLS connection to 14.5 KB, as the plain gate holds 4.5 KB. TLS adds no field to a connection and nothing to the request path: the allocation rows of [ADR 0003](0003-the-trade-budget.md) are plain-connection rows and are unchanged.

**TLS and parking, built (step 16).** `crypto/tls` reads a whole record from the kernel and returns the bytes asked for, so decrypted bytes (a pipelined request) can sit inside the `*tls.Conn` while the kernel's socket shows nothing readable, and `crypto/tls` has no method that says whether it holds any. The engine does not need one: a connection parks only after its one-byte idle read on the `*tls.Conn` returned a timeout with no byte, and `tls.Conn.Read` returns that only when its buffer of decrypted bytes is empty and it is blocked on the socket for the rest of a record (a whole record already read would have been decrypted and returned first). What it holds then is at most a part of a record, whose rest must come through the socket and wakes it. A handshake never parks, because it runs before the connection first waits. Parked, an idle TLS connection holds **7.6 KB of heap plus stack** (7,577 to 7,585 B, marginal from 10,000 to 20,000, three interleaved runs) against 12.0 KB kept on a goroutine, the 4 KiB stack gone, and **17.4 KB of RSS** from 0 to 20,000 connections against 22.8 KB ([`docs/research/parking/`](../research/parking/report.md), [ADR 0005](0005-our-own-http1-engine-with-a-goroutine-per-connection.md)). The rest is crypto/tls's own state, both directions' cipher state and record buffers, which parking does not touch. The gate is 9.1 KB parked (`TestTheMarginalHeapAndStackOfAnIdleTLSConnectionStaysUnderItsCeiling/parked`) and 14.5 KB `WithoutParking`. The tests that hold it: a request whose first TLS record arrives in two parts with a pause past 100 ms between them is answered, and two pipelined requests in two records are both answered, parked or not (`internal/engine/park_test.go`). What step 3 did not do, mTLS and certificate reload, is built in milestone 3 ([ADR 0066](0066-client-certificates-are-verified-by-the-tls-config-and-read-as-verified-chains.md), [ADR 0067](0067-a-certificate-is-reloaded-through-get-certificate-and-a-failed-reload-changes-nothing.md)); session-ticket key rotation is `crypto/tls`'s own.

HTTP/2 (h2 over ALPN, and h2c) is milestone 4 ([`docs/roadmap.md`](../roadmap.md)), not earlier, because the reference workload ([ADR 0002](0002-the-reference-workload.md)) usually sits behind a load balancer that speaks HTTP/2 to clients and HTTP/1.1 to the service. It is on the list a finished framework carries because without it bites cannot face clients directly.

**What "protocol-independent" means, precisely.** An Input, an Output, an error, a Provider, a middleware's request view and a `Stream` carry nothing that exists only in HTTP/1.1: no `Connection`, `Transfer-Encoding`, `Keep-Alive` or `Upgrade` header reaches them, and chunking is the engine's business. So a future HTTP/2 engine changes no user code. Three things are per engine and are redesigned with it: the goroutine per connection of [ADR 0005](0005-our-own-http1-engine-with-a-goroutine-per-connection.md) becomes one per stream, disconnect detection ([ADR 0016](0016-the-handler-context-is-cancelled-on-disconnect.md)) becomes a stream reset, and buffer pooling is redone for multiplexed frames. WebSockets stay on HTTP/1.1 (RFC 8441 is not planned).

**What was rejected:** logging every failed handshake at Debug, which hid the one failure that points at the operator's certificate, and built the remote address (4 allocations, about 50 ns) before the level was checked; a Warn on every failure, which lets a scanner or an attacker fill the log.

**What was rejected, at step 16:** keeping every idle TLS connection on a goroutine until `crypto/tls` could be asked whether it holds bytes, the position before parking was built. It cannot be asked, and need not be: the timed-out idle read is the proof, and parking took 4.4 KB of heap plus stack off every idle TLS connection with the tests above holding ([`docs/research/parking/`](../research/parking/report.md)). Inspecting `crypto/tls`'s unexported buffers with reflect was not needed and was not done.

**What was rejected, earlier:** the first draft of this ADR said what TLS adds per connection "is measured before it ships", with the figure unknown; it is now the 11.9 KB above. A handshake started lazily by the first read (`tls.NewListener`) was rejected: it would run under the idle and head deadlines, not its own, and would not count as a handshake against `MaxConns`.

**Considered:** HTTP/2 through net/http's server as a second engine from the start. Not rejected, only not first: it is the cheapest way to add HTTP/2, at net/http's allocation cost, and milestone 4 weighs it against an engine of our own with both measured.

**What was rejected, in milestone 2: refusing `acme-tls/1` with every other protocol.** The set of protocols was `http/1.1` alone, which also refused `acme-tls/1`: with the engine's forced `NextProtos` of `[http/1.1]` the CA's hello fails with `no application protocol` before `GetCertificate` is called (measured, [`docs/research/decisions-small/`](../research/decisions-small/report.md), section 3, probe `tlsalpn`), so autocert could not answer the challenge. It was a known gap deferred to milestone 3 with what it would need, from that probe: the allowed set `{http/1.1, acme-tls/1}` with `http/1.1` first, `h2` still refused, the engine adding `acme-tls/1` only if listed (also on a `GetConfigForClient` config), a refusal for `acme-tls/1` with only static `Certificates`, and a negotiated `acme-tls/1` closed quietly and not counted as a failed handshake. All of it is what was built above. mTLS ([ADR 0066](0066-client-certificates-are-verified-by-the-tls-config-and-read-as-verified-chains.md)) and certificate reload ([ADR 0067](0067-a-certificate-is-reloaded-through-get-certificate-and-a-failed-reload-changes-nothing.md)) were built in the same track; session-ticket key rotation is `crypto/tls`'s own.
