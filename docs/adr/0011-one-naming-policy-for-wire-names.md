# One application-wide policy maps Go field names to wire names

Exported Go fields begin with a capital letter, so a rule must turn `PageSize` into what a client sends. The application sets one naming policy, snake_case by default, and it applies to path parameters, query parameters, cookies and body fields alike; error locations and the API description use the same names.

**How a name is split.** A run of capitals is one word, and its last capital starts the next word when a lower-case letter follows: `ItemID` is `item_id`, `HTTPStatus` is `http_status`, `UserIDs` is `user_ids`. Digits stay with the word before them. A lone lower-case `s` after a run of capitals is a plural and stays with the run, so `UserIDs` is `user_ids` and `URLs2` is `urls2` rather than `user_i_ds`, while `HTTPSServer` is still `https_server`; the rule as first written produced `user_i_ds`, which building it showed. Two fields of one struct that produce the same wire name are refused at Registration.

**Headers** are not under the policy: a header field's name becomes its canonical kebab form, `RequestID` to `Request-Id`, `IfNoneMatch` to `If-None-Match`, which covers the standard headers without help. In a header's name, and only there, a leading `X` followed by an upper-case letter is a word of its own, so `XAPIKey` is `X-Api-Key` and `XCSRFToken` is `X-Csrf-Token`; header names are compared without regard to case, so that matches the `X-API-Key` a client sends. Matching stays exact: only the derivation of the name changes. Three kinds of name stay wrong under any splitting rule and are what `WireNames` is for: a brand in camel case (`XGitHubEvent` is `X-Git-Hub-Event`), a run of digits that is a word (`XHubSignature256` is `X-Hub-Signature256`), and `ETag` (`E-Tag`). [`docs/research/header-names/`](../research/header-names/report.md) puts 19 names against the rule: as first built, 7 were read from the wrong name, and the X rule fixes 4 of them. Built 2026-11-01, milestone 3 wave 0 (`TestALeadingXBeforeACapitalIsAWordOfItsOwnInAHeaderNameOnly`, `TestAHeaderFieldXAPIKeyIsReadFromXAPIKeyAndItsErrorIsLocatedThere`).

**Where a header's error is.** A field error in a header is located by the header's canonical name, `header.X-Api-Key`, not by the naming policy, because headers are not under the policy and a client looks for the name it sends. A `Validate` method that locates a header error writes the same form.

**Names no rule produces** (`X-Api-Key`, `$top`, `page[size]`, `OAuth2Token` wanted as `oauth2_token`) are given by an optional method on the section's struct, `WireNames() map[string]string`, keyed by Go field name and checked at Registration against the struct's fields, so a stale entry is refused rather than ignored. **Each struct in a section names its own fields** (decided 2026-11-03): a section made of embedded structs, `Query struct{ Filter; Paging }`, reads each embedded struct's own `WireNames` for that struct's fields, and the section's own method wins for a field both name, because it is the route's view of the whole. Before, only the section's method was read, and when two embedded structs both had one Go promoted neither, so their names fell back to the policy without a word: on a Query the parameter the client sent under the intended name was then an unknown key, ignored, and the filter matched every row. A promoted method is told from a declared one by what it returns (the rule [ADR 0020](0020-descriptions-come-from-registration-and-later-from-doc-comments.md) uses for `Descriptions`), and each struct's keys are checked against its own fields, so a stale entry in an embedded struct is refused naming that struct. A body type that already carries `json` tags, because it is shared with other code, keeps them, and a tag wins over the policy. **A `json` tag on a text Section's field is not read, and one that names the field otherwise is refused** (decided 2026-11-03): ``PageSize int `json:"pageSize"` `` in a Query would be read as `page_size` under the snake_case policy while its author meant `pageSize`, so Registration names the field, the tag's name and the wire name and points to `WireNames`. A `json` tag that agrees with the wire name, as on a struct shared between a Query and a body, changes nothing and is let through, as is one with no name (`json:",omitempty"`); a header compares without case. Before, such a tag was ignored, and the parameter the client sent under the tag's name was an unknown key. The tags other frameworks read for a place (`query:"q"`, `path:"id"`) are refused by [ADR 0021](0021-validation-is-a-method-and-a-few-constraint-types.md).

**Seeing the names** (decided 2026-11-03). A policy is a Go function inside the application, so the wire name of `OrgUnitID` under a camelCase policy is written nowhere in the source: a reviewer cannot grep `orgUnitId`, and a body's JSON shape is visible only by running the app, where a Huma user reads it in a tag. `App.WriteWireTable(w)` prints, route by route, the section, the Go field path, the wire name and the type of every path, query, header and cookie field, of the body (nested objects, lists and maps included) and of the success responses. It is read from the plans Registration compiled: the text sections' fields as the decoder will look them up, and the body and response types through `jsoncodec.Describe`, the function the API document is built from, with the app's own `Names`, `Formats` and `AllowUnknown`. So it works for any policy and cannot disagree with the decoder, the encoder or the document. It spends none of the four axes: it is called by a test or a `main`, never on a request, and the only cost at Registration is one retained record a route. Undocumented routes are listed, since they decode the same way; WebSocket routes and response wrapper headers are not.

**One policy per app.** An API whose v1 is camelCase and v2 snake_case is two apps mounted on one engine under two prefixes.

**What this costs:** `WireNames` is a map of strings, which is what a tag is; the difference is that it is checked when the program starts and lives in one place per struct. It is for the names no rule can produce, not the ordinary case.

**Considered, for seeing the names:** a `-wire` mode of `bites-doc`, rejected because the tool reads syntax and cannot run the application's policy function, so it could handle only the built-in policies and would print a plausible wrong table for a custom one, which is worse than none; the tool would also have to repeat the splitting rules of this ADR in a second place, and the two would drift. Reading the API document was rejected as the answer because it leaves out Undocumented routes, shows a body only as a schema and has no Go field path to grep against. A `bitetest` helper was rejected because the table needs the registered plans, which only the App holds.

**Considered:** a tag on each field, as Huma and Gin do. Rejected because a tag repeated on every field is where names drift apart, and the policy is one line. A policy per route group was rejected because one app speaking two conventions is two APIs, and mounting two apps says so.

**What was rejected for headers** (2026-11-01). The rule as first built, under which a run of capitals after the leading `X` made one word, so `XAPIKey` was read from `Xapi-Key` and a client sending `X-API-Key` got a 400 for a header it did send ([`docs/research/header-names/`](../research/header-names/report.md)). Matching a header by its letters and digits alone, ignoring dashes and case, so every spelling of `X-API-Key` would match: it fixes every row of the probe, and it lets a client send `X-ApiKey` past a proxy that strips `X-Api-Key` by its exact name before setting its own, the attack nginx avoids by dropping headers with underscores. Refusing a header field whose name starts with `X` and a run of capitals: a start-up panic where a rule gives the right answer. A list of known header names in the core: it grows forever and is still wrong for the header it does not list. Leaving the rule and documenting `WireNames` for every such header: the common case would need the escape hatch. Locating header errors by the naming policy (`header.x_api_key`), which a comment in `validate.go` showed: the client would be told about a name it never sent. Lower case (`header.x-api-key`), the form HTTP/2 uses on the wire: the canonical name is the one the API document shows.
