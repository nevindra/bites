# The `bitetest` WebSocket client reads on its own goroutine, answers pings by default and times out in real time

`Server.DialWS(WSRequest{Target: "/rooms/7"})` opens a WebSocket on the in-memory server and returns a `*WS` after a valid 101 ([ADR 0027](0027-an-in-memory-entry-point-runs-the-engine-path.md)); it fails the test, printing the answer, for any other. `TryDialWS` returns the client or, when the server refused, a nil client and the HTTP `Response` (a 400 naming a field, a 401 from a Provider, a 403 for an origin, a 404, a 426), which is how a refused handshake is tested. The client sends a random `Sec-WebSocket-Key`, verifies the `Sec-WebSocket-Accept` the server returns, sends masked frames as a browser does, and adds the headers of `WSRequest.Header` (an `Origin`, a cookie).

**It sends** `SendText`, `SendBinary`, `SendJSON`, `SendFragments` (one message over several frames), `Ping`, `Pong` (an unsolicited pong, which counts as a sign of life, [ADR 0039](0039-heartbeats-run-on-one-timer-wheel.md)), `Close(code, reason)` and `Leave` (the connection dropped with no Close frame). **It reads** `Read` (the next message of any kind), `ReadText`, `ReadJSON`, `ReadData` (a text or binary message, skipping pings and pongs), `ReadPing`, `ReadClose` and `ExpectClose(code)` (the server's status and reason), `ExpectEOF`, `Quiet()` and `TryRead(d)` for a test that wants the error. A `Message` has a `Kind` (`Text`, `Binary`, `Ping`, `Pong`, `Close`), its payload, and for a Close its `Code` (1005 when the server sent none) and `Reason`; fragments are joined and a text message that is not UTF-8 is an error.

**One goroutine reads from the moment the client is dialled.** It parses the server's frames and hands whole messages over a channel, so the server's writes never wait on the test, and a read can time out without a second goroutine reading the same connection behind it (the hand-written helper of the repository's own tests starts one goroutine per read and relies on the test ending when a read times out). It answers each ping with a pong of the same payload before delivering it, as a browser does, so a test that advances the clock by a heartbeat interval and moves on is not closed with 1008 by its own client; `WSRequest.NoAutoPong` turns that off for the test of the missed pong ([ADR 0039](0039-heartbeats-run-on-one-timer-wheel.md)).

**Timeouts are real time and never the app's clock.** A read waits at most `WSRequest.Timeout` (five real seconds by default) and then fails the test, so a test never hangs. The server's own timeouts run on the app's clock and are moved with `Clock.Advance`; the client's wait is not, because a fake clock that only moves when told would make a missing message wait for ever.

**Its refusals.** None at Registration (it is test support); it fails the test with the answer or the error for a handshake that is not a 101, a wrong accept key, a frame over 1 GiB, a connection that ends when a message was expected, and a message of the wrong kind where the test named one.

**Axes:** none; test support only.

**Scenarios it was put against.** The chat room of the reference workload: several clients dial the same route, each reads its own messages. A heartbeat test: advance by the interval, `ReadPing`, send a message, read the echo (the echo proves the pong was read before the clock moves again); the client with `NoAutoPong` is closed with 1008 at the second missed pong. A refused origin: `TryDialWS` returns the 403 problem. A client that leaves: `Leave`, and `OnClose` sees 1006.

**`SendJSON` writes as the app writes** (decided 2026-11-04): with the app's naming policy and codec, through an internal door as `Start` replaces the logger. It used `encoding/json`, so a route's own untagged message type went out under Go names, the app closed the socket with 1007 as malformed, and the test saw only a read that timed out; the testing guide's example did exactly that and passed review because the docs' blocks were compiled and not run ([`docs/research/agent-usability/`](../research/agent-usability/run-2/report.md), rows 5 and 6).

**A stream of events is read the same way** (built 2026-11-04). `Server.OpenEvents(Request)` reads the head of an `SSE` or `Events[T]` answer, fails the test with the status and body when it is not a 200 stream, and returns an `*EventStream` whose reader goroutine parses events and comments as they arrive; `Next` fails after five real seconds and `TryNext` returns `io.EOF` at the end. `Do` cannot read a live stream, which has no end, and an agent building an SSE route found no way to test it but writing the request and parsing the stream by hand ([`docs/research/agent-usability/`](../research/agent-usability/report.md), row 5). A comment is returned as an `Event` with only `Comment` set, so a handler that writes one when it is ready lets a test wait for it before publishing.

**What it fails at.** Because the client reads eagerly, it cannot show a slow reader: the server never sees backpressure from it. A test of [ADR 0037](0037-a-slow-reader-is-closed-not-buffered-forever.md) dials with `Server.Dial` and writes and reads frames by hand, as the repository's own tests do. It does not send a frame that breaks the protocol (an unmasked frame, a reserved bit, a bad UTF-8 text) either, for the same reason: those tests need the bytes, and `Dial` gives them. It does not negotiate subprotocols or extensions, which the server ignores ([ADR 0046](0046-websocket-origins-and-inbound-limits.md), [ADR 0040](0040-no-permessage-deflate-for-now.md)).

**What was rejected:** reading on demand with a goroutine per read (a timed-out read leaves its goroutine reading, so the next read would race it); a deadline on the connection for the timeout (the in-memory connection measures deadlines on the app's clock, which does not move); a helper that fails the test on a ping the test did not expect (a heartbeat that falls due while the clock moves is not a failure).

**Nothing arriving is a ping, not a wait** (decided 2026-11-04). The first build had `ExpectSilence(d)`, which read for `d` of real time and passed if nothing came; an application's tests that a private room's activity did not reach an outsider each waited 150 to 300 ms, and a slow machine could pass one that should fail. `Quiet()` replaces it: it sends a ping with a payload of its own and reads up to the pong that answers it. The engine queues a pong in the socket's one queue, behind every frame already queued (`WS.control`), so the pong arriving means everything the server had for the socket has arrived, and a data message or a Close before it fails the test with what it was. It does not wait for what is not queued yet (a goroutine of the application that has not run), which the real-time wait did not promise either. Rejected: a hook into the engine's queue (`Server.WaitEnded`'s shape), which would see the queue but not the bytes still in the in-memory connection or the client's reader; and keeping both, two ways to say one thing.

**`Pending` returns what `Quiet` asserts** (decided 2026-11-05, from an application's tests). A test of what another socket's handler produced does not know how many frames to read, and `Quiet` could only say there were none. `Pending() []Message` is the same wait (a ping of its own, read up to its pong) returning the data messages in order and removing them from what the test has still to read; `Quiet` is `Pending` that fails when the list is not empty, naming the first message. It is one mechanism with two names that answer different questions, assert and return, so it is not a second spelling of one thing: a test cannot say "nothing arrived" with `Pending` without writing the assertion `Quiet` is. A Close is returned as the last `Message` and `Pending` stops there without waiting for a pong, because a closed connection answers none; failing the test would hide the data before the Close, which the test asked for, and a test that wants no Close reads the last `Kind`. `Quiet` still fails on a Close. Rejected: a second wait with its own ping for each name (two mechanisms to keep equal), and `Pending` failing on a Close (it could not report "two frames and then a Close").

**Three cases pass too early, and one is the broker** (decided 2026-11-05). The ping waits for the server's queue and no goroutine of the application, so a frame queued by another socket's handler, by `OnClose`, or by a broker that delivers on its own goroutine is not waited for. `bitetest.Broker.Async` makes the in-memory broker deliver as `modules/pgnotify` does, on a goroutine for each subscription in the order of its Publish calls, so a test can show the difference instead of passing with a broker that is kinder than production; the default stays synchronous, which needs no wait. The test that shows `Quiet` passing early holds the delivery on a gate and then reads the expected frame. `Broker.Settle` (decided 2026-11-05) returns once the bus is idle, chains included, so `Settle` then `Quiet` asserts an absence on the asynchronous path without a real-time wait; it panics inside a subscription's callback and returns at once without `Async`.
