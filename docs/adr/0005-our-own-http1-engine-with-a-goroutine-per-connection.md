# Our own HTTP/1.1 engine, with a goroutine per connection and buffers held only during a request

The server under bites is written here: one goroutine per connection while it has something to do, which waits for the next request still holding the read buffer of the last one for the first 100 ms of an idle wait, reading straight into it, and blocks on a one-byte read holding nothing after that, taking a buffer from a pool only when bytes arrive. A connection still idle after 100 ms is parked on the engine's epoll and its goroutine ends; bytes give it a goroutine again (below, "Parking, built"). It is not net/http's server and not an event loop: a request, a handler and a WebSocket message always run on a goroutine of their own connection.

Measured on 2026-10-30, two physical cores for the server ([`docs/research/engines/`](../research/engines/report.md)):

| | idle, bytes a connection (marginal, 10k to 20k) | GET /, req/s | 1,000 handlers blocked 10 ms, peak RSS | allocations a request |
|---|---|---|---|---|
| hand-written, buffer pooled (this design) | 3,408 | 1.34M | 19.3 MB | 0 |
| hand-written, 4 KiB buffer held | 7,713 | 1.45M | 17.2 MB | 0 |
| net/http | 19,926 | 620k | 59.2 MB | 13 |
| fasthttp | 16,383 | 1.19M | 30.0 MB | 0 |
| fib (event loop) | 1,078 | 1.14M | 77.6 MB | about 1 |
| nbio (event loop) | 1,151 | 536k | 34.9 MB | about 27 |

**Why not net/http's server:** 13 allocations and about 20 KB of every idle connection are its own buffers and bookkeeping, not the goroutine: the same model with its buffer pooled holds 3.4 KB.

**Why not an event loop:** it is three times smaller per idle connection, and that is all it wins (and parking, below, has taken that from it). With handlers that block, which is what a database call in ordinary Go is, its worker pool grows to a goroutine per blocked handler and it held four times the memory (fib, 77.6 MB). Staying small needs the handler written as callbacks (fib's `Retain`/`Release`, 28.4 MB and about 7% slower), which gives up what goroutines exist for. Every event-loop library measured also reuses request objects across requests, which [ADR 0008](0008-no-pooled-object-reaches-the-user.md) refuses.

**What this costs:** an HTTP/1.1 parser of our own is a security surface (request smuggling above all), so it is fuzzed differentially against net/http's parser before it serves anything. Pooling the buffer costs about 5% of plain throughput, because a request is read in two calls. The 1.34M figure comes from a server that answers GET with no body and no pipelining, so it is a ceiling, not a promise. **Idle WebSockets**, which [ADR 0002](0002-the-reference-workload.md) makes a first-class case, were measured separately ([`docs/research/ws-idle/`](../research/ws-idle/report.md)), bytes per idle socket, marginal from 10k to 20k:

| | per idle WebSocket | at 1M sockets (extrapolated) |
|---|---|---|
| goroutine per connection, buffer pooled (this design) | 3,615 | 3.6 GB |
| fib (event loop) | 1,292 | 1.3 GB |
| nbio (event loop) | 1,452 | 1.5 GB |
| gws | 13,058 | 13.1 GB |
| gorilla/websocket | 17,285 | 17.3 GB |
| coder/websocket | 23,789 | 23.8 GB |

The event loop stays 2.5 to 2.8 times smaller per idle socket, about 2.2 GB at a million. Of this design's 3.6 KB, 57% is the goroutine's minimum 2 KiB stack, and nothing tried (a shallower stack at the blocking point, no read in flight at all) moved it by more than the spread between runs; only releasing the goroutine while a socket is idle can.

**The engine as built** (`internal/engine`) holds 3.1 to 3.5 KB per idle connection, mostly 3.2 to 3.3 KB, as marginal heap plus stack from `runtime/metrics` with the client in a child process, eight runs at 200 to 1,200 and 1,200 to 2,200 connections. That is 300 to 400 B over the bare prototype: the connection struct, which carries the Exchange, the slab header and the list pointers so that a request allocates none of them. The figure is a different measure from the RSS table above, so the two are compared with care; the tests assert a 4.5 KB ceiling, which a connection still waiting on a grown stack fails, and log the number. Milestone 1's benchmark took it at scale ([`bench/result/milestone1.md`](../../bench/result/milestone1.md)): through the whole app, each connection having served one request, the marginal cost from 10k to 20k connections is 3,157 to 3,166 B of heap plus stack and 3,974 to 4,187 B of RSS, against 18.2 KB and 19.1 to 19.8 KB for net/http on the same harness.

**An idle connection waits on a fresh stack, where it cannot park.** Go grows a goroutine's stack while a request runs (a typed route took it from 2 KiB to 4 KiB, a handler calling a driver or `fmt` takes it further) and does not shrink a stack of 4 KiB under a goroutine blocked in a read: the runtime halves a stack only when what is in use, plus about 800 B of guard, is under a quarter of it, and the frames of a blocked read are larger than a quarter of 4 KiB leaves. A stack of 8 KiB or more is halved; a busy connection's wait keeps it with padding (below). So the connection's idle read first waits 100 ms (`moveAfter`); a connection still idle then hands the rest of its wait to a fresh goroutine and the old one exits, taking its grown stack with it. A busy connection never moves and sets the one deadline it set before. Through the whole app an idle connection that has served a request holds 3.1 to 3.4 KB (marginal, 1,200 to 2,200 connections), not 5.1 to 5.4, with throughput, p99, CPU and allocations a request unchanged ([`docs/research/stack-handoff/`](../research/stack-handoff/report.md)). What it fails at: a client that sends a request just over every 100 ms pays a move each time, about 1.3 to 2.6 µs of CPU, and a connection idle for less than 100 ms still holds its grown stack. Since parking, the move is what happens where a connection cannot park (off Linux, an in-memory connection, a WebSocket assembling a message, `WithoutParking`); a parked connection's next goroutine starts on a fresh stack anyway.

**A busy connection waits holding its buffer (2026-11-04).** The first 100 ms of an idle wait, the stretch before it moves or parks, read straight into the scratch the last request used, which the connection keeps instead of returning to the pool: the next request comes whole with that one read, its head needs no `HeadTimeout` armed, and the answer finds its write deadline still armed (ADR 0024). A keep-alive request had cost two reads and five deadline changes (the wait's, the head's armed and cleared, the write's armed and cleared); it costs one read and one ([`docs/research/optimisation-pass/`](../research/optimisation-pass/report.md), `TestABusyKeepAliveConnectionReadsEachLaterRequestWithOneReadAndChangesOneDeadline`). A connection quiet for 100 ms gives the scratch back and clears the write deadline before it moves or parks, so the idle figures below are unchanged and the connection struct keeps its size class (416 B); the state that tells a write what is armed lives in the scratch. What it costs: during those 100 ms a connection holds its scratch (about 4.6 KB with its 4 KiB buffer) beside the goroutine and stack it already held for them, so at most the connections that sent a request within the last 100 ms hold one, about 4.6 MB for every 1,000 of them. A WebSocket waits the same way between messages. What was rejected: a separate, shorter window (10 ms) bounded that memory tighter, but split the first wait in two, an extra timer change for every client quiet between 10 and 100 ms, and moved the times every idle test pins.

**A busy connection's stack is not halved under its wait (2026-11-05).** A typed route grows its goroutine's stack to 8 KiB and three middleware take it to 16 KiB, while a hot wait's blocked read uses about 1.65 KiB counting the guard, under a quarter of either. The collector, which runs about a hundred times a second under load because a server's live heap is small, halved the stack at every cycle, and the next request grew it back with a copy. So a hot wait blocks under a frame of padding (`waitHot`): none at first, then 1 KiB, 3 KiB and 7 KiB, each tier taken by a wait that finds its stack moved under it (only a shrink moves a blocked goroutine's stack), which keeps stacks of 8, 16 and 32 KiB. The room is never zeroed, and a tier is reached only once the stack is large enough to have been shrunk at the tier below, so the padding never grows a stack. Each goroutine starts at no padding, since each starts on a fresh stack. Measured against the tree without it, three rounds interleaved ([`docs/research/stack-shrink/`](../research/stack-shrink/report.md)): p99 -21% on the typed GET and -22% on the POST with no middleware, -26% and -28% with three, throughput +1% to +3%, CPU a request 2% to 4% less, allocations and bytes a request unchanged, and an idle connection's 937 B against 939 B. What it costs: the padding is scanned stack, so the heap goal rises by its size (5 MB instead of Go's 4 MB floor with 256 connections waiting under 3 KiB), and the collector runs less often for it (60 cycles a second instead of 94 with three middleware). A connection keeps the stack its requests grew for the at most 100 ms it waits hot, which a busy one regrows to anyway. What it fails at: a stack beyond 32 KiB is still halved, and a goroutine pays one shrink for each tier before it settles. `TestAHotWaitStopsTheCollectorShrinkingAStackItsRequestsGrewTo16KiB` holds it.

**Parking, built (step 16).** A connection whose one-byte idle read has seen nothing for 100 ms is registered with the engine's poller, one epoll instance and one goroutine made at the first park, for one event (`EPOLLIN | EPOLLRDHUP | EPOLLONESHOT`), and its goroutine ends. Bytes, the peer's hangup, the idle timeout (now a node on the timer wheel of [ADR 0039](0039-heartbeats-run-on-one-timer-wheel.md), so rounded up to its one-second tick), Shutdown or Close, and a WebSocket's own end from another goroutine (its close deadline, the flusher or an inline Send closing the socket) each wake it, which starts one goroutine; that goroutine reads what woke it at once and serves on as before. Plain, TLS and WebSocket connections park alike; a WebSocket assembling a message does not, so `MessageTimeout` stays a read deadline ([ADR 0046](0046-websocket-origins-and-inbound-limits.md)). Everything else a parked WebSocket needs already ran on other goroutines and goes on doing so: the heartbeat on the wheel, and Send, Publish, Close and Shutdown's 1001 through the inline write or the flusher ([ADR 0037](0037-a-slow-reader-is-closed-not-buffered-forever.md)). It is the engine's default on Linux for TCP connections; `WithoutParking()` keeps every idle connection on a goroutine as before, and off Linux and on in-memory connections nothing parks.

*Exactly one goroutine owns a connection.* A word on the connection says who: a goroutine, a goroutine registering it (parking), nobody (parked), or woken while registering. The owner sets "parking" before it registers and swaps it for "parked" after; a wake swaps "parked" back to "owned" and only the swap that succeeds starts a goroutine, so two events, or an event and the idle timeout together, start one; a wake that finds "parking" marks it woken, and the owner, whose swap then fails, keeps the connection and reads again. Bytes that arrive between the decision to park and the registration are not lost: epoll reports a descriptor that is already readable when it is added or re-armed, and nothing read them, because the decision follows a read that returned none. One-shot registration fires once until the next park re-arms it, and each park carries a generation, so an event of an earlier park is dropped. A connection that has ended is owned for ever (only its owner ends it), so a late event, a late wheel callback or Shutdown never starts a goroutine for it; whoever closes a connection it does not own (Shutdown, Close, a WebSocket's close deadline, the flusher) closes it and then wakes it, so its own goroutine runs `finish`, which gives back its place under `MaxConns` and calls `OnClose`. The poller registers and forgets a descriptor inside `RawConn.Control`, where it is certain to be the connection's own and not a number the kernel has given to another connection since. The tests are in `internal/engine/park_test.go`, most of them on both paths (parked, and `WithoutParking`): requests sent around the moment eight connections park, all answered; concurrent wakes start one goroutine; a wake while registering leaves the connection with its goroutine; the idle timeout, Shutdown, Close and a client leaving each end a parked connection; a context is still cancelled when the client leaves mid-handler after the connection parked; a TLS record split across a park is read; a parked WebSocket gets a Send from elsewhere, its pings, a 1008 when it never answers, Shutdown's 1001 with `OnClose` seeing it, and a socket half through a message never parks.

*TLS* parks only after its idle read on the `*tls.Conn` timed out with no byte, which `crypto/tls` returns only with no decrypted byte and no whole record held ([ADR 0017](0017-tls-now-http2-later.md)); a handshake never parks.

*What it measured* ([`docs/research/parking/`](../research/parking/report.md), three interleaved runs, server on cores 2 and 3, the same binary with and without `WithoutParking`, and the tree before the step built in the same session), bytes a connection, heap plus stack marginal from 10,000 to 20,000 connections, with RSS from 0 to 20,000 (the marginal RSS is not sound for a connection this small: the second 10,000 fit partly in pages the first left resident):

| plain, RSS 0 to 20k | 3,479 [3,216-3,958] | 5,184 [5,116-5,225] | 5,179 [5,105-5,222] |
| TLS, heap plus stack | 7,581 [7,577-7,585] | 11,994 [11,990-11,999] | 11,966 [11,961-11,970] |
| TLS, RSS 0 to 20k | 17,440 [17,433-17,446] | 22,777 [22,639-22,951] | 22,568 [22,532-22,637] |
| WebSocket, heap plus stack | 1,642 [1,632-1,661] | 3,966 [3,964-3,969] | 3,934 [3,932-3,938] |

That is 73% less a plain connection, 37% less a TLS one (the rest is crypto/tls's own state) and 59% less a WebSocket, and a parked plain connection holds less heap plus stack than fib's 980 B ([`bench/result/fib.md`](../../bench/result/fib.md)). A connection that is never idle for 100 ms never parks, so busy connections are unchanged: GET 829k against 831k req/s, POST 676k against 677k, GET over TLS 768k against 767k, WebSocket echo 952k against 954k messages a second, every p99 within 2% and inside the spread, and a typed POST at 2.007 allocations and 321 B either way. A parked connection costs about 180 B of its own (a `parkState` made at its first park) and 8 B in the poller's table; the connection struct grew from 352 to 360 B, inside its size class.

*What it costs.* A request that finds its connection parked pays the wake: with 2,000 connections each sending a request every 300 ms, p50 32 against 25 µs, p90 76 against 42, p99 101 [99-103] against 72 [69-77] µs, the same for TLS (106 against 74) and WebSocket (101 against 71), and 0.4 to 0.7 µs more server CPU a request (14.3 against 13.6 µs plain). That p99 is 40% over, past [ADR 0003](0003-the-trade-budget.md)'s 10%, in that scenario only, and it is accepted for the memory axis, which ADR 0003 holds hard: 30 µs on a request to a connection that had been idle at least 100 ms, against 2.3 to 4.4 KB off every idle connection. A wake allocates nothing (3.01 allocations a request in the scenario parked, not parked and before; the third is the timed-out read's error, paid by every request after an idle wait since milestone 1). An idle WebSocket is woken by each heartbeat's pong, about 670 wakes a second at 20,000 sockets with the 30 s default (arithmetic). Each Server holds one more goroutine and OS thread, blocked in `epoll_wait`, from its first park. What it fails at: a client that sends a request every 150 ms to 1 s pays a wake on every one; a park threshold later than the move (park after 1 s) would spare it, and is the change to make if a workload shows the cost. Not measured: Shutdown's time with 20,000 parked connections, and wakes on a CPU-saturated server.

## What was rejected

- **Deferring parking until a workload needs more than a few hundred thousand sockets, and parking WebSockets only.** The position before step 16, when the cost of a wake and of keeping one goroutine owner were not known. Measured, parking takes 2.3 KB off every idle plain connection and WebSocket and 4.4 KB off a TLS one, leaves busy connections unchanged, and costs about 30 µs at p99 on a request that finds its connection parked ([`docs/research/parking/`](../research/parking/report.md)); an HTTP keep-alive connection waits idle as much as a WebSocket does, so the same code parks both.
- **Registering parked connections in the disconnect watcher's slots** ([ADR 0016](0016-the-handler-context-is-cancelled-on-disconnect.md)): a slot, its callback and its list entries are about 150 B a registration, against one pointer in a table indexed by descriptor; the poller is a second epoll instance beside the watcher.
- **Reading crypto/tls's unexported buffers (by reflect) to decide whether a TLS connection may park**: not needed, since the timed-out read already says it holds no byte and no whole record, and it would break with any release of Go.

- **Leaving a hot wait's stack to the collector** (the position until 2026-11-05, which took a blocked read to be never shrunk; true of a stack of 4 KiB only). With `GODEBUG=gcshrinkstackoff=1` the typed route's p99 fell 18% and three middleware cost +6% instead of +17% ([`docs/research/middleware-p99/`](../research/middleware-p99/report.md)); a library cannot set that for the process, since a `//go:debug` line is honoured only in the main package. A fixed padding was rejected too: 1 KiB keeps nothing above 8 KiB, and 7 KiB grows a stack a small route keeps at 4 KiB ([`docs/research/stack-shrink/`](../research/stack-shrink/report.md)).
- **Moving the wait to a fresh goroutine after every request.** Idle memory came back to 3.1 to 3.5 KB, but every request then grew a new stack again: 21% of throughput on a typed route and 35% on one with a 6 KiB handler, with p99 up by a quarter to a half ([`docs/research/stack-handoff/`](../research/stack-handoff/report.md)). Outside [ADR 0003](0003-the-trade-budget.md)'s 10%.
- **A pool of workers running the request while the connection's goroutine waits.** Not built: it costs a hand-off and a wake a request, the scheduler work that made the move on every request expensive, and its workers keep grown stacks.
- **Restating the figure as 5.1 to 5.4 KB.** It keeps 2 KiB more of every idle connection that the move after 100 ms removes at no measured cost.
