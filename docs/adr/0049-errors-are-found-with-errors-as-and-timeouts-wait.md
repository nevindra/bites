# A status error is found with errors.As, and a timed-out handler is waited for, never abandoned

**A located error comes first** (decided 2026-11-04). When the chain holds a located error (`Invalid`, a `*FieldError`), anywhere in it and wherever it was returned (a handler, a Provider, a middleware, `Validate`), the answer is the 400 of [ADR 0012](0012-client-errors-are-400-problem-json.md) listing every located error found, and a status elsewhere in the chain does not change it. A handler often learns a field is wrong only after a lookup (an order names a product that does not exist), and its answer must have the shape the decoder's has, so a client reads one list. Until 2026-11-04 only `Validate`'s error was searched for located errors, and an `Invalid` from a handler was a plain error and a 500 with nothing for the client: an agent that wrote it, as the `Invalid` doc invited, met that trap in the usability test ([`docs/research/agent-usability/`](../research/agent-usability/report.md), row 3).

**Finding the status.** Otherwise the framework looks for an error with a status through the whole chain, and the nearest one found decides: a `*StatusError`, or an error of the application's own that implements `HasStatus`, `HTTPStatus() (status int, message string)`. So `fmt.Errorf("load user: %w", bites.NotFound("no such user"))` is a 404, and so is `fmt.Errorf("load user: %w", &repo.NotFoundError{What: "user"})` when that type has the method. The chain is walked as `errors.As` walks it, through `Unwrap() error` and through the branches of an `Unwrap() []error` (an `errors.Join`), taking the first branch that has a status. The body carries that error's own message (the `StatusError`'s `Message`, or the second result of `HTTPStatus`), not the outer text, so the wrapping words (often internal) never reach the client, and neither does the implementer's own `Error()`. Anything without a status in its chain is a 500 with no message ([ADR 0012](0012-client-errors-are-400-problem-json.md)). A `StatusError` may carry extra problem+json members (a machine-readable `code`) and headers; a `HasStatus` carries a status and a message only, and an error that needs more is converted in the handler with `NewError(...).With(...)`, or with `WithMembers` when a client reads the data and the route states its type ([ADR 0088](0088-an-error-that-carries-data-states-its-type-with-error-status-and-sends-it-with-members.md)). A status outside 400 to 599 from either is a logged 500. The framework maps no driver's errors, and mapping them here would mean importing pgx ([ADR 0006](0006-no-third-party-dependency-in-the-core.md)); the application writes the mapping, in the handler or once in `WithErrorMapper` (below). `HasStatus` does not contradict that: the framework still knows no application's or driver's type, the application states on its own type what answer it is, and the framework reads a method. The nearest decides because the outer error is the later decision: a handler that wraps an application error in `NotFound(...)` has said what the client should see, and an application error that wraps a `StatusError` (to add its own context) is the same error as far as the client is concerned. Every place that read a `*StatusError` with `errors.As` (the handler's error, a Provider's verification, the 401 challenge of alternative credentials) reads the same walk, so an application error from a `Verify` function is answered, and challenged, like a `StatusError`'s. Cost: none on a success; an error that is a `HasStatus` makes one `StatusError` on its way out, on the error path only.

**A status error can carry response headers** (built 2026-11-01, milestone 3 wave 1). `StatusError.WithHeader(name, value)` returns a copy whose problem+json answer also carries the header, after any it already carries; the error it was made from is unchanged. A Provider answers only with an error ([ADR 0023](0023-provided-sections-are-checked-at-registration.md)), so without it an auth Provider could not send the `WWW-Authenticate` challenge RFC 9110 requires of a 401, nor a rate limit the `Retry-After` of a 429 ([ADR 0054](0054-auth-providers-parse-the-credential-and-the-application-verifies-it.md), [ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md)). A header the engine writes itself (`Content-Type`, `Content-Length`, `Date`, `Connection`, `Transfer-Encoding`) or a name that is not a token is left out and logged at Error, at request time, since an error value is made by the handler and Registration never sees it; a CR, LF or NUL in a value is replaced by a space, as in every header. Tests: `problem_test.go`. Rejected: a header map on `StatusError` as an exported field, which a handler could fill with the engine's own headers and which makes a shared error value mutable.

**A client that left.** When the context was cancelled because the client disconnected ([ADR 0016](0016-the-handler-context-is-cancelled-on-disconnect.md)), nothing is written and nothing is logged as an error; the access log records the request as abandoned by the client.

**Nothing written is the engine's rule too** (built 2026-11-01, milestone 3 wave 0). Before that, the framework kept the rule (`answerError` returns without an answer when the cause is `ErrClientGone`) but the engine did not: finding no answer set, it wrote its own 500 (`handle` in `internal/engine/conn.go`), and after a panic it wrote one whether or not anyone was there. Now, when the cause is `ErrClientGone` and the handler set no answer or panicked, the engine writes nothing and closes the connection; the panic is still logged with its stack ([ADR 0028](0028-panics-are-recovered-by-the-engine.md)). A value the handler returned is still written, since it is the handler's answer and the write fails harmlessly if nobody reads it; an error it returned, a status error included, is not answered. It costs nothing where an answer was set, and one load of the context's state where none was. A client that half-closes after sending its request, which ADR 0016 already cancels as a disconnect, now gets the connection closed instead of a 500 with no detail: neither is the answer it wanted, and the second is what this rule says (`TestNothingIsWrittenToAClientThatLeftWhenTheHandlerSetNoAnswerOrPanicked`, `TestAnAnswerTheHandlerSetIsStillWrittenAfterTheClientHalfClosed`). Writing the 500 and letting it fail, the behaviour as first built, was rejected: it contradicted this ADR and cost a system call for nobody.

**A timeout.** The per-route timeout middleware ([ADR 0032](0032-four-first-party-middleware.md)) cancels the context with `context.DeadlineExceeded` as its cause and **waits for the handler to return**; the answer is then 503, whatever the handler returned, and a handler that took far longer than its deadline is logged with how long it ran. Go cannot stop a goroutine, and answering while the handler still runs would mean a second goroutine touching the request and a response written while the handler might still act, which [ADR 0009](0009-the-response-comes-only-from-the-return-value.md) exists to prevent. A handler that ignores its context is therefore late, visibly, rather than leaked.

**Built in step 7 of milestone 2 (the timeout).** "A handler that took far longer than its deadline" is one that ran more than twice its deadline, logged at Warn with the method, path, deadline and how long it ran; a handler that returned at the deadline is not logged, since the 503 and the access log already say so. The context cancelled is the request's own, not a derived one, so the cause reaches everything holding the request's context and the timeout costs no allocation ([ADR 0032](0032-four-first-party-middleware.md) has the mechanism and the rejected alternatives). Whatever the late handler returned, a value, an error or a Stream, is dropped and the answer is the 503; a Stream returned in time is not under the deadline.

**An error of a type the application does not own is mapped by a function it gives the app** (built 2026-11-03). `WithErrorMapper(func(error) *StatusError)` is the case the last paragraph of this ADR said would reopen the option: an application over pgx has to wrap every handler return in a conversion or wrap every handler at registration, because `*pgconn.PgError` (SQLSTATE 23505 to 409, 23503 and 23514 to 422) and `pgx.ErrNoRows` (404) are types it cannot add a method to, and middleware cannot do it for the handler, since `Next.Call` returns a Response and never an error. The rules:
- **It runs only when the chain has no status.** `findStatus` is asked first, so the application's own `StatusError` or `HasStatus` answers and the mapper is not called; a mapper is for a type with no answer of its own, never a second opinion on one that has it. The function receives the whole error, wrapped and joined as returned, and uses `errors.Is` and `errors.As` itself.
- **It is consulted at the one place every error is answered** (`answerError`), so a handler's, a Provider's (a `Verify` function's included), a middleware's, a stream's and a WebSocket upgrade's error are all mapped, and nothing is asked when the client left. It returns a `*StatusError`, not a status and a message, so a code member or a `Retry-After` is possible, which the two-value `HTTPStatus` was rejected for lacking: here the application builds the value in a function of its own, where `HasStatus` asked every error type to import the framework.
- **It may be given more than once** and the functions are asked in the order given, the first non-nil answer winning, so a module can add its own mapping beside the application's. `WithObserver` refuses a second because order is the whole of an Observer's meaning; here the order only breaks a tie. A nil function panics in `New` with the line that gave it, and the refusal table has the row. It is the app's and has no Group form: a driver's error means the same on every route, and a per-group mapper would need the route at the place errors are answered, which holds none.
- **The answer is a `StatusError`'s, and so is its logging.** A mapped 4xx is not logged, as a returned `StatusError` is not. A mapped 5xx is logged at Error with the original error, the status, the method and the path, because the message the mapper chose is the client's and the reason is ours; its message is sent as written, the same trust a returned `ServiceUnavailable("...")` has. An empty message is a title and a status only. A status below 400 or above 599 is a logged 500, the rule for `NewError`. A mapper that panics is recovered, not left to the engine: the panic and the original error are logged and the error is answered as unmapped, so a bug in a mapping costs one request a 500 and not its connection, and the real error is not lost behind the panic. The functions after it are not asked.
- **A mapped 401 gets no `WWW-Authenticate`** unless the mapper adds it with `WithHeader`: the challenge belongs to the auth Providers' own errors, which carry theirs.
- **Cost.** None on a success (2 allocations for a typed JSON request, asserted with and without the option). A mapped error costs the allocations of the same `StatusError` returned by the handler (5 in the measured request, which includes decoding its body), and an unmapped one pays one call per function. Tests: `problem_test.go` (a foreign type wrapped with `%w`, the application's answer winning, a Provider and a middleware, order, a mapped 5xx and an empty message, an invalid status, a panic) and `budget_test.go`; the refusal row is in `refusal_test.go`.

**What was rejected:** finding only a `*StatusError`, which was the first position of this ADR: an application whose services return their own error types (a not-found, a validation failure, a conflict, an invalid transition) had to convert every one at every handler that can fail, and a handler that forgot was a 500 for what was a 404. A `WithErrorMapper(func(error) *StatusError)` option on the app was rejected at first: it is a second place the answer is decided, away from the type that knows it, it runs on every error including those the type could have answered itself, and an app-wide function that switches on types is the file that grows with every new error. The driver's types are the case that reopened it, in the form this ADR then named: it runs only when the chain has no status, so the first two objections are answered; the third stays true and is the application's to manage. A mapper returning a status and a message was considered and rejected: it cannot carry a `code` member or a header. A third form, `HTTPStatus()` returning a `*StatusError`, would let the type carry members and headers; it was left out because it makes every implementer import the framework's error type and construct it, where the two-value method needs neither, and because no port has needed a code member on a mapped error yet (open question in `docs/roadmap.md`).
