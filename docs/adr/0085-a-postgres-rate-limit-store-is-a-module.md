# A Postgres rate limit store is a module, and a Take is one statement over one row of GCRA

[ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md) gave `RateLimiter` a `RateLimitStore` seam and no store but the in-memory one, so an application that runs several instances behind a balancer keeps its limits for each instance: N instances allow N times the limit of a sign-in, an emailed code or an invitation, which is exactly where a limit is a security control. The reference deployment is one binary and Postgres ([ADR 0002](0002-the-reference-workload.md)), so the Postgres store comes before a Redis one, as it did for sessions ([ADR 0082](0082-a-postgres-session-store-is-a-module.md)). Decided on 2026-11-05 and built.

**Decision.**

- **`modules/pgratelimit` is the Postgres store**, with its own `go.mod` and `github.com/jackc/pgx/v5` at the version `pgsession` uses ([ADR 0006](0006-no-third-party-dependency-in-the-core.md), [ADR 0070](0070-optional-features-are-modules-under-modules-each-with-its-own-go-mod.md)); the core changes nothing. `pgratelimit.New(Options) *Store` returns a `bites.RateLimitStore`. `Options` are `Pool` (required, never closed), `Table` (`bites_ratelimit`), `Name` (empty), `SweepEvery` (10 minutes) and `Log`. `Schema()`, `CreateTable(ctx)`, `Sweep(ctx)` and `Service()` are those of `pgsession` for the reasons [ADR 0082](0082-a-postgres-session-store-is-a-module.md) gives, and the table is never created by `New` or `Start`.
- **The algorithm is GCRA with one number a key, the same as the in-memory store**, not a stored token count. A bucket is `tat`, the time it is next full, in Unix nanoseconds as a `bigint`. A request is allowed when, after adding one interval to the later of now and `tat`, `tat` is at most `burst` intervals ahead of now. A token count needs two fields (tokens and the time they were counted at) and arithmetic with a division that rounds, in SQL, where it is a place for an off-by-one that the in-memory store does not have; GCRA is one comparison and one addition on integers, so the two stores give the same answer to the nanosecond for the same calls (the conformance suite of [ADR 0086](0086-a-store-is-held-to-its-interface-by-a-conformance-suite-in-bitetest.md) runs on both). A `bigint` and not a `timestamptz` because a `timestamptz` keeps microseconds and the interval of a limit can be shorter than that matters to the comparison; the limit's own refusal of a bucket over ten years keeps the sum far from overflowing, and `Take` refuses a burst and interval whose product does not fit.
- **A Take is one statement and one round trip.** It is a CTE around `INSERT ... ON CONFLICT (key_hash) DO UPDATE SET tat = GREATEST(tat, $now) + $interval WHERE GREATEST(tat, $now) + $interval - $now <= $burst * $interval RETURNING tat`. The upsert is atomic per key: Postgres locks the row, re-evaluates the `WHERE` on the latest version and either writes or leaves it, so two instances taking at once cannot both get the last request, with no explicit transaction, advisory lock or retry. A new key is the insert, always allowed since a burst of at least one is checked first. When the `WHERE` is false the statement returns no row from the upsert, so the CTE also reads the row as the statement began, which is what a refused request reports (`Reset`, and `RetryAfter` as the time until `tat` is `burst - 1` intervals ahead). A refused request writes no new version of the row, so a client that keeps trying neither pushes its own retry time away nor makes dead tuples (the sweep and the autovacuum are not paid by a flood). **One exception to one round trip:** when two instances create the same key in the same instant, the loser's snapshot has no row to report and it reads the row with a second query; this is the first request of a key, never a hot path. The reported `RetryAfter` of a refusal is from the row as the statement began, so under heavy contention on one key it can be a little early, never negative (`max(..., 1ns)`); the allowed answer is exact.
- **The clock is the `now` the interface passes, not Postgres's `now()`.** `Take`'s `now` is the application's clock ([ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md)): a test moves `bitetest.Clock` and a request carries the time the app measures with, and a store on the database's clock would make the same limiter behave differently in a test than in production and could not be driven by the suite's fixed times. The price is skew between instances. `tat` is an absolute time written by whichever instance spent last, so an instance whose clock is ahead by `s` leaves a `tat` that a slower instance reads as `s` further in the future: the slower instance has `s` less of its bucket, and the faster one reads a slower one's `tat` as `s` earlier, with `s` more. The error is at most `s` of bucket, that is `s/interval` requests, in either direction, and it does not accumulate: it is not a count that drifts, it is one comparison. With instances kept within a second by NTP (which a Postgres deployment with a primary and replicas already wants) a limit of 5 a minute is off by a twelfth of a request. An application whose clocks are not synchronised to within its interval has a larger problem than its limits, and the reference says so. **Postgres's clock is not used at all by `Take`;** the sweep uses `bites.Now(ctx)`, the clock of the app whose Service runs it (the real one outside a test), with a grace (below).
- **The key is stored only as a hash**, `SHA-256` of the Name's length, the Name and the key. Keys are emails, IP addresses and `/64` prefixes, personal data a limit table should not hand out in a dump, a backup or a read-only injection elsewhere, for the reason [ADR 0082](0082-a-postgres-session-store-is-a-module.md) hashes session ids. Unlike an id, a key can be guessed (an address, an email is a short enumerable space), so the hash does not make a dump unreadable to someone who can try candidates; it keeps a casual reader and a log of the table from seeing keys, and the reference says that. An HMAC with a server key would stop the guessing and tie the table to a secret that rotation would have to carry; not done, argued below.
- **`Name` keeps limiters that share a table from sharing a bucket.** The `RateLimitStore` interface is not told which limiter is calling, and a key such as an email is the natural key of a sign-in limit and an invitation limit both, with different bursts: on one table they would be one bucket. Each `RateLimiter` gets its own `Store` with its own `Name` (the limiter's `Name` is the obvious value), or its own `Table`. The Name is mixed into the hash with its length in front, so no Name and key pair can be shifted into another. Instances of one limiter must give the same `Name`.
- **The table is `UNLOGGED`.** A bucket is state that costs nothing to lose: an empty table is every bucket full again, which is what the in-memory store does on every restart. Skipping the write-ahead log makes a Take about forty times cheaper (measured below), because the commit of a transaction that wrote only unlogged tables waits for no `fsync`. The cost is stated: a crash of Postgres or a failover to a replica empties the table, so every limit resets once, and the table is not on a replica. A limit whose loss is not acceptable (a quota that is billed) is not a rate limit, and wants a logged table of the application's own; `Schema` is the text, an application that wants it logged changes one word, and `CREATE ... IF NOT EXISTS` never converts a table that exists.
- **Idle rows are swept by a `bites.Service`, a `bites.Every` as `pgsession`'s is.** `Service()` is named `pgratelimit`, runs on the app's clock like `pgsession`'s, and serves one Service per Store. The sweep ignores `Name` and deletes the idle rows of every limiter in the table, so an application with several Stores on one table registers one Service for the table, not one for each Store (the app refuses a second Service named `pgratelimit`, and the reference says so, since only the SQL showed it); a Store on a second table is swept by a `bites.Every` of another name calling its `Sweep`; `Sweep(ctx)` deletes, in batches of 1000 with `FOR UPDATE SKIP LOCKED`, the rows whose `tat` is more than `SweepGrace` (one minute) in the past, which is a bucket that has been full for a minute. A full bucket is what a new key gets, so deleting it loses nothing (the argument of [ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md)'s eviction); the grace keeps that true when the instance that sweeps runs ahead of the one that wrote the row by less than a minute. A row is a key's last use plus its bucket's length, so the table holds the keys active in the last `burst * interval` plus ten minutes, bounded by what clients did, not by a number the framework chooses, and that is the one difference from the in-memory store's `MaxKeys`. The table is bounded in practice by the sweep and in principle by the number of keys clients can make; a client that rotates a key it controls (a header) writes a row for each, which is the case [ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md) already says wants a key the client does not choose.
- **Errors are wrapped**: `pgratelimit: take: <pgx error>`, `sweep`, `create table <name>`; a `Take` with a burst under one, a non-positive interval or a bucket that does not fit is an error that says what to change. A store error is a 500 as [ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md) says: the limiter fails closed, and an application that would rather fail open wraps the store in a type whose `Take` returns `Allowed` on an error; the module does not offer that second spelling.

**Refusals** (rows of `modules/pgratelimit/pgratelimit_test.go`, each ending `registered at <file:line>`; the reference lists them):

- `pgratelimit.New: Pool is nil: ...`, `Table "<name>" is not a plain identifier: ...` (the name is quoted into SQL, so the check keeps a configured name from becoming SQL), and `SweepEvery is -1s, which is not a time: ...`, as in `pgsession`.
- Not caught before the first request: a table that does not exist or has another shape (the first `Take` says so with Postgres's message), **two limiters with different bursts on one table and one Name**, which share buckets (`Take` receives only a burst and an interval, and a store that refused a second pair would refuse any valid limiter that changes its limit; give each limiter its own `Name`), and instances of one limiter given different Names, which do not share.

**What it costs** ([ADR 0003](0003-the-trade-budget.md)). Core: none; no file of it changes, so allocations per request and memory per idle connection do not move. Module: **one round trip to Postgres for each limited request** (two in the instant two instances create one key), a statement on the primary key, plus the allocations of pgx for it, which count against the request only when the application chose this store. Measured on the Ryzen 7 9700X with Postgres 17 in Docker over loopback, `BenchmarkTake` (three runs, 2 s each): **about 26 µs a Take** for a new key from one caller (23.3, 26.3 and 35.2 µs), about 22 µs for a refused request (21.2 to 28.6), and about 7 µs a Take when 16 goroutines all take the one key (7.0 to 9.8 µs), which is the row lock serialising them at the rate of the lock. The same table logged (not `UNLOGGED`) measured about 1.0 ms a Take for a new key (0.98 to 1.10 ms), one commit's `fsync` each; that is the number the `UNLOGGED` choice avoids. A 26 µs round trip on a loopback is a floor; across a network it is the network's round trip plus that. Per row, a 32-byte hash and 8 bytes of `tat`, plus a primary key and one index on `tat`. Per store, one goroutine sleeping on a ticker. No number of [ADR 0003](0003-the-trade-budget.md) is raised.

**Scenarios it was put against.**

- _Three instances behind a balancer, a limit of 5 a minute on `POST /login` per email_: every instance takes from the same row, so the application allows 5, not 15 (`TestARateLimiterOnTwoInstancesLimitsOnceNotTwice`); forty rounds of eight concurrent takers split between two stores and pools on a burst of 3 are allowed exactly 3 each (`TestTwoStoresOnOneTableShareTheirBucketsAndNeverBothGetTheLastRequest`), and the conformance suite's concurrent subtests hold it for one store.
- _A hostile client_ guessing a password from a thousand addresses: each address is a bucket of its own for the address limit, and the limit per email (the handler's `Allow` with the body's email, [ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md)) is one row all of them contend on, which is what makes it hold; the row's lock is held for a statement, so the thousand are serialised at about 7 µs each, not at a commit's `fsync`.
- _A flood of refused requests on one key_: they write no new row version (`TestARefusedTakeWritesNothingToTheTable`), take the row lock for the statement, and each costs a round trip; the application's own address limit in front, which is in memory, is what keeps a flood from reaching the database.
- _A dump of the table_: 32-byte hashes and times. An attacker who has it and a list of emails can see which were active in the last bucket length by hashing the list. That is less than the table of raw keys gives and more than nothing, as the decision says.
- _Postgres restarts or fails over_: the table is empty, every bucket is full, requests flow; the limits are back after one bucket length of use. An application that cannot accept that does not use this store for that limit.
- _Postgres is down_: every limited request is a 500 until it is back ([ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md)); the application that would rather serve wraps the store.
- _An instance's clock 30 s ahead_ with a limit of 5 a minute: its writes leave a `tat` 30 s further on, so a peer that reads it has the bucket 30 s fuller of spent requests, 2.5 requests of 5; the reverse for the peer's writes. A limit of 100 a minute is off by 50. The module does not hide it; the reference says to keep clocks within a second.
- _A sweep on several instances at once_: the batch delete with `SKIP LOCKED` is the one tested for `pgsession`; `TestSweepsOnSeveralInstancesAtOnceDeleteEachRowOnce` deletes 3000 rows between four concurrent sweeps.
- _One key, two limiters_: the same email on sign-in and on invitations, one table: stores with their own Names keep them apart (`TestLimitersWithDifferentNamesOnOneTableDoNotShareABucket`), and stores with no Name would share, which is stated.

**What it fails at.**

- **A round trip a limited request**, which an in-memory limit does not pay. A route the application limits twice (an address limit in memory against floods, a limit per email in Postgres against guessing) pays it for the second only; the guide says to put the cheap one first.
- **A hot key is one row**: takes on it serialise on the row lock, about 7 µs each here, so a key taken more than about 100,000 times a second from one database is a limit of the lock. A limit that busy is a limit of an address in front of a CDN, which belongs in memory.
- **The table is lost on a crash** and not replicated (above).
- **Skew** (above), and the hash is guessable for a small key space.
- **`RetryAfter` of a refusal can be early** under contention (above).
- **Several limiters on one table need distinct Names and nothing checks it.**
- **The schema is not migrated**, as for `pgsession`.
- **Postgres only.** A Redis store is a module of its own when an application asks; the interface and the conformance suite are what it must meet.

**Considered and what was rejected.**

- **A stored token count** (`tokens`, `updated`): two columns and a refill computed in SQL with a rounding of its own; it answers the same questions as `tat` with more places to be wrong, and the in-memory store would then be GCRA while the shared one was not.
- **A fixed window counter** (`key, window, count`): one `INSERT ... ON CONFLICT DO UPDATE SET count = count + 1` and no time arithmetic, and it lets a client make twice the limit across a window boundary and synchronises every client's reset; [ADR 0055](0055-rate-limiting-is-a-token-bucket-per-key-with-a-bounded-store.md) rejected it for the in-memory store for those reasons and they hold here.
- **Postgres's `now()` as the clock:** exact between instances (there is one clock), at the price that `bitetest.Clock` and the `now` the interface passes would be ignored, so a test of a limit would sleep and the suite of [ADR 0086](0086-a-store-is-held-to-its-interface-by-a-conformance-suite-in-bitetest.md) could not move time. The error of skew is bounded by the skew; a limit is not a ledger.
- **A transaction with `SELECT ... FOR UPDATE` and an `UPDATE`:** two or three round trips and a held lock across the application's network latency, which is what the single upsert avoids.
- **An advisory lock per key:** a second round trip for a lock that the row's own lock gives.
- **Always updating on a refusal** (`SET tat = CASE ... END` and returning whether it moved): one fewer reading of the row, and a new row version, an index entry and a dead tuple for each refused request, which turns a flood into table bloat.
- **A logged table:** durable across a crash, at 1 ms a Take on this machine; a bucket that survives a crash is not worth forty times the cost.
- **The key stored in the clear:** a column `text` is searchable, and it is also a list of every email that signed in, in a table that is a limit.
- **An HMAC of the key with a server secret:** stops a dump from being tried against a list of emails, and makes the store need a secret that every instance holds and that rotation would have to carry, which would empty every bucket on rotation. A deployment that needs that wraps its keys in the `Key` function or in the `Allow` call, where the application already has the secret.
- **A `Name` in the `RateLimitStore` interface**, so a store knows its limiter: a change to a seam every store implements, to give a module what an option (`Name`) gives it.
- **Refusing a store used with two different burst and interval pairs:** it would refuse a limiter whose configuration changes between deploys, and the conformance suite's own subtests call one store with several pairs.
- **Evicting by a `MaxKeys` as the in-memory store does:** a delete on the write path of a database, for a bound the sweep already gives.
