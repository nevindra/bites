# A streamed response is a return type whose writer exists only inside its function

A handler that streams (server-sent events, a large download, NDJSON) returns a `Stream`: the status and headers, and a function that receives a writer valid only while that function runs. The headers are fixed before the first byte, so they cannot be set late ([ADR 0009](0009-the-response-comes-only-from-the-return-value.md)); the write timeout of [ADR 0024](0024-limits-are-on-by-default.md) applies to every chunk of at most 64 KiB, and only the total duration is lifted (below); and the function's context is cancelled when the client leaves ([ADR 0016](0016-the-handler-context-is-cancelled-on-disconnect.md)). Server-sent events are a thin type on top of `Stream`, so an SSE handler writes events, not bytes, and `Events[T]` is a thinner one still, so a handler whose events carry JSON sends values of `T`, not strings.

**The shape, as built (step 10).** `Stream{Status, Header, Cookies, Live, Func}` and `SSE{Header, Cookies, Func}` are returned by value, like the status wrappers of [ADR 0013](0013-other-statuses-are-wrapper-types.md); `Func` is `func(ctx context.Context, w *StreamWriter) error` for a `Stream` and `func(ctx context.Context, e EventWriter) error` for an `SSE`. The function does not run inside the handler. The terminal step of the chain writes the status line and the headers into the engine's response buffer and hands the engine the function; the engine runs it on the connection's goroutine after the outermost middleware has returned, so every middleware has decorated the head before the first byte, and the request's context stays live until the function has returned. A stream is the whole return type: a `*Stream`, a `*SSE`, a stream as the `Body` of a wrapper and a stream on a HEAD route are refused at Registration; an interface-typed return may carry one, resolved per type as for any wrapper. A `Status` of 0 is 200, a `Func` that is nil, and a status without a body (1xx, 204, 304 or outside 200 to 599), are a 500 and logged, because the value is not known at Registration. A `Content-Type` in `Header` is used; a `Stream` without one is `application/octet-stream` and an `SSE` is `text/event-stream` with `Cache-Control: no-cache` unless the header gives its own.

**Typed events.** `Events[T]{Header, Cookies, Func}` is an `SSE` whose `Func` is `func(ctx context.Context, e EventSender[T]) error`: its head, its status of 200, its liveness and its clean end at Shutdown are the `SSE`'s, and it is a stream to every rule above (refused by pointer, as a `Body` and on a HEAD route; allowed in a `Returns`). `T` is known at Registration, so the route compiles `T`'s encoder there with the framework's codec ([ADR 0015](0015-json-is-our-own-codec-on-jsontext.md)) and its naming policy, and refuses a `T` the encoder cannot compile, `[]byte` (JSON writes it as base64, which is never what a byte event means; text goes in an `SSE`), and the framework's own response types, which have a status and headers an event cannot carry. Registration reaches `T` through an unexported method of `Events[T]` on a zero value boxed once: it names `T` and builds the stream's runner, a generic type that calls `Func` with a sender of the right `T`, so the per-request path stays the non-generic plan of [ADR 0013](0013-other-statuses-are-wrapper-types.md) and the runner is still the stream's one allocation of its own. In the API document the response is `text/event-stream` with `{"type": "string"}` as before, and the event under the media type's extension `x-itemSchema`: an object of `id`, `event`, `retry` and a required `data`, a string with `contentMediaType: application/json` and `contentSchema` the schema of `T`, as a component. That is the shape OpenAPI 3.2 states under `itemSchema`; the document is 3.1, which has no keyword for the items of a stream and allows `x-` keys on a Media Type Object, so moving to 3.2 renames one key. Two `Events` in one interface return give a `oneOf` of their events; an `Events` beside an `SSE` gives none, since the `SSE`'s data is any text. The goldens with it validate against the official 3.1 schemas, and the check reads `x-itemSchema` as a Schema Object ([`docs/research/openapi-valid/`](../research/openapi-valid/)).

**The writer.** `StreamWriter` has `Write`, `WriteString` and `Flush` and is safe for concurrent use. Writes are buffered, in the response buffer the engine already pools, and go out as one chunk when 64 KiB have gathered, on `Flush`, and when the function returns; a `Write` of 10 MiB is therefore 160 chunks of 64 KiB, each under its own deadline. Nothing is sent, not even the head, before the first of those, so a panic or an error returned before it is the ordinary answer to a panic or an error ([ADR 0028](0028-panics-are-recovered-by-the-engine.md), [ADR 0049](0049-errors-are-found-with-errors-as-and-timeouts-wait.md)) and a function that waits for its first event before it has anything to say calls `Flush` to open the response. The writer the function receives is a heap object of its own, owned by the stream, not the pooled one: when the function returns the engine detaches the connection from it under its lock, so a `Write`, `WriteString` or `Flush` made later by a goroutine that kept it returns `ErrStreamClosed` and touches nothing, and a write racing the return either completes first or fails ([ADR 0008](0008-no-pooled-object-reaches-the-user.md)). A failed write is kept: every later write returns the same error, and when the function returns the connection is closed, never reused. `SSE`'s `EventWriter` is a one-word value over the same writer; `Send(Event{ID, Name, Data, Retry})` writes the fields in that order, one `data:` field per line of `Data` (LF, CR and CRLF all end a line), and flushes; `Comment(text)` writes `: text` lines and flushes, the heartbeat. An `ID` or `Name` with a line break (or an `ID` with a NUL) returns `ErrBadEvent` and sends nothing, because it would end the field and let the sender start another. An event whose only content is a `Retry` sends no data field and dispatches nothing; every other event sends at least one, so an event with only a `Name` still dispatches. `Events[T]`'s `EventSender[T]` is a two-word value over the same writer and the runner's state: `Send(name, v)` and `SendEvent(ev, v)`, which takes the `ID`, `Name` and `Retry` of an `Event` whose `Data` must be empty (an `ErrBadEvent`, wrapped with a message of its own, if not), write the head fields, then `data: ` and `v` encoded by the compiled plan, then flush; `Comment` is the `EventWriter`'s. The value is one line: JSON has a raw line break only as whitespace between tokens, so one a `MarshalJSON` wrote is sent as a space. An encoder error (a NaN) sends nothing. The event is built in a 512-byte buffer inside the runner, under a lock so the sender stays safe for concurrent use; a larger event grows the buffer, which is kept up to 64 KiB and dropped back to the 512 bytes above that. Measured through the engine (`TestAnEventsStreamAllocatesWhatAnSSEStreamDoesAndATypedEventAllocatesNothing`): an `Events` stream is 4 allocations with 0, 1 and 100 events, as an `SSE` is, so a typed event allocates nothing. `BenchmarkAnEvent`, 100 events of about 30 bytes of data a request on the in-memory connection, four interleaved rounds on an Apple M1 Pro ([`docs/research/typed-events/`](../research/typed-events/report.md)): an `SSE` sending a constant string took 173 to 183 ns an event, an `Events` 214 to 218 ns, and an `SSE` whose handler does what `Events` replaces, `json.Marshal` and `string(body)`, 483 to 502 ns and 3.9 allocations an event; the stream's bytes rose from about 395 to 990 a request, the runner's 512-byte buffer. These times are a laptop's over the in-memory connection, a ratio within one run and not the TCP numbers of [ADR 0003](0003-the-trade-budget.md), which wait for the reference machine.

**How a stream ends.** The function returns nil: what is buffered is sent with the terminating chunk, the write deadline is cleared, and the connection serves its next request. It returns an error, or panics, after the first byte: the connection is closed with no terminating chunk (a client sees a cut stream, not a complete one) and no 500 is attempted, since the status line has gone; the panic is logged with its stack, an error is logged unless it is the context's cancellation or a failed write. The client leaving cancels the context with `ErrClientGone` as for any request ([ADR 0016](0016-the-handler-context-is-cancelled-on-disconnect.md)), armed when the function first looks at `ctx.Done()`; a function that never looks finds out from its next write failing. On HTTP/1.0 there is no chunking: the response carries `Connection: close` and the body ends when the connection does. A request whose body was not read, a `Connection: close` request and a server in Shutdown also get `Connection: close` and the close after the stream. A HEAD request is given the head, with `Transfer-Encoding: chunked`, and `Func` does not run.

**What middleware sees ([ADR 0022](0022-middleware-sees-a-request-view-and-returns-a-response-value.md)).** A `Response` for a stream has the status, the content type and the headers added so far, `Size()` is 0 because the body does not exist yet, and `Streaming()` is true. A middleware can add headers and change the status, which go out with the head. It cannot see or wrap the body, as with any answer, so a compression or ETag middleware cannot apply to a stream (they are engine features anyway, [ADR 0031](0031-gzip-only-and-off-by-default.md)). An error returned by a middleware, or a fresh `Response`, drops the stream and its function never runs. The access log of [ADR 0032](0032-four-first-party-middleware.md) therefore records a stream's status and head when the chain returns, not when the stream ends, and cannot record its size.

**The write timeout applies to each chunk.** The engine splits what the function flushes into chunks of at most 64 KiB and arms `SetWriteDeadline(now + WriteTimeout)` before each, re-arming only when less than half of the timeout remains, so a busy stream arms rarely, a heartbeat every 15 s arms once a flush, and every write still has at least `WriteTimeout / 2`. The deadline is cleared once, when the stream ends, not after each flush. The chunk is 64 KiB because a Go deadline covers the whole `Write`: a 10 MiB flush at 30 s would demand 340 KiB/s and kill a client on 1 Mbit/s, where 64 KiB needs 2.2 KiB/s. When a stream starts the engine also sets `TCP_NOTSENT_LOWAT` to 16 KiB on the socket (`SetsockoptInt` through `SyscallConn`, once per stream, never on the plain path), because the deadline alone does not stop a slow reader of small events: a client that never reads absorbed 4.1 MiB (about 42,000 events of 100 B) before the first flush blocked, and a stream at one event a second held the connection for hours first. Measured with the option, the accepted backlog of a client that never reads fell from 4,132 KiB to 117 KiB, 35 times less, and a 64 KiB write loop on loopback was unchanged (14.8 to 15.0 GB/s); `SO_SNDBUF` of 64 KiB gave 260 KiB but caps the bandwidth-delay product of downloads. The cost is about 114 ns for an arm and +0.15 µs (+10%) on a 100 B loopback write when armed on every flush, which the half-timeout rule makes near zero for a busy stream; an idle stream arms nothing. Evidence: [`docs/research/decisions-bodies/`](../research/decisions-bodies/report.md), section R3.

**A stream that ends because the server is going away.** Only a stream declared live is cancelled when Shutdown starts: `SSE` is live by construction, and `Stream` has a `Live` flag that an NDJSON feed sets. A plain `Stream` (a large download) drains until the Shutdown context ends, as [ADR 0029](0029-shutdown-drains-and-then-closes.md) says, because cancelling it would cut a 2 GB download at the first SIGTERM. A live stream's function returns with the cause `ErrServerClosed`; an SSE response then ends cleanly (EventSource reconnects either way), and a live stream that is not SSE ends without its terminating chunk, so a client cannot mistake a cut stream for a complete one. Evidence: [`docs/research/decisions-websocket/`](../research/decisions-websocket/report.md), section R5.

**A sized stream.** A body whose length is known before the first byte (a `File`, [ADR 0043](0043-cookies-and-bodies-other-than-json.md)) uses the same runner and writer with a declared length: `Exchange.StreamSized(n)` puts `Content-Length: n` in the head and sends no chunks, a write past `n` fails with `ErrStreamOverrun`, a function that ends having written fewer than `n` bytes closes the connection (the client sees a short body, never a wrong one), and the writer's `ReadFrom` reads a file straight into the 64 KiB buffer. A HEAD request gets the same head and no body, and the function does not run. The stream path was reused for a `File` rather than the engine's buffered write, which would hold the file whole in memory.

**What was rejected:** running the function inside the handler's call, which would write the head before the middleware outside it could add its headers (CORS would be lost on every stream) and would keep the chain's pooled state alive for the whole stream; a writer that is the pooled object of the connection, which a goroutine that kept it would write into the next request's response; writes sent as they are made, which cost a system call for each small write and give a 10 MiB write no chunking to put a deadline on; a `Stream` function with no error return, which leaves no way to say a stream failed before it began; lifting the write deadline for the whole response, which let a client that never reads hold the connection for ever; cancelling every stream when Shutdown starts, which truncates finite streams and, if the terminating chunk were written because the function returned normally, would present the truncation as complete; and doing nothing, which makes every deploy wait the full grace for SSE. For typed events: a `*EventSender[T]`, as a WebSocket's `*Socket[T]`, which escapes to the user's function and is one more allocation a stream (a `Socket` is kept for the connection's life, a sender only for the function's, so a value fits it as `EventWriter` fits an `SSE`); encoding into a stack array as `EventWriter.Send` does, which the encoder's destination leaks (`go build -gcflags=-m`: `leaking param: dst`), so every event would have allocated its 1 KiB; a buffer made on the first event, one allocation more for every stream that sends; `SendID(id, name, v)`, two strings in a row that swap without a compile error, and no `Retry`; an `Event` with a typed `Data`, which would make `Event` generic and break every `SSE`; and leaving JSON events to `SSE` and `json.Marshal`, which costs about 4 allocations and 260 ns an event and leaves the document unable to say what an event holds.

**What it fails at:** a stream function that is slow to produce its first byte holds the connection with nothing sent unless it calls `Flush`, and a browser's `EventSource` does not report open until then; middleware cannot see a stream's size or its end, so an access log of one is a log of its start; a function that spawns a goroutine to write holds the response open only as long as it keeps the function from returning, and its late writes fail rather than wait; an SSE event larger than 1 KiB allocates its own bytes (claim, not measured); `TCP_NOTSENT_LOWAT` is set at the first byte and restored to 0 at the end of the stream, two system calls a stream, so that a kept-alive connection's plain answers are as before, and on a TLS connection the option is on the socket under it; a peer that vanishes with no RST and a buffer that is not full is caught by TCP keepalive, not by the deadline; the 64 KiB chunk is a constant that may be wrong for a real-time client; a handler that ignores its context keeps the connection until the Shutdown context ends; and 20,000 live SSE clients are cancelled in the same millisecond (the 1001 of a WebSocket is spread over a window, [ADR 0029](0029-shutdown-drains-and-then-closes.md), but an SSE stream is cut at once, because the function returns by itself and EventSource reconnects after its own `retry` delay). `TCP_USER_TIMEOUT` equal to the write timeout (Linux only) closed a never-reading and a trickling reader with no deadline at all (write failed after 1.47 to 1.49 s with a 1 s value), but the in-memory entry point and the fake clock cannot test it and it is not portable, so it complements the per-chunk deadline and does not replace it. `Events[T]` holds its 512-byte buffer for the life of the stream, about 600 B more per live stream than an `SSE` (a runner of 640 B against 48 B), and its first event over 512 B, and each larger one after it, allocates; its data is JSON only; `x-itemSchema` is an extension, which 3.1 tools ignore until the document moves to 3.2; and a value is encoded under the sender's lock, so two goroutines sending at once take turns for the encoding as well as for the write.
