# A success status other than 200, and any response header, is a generic wrapper type

A handler that returns a plain value `T` answers `200` with it as JSON. Anything else is a type the handler returns: `OK[T]`, `Created[T]`, `Accepted[T]`, `NoContent`, `NotModified`, `SeeOther`, `Redirect` (with its status, 301, 302, 307 or 308). Every wrapper has a `Header` and a `Cookies` field, so a 200 with `Cache-Control` or a `Set-Cookie` is `OK[T]` with them filled; a plain `T` is `OK[T]` with neither. A `Created` has its `Location`, a redirect its target. The API document states a `Created`'s `Location` header only for a route registered with `SetsLocation()`, and then as a required header; for any other route it states none. The engine sends `Location` when the field is not empty, and most handlers leave it empty, so a document that listed the header on every `Created` made a generated client expect one the server never sent (the first position, decided 2026-11-03, was to document it as optional with a description saying when it is present, which still stated it on every creating route, those that never set one included). The type cannot say whether a handler sets it, because the field is a string and emptiness is a run-time fact, so the route says: `SetsLocation()` is a route option (refused on a group, whose routes differ in what they return, and on a route whose handler cannot return a `Created`, a WebSocket or a static route), it marks every `Created` plan the route can answer with (a plain return, a variant of a OneOf, a type given to `Returns`), and it turns the document's header into a required one. A route that opted in and returns a `Created` with an empty `Location` gets a logged 500 naming the option, as a `Redirect` with a status outside the four does: the document promised the header, and a client built from it would fail on the answer. A handler that sets `Location` on a route without the option still sends it, so no running answer changes. A distinct wrapper type (`CreatedAt[T]` with a required `Location string`, or a `Located[T]`) was considered and rejected: the choice would live in the return type, so the handler's signature would change when a route learns to set a header, a OneOf and a `Returns` list would each need both spellings, and the empty-string check would still be a run-time fact. A field whose presence decides (`Created[T, L]`) was rejected for the same reason and for generic noise. Making `Location` required on `Created` for every route (a Registration refusal when empty) was rejected, since a `Created` without a resource URL is legitimate. Bodies other than JSON are their own types ([ADR 0043](0043-cookies-and-bodies-other-than-json.md)).

A handler that can answer with more than one of these types returns a `OneOf2[A, B]`, `OneOf3[A, B, C]` or `OneOf4[A, B, C, D]` of them, and a handler with more answers than that, or one that returns an interface of its own, returns the interface and lists each type with `Returns[T]()`. Error statuses never come from the output type; they come from the returned error ([ADR 0012](0012-client-errors-are-400-problem-json.md)), with one exception: a `Page`, an HTML page for a browser, carries its own `Status`, 200 or a 4xx, checked per response and stated in the API document as a `200` and a `4XX` answer, because a browser shows the body of an answer and a form shown again with its mistakes is a page, not a problem ([ADR 0078](0078-a-page-for-a-browser-is-a-page-and-a-form-it-shows-again-is-a-submitted-body.md)).

**What this cannot do:** a header whose name is decided at run time cannot appear in the API description; a route that sends one declares it as a registration option.

**Considered:** a `Status() int` method on the output type. Rejected because the API description could only learn the status by calling it, so it would be invisible at registration; a wrapper is a type, and registration reads types.

**A OneOf is the return type of a handler with more than one answer.** It holds one of its type arguments, chosen with the method of that variant's letter on any value of the type (`DocAnswer{}.B(bites.NotModified{...})`, where `DocAnswer` is an alias the application names once), and the compiler refuses a handler that returns anything else. Registration compiles each type argument exactly as if the handler returned it alone, so a variant is any return type (a plain value, a wrapper, `Text`, `Bytes`, `File`, `Stream`, `SSE`), and the API document describes the variants as it describes the types of `Returns`: each by its status and schema, two of one status sharing a response, a `oneOf` when their schemas differ. The OneOf is a struct with an unexported tag and one field per variant, so the chosen value is held where it is, never boxed: the engine reads the tag and writes the variant from its offset in the handler's own return value, with no copy, no type switch and no reflection on the request path. Its size is the sum of its variants' sizes. Go has no variadic type parameters, so each count is a type of its own, written by hand, and four is the last; a handler with five answers falls back to an interface with `Returns`.

**A OneOf with no variant chosen, its zero value returned with a nil error, is a logged 500**, as an undeclared type returned through an interface is, with the message `the handler returned a OneOf2 with no variant chosen and no error: choose one with the method of its letter`. It cannot be caught earlier: a zero value of every Go type exists, the compiler cannot tell `DocAnswer{}` from `DocAnswer{}.A(v)`, and Registration never calls the handler. Reading the zero value as the first variant was considered and rejected: a forgotten choice would answer a zero `A` (an empty 200, a 201 with no `Location`) with no trace, where a 500 in the log names the mistake. Returned with an error, the OneOf is not read. `Value()` gives a test that calls a handler directly the chosen variant, boxed; the engine never calls it.

**`Returns[T]()` declares what an interface-typed return may hold.** It is a route option that appends `T` to the route's list. A route whose output is an interface needs at least one; each `T` is compiled at Registration, must implement the interface when it has methods (`*T` is what is checked, so a method with a pointer receiver counts, and a handler may return `T` or `*T`), and may not repeat; `Returns` on a route whose output is not an interface is refused, and so is `Returns` given to a `Group` or to a WebSocket route. The wrappers have no methods, so for a handler returning `any` the declaration is the only check, stronger than the compiler's. The list also gives the API document its statuses and schemas ([ADR 0020](0020-descriptions-come-from-registration-and-later-from-doc-comments.md)): each type is described as it would be if the handler returned it alone, and two types with one status share a response (a `oneOf` when their schemas differ). At run time the plan is found in the route's own slice by comparing `reflect.TypeOf(v)`, which replaced the app-wide `sync.Map` and the compile on first use; a handler that returns an undeclared type gets a logged 500 naming the `Returns` to add, and is never compiled on the fly. A value the interface holds by pointer is written from that pointer, with no copy; a type an interface holds directly (a struct whose only field is a map or a pointer) is copied once, as before. Evidence: [`docs/research/decisions-middleware/`](../research/decisions-middleware/report.md), section R12.

**What it costs.** A OneOf return costs 2 allocations, what a plain output costs: measured over the in-memory connection with the same Input as the 2-allocation row, a wrapper variant and a plain value variant of a `OneOf3` both 2.00 (`TestAOneOfReturnAllocatesNoMoreThanAPlainOneBecauseNothingIsBoxed` in `budget_test.go`), against 3.00 for the same answers through an interface in the same run. A route that returns no OneOf pays one nil check in the write step. An interface return costs 3 allocations: the two of a plain output, and the one the handler makes boxing its wrapper into the interface (measured over the in-memory connection with the same Input as the 2-allocation row: a wrapper by value, a plain value and a pointer to a wrapper all 3.00, in `budget_test.go`). It was 4 when the value was read out of the interface by `reflect.New`; [ADR 0003](0003-the-trade-budget.md) has the row. The 3 is as low as it can be while the handler returns an interface, because the boxing is the handler's.

**What it fails at:** a OneOf with no variant chosen is a 500 at request time, which only a test that runs the handler catches; the letters say nothing of the answer (`.B` is the 304 only because `B` is `NotModified` in the alias); reordering the type arguments of an alias is caught by the compiler, since no two variants share a type, except for a value assignable to both (an untyped constant, or an unnamed literal given to two named types of one underlying type), which then silently changes variant; a OneOf of large variants is copied whole on return, a claim not measured, since every answer fits in a few words; and past four answers the handler is back on an interface, where an undeclared type is a 500 at request time and not a compile error, and `Returns` can drift from the real returns, which only a test that runs the handler catches.

**What was rejected:** `Either[A, B]` was considered when `Returns` was built and deferred, "for now", because Go has no variadic generics, so every arity is hand-written, and because the boxing it would save had not been shown to matter. The interface return then measured 3 allocations against 2 for a plain one, the one extra being the handler's boxing that no plan can remove; three hand-written types of a few lines each are a smaller cost than an allocation on every request of every handler with two answers, and than a declaration the compiler cannot check. The name `Either` was not kept: it says two, and three counts are needed; `OneOf` is the word the API document already uses for the same idea. Constructors as functions (`bites.First[A, B](v)`) were rejected because Go cannot infer `B` from `v`, so every return would name every type argument again; a method on the zero value takes them from the alias.

**Refusals of a OneOf, in the table:** a variant the encoder cannot compile, or any refusal of a return type (with the variant's letter); one type named twice; a OneOf as a variant; a pointer variant; an interface variant; a stream variant on a HEAD route; `Returns` on a route that returns a OneOf; a OneOf given to `Returns`; a pointer to a OneOf as the return type; a OneOf as the Body of a wrapper; a OneOf inside a returned value, a request body, a Socket's message or an Inbox's message, where JSON would write it as `{}` because its fields are unexported.

**Refusals in the table:** an interface output with no `Returns`; a `Returns[T]` where `T` does not implement the output; a repeated `Returns[T]`; `Returns` on a route whose output is not an interface; `Returns` given to a `Group`; and five more found in building it: a `Returns` of a pointer type, a `Returns` of an interface type, a `T` the encoder cannot compile (with the encoder's reason), a `T` that is a stream on a HEAD route, and `Returns` on a WebSocket route.

**An answer with no body is a 204, and the framework has no way to say "200 and nothing".** A handler that has nothing to return answers `NoContent` (204). A handler that returns an empty struct as its output (`struct{}`, or `OK[struct{}]`) answers 200 with the JSON object `{}`, because a value is encoded as JSON and an empty object is its encoding; no JSON output produces a 200 with zero bytes, so "a 200 with an empty body" cannot happen by accident through a typed output, and `Text`, `Bytes` and `File` reach it only by being given nothing, on purpose. It was asked for (a port from Huma, where a handler with no output answered 200 with no body, wanted `OK[Empty]` or a status option), and it is not built: RFC 9110 gives that meaning to 204, a client generator reads 204 as "no body" and 200 as "a body to parse" (so a 200 with none makes a typed client fail to parse it, the case that costs a day to find), and the API document would have to state a 200 with no content, which says less than the 204 it replaces. The price is the port's: a route that answered an empty 200 changes its status and its documented response, and a client that called `res.json()` on it now has to look at the status first. That is the port's to change, not a mode of the framework. Rejected: `OK[Empty]` (a 200 with no body), a `Status(200)` route option that overrides `NoContent`'s status (a wrapper whose name and status disagree, and the API document would need to read the option), and refusing an empty `Text` or `Bytes` body with a 200 at run time (it is not an error, only unusual, and the refusal would be a 500 for a valid answer).
