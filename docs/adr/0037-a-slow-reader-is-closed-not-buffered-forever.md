# Each socket's send queue is bounded, and a reader that falls behind is closed

`Send` never blocks; it queues. Each socket's queue is bounded, 1 MiB by default and configurable, and a socket whose queue would overflow is closed with status 1008. The queue holds references to frames, not copies ([ADR 0038](0038-a-broadcast-is-framed-once-and-shared.md)), so a bound counts what the socket alone is holding back.

**Why:** fib's own guide warns that a peer that never reads keeps queueing what is sent to it ([`docs/research/fib.md`](../research/fib.md)); one stalled client must not be able to grow the server's memory without bound.

**Who writes.** There is no writer goroutine per socket: one kept per socket added +4,182 to +4,227 B of heap plus stack after a single write, more than the whole 3.1 to 3.5 KB an idle connection holds. `Send` and `Publish` append a reference to the shared frame to the socket's queue under a per-socket mutex, and a flusher goroutine is started when there is something to send and no flusher is running; it writes until the queue is empty and exits, under a write deadline. A publish walks its subscribers in a few shard workers. On plain TCP a worker first tries one non-blocking write inline and queues the frame and starts a flusher only when the kernel took less than the whole frame; on TLS (a `tls.Conn` cannot be written without blocking, and a write timeout corrupts its state for good) and for control frames (the heartbeat's ping, which runs on the wheel and must not block, and the 1001 of Shutdown) the frame goes straight to the queue and the flusher. Measured with 20,000 loopback sockets and one 16 byte frame to each: a flusher per burst where none runs 28.6 to 32.6 ms but about 17,000 to 18,200 goroutines alive at once, 70 to 73 MiB of stacks (a transient, as large as the whole idle footprint of the 20,000 sockets); shard workers writing inline 27.5 to 29.2 ms with 17 to 29 goroutines and 3 MiB, at zero allocations. A blocking inline write by the publisher with one stalled socket first held the publisher for the whole deadline (278 to 286 ms against a 200 ms deadline); with the flusher the publisher returned in 10 to 30 ms. Evidence: [`docs/research/decisions-websocket/`](../research/decisions-websocket/report.md), section R7. If the second code path is judged too much for the first build, the flusher alone is acceptable and the 70 MiB peak is the figure to state here.

**A send-queue budget for the whole app.** The 1 MiB bound counts a shared frame once per socket, which is conservative for broadcasts but leaves no bound on distinct per-socket data: 20,000 stalled sockets each holding 1 MiB of different frames is 20 GB (arithmetic). An app-wide send-queue budget, closing the socket that would exceed it, like the reassembly budget of [ADR 0046](0046-websocket-origins-and-inbound-limits.md), bounds it; its default and close status (1013 or 1008) are set when it is built. **What was rejected:** a persistent writer goroutine per socket. **What it fails at:** two code paths; the allocations of the real queue are 2 a socket a burst in the probe's slice version and need a ring or a reusable slot to reach zero; coalescing queued frames into one `writev` and the ~40 bytes the queue adds to an idle socket are not measured (to be asserted by the idle gate).

**Built.** Both paths of "Who writes" exist; the "flusher alone" fallback was not needed. A `Send` on plain TCP writes inline only when the socket's queue is empty and no flusher is running, with one non-blocking syscall through `RawConn.Write` whose callback returns at once; a short write queues the rest and starts the flusher, and a write error closes the socket. The flusher takes the whole queue, writes it under a write deadline (`Limits.WriteTimeout`) and clears the deadline when the batch is out, so a deadline never survives into a later read. The queue is counted in bytes: a frame over the socket's `SendQueue` closes it with 1008 and `Send` returns `ErrSendQueueFull`; a frame that would take the app past `SendBudget` closes the socket with 1013 and returns the same error. A socket closed for its queue drops what is queued behind the Close, except the rest of a frame a short inline write left: that stays at the head, because dropping it would put the Close frame inside that frame's payload. The budget is returned as each frame leaves the queue, as a closing socket drops its queue, and when a socket ends with frames still in it. A frame is shared by the queues that hold it and freed by the collector, with no reference count in the engine. Allocations: [ADR 0003](0003-the-trade-budget.md).
