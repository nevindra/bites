# Agent usability test, run 4: task tracker

A multi-tenant task tracker (`example.com/tasks`, one service `cmd/tasks`, in-memory) was built by Claude (Sonnet 5.5, `claude-sonnet-5-5`) on 2026-11-04 against nilo-go commit ae32dd3 (clean tree). It lives in `docs/research/agent-usability/run-4/app/`. Files: `go.mod`, `cmd/tasks/{main,app,auth,store,hub}.go`, `cmd/tasks/web/{index.html,app.js}` (embedded), `cmd/tasks/testdata/openapi.json` (recorded by `nilotest.Document`), and tests in `cmd/tasks/{helpers,app,more}_test.go` (24 tests). `go vet ./...` is clean, `go test ./...` passes, and `go test -race -count=2 ./...` passes (48 test runs). I also ran the built binary once against a real socket (a hand-made HS256 token via curl: POST /api/tasks gave 201 with `X-Request-ID`, GET / gave the dashboard, the access line carried `user=ada`).

The agent returned this report as its final answer, because a subagent may not write report files; the session that ran it saved it here unchanged, and added the last section.

I did not open `docs/research/`, `docs/adr/`, `docs/design/`, `docs/roadmap.md`, or any framework `.go` source outside `examples/`. I did not need to.
- Copied shapes: the `go.mod` replace pattern and `Caller Claims`/`jwt.New[Claims]` wiring from `examples/shop`; the shutdown block from `getting-started.md`; the Static/`fs.Sub` snippet from `files.md`; the rate-limit-in-a-Provider shape from `security.md`; the Events handler from `streaming.md`; the `refusal`/`Document` test shapes from `testing.md`. The assignment is close to what the guide pages teach, so the number of first-time successes probably overstates how hard an unguided task would be.

- The dashboard (`index.html`, `app.js`) is a minimal fetch-based list. It was not opened in a browser; it is only checked for being served with the right content types. It does not follow SSE or open the WebSocket (see log row 6).
- The tests use `nilotest` only (no real socket) except the one manual binary run above. The JWT tests use `jwttest.Token` with HS256 and the app's fake clock.

## What works, what is partial, what was given up

1. Tenant header, JWT user, admin role, 401 before 400: works. `X-Tenant` is a `Slug` type (`Length` 3 to 30, `Pattern` `^[a-z0-9]+$`) read through a Provider's `Header` section; the user is `CustomAuth` around `BearerAuth(v.Verify)`; `Admin` is a Provider needing `User`. Tests: no token and no tenant gives 401; token and no tenant gives 400 `header.X-Tenant`; slugs `ab`, `Acme`, `acme-inc`, 32 characters give 400; expired and forged tokens give 401 with `invalid_token`; non-admin merge gives 403; a task of one tenant is a 404 for another.
2. Tasks: works. Title 1 to 200 characters (`Length`), status enum, optional due date and assignee, create (201 + `Location`), get, list with `?status=todo,doing&due_before=2026-12-01`, `page`/`per_page` (capped at 100), per-tenant totals.
3. PATCH: works. `Opt[Title]`, `Opt[Status]`, `Opt[Null[Date]]`, `Opt[Null[UserID]]`; `If-Match: "<version>"` (ETag form); stale gives 412, missing gives 428, malformed gives 400, `"title": null` gives 400 at `body.title`.
4. 200 or 303: works. One handler returning `OneOf2[OK[Task], SeeOther]`; the document lists 200 and 303 (recorded in `testdata/openapi.json`). Merging is an extra admin-only route I added to produce the 303.
5. Bulk import: works. `POST /api/imports` answers 202 at once with the job id and `Location: /api/imports/{id}/events`; a goroutine creates the tasks; `GET .../events` is an `Events[Progress]` that ends with `state: "done"`. The test holds the job with a hook, reads the first event (`done:0`), releases it, and reads to the end. Partial: the job map is never pruned, and a failed item cannot occur (items are validated up front).
6. WebSocket per tenant: works in tests (`/api/ws`, one `Topic` per tenant, a typed `TaskEvent`; clients of the same tenant are told, another tenant is not; a client that sends is closed with 1003; no token gives 401). Partial or given up: it uses `Authorization` and `X-Tenant` headers, so a browser cannot connect (row 6).
7. Rate limit per user on writes: works (3 writes then 429 in the test, another user unaffected, reads unaffected, refilled by the fake clock). Request ID on every answer: works except the two probe paths (row 8). Access log: works, one `request` line per request, tested with a buffer logger (5 requests, 5 lines, each with `request_id=`).
8. Dashboard and API document: works. `/` serves the embedded `index.html` and `/app.js` (content types checked, missing file is a 404). `/openapi.json` lists per route: 400/401/404/412/428/429/default and so on, `security: bearerAuth` on every `/api` route (the WebSocket and Static routes are left out by design, as the guide says). The 429 on write routes comes from my explicit `ErrorStatuses(429)`: I added it because `security.md` names a 429 only for a `RateLimiter`'s middleware, and did not check what the document says without it. The dashboard does not follow SSE or the WebSocket.
9. Health, readiness, graceful shutdown: works. `/livez` and `/readyz`; `main` uses `signal.NotifyContext`, a `serve` function (`Listen`, `Shutdown` with a 20 s grace and a 5 s `WithShutdownDelay`, then waits for running imports). Tested: readiness turns 503 during the delay, requests are still served during it, and an open import stream ends on shutdown. `main` itself (signal handling and a real port) was exercised once by hand, not by a test.

## The five changes that would have helped most

1. Make `nilotest.JSON[T]` and `Response.JSON` decode the types the framework writes: `nilogo.Null[T]`, `nilogo.Opt[T]` and `nilogo.Date` (or say in the `nilotest.JSON` reference entry that they do not, and give a DTO pattern). Row 3 is the only place the helper contradicted the "the same shapes the app wrote" promise.
2. Give browsers a documented way in for WebSocket and SSE routes: a worked example (and a first-party Provider or `BearerAuth` option) that reads a token and a tenant from the query or from `Sec-WebSocket-Protocol`, still checked at the handshake, still stated in the OpenAPI/`security` entry. Today `websockets.md` says "a cookie or a query token" but `providers.md` forbids a `Query` section in a Provider's dependencies and `BearerAuth` reads only the header (row 6, unverified).
3. Put the full signatures of the `nilotest.WS` / `EventStream` methods in the guide's "Testing a WebSocket" paragraph (or link each name to the reference heading); `ExpectSilence`, `ReadClose`, `Leave` are listed there as bare names (row 4).
4. Make the EOF a test client sees after `Shutdown` explain itself, or make `nilotest` say "the listener is closed because the app is shutting down; set `WithShutdownDelay` to keep serving". Also mention `WithShutdownDelay` in the `testing.md` shutdown/readiness text, not only in `deploying.md` (row 5).
5. Say in one place what an `Output` type with `Null[T]` means for the 400 of an `Input` that reuses the same type, and add a one-line "optional on create = `Opt[T]`, nullable on patch = `Opt[Null[T]]`, `Null[T]` alone = required but may be null" box at the top of `requests.md#marking-a-field-optional-nullable-or-both` (row 2 was my misreading, but it is the first trap the PATCH requirement leads into). Also align the `Values()` row of the `requests.md` table with the CSV example below it (row 7).

## What worked well

- The refusal-first design held: the whole app registered on the first compile with no Registration panic, and `TestTheAppRegisters` is a three-line test.
- The ordering rule in `providers.md` ("a tenant read from a header and a `User` from a token, on one request with neither, answers the 401") is exactly what the assignment's first point needs, is stated in the guide, and held in the test.
- 400 answers name every field at once, with wire names and codes, including inside lists (`body[1].status`, `query.status[1]`), so the tests assert locations and not prose.
- `OneOf2` gave both the 200/303 handler and the document entry with nothing to write; `Opt[Null[T]]` gave PATCH semantics in one type per field.
- `nilotest` covered nearly every numbered point without a port: `OpenEvents`, `DialWS`/`TryDialWS`, the fake clock moving JWT expiry, the rate-limit refill and the shutdown delay, `WaitEnded` before reading the access log, and `Document` for the contract.
- The `jwt` module and `jwttest.Token` needed one call each; `CustomAuth` made the document state the bearer scheme and 401 on every route that asks for `User`.
- `go doc` output and reference entries carried doc comments and zero-value meanings, so no framework source file was needed.

## Review against the source

Checked by the session that ran the test, on 2026-11-04, at ae32dd3. Row 3: `nilotest`'s `JSON` and `Response.JSON` decode with `encoding/json/v2` and only case-insensitive names (`nilotest/nilotest.go`), not with the app's codec, and `Null`, `Opt` and `Date` read their JSON only through that codec, so the failure is real. Row 4: the testing guide names the WebSocket client's methods without their signatures. Row 6: `docs/guide/websockets.md` says a browser-facing route authenticates "with a cookie or a query token", while a Provider's `Query` section is refused (`provide.go`) and `BearerAuth` reads only `Authorization`; a query token works only through a Provider that parses `req.RawQuery()` by hand, with no located 400 and nothing in the API document, so the gap is real though the run did not probe it. Row 7: the table in `docs/guide/requests.md` says `Values() []string` where the reference and the same page's example use `Values() []T`. Row 8 is documented behaviour. Not a row but found in the review: a `RateLimiter.Allow` called inside a Provider puts no 429 in the API document, since only the limiter's middleware is recognised; the run stated it with `ErrorStatuses(429)`. The app's 24 tests pass.

## After the fixes

All five findings were fixed on 2026-11-04 after ae32dd3 (see item 1 of the roadmap). One change reached this app: `ErrorStatuses(429)` now documents a 429 as `TooManyRequests`, the rate limit's answer with `Retry-After` and `RateLimit`, rather than as `Error`, so the app's `testdata/openapi.json` was accepted again with that difference on its three write routes; the app's code is unchanged and its 24 tests pass. Writing the testing guide's shutdown example found one more trap: `nilotest.Start` served the app on a goroutine, so a `Shutdown` called right after it could find no server, return nil and stop nothing; `Start` now builds the server before it returns.
