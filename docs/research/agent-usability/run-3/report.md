# Agent usability test, run 3: file sharing

I built a file-sharing service, `example.com/files` (in `docs/research/agent-usability/run-3/app/`, one service `cmd/files`, everything in memory), against nilo-go commit `7450052`, on 2026-11-04, as the model Claude Sonnet 5.5 (`claude-sonnet-5-5`). The nilo-go working tree had uncommitted changes (many modified docs and sources, `CHANGELOG.md` deleted), so the docs and code I read are the working tree and not that commit. The service has all ten points of the assignment: browser sign-in with a form post, a server-side session and CSRF; a multipart upload with a size limit; a download with `ETag` and `Range` as an attachment; `PUT` rename guarded by `If-Match`; a JSON API under `/api` with an API key and `?limit=&cursor=` paging; an NDJSON export; rate-limited public share links; CORS for one origin on `/api`, gzip and an OpenAPI document that states error statuses; a mounted `net/http` handler (`expvar` and a health page) left out of the document; and graceful shutdown in `main`. There are 48 tests (`api_test.go`, `files_test.go`, `web_test.go`, `shutdown_test.go`), all through `nilotest` except the shutdown test, which uses a real loopback listener and `SIGTERM`. `go vet ./...`, `go test ./...` and `go test -race ./...` pass in the app's module, and a built binary answered over a real socket for a smoke check (an API call, a form sign-in, a clean exit on `SIGTERM`).

The agent wrote this report as its final answer, because a subagent may not write report files; the session that ran it saved it here unchanged, and added the last section.

What may distort the findings. (1) I read nearly the whole guide before writing code, which understates the stumbles an agent that skims would have, especially around the options and listening APIs. (2) Output of `go test` in this environment is condensed by a hook (RTK); a failing assertion's message was hidden and I had to re-run with `rtk proxy go test` to see it (twice). (3) Most findings were made through `nilotest`; the real-socket check covers only the binary's start, a form sign-in and shutdown. (4) Rows 10 and 11 were found by deliberate probes after I had already designed around the documented behaviour, so they show what a different first attempt would hit, not what I hit. (5) A single author, one pass: no concurrency test of rename races, though the `If-Match` check and the write are one critical section in `Store.Rename`. (6) Nothing about performance or the allocation budget was measured.

## What works, what is partial, what was given up

1. Browser sign-in, session, CSRF: works. Form post to `Form[LoginForm]`, a `SessionStore` kept in memory (so logout really revokes), `__Host-session` cookie, CSRF on every state-changing browser route. Partial: the sign-in form itself needed an extra origin check (row 11), and the security of the session routes in the document needed `CustomAuth` and a manual `Load` (row 8).
2. Upload: works. Title and file in a `multipart/form-data` body read with `Each`, `MaxBody(cfg.MaxUpload)` (64 KiB in tests), located 400s for a missing title (`body.title`) or file (`body.file`). Partial: the 413 does not say the limit (row 4).
3. Download: works, including `Range`, `If-Range`, 304, 416 and the attachment name (`attachment; filename="q3 report.txt"`, kept on a 206). Rough edge that worked first time: a `File` needs a `Root` or an `FS`, and `Bytes` has no `Range` or `ETag`, so for bytes held in memory I wrapped each file in a one-entry `testing/fstest.MapFS` in production code (`fileOf` in `handlers.go`). The files guide does say an `fs.FS` may be in memory, but there is no direct `File{Data: []byte}`. The document says `*/*` for the response (row 9).
4. Rename with `If-Match`: works. Stale is a 412 with the current ETag in the detail; missing is a 428 (my choice, because it tells a client to retry with a header, where a 400 `required` would not say which value; the 428 detail names the ETag to send and the problem carries an `etag` member). Partial: title `Status 428` (row 6). The check and the write are one critical section (`Store.Rename`).
5. JSON API under `/api`: works. API key header (`X-API-Key`) through `APIKeyAuth`, 401 with a `WWW-Authenticate` challenge, paging by `limit` (default 20 through `Defaults`, range 1 to 100) and an opaque `cursor`, a bad cursor a 400 that names `query.cursor` through `nilogo.Invalid`.
6. NDJSON export: works as a plain (non-`Live`) `Stream` with `application/x-ndjson`, one `json.Encoder` line per file; empty store gives an empty body. Not compressed by gzip (documented for streams). Document shows `*/*` (row 9).
7. Public share links: works. `POST /files/{id}/share` creates a token, `GET /s/{token}` needs no credential and is limited by a `RateLimiter` middleware on the `/s` group (3 a minute in tests, keyed by address: a second client is not affected, and the clock refills it). Unknown token is a 404.
8. CORS, gzip, OpenAPI: works with the caveats of rows 8 to 10. CORS for one origin is only on `/api` through a path-checking wrapper (row 10). `WithGzip(Gzip{})` compresses JSON of at least 1 KiB when asked and leaves small answers and no-`Accept-Encoding` clients alone. The document lists `400/401/403/404/412/415/428/default` (and `413`, `429`) where asked, from `ErrorStatuses` and from what the framework adds itself.
9. Mounted `net/http`: works. `expvar.Handler()` and a health function in one `ServeMux`, mounted at `/debug/` behind a middleware that wants an admin key, and absent from `/openapi.json` (tested). Used `stdhttp.Mount` with `nilogo.Use`; no stumble.
10. Graceful shutdown: works (`run` takes the listener, `app.Serve`, `signal.NotifyContext`, `Shutdown` with a 25 s grace, waits for `ErrServerClosed`). Tested with `SIGTERM` to the test's own process. Nothing in the ten points was given up. Not done: a test that a request in flight is drained.

## The five changes that would have helped most

1. State the response content type and headers of a `Stream` and a `File` in the OpenAPI document. Add route options such as `ResponseContentType("application/x-ndjson")` and `ResponseHeaders(...)` (or read them from a typed field on `Stream` and `File`), so the export and downloads stop being `*/*` with no `ETag` or `Content-Disposition` (row 9).
2. Let `CustomAuth` take dependencies, or give the session a first-class security scheme (for example `Sessions.Provider()` returning a `CustomAuth` ready for a cookie user). Today a session-cookie user needs the manual `Load` inside the Provider and a second `app.Provide(sessions.Load)` (row 8).
3. Put a sentence and a refusal where CORS is scoped. In `first-party-middleware.md`, say how to limit `CORS` to a path prefix (a wrapper, or a supported `Paths` option), and make `Group.Use(nilogo.CORS(...))` and the option `nilogo.Use(CORS)` a Registration refusal, since a preflight can never reach it and the 405 gives no hint (row 10).
4. Document login CSRF in the CSRF section of `security.md`: say that a request with no cookie passes even with a foreign `Origin`, so a sign-in form needs the origin check. Better, make `CSRF` refuse a present `Origin` that is neither listed nor same-origin even without a cookie, for routes that opt in (row 11).
5. Put the limit and the offending size in the 413 detail (`request body too large: at most 65536 bytes`), name 428 (`PreconditionRequired`) next to `PreconditionFailed` with the title `Precondition Required`, and make an unnamed status take its standard reason phrase as the title instead of `Status 428` (rows 4, 6). Alongside, add a line about `nilogo.Options` to the groups or routing guide and let `Group` accept a shared option set without a prefix (row 1).

## What worked well

The refusals at Registration were the best part: both panics (rows 1 and 2) named the route or the field, the rule and the line, and the `Range` one gave the exact signature to write. Reading the guide first was enough to get every one of the ten points working: the pages are written as tasks and almost every claim I tested (a replayed cookie after `Clear`, `Content-Disposition` on a 206, `If-Range` with a stale tag, `Vary: Accept-Encoding` on small answers, the shared `429` component, `Defaults` plus `Range` naming `query.limit` for `0`, `101`, `abc` and an empty value) held exactly as written. Typed inputs removed the code I would normally write: no decoding, no manual `limit` parsing, no bad-value handling; `Opt[string]` for `If-Match` made the 428-or-not branch one line. `nilotest` made every point a short test with no port, including the clock-driven rate limit refill, a chunked oversized upload on `Dial` and `Read`, and a preflight; a failing test also prints the app's log, which is where a problem showed what failed. `nilogo.Invalid("body.title", "required")` from a handler gave a located 400 identical to the framework's own, which let upload validation that depends on the whole multipart body look like the rest of the API. `nilotest.Start` plus the same `newApp(Config)` for `main` and the tests meant no test needed special wiring.

## Review against the source

Checked by the session that ran the test, on 2026-11-04, against the working tree. Row 1: no page under `docs/guide/` mentions `nilogo.Options`. Row 4: the engine's 413 is `ErrBodyTooLarge` with the fixed reason `request body too large` (`internal/engine/exchange.go`). Row 6: a status with no reason phrase of its own is titled `"Status " + code` (`internal/engine/status.go`), and 428 is among them. Row 9: a response with no JSON type is described as `*/*` (`openapi.go`). Row 10: no refusal names `CORS` on a group or a route; the guide says it is app middleware, which a reader of `Group.Use` does not meet. Row 11: `docs/guide/security.md` states that a request with no cookie passes, and nothing says what that means for a sign-in form. Row 8 is the limit ADR 0069 states under "What it fails at" (a Provider with dependencies cannot be given to `CustomAuth`). The app's 48 tests pass. Rows 2, 3, 5, 7 and 12 are the agent's own and need no change, though row 12 shows `app.Serve(ln)` is easy to miss on the deploying page.

After the fixes of roadmap item 1 the 413 names the limit, so `TestUploadOverTheLimitIsA413ThatSaysTheBodyIsTooLarge` in `app/` was changed to expect the new detail; nothing else in the app was touched, and its workarounds (the CORS path wrapper, the origin check on `/login`, the manual `Sessions.Load`) are kept as the record of what the run met.
