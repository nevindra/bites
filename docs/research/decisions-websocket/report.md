# Stress test of R5 to R8 and the ADR 0046 gaps (WebSockets and shutdown, steps 12 and 13)

Run on 2026-10-31, AMD Ryzen 7 9700X, go1.27.2, tree uncommitted, probes pinned `taskset -c 0,1,8,9` (GOMAXPROCS 4). Probes are in this folder, one module (`go.mod`, replace to `../../..`): `reasm/` (R6), `bcast/` and `micro/` (R7), `origin/` (R8), `ctl/` (ADR 0046 gaps). "measured" means a probe here printed it; "claim" means reasoned or read from code, not run. The bcast probe puts both ends of 20,000 loopback TCP connections in one process, the client ends never read, a frame is 16 bytes, three runs of five bursts each; the spread quoted is min to max over the runs.

## R5: cancel stream contexts when Shutdown starts

Design as stated: Shutdown marks every connection that is serving a `Stream`, cancels its context with `ErrServerClosed`, and the stream's function returns. Today (`internal/engine/server.go`) Shutdown only cancels live contexts in `forceClose`, after the caller's ctx has ended, and the stream type is not built yet (step 10).

Attacks and findings:

- ADR 0030 says `Stream` is also "a large download" and NDJSON. Cancelling every stream at Shutdown start cuts a 2 GB download at the first SIGTERM, where ADR 0029 promises in-flight requests finish. Worse, if the engine then writes the terminating chunk because the function returned normally, the client sees a complete, silently truncated body. Claim (the Stream writer is not built), but it follows from ADR 0030's text.
- An SSE stream has no end of its own, so waiting for it burns the whole Shutdown context every deploy (30 s typical) and then force-closes. That is the case R5 is right about.
- A race: a keep-alive connection can return a `Stream` after Shutdown began. The starter must set the stream state and then read the closing flag; Shutdown must set the flag and then walk the connections; with both orders each side sees the other. Claim.
- Thundering herd: 20,000 EventSource and WebSocket clients all told to leave in the same millisecond reconnect to the next instance together. Not solved by R5 (a jittered 1001 over a few seconds would; claim, not built).
- Cost: nothing on the non-stream path, one atomic store when a stream starts. Axis spent: none (claim; no allocation is added, Cancel already exists and is called by `forceClose`).

Best alternative: cancel all streams (R5 as written). It lost because it truncates finite streams. Another alternative: do nothing and let the Shutdown context expire. It lost because every deploy then waits the full grace for SSE.

Verdict: MODIFY. Only a stream declared live is cancelled at Shutdown start: `SSE` is live by construction, and `Stream` gets a `Live bool` (or the type of a live stream is distinct) that NDJSON feeds set; a plain `Stream` drains until the Shutdown context ends, as ADR 0029 says. When a live stream's function returns with cause `ErrServerClosed`, an SSE response ends cleanly (EventSource reconnects either way); a non-SSE live stream ends without the terminating chunk, so a client cannot mistake it for complete. Add a Registration refusal row only if `Live` is a field: none is needed, a bool cannot be misused. What it fails at: a handler that ignores its context keeps the connection until the Shutdown context ends (the same as today), and the reconnect herd above.

## R6: fragmented message deadline, 256 MiB reassembly budget, buffers only for fragmented messages

Facts measured:

- The `ws.Reader` already aliases the slice it is fed and holds no message buffer: every `KindData` payload lay inside the fed slice in all feeds tried (measured, `reasm`). It emits a chunk per read, with `Start` on the first and `End` on the last.
- So "reassembly buffers only for fragmented messages" is wrong as stated. A single-frame 3000 byte message fed in two reads of 1500 produced 3 data events (Start once, End once): any message whose first event lacks `End` needs assembly, fragmented or not (measured). With the engine's 4096 byte pooled scratch (`bufSize` in `internal/engine/server.go`), a 64 KiB single frame arrives as 17 events in 4096 byte reads (measured).
- To hand a single 64 KiB message to the decoder without assembly, the buffer must hold the whole frame: 65,543 bytes for a payload of 65,535 (4 byte header, 4 byte mask), 65,550 at the most with an 8 byte length. Held per socket that is 20,000 x 64 KiB = 1,250 MiB heap in use (measured, exact allocation), against 72 MB for all 20,000 idle sockets (3,615 B each, `docs/research/ws-idle`). A per-socket buffer of that size is impossible; a pooled one is held only while a read is in flight and does not help the attack, because the attacker holds the read open.
- "Decoded straight from the read buffer" breaks ADR 0008. `jsoncodec` decodes strings without escapes as views of the body (`state.str`): after decoding `{"text":"hello world"}` from the read buffer and reusing the buffer, `Text` read `XXXXXXXXXXX` (measured). Decoding from a fresh slab copy kept `hello world` (measured). The copy costs one allocation and about 15 ns for a 39 byte message: 158 to 159 ns against 143 ns, three runs, and +1 allocation (3 against 2 in this harness, whose two baseline allocations are its own escaping locals; the delta is the slab) (measured). So an `OnMessage` costs one allocation for its slab plus one per list, which needs a row in ADR 0003's table; not a zero.
- Reassembly strategies for 20,000 sockets each holding 64 KiB less one byte (measured): exact allocation 1,250 MiB heap in use, 1 allocation a socket; `append` doubling from 4 KiB 1,982 MiB in use, 4,814 MiB allocated in total, 8 allocations a socket (rejected); size classes 4, 16, 64 KiB grown as bytes arrive 1,343 MiB, 1,641 MiB allocated, 3 allocations a socket.
- Per-connection state is unaffected: a Reader is already about 150 bytes (`ws/doc.go`), holds its header and mask itself, so after every `Feed` that consumes all its input the engine can return the pooled scratch even mid-message, and a socket mid-message holds only its assembly buffer. At 20,000 sockets with 4 KiB scratches that would otherwise be 78 MiB (arithmetic) of pooled buffers pinned by sockets that sent a header and stopped.

Attacks:

- 20,000 sockets each send 64 KiB less one byte and stop. Unbounded: about 1.25 to 1.34 GB (measured above). With a budget B and charging held capacity, the app holds B plus the 72 MB idle baseline; at 256 MiB that is 328 MB, 4.5 times the idle footprint, and 4,096 sockets can each hold a full message; at 64 MiB (1,024 full messages) it is 136 MB. Arithmetic from the measured figures.
- Charging the declared length at the frame header lets an attacker reserve 64 KiB with a 14 byte header and no payload; charging held capacity as bytes arrive (the 4, 16, 64 KiB classes) forces the attacker to send at least 4 KiB and up to a 4:1 amplification. Claim, from the strategy numbers.
- The attacker keeps the budget full by reconnecting: honest large messages then get 1013 for as long as the attack lasts, while small messages (under the first class, never charged) and all HTTP keep working. A budget protects the process, not the honest client; evicting the oldest assembly instead of refusing the newest would protect the honest one. Claim, not built.
- A dribbling sender: the heartbeat does bound it, since a client in the middle of a frame cannot answer a ping, so two missed pongs end it in about 60 s (code reading of ADR 0039 and the Reader), but that is twice R6's "within the heartbeat interval" and tied to a setting the user may raise to minutes. An own deadline is needed.

Alternatives compared: (a) the recommendation; (b) a per-socket 64 KiB buffer held for life (1,250 MiB at 20,000, rejected on ADR 0005); (c) assemble in a pooled buffer and copy into the slab for decode (a second 64 KiB copy per large message, and a pool whose buffers attackers pin); (d) assemble straight into a fresh allocation that becomes the message's slab (no copy, no pool, charged to the budget while assembling and released at hand-off or close).

Verdict: MODIFY.

- Assembly exists for any message that does not arrive whole in one `Feed`, not only fragmented ones. A message that arrives whole is copied once into its slab and decoded from the copy (one allocation), never from the read buffer.
- The assembly buffer is a fresh allocation that becomes the slab (alternative d), grown 4, 16, 64 KiB and charged by held capacity; the first class is free of charge so ordinary chat messages never touch the budget.
- The budget default is 64 MiB, not 256 MiB, configurable; it equals the idle footprint of 20,000 sockets, the number ADR 0003 holds hard. This is a judgement, labelled as such: 256 MiB is also defensible for machines with gigabytes of headroom. Over budget the socket is closed with 1013; 1013 is a status only the server sends (see the echo gap below).
- The completion deadline is its own limit, `MessageTimeout`, default 30 s as ADR 0024's body-read row, armed with `SetReadDeadline` when a message first spills and cleared when it completes, not with the heartbeat and not on the wheel. It costs about 110 ns, only for spilled messages (`SetWriteDeadline` measured 108 to 117 ns, `micro`), and nothing for an idle socket. Closed with 1008 (claim: no existing row; 1002 and 1009 are the other candidates).
- ADR 0024 and ADR 0046 each get a row; the budget refusal is a close, not a Registration panic. A route whose `MaxMessage` is above the app budget is a Registration refusal (a message that could never be assembled).

What it fails at: the reconnecting attacker above; a budget too small for an app whose legitimate traffic is large pastes; and `MessageTimeout` being a plain read deadline that a step 16 parked socket never sees (mid-message sockets are not idle, so they are not parked; claim).

## R7: flusher goroutine started when there is something to send

Design as stated: `Send` and `Publish` append a reference to the shared frame to the socket's queue under a per-socket mutex; if no flusher runs, start one; it writes until the queue is empty and exits; a write deadline bounds a stalled reader; the 1 MiB queue closes a socket whose backlog would overflow (1008).

Measured, 20,000 loopback sockets, one 16 byte frame to each, medians of five-burst runs, three runs, spread in brackets (`bcast`, `micro`):

| model | burst, ms | ns per socket | allocations per socket per burst | peak goroutines | peak stack |
|---|---|---|---|---|---|
| A inline blocking `Write`, one publisher | 67 to 73 | 3,350 to 3,420 | 0 | 13 | 0 MiB |
| A4 inline blocking, 4 publishers | 25 to 28 | 1,310 to 1,430 | 0 | 13 | (stack class is stale after the first goroutine mode) |
| B `go` per socket per burst | 27.5 to 29.9 | 1,380 to 1,410 | 1.2 | about 18,700 | 72 MiB |
| D flusher if none runs (R7) | 28.6 to 32.6 | 1,430 to 1,580 | 2 | 17,000 to 18,200 | 70 to 73 MiB |
| C persistent writer goroutine per socket | 28.4 to 28.6 | 1,420 to 1,430 | 0 | 20,013 | 78 MiB, permanent |
| H 4 workers write inline without blocking, spill to a flusher | 27.5 to 29.2 | 1,380 to 1,470 | 0 | 17 to 29 | 3 MiB |

Further measurements:

- Starting and finishing a goroutine costs 201 to 236 ns alone and 106 to 113 ns in bursts of 1,000; a write to a loopback socket is about 1,300 ns of the burst. So the goroutine per burst is roughly 8 to 15% of a write (micro). `SetWriteDeadline` costs 108 to 117 ns and `wheel.Add` 49 to 52 ns with no allocation (micro).
- Memory of model C, a writer goroutine kept per socket, is +4,182 to +4,227 B of heap plus stack per socket after one write (measured), more than the whole 3.1 to 3.5 KB an idle connection holds (ADR 0005). It is rejected on ADR 0003 and ADR 0005, as the roadmap says.
- Model A with one stalled socket first in the list (send buffer full, write deadline 200 ms): the burst took 278 to 286 ms, the publisher goroutine held for the whole deadline (measured). D with the same stalled socket: the publisher returned after 10 to 30 ms, the stalled flusher ended at the deadline, 201 ms, and nobody else waited (measured). H: the publisher returned in 73 ms (it is one worker), the stalled socket's own flusher ended at 200 ms.
- Model D's transient cost is the finding the recommendation does not state: the publisher creates goroutines faster than they run, so about 17,000 to 18,000 are alive at once, 70 to 73 MiB of stacks, as big as the whole idle footprint of the 20,000 sockets. It is freed afterwards but it is a peak. Model H avoids it (3 MiB, 17 to 29 goroutines) at the same time per burst, because the writes themselves, not the goroutines, are the cost.
- Why a flusher is needed in any case: the wheel's callbacks "must not block" (`internal/wheel/wheel.go`), so the heartbeat ping cannot write inline; a `tls.Conn` cannot be written without blocking, and a write timeout corrupts its state for good (crypto/tls docs, line 142 of `conn.go`), so H's inline attempt is for plain TCP only; the 1001 of Shutdown to 20,000 sockets is the same burst (about 30 ms measured as D) and wants the same mechanism.

Not measured (claims): coalescing several queued frames into one `writev` when the queue holds more than one; memory added to the idle socket by the queue slice header, the mutex and the flusher flag (about 40 bytes by reading the struct, to be asserted by the 4.5 KB idle test); the allocations of the real queue, which in the probe's slice-of-frames version are 2 a socket a burst and need a ring or a reusable slot to be zero.

Verdict: KEEP, with one MODIFY. The flusher is the one mechanism that serves pings, TLS, spill and shutdown, and it keeps the idle socket free of a writer stack (rejects model C). Add: `Publish` walks the subscribers in a few shard workers that try one non-blocking write on plain TCP and only queue and start a flusher when the kernel took less than the frame; TLS and control frames go straight to the queue and flusher. This is measured equal in time, zero allocation and 3 MiB instead of 70 MiB of transient stack at 20,000 sockets, at the price of a second code path. If that is judged too much for step 12, D alone is acceptable and the 70 MiB peak is the figure to state in ADR 0037 (it is a peak, not an idle cost). What it fails at: a queue's byte bound counts shared frames once per socket, so the 1 MiB bound is conservative for broadcasts but there is no app-wide bound for per-socket distinct data: 20,000 stalled sockets each holding 1 MiB of different frames is 20 GB (arithmetic). A send-queue budget like R6's, closing with 1013 or 1008, is a gap worth an ADR line (claim).

## R8: Msg type decides binary; subprotocols ignored; Origin default and AllowOrigins

- Binary. `[]byte` accepts binary and text. `Raw[T]` does not: it is `T` decoded from JSON with its bytes kept (`compile.go`), so a binary frame to it is JSON in an unexpected frame type and answering 1003 is right; R8 as written lets `Raw` accept binary, which has no use (the decode would run on bytes the app declared are not text). Any other `Msg` answers a binary frame with 1003. The check is on the first `KindData` event with `Opcode == OpBinary`, before any assembly, so a binary flood costs one close each (claim; the Reader reports opcode and decides nothing, `ws/doc.go`). Registration knows the Msg type, so the route records `acceptsBinary` once. `Send` with an `Out` of `[]byte` writes a binary frame, anything else a text frame, the same rule in the other direction (claim, needs a line in ADR 0036). Verdict: MODIFY, `Raw` drops out.
- Subprotocols ignored: KEEP. The 101 answer then names none (`AppendUpgradeResponse` adds none), which is what a client that offered several expects to be told. What it fails at: a client library that insists on one (some MQTT-over-WebSocket clients) closes the socket itself.
- Origin default. Compare the Origin's authority with the request `Host`, without case, dropping a port only when it is the default of the Origin's own scheme, never inferring the scheme of the connection, because behind a TLS-terminating proxy the engine sees plain HTTP while the browser's Origin says https. The candidate function in `origin/` was run on 15 cases (measured): same host true, different case true, `https://example.com:443` against `example.com` true, `http://localhost:3000` against `localhost:8080` false, `null` false, trailing slash, userinfo, `example.com.evil.com`, a `ws` scheme and a mismatched default port all false, IPv6 with port true. A plain host and port string comparison without the default-port rule would refuse `https://example.com:443`; scheme inference would refuse every proxied deployment. Repeated `Origin` headers: refuse (claim). What it fails at: the scheme is not compared, so an `http://` page on the same host passes; the behind-a-proxy case wins over that gap, and a proxy that rewrites `Host` breaks the default (then `AllowOrigins` is the answer).
- Missing Origin accepted, `Origin: null` a mismatch: KEEP (sandboxed iframes and `file://` pages send `null`).
- Order: Origin is checked before Providers and Input decoding, answered 403 with problem+json. Otherwise a cross-site page makes the server run a cookie-reading Provider (a database lookup) for a request it will refuse. ADR 0036 says the Input is decoded "before the upgrade" and Origin "as well"; the order is the addition (claim).
- `AllowOrigins(...)` takes full origins `scheme://host[:port]`, compared exactly after lowercasing. Registration refuses (each a table row naming the route and where it was registered): `"*"` ("use AllowAnyOrigin() and say so"), `"null"`, an entry with no scheme, a path, a trailing slash, or any `*` (wildcard subdomains are a later feature, claim). `AllowAnyOrigin()` as a separate name makes the dangerous choice visible in code review and greppable; `AllowOrigins("*")` refused is cheaper than documenting it. Combining `AllowAnyOrigin()` with a list is a refusal. Verdict: KEEP, with these refusals made explicit.

## ADR 0046 gaps

- Client close codes: 1000 to 1003, 1007 to 1011, 3000 to 4999, as built and as the Autobahn suite expects. KEEP, with one MODIFY found by the probe: a client that echoes the status the server closed with is refused. `ctl` fed a client Close with 1012 and with 1013: both failed with 1002 "close status not allowed on the wire"; 1000, 1001, 1008, 1009, 1011 were accepted (measured). R6's budget close is 1013, so a well-behaved client that echoes it is logged as a protocol violation. The engine must accept the echo of the status it sent (a `Reader` call, or the engine ignoring the Reader's refusal once its own Close is sent and the peer's Close frame has begun), while Autobahn's rejection of an unprompted 1012 to 1014 stays. Claim for the browser behaviour (browsers answer a Close with the same status; not run here).
- Pong flood: as built, unlimited: 1,000,000 pongs at one instant, 0 refused, 16 ns and 0 allocations each (measured, `ctl`). Unsolicited pongs are legal keep-alives, so one frame is never an error. The cost of a pong in the Reader is small; the cost that matters is in the engine: if a pong re-arms the heartbeat node it takes the wheel's global lock, so a flood from one socket contends with every other socket's heartbeat. Verdict: KEEP the shared bucket (pings and pongs drain one allowance of 32), and in the engine a pong only sets a flag the heartbeat tick reads, never touching the wheel. The bucket stays cheap and closes the flooding socket with 1008, as for pings.
- Ping bucket 32 refilled at 32 a second: the 33rd ping at one instant fails with 1008, and 3,200 pings at exactly 32 a second for 100 s were all accepted (measured). KEEP; write it in ADR 0046 as built (burst of 32, sustained 32 a second).
- Handshake answers: 405 with `Allow: GET` for another method (HEAD included), 400 problem+json for the rest, 426 problem+json with `Sec-WebSocket-Version: 13` for another version (the codec's `HandshakeError.WantVersion` already carries it). KEEP. A plain GET with no `Upgrade` header could be 426 with `Upgrade: websocket`, which is what RFC 9110 means by that status and tells a developer opening the route in a browser tab what to do; either is acceptable and the problem `detail` should name the route as a WebSocket route either way (claim). 403 problem+json for a refused Origin, before any Provider runs.

## Summary of verdicts

| | verdict |
|---|---|
| R5 cancel streams at Shutdown start | MODIFY: only live streams (SSE and declared live streams); plain `Stream` drains; no terminating chunk when a non-SSE stream is cut |
| R6 deadline, budget, assembly only for fragmented | MODIFY: assembly for any message not whole in one read; decode from a fresh slab (one allocation), never from the read buffer; own 30 s `MessageTimeout` as a read deadline; budget 64 MiB charged by held capacity; echo of 1013 accepted |
| R7 flusher on demand | KEEP, plus inline non-blocking first try on plain TCP in sharded publish workers (70 MiB transient stacks avoided, measured) |
| R8 binary, subprotocol, Origin | MODIFY: `Raw[T]` does not take binary; Origin compared by authority without scheme inference; 403 before Providers; `AllowOrigins` refusals for `*`, `null`, wildcards, malformed entries; `AllowAnyOrigin()` |
| ADR 0046 gaps | KEEP all four, with the close-status echo exception and pongs never touching the wheel |
