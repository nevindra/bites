Machine: Ryzen 7 9700X, Go 1.27.2 linux/amd64. Probes in `$DIR/probe/{std,json,fw}`; clones in `$DIR/src` (huma v2.40.0, fuego v0.21.0, chi v5.5.0). "[probe]" = I ran it this session.

## Std (Go 1.27.2)
1. **ServeMux.** [probe] Conflicts panic at registration with a full explanation and both registration file:line. `GET /a/{x}` + `GET /{y}/b`: "both match some paths, like "/a/b". But neither is more specific than the other." Identical patterns with different wildcard names conflict ("/a/{y} matches the same requests as /a/{x}"). `{x...}` not at end panics: `{...} wildcard not at end`. 405: [probe] `POST /users/1` against a GET-only route gives 405, `Allow: GET, HEAD`, text/plain body "Method Not Allowed\n". Trailing slash: [probe] `/users/1/` against `GET /users/{id}` is 404; `GET /dir/` pattern makes `/dir` a 307 to `/dir/`; `{$}` matches only the exact slash (`/exact` 307 to `/exact/`); `//users/1` 307-cleans to `/users/1`. HEAD is served by a GET route. Pattern is exposed as `r.Pattern`; values via `r.PathValue`.
2. **Footguns still present.** [probe] `Write` then `WriteHeader(500)`: client sees 200 "hi", server logs `http: superfluous response.WriteHeader call from ... (main_test.go:38)`. `Header().Set` after `Write`: silently dropped (client X-Late empty, no log). `http.Error(...)` then `Write("ALSO")` without return: both reach the client, body "bad\nALSO", status 400. All three are still there.
3. **Context cancellation.** [code] `net/http/request.go:354-356`: context cancelled when client connection closes, request cancelled (HTTP/2), or ServeHTTP returns. [probe] a handler blocked on `r.Context().Done()` saw `context canceled` when the client timed out.
4. **encoding/json/v2.** [release-notes] go.dev/doc/go1.27: `encoding/json/v2` and `jsontext` are released; `encoding/json` is now backed by the v2 implementation with v1 behaviour kept; opt-out `GOEXPERIMENT=nojsonv2` "expected to be removed in a future release"; v2 "rejects invalid UTF-8 ... and rejects duplicate names". [probe] `import "encoding/json/v2"` builds by default in 1.27.2; with `GOEXPERIMENT=nojsonv2` it fails ("build constraints exclude all Go files"). So it is not behind an opt-in any more. Wire differences [probe], zero struct marshalled: v1 API `{"S":null,"M":null,"B":null,...}`; v2 `{"S":[],"M":{},"B":"",...}` (nil slice becomes `[]`, nil map `{}`, nil []byte `""`). Duplicate key `{"name":"a","name":"b"}`: v1 takes "b", v2 errors `jsontext: duplicate object member name "name"`. Unknown field: accepted by both. []byte base64: same. Removed during the experiment per release notes: `format` tag, `unknown` tag, `DiscardUnknownMembers`, `inline` renamed `embed`.

8. **Shape** [docs] README, verbatim:
```go
huma.Get(api, "/greeting/{name}", func(ctx context.Context, input *struct{
    Name string `path:"name" maxLength:"30" example:"world" doc:"Name to greet"`
}) (*GreetingOutput, error) {
    resp := &GreetingOutput{}
    resp.Body.Message = fmt.Sprintf("Hello, %s!", input.Name)

type GreetingOutput struct { Body struct { Message string `json:"message" example:"Hello, world!" doc:"Greeting message"` } }
```

Signature `func(context.Context, *In) (*Out, error)`. Input tags [docs request-inputs.md]: `path`, `query`, `header`, `cookie`, `required`; the body is a field named `Body`. Query/header/cookie optional by default, path always required. Output: struct with `Body`, optional `Status int`, header fields. Unlike your design, a path param needs the `path:"name"` tag: the tag is the binding. Every input and output must be a struct (panics `input must be a struct`, [code] huma.go:824-829). Port: the registration builds the Operation by reflection at `huma.Get` time.

So a mismatch is silent; huma.go has panics for other things (huma.go:222 pointer params, 814-829 missing method/path, 892 multipart) but not this.

## Mistakes a new framework should not repeat, with evidence
- **Binding by name string, checked never.** Both frameworks accept a route whose `{id}` has no matching input and run the handler with zero (Huma [probe] 200 id 0; Fuego [probe] `PathParamInt("idd")` returns 0). A zero that equals a valid value is the worst failure mode. Registration must reject it (ServeMux already panics for pattern conflicts [probe], so panic at startup is acceptable Go style).
- **Silent coercion to zero in a helper** (Fuego `PathParamInt`, `QueryParamBool` documented "returns default"). Error path should be the only path.
- **Two status codes for "bad input"** (Huma 400 for malformed JSON, 422 for schema failure [probe]). Defensible but surprising; pick one and say it.
- **Leaking Go internals in 400 bodies** (Fuego: `json: cannot unmarshal ... Go struct field FIn.age`, `Key: 'FIn.Name' Error:Field validation for 'Name'` [probe]). Field names should be wire names.
- **A typed-params feature announced before it exists** (Fuego docs "incoming syntax, not available currently", #356 is the top issue): the typed path is the core promise and it stayed a hand-parsed string API.
- **Spec gets less type information than the handler has** (Fuego path param typed string, controller names in descriptions [probe]).
- **Extra fields on every response by default** (Huma `$schema`, example.com URL [probe]) and a Link header; opt-out should be the default.
- **Cost of reflection paths**: 3.2x and 8x ns, 11 and 36 allocs versus 4 [bench]. Your allocation budget is a stronger position than either has.
- **Release channel drift** (Fuego GitHub "Latest" 20 months behind the tag; a retracted v1.0.1 tag [gh + go.mod]).
- **Bus factor**: Huma 943 vs 53 commits; a heavy single-maintainer risk is real for either.
- **Go's own footguns remain** (superfluous WriteHeader, late Header().Set dropped, http.Error without return [probe]); a "write once from the return value" design removes all three. Neither Huma nor Fuego fully does (Fuego's `c.SetHeader`/`c.Response()` escapes exist [code ctx.go]).
- v2 JSON differences (nil slice -> `[]` in v2 only) change wire output depending on a build switch; a framework that serialises must pin one behaviour.

## Things worth copying
- Huma: whole-response errors collected in one problem+json with `location` like `body.age` / `path.id` [probe]; secure defaults (unknown body property rejected, 1 MiB limit) [probe/docs]; router-agnostic core with zero third-party deps via humago [probe]; `Body`/`Status`/header fields in the output struct; OpenAPI 3.1 from types with `doc:`/`example:` tags; humatest-style in-process tests.
- ServeMux: registration-time conflict panics with the exact paths and registration file:line [probe]; reuse std patterns instead of inventing syntax; `r.Pattern`.
- Fuego: plain return values (no wrapper), `ContextNoBody` shortcuts, and the whole thing being a plain `http.Handler`.
- Go 1.27: build on `encoding/json` (now v2-backed) and `Server.Protocols`; do not wait for HTTP/3.

## What Huma/Fuego already do that your design proposes, and where yours would differ
Already done: functions as handlers with typed input and output (Huma fully; Fuego only for the body), OpenAPI 3.1 from types (both), field-level validation errors (Huma strongly), framework-written response from the return value (both), running on std ServeMux (both).
Genuinely different in your design, if built as described: (1) no annotations: Huma needs a `path:"id"` tag per parameter and `doc:` for docs; (2) argument types, not an input struct plus `Body` field wrapper; (3) the mismatch between route pattern and arguments becoming a startup failure rather than a zero; (4) a 400 that names the field with the wire name, always, with one status policy; (5) a measured allocation budget close to the 4 allocs of plain net/http. Challenge: Go keeps no parameter names (as in Zig) so (1) forces either positional binding or a struct type per route; Huma's own tags exist for exactly this reason, and Fuego's string lookups are the failure case when you avoid it. I did not verify that Go reflection can recover parameter names (it cannot from `reflect`; I did not test it) or whether any other library does it.
